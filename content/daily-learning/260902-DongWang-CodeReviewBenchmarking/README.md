## 历史精读正文

### 当代码审查研究各用各的数据和指标时，我们真的能比较它们吗？

- **论文**：Can We Benchmark Code Review Studies? A Systematic Mapping Study of Methodology, Dataset, and Metric
- **作者**：Dong Wang、Yuki Ueda、Raula Gaikovina Kula、Takashi Ishio、Kenichi Matsumoto
- **来源**：Journal of Systems and Software，Volume 180，2021，111009
- **DOI**：[10.1016/j.jss.2021.111009](https://doi.org/10.1016/j.jss.2021.111009)
- **研究材料**：覆盖 2011—2019 年高影响力软件工程会议和期刊

> 一句话结论：代码审查研究已经形成了一些常用指标族，但数据、任务定义、审查平台和指标操作化仍高度分散；因此在 2021 年时，领域还不具备构建统一 benchmark 的条件。

### 4.1 论文地图

这篇论文不是在提出新的代码审查模型，而是在检查整个代码审查研究领域是否已经具备“公平比较模型”的基础设施。

作者从 34 个软件工程会议和期刊中获得 19,847 篇论文，通过筛选最终保留 112 篇代码审查研究，分别整理：

1. 研究采用了什么方法；
2. 数据能否由其他研究者重新获得；
3. 使用了哪些指标；
4. 相同研究问题是否存在共享数据和指标；
5. 这些共同点是否足以构成 benchmark。

论文发现：

- 73/112，即约 65% 的论文属于实证评价研究；
- 84 篇定量或混合方法论文中，只有 42 篇提供可访问的公开数据或复现包；
- 31 篇定量研究一共使用了 457 个指标；
- 这些指标可以归并成 16 个指标族；
- 同主题研究会使用一些相似指标，但很少共享同一数据集。

#### 核心矛盾

```text
过去
代码审查数据越来越容易从 Gerrit、GitHub 等平台取得
↓
结果
研究者大量开展实证分析和机器学习研究
↓
问题
每个团队重新采集数据、定义标签并选择指标
↓
后果
论文都报告准确率或相关性，却未必在回答同一个问题
↓
作者的工作
系统整理方法、数据和指标，判断领域是否已具备统一评价条件
```

### 4.2 先弄清三个容易混淆的概念

#### Benchmark 不只是一个数据集

一个完整 benchmark 至少需要：

- 明确的任务；
- 稳定的数据和划分方式；
- 一致的输入、输出和标签；
- 能对应研究主张的指标；
- 可复现的评价程序；
- 对数据泄漏、时间演化和外部有效性的说明。

所以，把几个 GitHub PR 打包公开，不一定已经形成 benchmark。

#### Metric 与 construct 不是一回事

**Construct** 是研究者真正想研究的概念，例如“审查质量”“审查效率”“审查者经验”。

**Metric** 是把概念变成可测数字的具体办法，例如评论数量、关闭时间、历史审查次数。

同一个 construct 可以有多种操作化方式；同一个 metric 也可能无法完整代表 construct。例如“评论更少”可能表示效率提高，也可能表示沟通和知识传递减少。

#### 可获得数据不等于可复现研究

论文把“提供公开数据或引用公开数据集”视为具有复现潜力。但严格复现通常还需要：

- 原始采集规则；
- 数据清洗代码；
- 时间窗口；
- 排除标准；
- 模型和参数；
- 随机种子；
- 评价脚本。

因此，论文报告的 50% 更接近**数据可获得率**，不是完整计算复现率。

### 4.3 为什么现有研究还不能直接互相比较

作者真正观察到的 gap 不是“完全没有公共数据”，而是存在三个彼此连接的问题。

#### 问题一：研究集中于观察现象，解决方案和实践反馈较少

112 篇研究中：

- 73 篇是 evaluation；
- 18 篇是 survey；
- 13 篇提出 solution；
- 只有 4 篇属于 experience report。

这说明领域非常擅长从已有仓库中挖掘关系，比如“哪些因素与 PR 接受相关”，但较少报告工具部署后的真实经验，也较少提出并长期评价能解决问题的系统。

这里值得注意的是，作者把“评价研究很多”视为领域成熟的一面，也把“实践经验少”视为缺口。但这并不能单凭数量证明领域缺少实际影响：经验报告也可能发表在工业会议、技术博客或不在作者选择的顶级 venue 中。

#### 问题二：只有一半定量研究提供公开数据

在 84 篇定量或混合研究中：

- 42 篇提供了公开数据、复现包或可追踪的已有数据集；
- 约 38 篇虽然使用了开放项目或企业数据，却没有提供可直接复用的数据；
- 其余论文只提供部分数据或其他不完整形式。

更值得警惕的是，公开链接主要托管在 GitHub、Bitbucket、个人主页或大学页面；只有 3 篇使用作者所称的永久存储平台。

因此，“论文中有一个链接”并不保证五年后还能复现。

#### 问题三：指标有局部共识，但操作方式过于分散

作者从 31 篇定量研究中提取了 457 个指标，归入 16 类，包括：

- 经验；
- 代码；
- ownership；
- 评论；
- 文件；
- 参与者；
- 时间；
- revision；
- workload；
- decision；
- defect 等。

其中：

- Experience 类包含 76 个指标；
- Code 类包含 72 个指标；
- 28/31 的论文使用了代码相关指标。

这里最值得注意的不是“457 很多”，而是：即使两个研究都声称控制了经验，它们也可能分别使用历史提交数、历史审查数、文件级经验或项目任期。它们在统计表里都叫 Experience，实际调整的变量却不同。

### 4.4 作者如何完成系统映射

整体流程如下：

```text
选定34个高影响力软件工程会议和期刊
↓
收集2011—2019年的19,847篇论文
↓
通过代码审查相关检索式得到437篇候选
↓
两名研究者按纳入/排除标准筛选
↓
保留112篇代码审查研究
↓
人工标注方法、贡献、数据来源和可复现性
↓
从定量研究中抽取457个指标
↓
将指标合并为16类，并映射到9类研究问题
↓
检查同主题论文是否共享数据和指标
```

#### 分类为何需要人工判断

像“审查者历史参与次数”可以属于经验，也可能被解释为 ownership 或参与度。作者由多名研究者讨论有争议的分类，而不是单人机械编码。

这提高了分类一致性，但论文没有报告 Cohen’s κ 或 Krippendorff’s α 等独立编码一致性指标。协商后达成共识能够生成最终标签，却不能告诉我们原始分类到底有多模糊。

### 4.5 RQ1：代码审查研究主要在做什么？

#### 真正问题

研究主要是在理解既有现象、验证模型，还是提出解决真实问题的工具？

#### 设计

作者按照 contribution 和 methodology 两个维度给 112 篇论文分类。主要方法包括 evaluation、validation、survey、solution 和 experience。

#### 关键结果

- 65% 的论文采用 evaluation methodology。
- 53 篇“理解代码审查过程”的论文属于评价研究。
- 48 篇研究社会—技术因素的论文属于评价研究。
- 只有 4 篇经验报告和 13 篇 solution 论文。

#### 能支持的结论

它说明所选高影响力 venue 中，代码审查研究以观察、解释和评价为主。

#### 不能支持的结论

它不能证明研究者没有开发实用工具，因为：

- 工具工作可能发表在其他 venue；
- 工业经验可能只存在于 SEIP、博客或内部报告；
- 作者排除了八页及以下论文，可能过滤掉部分工具演示和经验报告。

> **RQ1 Takeaway：代码审查研究拥有大量观察性证据，但将证据转化为部署、干预和实践反馈的研究相对不足。**

### 4.6 RQ2：代码审查研究有多大复现潜力？

#### 真正问题

其他研究者能否拿到相同的数据，重新执行或扩展研究？

#### 设计

作者只分析定量和混合方法研究，并把数据分成：

- 公开复现数据；
- 开放项目数据但未提供复现包；
- 企业或封闭数据；
- 部分公开数据；
- 引用已有数据集。

#### 关键结果

- 42/84 篇提供公开数据或指向可获得的数据集。
- Qt、OpenStack 和 Android 是使用 Gerrit 数据时最常见的项目。
- GitHub/Bitbucket 与个人或大学页面各承载了 17 个复现资源。
- 只有 3 个资源使用永久存储。

#### 证据边界

“数据公开”最多说明其他人可能取得输入数据。论文没有系统核查链接是否仍有效、代码能否执行、结果能否完全重现。

> **RQ2 Takeaway：当时约一半定量代码审查论文具备数据层面的复现入口，但完整计算复现能力可能低于 50%。**

### 4.7 RQ3：领域是否已经形成共同指标？

#### 真正问题

相同研究主题是否使用足够一致的指标，从而可以形成共同评价协议？

#### 关键结果

作者发现了局部规律：

- Quality Assurance 研究全部使用代码指标，约 82% 使用 ownership 指标；
- Acceptance Prediction 的三篇论文都使用 Code、Experience 和 File 指标；
- Review Participation 研究都使用 Experience 指标；
- 不同研究主题确实形成了不同的指标组合偏好。

但共享数据非常少：

- Quality Assurance 主题只有约 18% 使用共同数据；
- 多个主题完全没有共同数据；
- Gerrit 和 GitHub PR 场景能提供的字段也不同。

这意味着“指标族已经有共识”，但“比较所需的共同实验条件”还不存在。

> **RQ3 Takeaway：共同指标只能构成 benchmark 的候选组件；没有一致数据、任务和标签，不能据此公平比较模型。**

### 4.8 表 8 真正告诉我们的是什么

表 8 把研究主题、常见指标族、共同数据和审查平台放在一起。

最值得看的不是每个百分比，而是两个不对称现象：

1. **指标共识明显高于数据共识。**
   例如质量保障研究普遍使用 Code 和 Ownership，但很少在同一数据上验证。这意味着结果差异可能来自项目、平台和采样，而不只是方法。

2. **平台决定了能研究什么。**
   Gerrit 更常被用于质量保障研究，GitHub Pull Request 更常用于 CI 与 Review。不同平台记录的事件、角色和状态不同，这会影响研究者可以构造的 Treatment、Outcome 和 Confounder。

论文借此得出“目前不能 benchmark”的结论。这个结论总体合理，但“不能”更准确的意思是：**无法建立覆盖所有代码审查研究的单一 benchmark**。针对某个窄任务，例如 reviewer recommendation 或评论生成，仍然可能构建局部 benchmark。

### 4.9 从因果研究角度重新审查这篇论文

这篇论文不估计因果效应，但它对 Causality for Code Review 有一个很直接的提醒：

> 因果研究不能从一张“常用变量清单”自动推出正确的调整集。

例如 Experience、Code size 和 Ownership 在很多论文中常见，但它们究竟是：

- Confounder；
- Mediator；
- Moderator；
- Collider；
- Treatment 的组成部分；

必须由具体的 data-generating process 决定。

如果研究“提供仓库上下文是否提高代码审查质量”：

- 任务复杂度可能是 Moderator；
- 如果复杂任务更可能被分配更多上下文，它也可能成为 Confounder；
- 模型探索过程中产生的 token 数可能是 Mediator；
- 只分析模型最终选择深入探索的 PR，则可能引入 selection bias。

所以，本文整理出的 457 个指标更适合作为**候选变量词典**，不能直接当作“全部放进回归模型”的依据。

### 4.10 论文自身的局限

#### 作者承认的局限

- 只选择 34 个高影响力 venue；
- 搜索词可能遗漏使用不同术语的研究；
- 部分论文先由第一作者依据标题和摘要筛选；
- 方法、贡献和指标分类存在主观性；
- 指标分组缺少已有结果可供外部验证。

#### 还可以进一步质疑的地方

1. **时间截断非常严重**
   数据止于 2019 年，完全没有覆盖预训练模型、LLM、Agent 和当前仓库级 benchmark。它适合解释领域的历史基础，不能代表 2026 年现状。

2. **“高影响力 venue 等于高质量样本”是未经验证的前提**
   这种筛选提高了论文平均质量，却可能系统性遗漏工具、工业经验和复现研究，恰好影响 RQ1、RQ2 的比例。

3. **457 个指标不等于 457 个独立构念**
   很多指标只是同一概念的不同操作化。直接强调数量可能夸大领域分裂程度。

4. **没有评价指标本身的测量有效性**
   论文统计了哪些指标被使用，却没有判断这些指标是否真的测量了作者声称的能力。

### 4.11 对你后续研究的可操作启发

#### 建立“变量—角色—时间”表，而不只是指标表

对每个变量记录：

| 变量                | 因果角色                  | 测量时间   | 是否受 Treatment 影响 |
| ------------------- | ------------------------- | ---------- | --------------------- |
| PR 难度             | Confounder/Moderator 候选 | 干预前     | 否                    |
| Repository Context  | Treatment                 | 审查开始时 | —                     |
| Agent token 使用量  | Mediator 候选             | 干预后     | 是                    |
| 审查意见有效性      | Outcome                   | 审查结束后 | 是                    |
| Reviewer confidence | Outcome/Mediator 候选     | 审查后     | 是                    |

这可以避免把 post-treatment variable 错误放入调整集。

#### Benchmark 与 causal experiment 分开设计

Benchmark 回答：

> 哪个系统在固定数据和指标上表现更好？

因果实验回答：

> 对同一个任务，改变某个上下文或流程因素会导致什么变化？

你可以共享同一个 PR 数据池，但二者需要不同的估计目标和分析协议。

#### Outcome 不应压缩成一个总分

至少分别测量：

- 缺陷发现 Recall；
- 评论 Precision；
- 证据定位正确率；
- 严重性校准；
- 审查时间与成本；
- 对人类决策的影响。

这比把所有维度加权成一个“Review Quality”分数更容易解释，也更适合异质处理效应分析。

### 4.12 真正的 Takeaway

#### 作者证明了什么

- 2011—2019 年高影响力代码审查研究以实证评价为主。
- 定量研究的数据公开程度有限。
- 代码审查研究大量使用代码和经验类指标。
- 同主题研究存在指标族层面的局部共识。
- 数据、任务和平台差异阻碍了统一 benchmark。

#### 作者没有证明什么

- 没有证明 2026 年仍然只有一半研究具备复现能力。
- 没有证明统一 benchmark 一定优于多个任务专用 benchmark。
- 没有验证整理出的指标是否具有良好的 construct validity。
- 没有说明哪些变量构成正确的因果调整集。
- 没有覆盖 LLM 生成评论和 Agentic Code Review。

#### 你真正应该记住什么

- **同名指标不代表相同构念，相同构念也不代表相同操作化。**
- 共享指标但不共享数据，仍无法公平比较方法。
- Benchmark 的任务、数据、标签、指标和评价协议缺一不可。
- 常用变量清单可以帮助发现候选变量，不能替代 DAG。
- 你的 Causality for Code Review 工作应把 benchmark performance 和 causal effect 明确分开。

> **如果一周后只记得一件事：代码审查研究不缺指标，真正缺的是让数据、任务、构念和评价主张彼此对齐的共同协议。**
