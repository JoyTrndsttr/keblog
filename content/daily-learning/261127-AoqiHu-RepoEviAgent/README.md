# RepoEviAgent：怎样出一道真正考仓库理解的题？

> 精读日期：2026-11-27  
> 原题：*RepoEviAgent: Scalable Synthesis of Evidence-Grounded Repository-Level Question Answering Tasks*  
> 作者：Aoqi Hu（新加坡国立大学）、Yueao Xing（北京邮电大学）  
> 来源：2026 年 11 月 24 日 arXiv v1，10 页。[全文](https://arxiv.org/html/2611.31873v1) · [PDF](https://arxiv.org/pdf/2611.31873)。未核实正式录用或公开工件，PDF 的 ACM 模板和占位 DOI 不算发表信息。

## 会说出函数名，和说对程序行为，差在哪？

设想你刚接手一个同步服务。有人问：「后台同步第一次失败后，第二次成功时，调用端还能读到第一次的错误吗？」找到重试函数只能走出第一步。你还得知道谁更新状态、谁读状态，以及更新发生在请求结束之前还是之后。答案里出现了正确的文件名，仍可能把状态更新的时间说反。同一个问题若做成修复任务，测试能直接判补丁；只要求解释时，怎样让评分也抓住这个差别？这个同步服务是本文的教学示例，不是作者的实验样本。

RepoEviAgent 把这个问题放到数据生产上：先从真实变更中找值得问的程序行为，再用可执行的环境收集证据，最后把正确回答拆成必须满足的具体条件。Aoqi Hu 与 Yueao Xing 也共同参与了 [EchoRec](https://arxiv.org/abs/2608.14011)，研究如何把有噪声的序列信号转成训练监督；该前作属于推荐系统，不是本论文的软件工程评测前身。本篇未明确标注通讯作者；未查到可核实的专属实验室信息。对仓库级上下文研究，值得读具体的评分设计：证据、结论和错误说法可以分别定义。

## 从真实变更中选题：PR 提供线索，待答的是代码行为

图 1 对照了人工逐项目配置、出题和核对的工作，与自动化的候选筛选、环境搭建、合成和验证。图 2 把后者拆成两阶段，关键在于每道题始终和一个确定的源码状态绑定。

第一阶段从 8,477 个逾千星仓库采集约 248 万条 PR 记录，保留 2020 年起至 2026 年 1 月 1 日前已合并的 PR，记录 base commit。模型尝试从 PR 标题与说明里关联 Issue，借此恢复需求背景。作者筛选修改 50 至 1,000 行功能代码、至多 50 个文件、具有非空测试补丁的变更，再用 DeepSeek V4 Flash 做行为变化与测试信号初筛，用 GLM-5.3 评任务价值、行为清晰度、测试信号、范围复杂度及接口清晰度，形成不同阈值的候选层。文档更新、机械重构等并非不重要，但常不适合这条以行为证据为主的生产线。

在示例里，某条 PR 的测试恰好涉及“先失败、后成功”。这使它比一次变量改名更适合当题材。锁定 base commit 是为了让题面和答案描述同一份程序，不能拿合并后的行为去解释合并前的快照。作者并未在文中给出每个筛选环节的保留率、用于验证 Issue–PR 匹配准确度的独立抽样结果，或证明所有问题都需要动态运行。初始 PR 数量主要衡量搜索范围，不能当成有效题规模。

## 把环境验收和答案验收分开

**环境建设。** 给每个候选任务一个独立容器，以 Python、Go、TypeScript、C 或 C++ 的语言基础镜像为起点。环境 Agent 读项目依赖和持续集成配置，自行配置并试运行，留下安装步骤及环境记录。环境等级分为 Full（项目真实测试成功）、Partial（能完成基本构建或导入）、Failed（不可用）。独立程序核查目标提交、仓库完整性和受版本控制文件是否被改动，对 Full 还会重跑声称通过的项目测试。验收关心的是“配置是否真实可用、源码是否还是目标版本”；环境能跑不代表生成的问题或参考答案正确。针对示例，遇到 Partial 环境就不能把未跑过的完整集成测试当证据。

**问题合成。** 第二个 Agent 接收环境记录，检查指定仓库的实现，通过类别轮转减少同质题。需要动态信息时可用运行观察支持判断。它产出的不是单个字符串，而是题面、参考答案、高层评分条件和相关记录。图 2 还区分评分文件与调试记录：前者记录 rubric 检查，后者帮助定位失败出在运行还是评估。与其要求答出一篇笼统的重试机制介绍，不如要求说明谁清空错误、在哪个分支执行，以及读操作何时看见变化；把“每次尝试后都会清空”这类和实际行为矛盾的说法单独标出。这里的示例只演示评分结构，没有对应到真实仓库。

用式 (1) 表示，一道题有固定镜像、题面和评分条件三部分。式 (2) 把每项必需条件的判断相乘：全部为 1 才过；缺一个关键条件，全题就是 0。正向条件要求出现必要事实或推理证据；负向条件用来识别不应出现的错误说法。模型裁判统一用 Claude Opus 4.6 判评分项。这样的全通过率比按平均相似度算分更能追问「缺了哪条就不能成立」，但只看整题也会隐藏部分正确；每题必选项数量或难度不同，比较类别时仍要注意。

**最终测试集与训练集是两条分支。** 合成共得到 28,467 个问答实例，先由自动验证筛查，再挑 334 道做测评，覆盖 168 个仓库、五种语言和八个类别；这 334 道据论文均经人工复查参考答案与评分条件。334 除以 28,467 不是“自动合格率”，其中还有多样性抽选。训练分支则让 GLM-5.3 对经验证的实例采四条轨迹（温度 0.95、最多 250 次交互），用 Claude Opus 4.6 保留符合所有必需条件的轨迹，再做监督微调（SFT）。256K 版本直接舍弃过长轨迹，128K 版本用切分和模型摘要。这两个处理同时改变可保留的训练样本及表示，论文没有单独比较其收益。

## 实验一：同一个 Agent 框架，模型差距出在哪？

作者固定 334 个问题和能力一致的 mini-SWE-agent 框架，用同一个裁判、同一全必需项规则比较五个模型。框架提供命令行工具，模型可以浏览代码并按需要核对程序行为；固定的是接口和任务，而非每个模型看见同样的代码、实际花同样的 token。表 1 的总体结果：

| 模型 | 整题通过率 |
|---|---:|
| GLM-5.3 | 76.35%（255/334） |
| DeepSeek-V4.1-Flash | 62.87%（210/334） |
| GLM-5.3-Flash | 52.40% |
| GPT-5.5 | 51.50% |
| Gemini-3.8-Flash | 24.85% |

差异并非在所有问题上等比例放大。图 3 定义样本构成：五语言中以 Python、TypeScript、Go 为主，另含 C/C++；八类涵盖接口、架构、熟悉代码库、并发、数据状态、容错、根因和安全理解。图 5 将总分拆成这些问题：API 类 GLM-5.3 为 80.0%、GPT-5.5 为 70.0%；架构类两者变成 73.1% 和 46.2%。根因诊断是 81.8% 对 52.3%。并发类只有八题：GLM-5.3 过五道，DeepSeek 过一道，另三模型为零。一两题就能大幅改动小组排名，群体趋势和精确比例应分开写。相近总分也能掩盖不同强项：相比 GPT-5.5，GLM-5.3-Flash 在代码库熟悉度高约 14 个百分点，却在 API 集成低约 8 个百分点。

图 4 则换成按语言分组：五模型平均为 TypeScript 60.4%、Python 55.3%、Go 49.1%、C++ 46.5%、C 43.0%；GLM-5.3 在 C++ 有 86.0%，GPT-5.5 为 41.9%。语言分组同时更换了仓库、题型和题目，不能把这个差异全归给语言。图 6 每个点只是一个模型的平均答案长度和通过率：GLM-5.3 约 1,472 词、76.35%，短于总体通过较低的 DeepSeek；回答最短的 Gemini 也没有更好。五个聚合点展示的是“长短与成绩没有简单排序”，没有对同一模型进行回答长度干预，也没有衡量输入上下文剂量。

## 实验二：合成轨迹能否迁移到另一套问答？

表 2 Panel B 在 SWE-Atlas-QnA 的 60 道题上，对各自基座和经过微调的版本做比较。Qwen3.5-27B 从 18.3% 到 53.3%，Qwen3.6-35B-A3B 从 20.0% 到 38.3%。平均得分也各有上升（0.666→0.928，0.690→0.845），同时平均输出字符数接近翻倍或更多。这里看到的是**整套训练数据及训练流程**对应的子集提升；没有在相同训练量下分别去掉运行证据、类别轮转、轨迹验收或摘要，所以不能把提升分配给其中一项。表 2 Panel A 参考模型用了全部 124 道题，不能据此说微调的 Qwen 超过了 Panel A 的 GPT-5.4 或 Opus 4.7。

## 证据够支持什么？

1. 论文展示了一条可生成大量候选，再精选为 334 道经人工复查的仓库问答的流程。环境上线与答案核验是两道不同检查，安排独立分工有清晰理由。
2. 在这一框架、数据和裁判下，五个模型总体及分组表现不同。并发、容错等组暴露了真实的失败样本，但小组规模和人工评分说明有限；正文没有给出逐题失败归因，不能把每次未过都解释成检索或推理失败。
3. 双模型在另一套问答的同一报告子集上，微调版比各自基座通过更多。不同子集的排行榜和产线单组件贡献均未证实。

至少还有三处测量边界。第一，作者报告人工复查了参考答案与 rubric，却没有报告对裁判判断的大样本人机复核、一致性，与换裁判后的排名稳定性；合成答、评分条件、裁判都有可能引入偏好。第二，设了变更规模、测试信号和仓库热度筛选，分布不是现实开发任务的随机样本；并无证据说明样本代表冷门项目、微小变更或每一种复杂任务。第三，缺少逐题证据必须运行才可得的比例、静态与执行条件的配对对照、阶段漏斗耗时或单位合格题成本。环境可执行是一项支持能力，与答题者确实借运行信息得分是两个问题。

## 对当前研究的启发

仓库上下文研究可以借它的**证据单位**，不必移用它的模型排行榜。在已有动机案例旁给三个单独的问题：两臂是否都看到核心事实？回答是否准确复述了决定性事实？最终所选文件是否真承担该责任？三项可以分别复核：源位置的可见性、只基于记录的事实核对、最终输出评分。例如“认出了正确函数名但归责到错的文件”不再和“根本没看到证据”混在同一解释里。适合把这段做成定性展示，干预结论仍由既有匹配设计支撑。

本研究的最新记录已把模型异质性和 RQ1 相关、RQ2 干预区分开。RepoEviQA 没有在相同核心证据下操纵表观上下文，也没有测等 token、等节点：可引用来说明为何值得按证据评判仓库理解，不用它支持表观上下文造成干扰的因果论断。给本科生做普通代码审查难度试点时，可从人工核验的小批样本开始，把“审查判对了”和“解释说对了关键原因”分开，既保留严格整题指标，也保留缺的是哪一项。
