以主动学习和模型投票提取高置信安全审查子集，并暴露选择偏差与召回率边界。

### 论文地图：作者在解决一个“罕见正例”问题

这篇论文真正面对的问题是：**真实代码审查中，安全相关评论很少，直接人工阅读几十万条评论成本太高；但没有足够的安全评论，又无法训练和评价自动安全审查模型。**

作者的解决办法不是直接生成更多安全评论，而是训练一个高精度筛选器：

```text
GitHub 真实代码审查数据
↓
多个轻量模型产生初始伪标签
↓
大模型验证 + 人工标注
↓
主动学习选择模型分歧样本
↓
训练五个分类器并进行集成投票
↓
从大规模审查数据中筛出安全相关评论
↓
形成 SeRe 数据集并评价评论生成模型
```

最终得到 **6,732 条安全相关审查记录**，覆盖 C、C++、C#、Java 和 Go。最需要记住的不是这个规模本身，而是：**作者主动选择了“宁可漏掉，也尽量不要混入假阳性”的建库策略。**

这决定了 SeRe 的用途和边界。

### 理解全文需要抓住的四个概念

#### 1. 安全相关评论不完全等于真实漏洞

作者把能够映射到 CWE，或者根据安全编码原则被认为涉及安全风险的审查评论标为安全相关。

这里包含三个不同层次：

- 指向真实、可利用的漏洞；
- 指向不安全的编码实践；
- 表达安全担忧，但不一定能对应一个确定漏洞。

论文抽样核验发现，数据集中约 **94%** 的样本确实属于安全相关评论，但只有约 **84%** 被认定能对应真实漏洞。两者不能混写。

#### 2. 主动学习是在决定“接下来最值得人工标哪条”

随机标注会把大量预算浪费在普通评论上。主动学习让模型优先交出自己拿不准、或者多个模型意见不一致的样本。

它提高的是标注效率，并不自动保证总体无偏。模型认为“肯定是负例”的区域如果藏有系统性漏检，主动学习可能一直看不到它们。

#### 3. Precision 和 Recall 对这个数据集承担不同角色

- Precision 高：筛出来的评论大多真的与安全相关。
- Recall 高：真实存在的安全评论大多能够被筛出来。

SeRe 的集成分类器 Precision 为 **92.75%**，Recall 只有 **42.38%**。因此它适合构造较干净的正例集合，却不能被自然解释为覆盖了真实世界约九成的安全审查活动。

#### 4. “未发现分布差异”不等于“证明分布相同”

作者用 Fisher 精确检验比较样本中的安全类别分布，多数检验没有拒绝“分布无差异”的零假设。

统计上，这只能说明当前样本没有提供足够证据发现差异。尤其罕见类别样本很少时，检验能力不足也会产生较大的 p 值。因此，论文题目中的 “Aligned with Real-World Review Activities” 应理解为**有限抽样下未观察到明显偏移**，而不是严格证明完全代表真实世界。

### 为什么现有数据不够

过去的安全代码审查数据通常有两个问题：

1. 通用代码审查数据规模很大，却没有安全标签。
2. 安全审查数据依赖关键词和人工筛选，规模较小，而且容易偏向研究者预先定义的安全类别。

已有相关数据分别只有 614 和 516 条左右。SeRe 希望同时取得：

- 更大的数据规模；
- 多语言覆盖；
- 不依赖固定关键词的发现能力；
- 可复现的数据构建流程。

这个 research gap 是真实存在的。不过，作者从“没有预设安全关键词”进一步推到“低偏差”，中间存在一个隐含前提：**模型对安全概念的已有理解不会带来另一种语义偏好。**

论文没有证明这一前提。多个基础模型的训练数据和安全知识来源可能相似，它们一致投票并不等于独立证据。

### SeRe 是怎样一步一步构建出来的

### 第一步：限定数据来源

作者从 GitHub 中选择 C、C++、C#、Java 和 Go 项目，并优先考虑各语言 star 排名前 10,000、PR 数不少于 1,000、许可证允许分发的仓库。

最后原始数据涉及：

- 359 个仓库；
- 373,824 条 review entries；
- 712,108 条评论。

作者保存的不只有 diff 和评论，还包括修改前后的文件、完整讨论以及审查后的 refinement。这使数据理论上可以支持评论生成、代码修改和对话研究。

但分类阶段只使用**每段对话中审查者的第一条评论**。因此，所谓“真实审查活动”并没有完整进入分类器；后续澄清、作者回应和多轮演化被保存在数据里，却没有参与安全性判断。

### 第二步：生成初始伪标签

作者先让多个轻量模型独立判断评论是否与安全相关：

- 全部判为正例或全部判为负例的样本，被视为边界清晰；
- 随后使用 DeepSeek-V3 进行验证；
- 为避免正负样本极不平衡，初始训练集被平衡为接近 1:1。

这一步解决的是冷启动：没有标签时，先获得一批相对容易的正负样本。

问题在于，平衡后的训练分布与真实约 4% 的安全评论比例完全不同。平衡训练本身可以接受，但最终分类阈值和概率不能直接被解释为现实中的安全风险概率。

### 第三步：用主动学习集中标注难例

作者把未标注数据分成 100 个批次，每批约 3,776 条。训练过程中，五个模型分别预测：

1. 全部判为正；
2. 模型之间存在分歧；
3. 全部判为负。

一致正例和分歧样本会进入人工确认；一致负例则被丢弃。经过迭代，共形成 **3,641 条人工标注训练样本**。

六名具有安全和代码审查经验的标注者参与判断，安全相关二分类的 Fleiss’ κ 为 **0.88**；14 类安全问题分类的 κ 为 **0.81**。这说明标注者之间的一致性较高，但 κ 衡量的是一致程度，不直接证明标签符合客观漏洞事实。

最值得警惕的是“一致负例被丢弃”。如果五个模型共享某种盲区，例如都不理解某个项目特有的权限语义，这类正例不会进入人工纠错环节。

### 第四步：五模型投票形成最终筛选器

五个约 7B–9B 的基础模型分别微调，最终采用 **4-out-of-5** 投票：至少四个模型判为安全相关，才输出正例。

论文还设计了一个动态加权 F1 目标。直观上，它不是单纯追求普通 F1，而是对 Precision 或 Recall 低于目标阈值进行额外惩罚，并通过参数强调作者期望的权衡。公式推导不是理解论文的核心；真正关键的是它把“高 Precision”写进了模型选择目标。

如果移除投票机制，单个模型的随机误判会更容易进入数据集；但论文没有报告完整的组件消融，所以我们不能量化：

- 主动学习贡献了多少；
- 大模型伪标签验证贡献了多少；
- 五模型集成贡献了多少；
- 4/5 阈值相对其他阈值究竟提高了多少最终数据质量。

作者说在验证集上比较过投票方案，但正文没有提供足够结果支持更细的归因。

### RQ1：现实审查评论中有多少涉及安全？

#### 作者真正想问什么

如果安全评论并没有那么稀少，就没有必要构造专用筛选流程。因此 RQ1 同时承担了“证明问题困难”和“描述数据构成”的作用。

#### 实验设计

作者人工分析了 3,727 条具有现实分布的评论，其中发现 151 条安全相关评论，并进一步归为 14 类。

#### 关键结果

- 安全相关评论占 **4.05%**。
- 内存管理占安全评论的 **38.99%**。
- 并发与同步占 **23.85%**。
- 异常处理占 **9.94%**。
- 非内存资源管理占 **7.95%**。
- 前两类合计超过 60%。

#### 怎么理解

结果说明安全审查评论确实是一个少数类问题；普通随机标注会非常低效。

但 4.05% 不能被当作所有 GitHub 项目的总体比例。数据来源已经限制在高 star、高 PR 数、五种语言和可分发许可证项目，并且只分类第一条审查评论。项目成熟度、语言和组织安全文化都可能改变这一比例。

> **RQ1 的 Takeaway：安全评论在该抽样框架中确实稀少，而且高度集中在内存和并发问题；它描述的是特定项目集合，不是普适基准率。**

### RQ2：筛选器到底有多可靠？

#### 实验设计

作者把集成分类器与关键词、GPT-4o、Gemini-1.5-Pro 和 DeepSeek-V3 比较，使用 Precision、Recall、Accuracy 和 F1。

#### 最值得看的结果

| 方法            |  Precision | Recall |     F1 |
| --------------- | ---------: | -----: | -----: |
| 关键词          |     13.57% | 12.58% | 13.06% |
| Gemini-1.5-Pro  |     54.82% | 71.52% | 62.07% |
| GPT-4o          |     41.58% | 76.82% | 53.95% |
| DeepSeek-V3     |     59.68% | 49.01% | 53.82% |
| SeRe 集成分类器 | **92.75%** | 42.38% | 58.18% |

集成分类器 Precision 最高，但 F1 并不是最高；Gemini 的 F1 更高。作者的选择成立，是因为目标不是最佳总体分类，而是尽量避免污染数据集。

此外，集成方法在两个既有安全审查数据集上的 Recall 分别为 **75%** 和 **85%**。这与内部测试的 42.38% 差异很大，说明数据来源与正例定义会强烈影响性能。

#### 作者的 claim 能有多强

可以支持：

- 该集成筛选器能构造一个假阳性较少的安全评论集合；
- 与简单关键词及所测单一 LLM 提示相比，它明显提高了 Precision。

不能支持：

- 它能发现大多数安全评论；
- 五个分类器具有相互独立的错误模式；
- 92.75% 的 Precision 可以跨平台、项目和语言稳定复现。

> **RQ2 的 Takeaway：SeRe 优化的是数据纯度而非覆盖率；把它称为高质量正例池合理，把它称为完整安全审查样本则不合理。**

### RQ3：“贴近真实分布”的证据有多强？

作者从最终数据集中随机抽取 447 条重新人工核验：

- **94%** 被确认确实是安全相关评论；
- **84%** 可对应真实漏洞；
- 数据覆盖 311 个过滤后仓库和五种语言；
- 三次分类分布比较中，各类别 Fisher 检验均未低于 0.05。

这里最容易被误读的是 Table 3。大量罕见类别的 p 值为 1.0，并不是“完美相同”，更可能是样本太少，列联表中几乎没有足够差异可供检验。并发类别的 p 值最低达到 0.06，异常处理最低为 0.07，已经显示可能存在一定分布漂移，只是未跨过作者设定的 0.05 阈值。

此外，所谓代表性集合仍来自同一套 GitHub 项目和相近标注定义，并非外部独立总体。这个设计验证的是**内部抽样一致性**，不是对真实软件产业的外部代表性验证。

> **RQ3 的 Takeaway：SeRe 的标签纯度证据较强，语言和项目覆盖也比既有数据广；但“无显著差异”不足以证明分布等价，更不能排除筛选器造成的系统性漏检。**

### RQ4：现有模型会生成可靠的安全审查意见吗？

作者测试了 AUGER、DISCOREV、LLaMA-Reviewer、CodeReviewer、DeepSeek-V3 和 GPT-4o。预处理后保留 **4,788 个评价样本**；超过 2,048 个代码变更 token 或 10,000 个上下文 token 的样本被删除。

#### 关键结果

- LLaMA-Reviewer Prefix 的 BLEU 为 **3.67**、ROUGE-L 为 **10.25%**。
- DeepSeek-V3 zero-shot 的 METEOR 为 **13.7%**、SBERT 语义相似度为 **39.82%**。
- 所有方法的 Exact Match 都接近零。
- DeepSeek-V3 与 GPT-4o 的 two-shot 结果没有优于 zero-shot，多个指标反而略低。

作者的解释是：传统代码审查模型更接近参考评论的措辞，而通用 LLM 更容易表达语义相近的内容。

但这些指标并没有真正回答“安全评论是否正确”。一条评论可能与参考文本措辞不同，却准确发现同一漏洞；也可能语义相似，却提出错误修复。论文 Figure 6 的案例恰好说明了这一点：多数模型提到了资源管理，却只有 GPT-4o two-shot 给出了直接针对该条件分支风险的建议。

#### 评价设计中的几个关键问题

1. **单参考答案问题**
   真实代码审查允许多种有效表达，BLEU、ROUGE 和 Exact Match 把“与原评论相像”当作“审查正确”的代理变量。

2. **构念效度问题**
   SBERT 相似度衡量语义接近程度，不验证漏洞位置、触发条件、严重性或修复是否正确。

3. **样本不完全一致**
   AUGER 只适用于 Java，因此它与多语言方法未必在完全相同的实验单位上比较。

4. **过滤了长上下文样本**
   超长代码和上下文被排除，而这些很可能正是仓库级安全审查最困难、也最需要自动化支持的样本。

5. **原论文括号内成绩不构成受控对照**
   Table 4 把模型在原始测试集上的成绩放在括号中，与 SeRe 成绩比较。但测试集、分布和难度都变了，性能下降不能仅归因于“安全任务更难”。

> **RQ4 的 Takeaway：SeRe 揭示了通用代码审查模型在安全评论上的明显困难，但现有文本相似度指标不足以证明哪种模型真正更会发现或修复漏洞。**

### 作者证明了什么

1. 可以利用伪标签、主动学习、人工标注和多模型投票，从几十万条审查记录中构造较大的安全评论数据集。
2. 在论文的测试分布上，集成分类器取得了 **92.75% Precision**，适合优先保证正例纯度。
3. 安全相关审查评论在所研究样本中约占 4%，内存和并发问题占多数。
4. 现有评论生成方法在 SeRe 上的文本指标整体较低，安全审查仍然困难。
5. SeRe 的标签纯度经过人工抽样核验，并公开了数据、训练代码和评价输出。

### 作者没有证明什么

1. 没有证明 SeRe 覆盖了真实存在的大多数安全审查评论；其内部 Recall 只有 **42.38%**。
2. 没有证明模型一致判负的样本中不存在系统性安全盲区。
3. 没有证明类别分布与所有真实项目等价；Fisher 检验未拒绝差异不等于完成等价性证明。
4. 没有证明语义相似度更高的模型能发现更多真实漏洞或产生更可执行的修复建议。
5. 没有通过消融实验识别主动学习、伪标签验证、模型集成和投票阈值各自的独立贡献。

### 对 Causality for Code Review 的直接启发

这篇论文最值得你借鉴的不是分类模型，而是把**数据进入研究样本的过程显式建模**。

如果使用 SeRe 研究某种审查方法的效果，可以画出这样的选择机制：

```text
真实安全问题类型 ─────→ 是否被模型识别
       │                     │
       ├→ 评论措辞/上下文 ───┤
       ├→ 项目与语言 ─────────┤
       └→ 问题显著程度 ───────┤
                             ↓
                     是否进入 SeRe 数据集
                             ↓
                      下游模型评价结果
```

`是否进入 SeRe` 是一个选择变量。若不同 treatment 对内存、并发、权限和跨文件问题的效果不同，而筛选器又更容易发现其中某些类型，那么在 SeRe 上估计的平均效果可能偏离真实总体效果。

可以直接设计三个后续实验：

1. **估计选择概率**
   从分类器判负的原始评论中进行分层人工抽样，估计不同语言、项目和安全类别的漏检率，再用逆概率加权修正下游评价。

2. **把安全类型作为 effect modifier**
   不只报告总体效果，分别估计模型对内存、并发、权限、资源管理及跨文件安全问题的异质处理效应。

3. **把 Outcome 从文本相似度改为可验证安全结果**
   对同一个漏洞进行随机或配对实验，比较不同上下文 treatment 是否能够：
   - 找到正确位置；
   - 说明正确触发条件；
   - 给出通过安全测试的修复；
   - 避免引入新的功能回归。

### 你真正应该记住什么

- SeRe 是一个**高置信、但不完整**的安全代码审查数据集。
- 92.75% Precision 很亮眼，但与 42.38% Recall 必须一起阅读。
- 主动学习降低了人工成本，同时也创造了一个需要分析的样本选择机制。
- “与真实分布无显著差异”不能写成“已经证明无偏”。
- 对自动审查而言，文本相似度只是弱代理；真正重要的 Outcome 应是漏洞真实性、定位、触发条件和修复有效性。
- 对你的研究，最有价值的问题是：**一个代码审查 benchmark 的筛选机制，会怎样改变我们最终估计到的干预效果？**
