## 历史精读正文

### Quality Gatekeepers：机器人上线之后，代码审查真的变好了吗？

- **标题**：Quality Gatekeepers: Investigating the Effects of Code Review Bots on Pull Request Activities
- **作者**：Mairieli Wessel、Alexander Serebrenik、Igor Wiese、Igor Steinmacher、Marco A. Gerosa
- **来源**：Empirical Software Engineering，27:108，2022
- **原文**：[DOI 10.1007/s10664-022-10130-9](https://doi.org/10.1007/s10664-022-10130-9)

> 一句话结论：覆盖率机器人上线后，项目的合并 PR 增多、未合并 PR 减少，合并 PR 中的人类评论逐渐减少；但这是建立在观察性时间序列假设上的结果，尚不能排除项目发展阶段和同期流程变化等替代解释。

### 4.1 先建立论文地图

这篇论文研究的不是“机器人能否准确写出审查意见”，而是一个更贴近真实组织的问题：

> 当项目真正采用代码审查机器人后，PR 的接受、拒绝、沟通和处理速度会怎样变化？

作者先观察两个项目，形成假设；然后分析 1,194 个 GitHub 项目采用机器人前后两年的月度数据；最后访谈 12 名有实际使用经验的开发者，解释统计变化可能通过什么机制产生。

核心矛盾可以概括为：

```text
过去：
代码审查机器人通常通过自身准确率或少量案例评价

问题：
工具即使“技术上准确”，也可能改变开发者的沟通、信任和决策行为

作者方案：
将机器人采用视为一次组织干预
→ 比较采用前后的活动趋势
→ 再通过访谈寻找可能的行为机制
```

#### 理解全文需要抓住的四个概念

1. **干预时点**
   作者把机器人第一次在 PR 中发表评论的时间近似为采用时点。它是整项分析的分界线，但这个近似可能不完全等于真实安装日期。

2. **分段回归**
   它分别拟合采用前趋势、采用瞬间的水平跳变以及采用后的趋势变化。重点不是简单比较前后均值，而是看原有趋势是否在采用点发生中断。

3. **随机效应**
   不同项目和编程语言天然存在差异。作者用混合效应模型吸收这部分项目间异质性，避免把所有项目假设成同一个总体。

4. **机制解释与机制验证**
   访谈者可以解释“为什么可能出现这种变化”，但这不等于统计上证明机器人通过该机制导致了结果。要证明中介机制，还需要额外的测量和识别设计。

### 4.2 为什么仅评价机器人的准确率不够

作者观察到，机器人进入代码审查后扮演的并不只是“自动检查器”。它还可能：

- 让贡献者在维护者介入之前自行修改代码；
- 给维护者提供一个看似客观的质量门槛；
- 替代原本由人类发送的提醒；
- 改变接受或拒绝 PR 的信心和速度；
- 在讨论中制造噪声，或者减少重复沟通。

因此，真正的 research gap 是：**当机器人被部署到真实项目后，人类协作活动如何变化，既有研究缺乏大规模纵向证据。**

这个 gap 有实践观察支撑，但论文动机中也包含一个隐含前提：月度 PR 活动发生变化，能够在相当程度上反映代码审查过程的改变。实际上，PR 数量和处理时间也会受到项目增长、贡献者构成、发布周期等因素影响。

### 4.3 方法如何一步步运行

```text
GitHub 项目和机器人评论记录
↓
识别首次机器人评论，近似采用时点
↓
保留采用前后各一年持续活跃的项目
↓
排除采用多个机器人、使用其他已知机器人或中途停用的项目
↓
按月聚合合并/未合并 PR 的数量、评论、关闭时间和提交次数
↓
拟合 8 个混合效应分段回归模型
↓
访谈 12 名维护者/贡献者，解释观察到的变化
```

#### 第一步：从 4,767 个候选项目筛到 1,194 个

作者要求项目在采用前后各活跃至少一年，并排除了采用多个机器人、已知其他类别机器人以及机器人后期不再活动的项目。

最终样本构成非常关键：

- Coveralls：730 个项目
- Codecov：460 个项目
- 其他两个机器人：共 4 个项目

所以，这篇论文表面上研究“代码审查机器人”，实际上几乎完全研究的是**代码覆盖率机器人**。它不能直接代表今天的 LLM 代码审查 Agent。

#### 第二步：把活动聚合成项目—月份数据

作者为合并和未合并 PR 分别计算：

- 每月 PR 数量；
- 每月 PR 评论数的中位数；
- 每月关闭时间的中位数；
- 每月提交次数的中位数。

这里选择中位数是为了降低极端 PR 的影响，但代价是可能掩盖长尾变化。例如，机器人也许只对最复杂的 10% PR 产生很大影响，月度中位数未必看得出来。

#### 第三步：分解“采用后的变化”

模型的直觉是：

```text
结果
= 原来的时间趋势
+ 采用当月是否发生跳变
+ 采用后的趋势是否改变
+ 项目规模、活跃度等控制变量
+ 项目和语言差异
```

三个最重要的系数是：

- `time`：采用前趋势；
- `intervention`：采用时点的即时跳变；
- `time after intervention`：采用后的斜率相对采用前改变多少。

作者还控制了项目年龄、PR 作者数量、累计提交数量和当月打开的 PR 数量，并将项目和编程语言作为随机效应。

公式推导本身可以省略。真正需要理解的是：**它估计的是原有趋势在采用点是否改变，而不是为每个项目构造一个真正未采用机器人的反事实世界。**

### 4.4 RQ1：机器人上线后，PR 活动怎样变化？

#### 合并与未合并 PR

作者真正想验证的是：机器人是否改变了贡献进入代码库的流量。

表 3 中：

- 合并 PR 的采用时点系数为 `0.095`；
- 未合并 PR 的采用时点系数为 `-0.163`；
- 两者采用后的趋势变化分别为 `+0.004` 和 `-0.004`。

因变量经过对数转换，粗略换算后，采用点对应约 **10% 的合并 PR 上升**和约 **15% 的未合并 PR 下降**。不过这只是条件模型中的水平跳变，不应解释成每个项目都会精确变化这么多。

更重要的是，采用前合并 PR 已呈上升趋势，未合并 PR 已呈下降趋势；机器人采用后，两种趋势都进一步加速。

**RQ Takeaway：**采用机器人与更高的合并流量、更低的未合并流量相关，但“更多合并”并不自动等于“审查质量更高”。

#### 开发者沟通

对合并 PR，机器人上线时评论中位数出现轻微上升，但此后月度趋势显著下降；对未合并 PR，只观察到小幅即时变化，没有长期趋势改变。

这更像是：

1. 刚上线时机器人评论本身增加了评论量；
2. 随后它替代了一部分人类重复提醒；
3. 人类评论逐渐减少。

但论文的指标没有区分评论质量、讨论主题和知识传递。因此，“评论更少”既可能意味着节省沟通，也可能意味着团队共享理解减少。

**RQ Takeaway：**机器人可能替代了部分重复沟通，但论文没有证明整体协作质量因此提高。

#### PR 处理速度

- 合并 PR：采用点出现时间跳变，但长期趋势没有显著改变。
- 未合并 PR：采用前关闭时间呈上升趋势；采用后的趋势改变为 `-0.028`，结合原来的 `+0.012`，意味着趋势反转为下降。

换句话说，机器人最明显改变的不是“更快合并”，而是**更快识别和关闭不满足质量门槛的 PR**。

**RQ Takeaway：**机器人似乎更像早期过滤器，而不是普遍的审查加速器。

#### 修改次数

无论合并还是未合并 PR，提交次数的长期趋势都没有显著变化。机器人上线瞬间的局部跳变不足以说明持续增加了修改工作量。

**RQ Takeaway：**论文没有证据表明机器人让贡献者长期进行更多修改。

### 4.5 RQ2：为什么会出现这些变化？

12 名受访者主要提出五类解释：

1. **贡献状态更透明**：覆盖率结果让维护者和贡献者更快判断 PR 是否达到要求。
2. **维护者更有信心**：机器人像质量闸门，减少接受或拒绝时的不确定性。
3. **讨论重点发生转移**：机器处理“请补测试”之类的重复提醒，人类可讨论更高层问题。
4. **反馈推动贡献者行动**：贡献者会补测试、修改 PR，或主动放弃不值得继续的贡献。
5. **机器人评论可能成为噪声**：重复消息可能打断讨论，最终被开发者忽略。

其中，8 人表示在自己项目中见过沟通减少，6 人见过更少或更快的拒绝，5 人见过更多合并。

需要特别注意：访谈开始时，研究者先向参与者展示了统计发现，再请他们解释原因。这容易产生锚定效应。参与者给出的内容是**事后机制推测和经验印证**，不是独立发现，更不是中介效应检验。

### 4.6 这套证据到底能支持多强的结论？

#### 论文能够支持的

- 在筛选后的 1,194 个活跃 GitHub 项目中，覆盖率机器人采用时点附近存在可测量的 PR 活动趋势变化。
- 合并、未合并 PR 的变化方向在大样本中较稳定。
- 人类评论减少和拒绝加快，具有统计证据及部分从业者经验支持。
- 机器人可能通过透明度、质量闸门和自动反馈改变协作过程。

#### 论文没有证明的

- 没有证明变化完全由机器人引起。
- 没有证明合并 PR 增加代表代码质量提高。
- 没有证明沟通减少一定是积极结果。
- 没有证明访谈提出的机制是实际中介路径。
- 没有证明结果适用于 LLM 审查机器人、企业内部项目或更复杂的语义审查任务。

#### 最重要的识别风险

作者把这套方法称为 RDD，但它更接近以采用点为断点的**中断时间序列/分段回归**。经典 RDD 通常还依赖阈值附近单位近似随机分配的条件，而这里项目主动选择何时采用机器人。

主要替代解释包括：

- 项目增长或成熟促使团队同时采用工具并改变审查流程；
- 发布周期、贡献者增长或维护政策在同一时期变化；
- 首次机器人评论不等于准确的安装日期；
- 未测量的自动化工具仍可能同期进入项目；
- 只保留前后持续活跃的项目，产生存活与选择偏差。

作者控制了一些可测变量并排除了已知多机器人项目，这提高了可信度，但不能消除时间变化的未测混杂。

### 4.7 对 Causality for Code Review 的直接启发

这篇论文最值得你借鉴的不是“机器人有效”的结论，而是它揭示了一个清楚的因果研究模板及其缺口。

#### Treatment 不应只定义为“采用/未采用”

可进一步拆成：

- 是否提供自动反馈；
- 反馈是否作为强制质量门槛；
- 反馈对贡献者和审查者是否同时可见；
- 反馈出现于人工审查之前还是之后；
- 反馈是否由 LLM 生成；
- 人类能否忽略或覆盖机器结论。

这样才能区分“机器人存在”“反馈内容”和“流程约束”的效果。

#### Outcome 不能只有 PR 是否合并

更合理的结果族包括：

- 有效缺陷发现率；
- 无效评论率；
- 人工审查时间；
- 讨论主题和知识传递；
- PR 返工次数；
- 合并后缺陷；
- 新贡献者留存；
- reviewer confidence 和 automation bias。

#### 可以升级为更强的因果设计

如果研究仓库上下文或 Call Graph 对自动代码审查的作用，可以做同一 PR 的随机配对实验：

```text
同一批 PR
↓ 随机分配
仅 Diff / Diff + Repository Context / Diff + Call Graph
↓
统一模型、Prompt、Token预算和工具权限
↓
测量缺陷发现、误报、证据定位、审查耗时和置信度
```

这里任务难度和仓库复杂度更适合作为 effect modifier，用于估计异质处理效应；只有当它们同时影响 Treatment 分配和 Outcome 时，才应作为 confounder 调整。

### 4.8 真正的 Takeaway

#### 作者证明了什么

- 覆盖率机器人采用前后，多个 PR 活动指标出现了系统性趋势变化。
- 最稳定的变化是合并 PR 增多、未合并 PR 减少。
- 合并 PR 的人工沟通趋势下降，未合并 PR 被更快关闭。
- 从业者认为透明反馈和质量闸门可能是主要机制。

#### 作者没有证明什么

- 没有识别出不依赖假设的纯因果效应。
- 没有证明更多合并、较少沟通等同于更高代码审查质量。
- 没有验证开发者提出的机制链。
- 没有覆盖现代 LLM Agent 型代码审查。

#### 你真正应该记住什么

- 工具上线会改变人的行为，不能只评价工具自身的准确率。
- “PR 活动变化”是组织结果，不是代码质量本身。
- 采用前后分段回归比简单前后均值更强，但仍需要明确反事实和同期干预假设。
- 访谈适合生成机制假设，不适合单独证明机制。
- 对你的研究而言，最值得做的是把上下文、Call Graph 或 AI 评论作为可控 Treatment，并同时测量技术结果与人的决策结果。

> **如果一周后只记得一件事：机器人可能通过改变人的信心和沟通方式影响代码审查，但采用前后趋势变化仍不是完整的因果识别。**
