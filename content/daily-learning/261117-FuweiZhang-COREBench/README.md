# 论文精读｜CORE-Bench：改动位置之外，编码智能体还需要找回什么？

- 精读日期：2026-11-17（加急精读）
- 论文：**CORE-Bench: A Comprehensive Benchmark for Code Retrieval in the Era of Agentic Coding**
- 作者：Fuwei Zhang、Yanzhao Zhang、Mingxin Li、Dingkun Long、Lexiang Hu、Pengjun Xie、Fuzhen Zhuang、Zhao Zhang
- 发表：EMNLP 2026 主会，36477–36505 页
- 原文：[ACL Anthology PDF](https://aclanthology.org/2026.emnlp-main.1604.pdf)
- 配套：[评测代码](https://github.com/zhangfw123/CORE-Bench-Eval) · [数据集](https://huggingface.co/datasets/zhangfw123/CORE-Bench)
- 标签：代码检索、仓库级上下文、软件工程智能体、相关性标注、CPI、检索评测

## 一、从一个迁移优化请求看问题：只找到需要改的一段代码，够了吗？

设想开发者希望 Django 把连续的 `CreateModel` 与 `AlterModelManagers` 操作合并，减少一次迁移操作。检索器找到了处理操作规约的分支，最后补丁也确实修改了这里。按照“是否找到了改动位置”打分，它已经成功。

但负责修改的智能体还有问题需要回答：合并后模型状态如何变化？迁移图是否仍然成立？管理器信息会在哪里被消费？已有辅助函数和测试约定是什么？这些代码未必出现在参考补丁中，却可能决定修复是否正确。

CORE-Bench 的附录给出这一真实实例 `django-15499`：其 Level-2 标注只有 **1 个改动相关块**，Level-3 扩充后有 **58 个相关块**，覆盖迁移图、对象检查、模型状态和辅助逻辑。这个例子提供了整篇论文的入口：代码检索的目标集合可以比“补丁碰到哪里”宽得多。

这里也自然出现另一个问题：58 个块是否都必须读？有些块只是看起来相关，有些块可能只在特定推理路线中有帮助。论文主要解决“如何建立更贴近真实仓库工作的检索评测”，并没有完成对每块上下文因果必要性的鉴定。把这两件事分开，才能理解它与我们当前 CPI 研究的交集及距离。

## 二、论文处在什么位置，作者为什么会做这件事？

CORE-Bench 是一个基准与评测工作，也附带面向仓库任务的嵌入模型微调实验。它没有提出一个从请求到补丁的完整新编码智能体。研究对象是其中的检索环节：给定需求，在正确版本的仓库里，优先取回什么内容。

第一作者[张富威](https://zhangfw123.github.io/)是北京航空航天大学人工智能研究院博士生，研究兴趣包括信息检索、大语言模型、知识图谱和推荐。他此前的工作包括 ACL 2025 的多层相关性文档标识符学习与 HierGR，以及跨语言检索中的层次知识增强。这条研究线解释了本文的关注点：如何定义检索目标、组织正负例、衡量模型排序，而非只看智能体最终是否修好一个 issue。

论文明确标注的通讯作者有两位：[庄福振](https://fuzhenzhuang.github.io/)与[张钊](https://zhangzhaocs.github.io/)。前者的研究覆盖迁移学习、多任务学习、推荐和知识图谱；后者关注知识表示与应用、检索增强及智能体相关问题。作者顺序与通讯身份以正式论文首页为准。

这篇论文值得精读，因为它把一个常被含混处理的词“相关”拆成了两种操作性目标：**参考修复涉及的内容，以及完成修复时可能有帮助的上下文。** 后者恰好接近我们的研究对象，但它仍然需要进一步区分“相关”“决定性”“有益”和“有害”。

## 三、三个层级究竟改变了什么？

### 3.1 Level-1：传统代码理解检索

Level-1 保留文本到代码、代码到文本、代码到代码及混合形式的检索。来源包括 APPS、CoSQA、SyntheticText2SQL、CLARC、CodeSearchNet、CodeTransOcean-DL、CodeFeedback-ST 和 CPRet 等。作者剔除了部分饱和或与目标场景对齐较弱的任务。

这些任务仍有价值。例如，模型能否把自然语言功能描述与实现联系起来，是仓库检索的基础。但它们通常不能充分覆盖这样的情形：同一个仓库里有许多近似包装器、适配器与配置入口，用户给出的又是一段带环境信息和错误堆栈的 issue。

### 3.2 Level-2：从 issue 找到改动相关块

输入变成真实软件请求，候选来自该请求对应的仓库版本。正例由参考补丁反向对齐到修改前的代码块得到。这一层回答：检索器能否找出参考实现实际触及的位置？

### 3.3 Level-3：取回更广的支持上下文

Level-3 包含 Level-2 的改动相关块，并加入智能体处理任务时访问过、又被相关性判断保留下来的代码、测试、文档和配置。它回答：检索器能否覆盖超出直接修改位置的支持材料？

| 层级 | 请求数 | 候选块总数 | 相关性标注数 | 每请求平均相关块 |
|---|---:|---:|---:|---:|
| Level-1 | 172,961 | 2,412,296 | 823,345 | 4.8 |
| Level-2 | 5,061 | 9,377,120 | 52,712 | 10.42 |
| Level-3 | 2,580 | 2,609,581 | 106,479 | 41.27 |

来源为正文表 1 与附录统计表。这里的“相关性标注”，即 qrels，是请求与候选块之间的标注关系；候选块总数也不等于每个请求都要搜索的范围。

Level-2 涉及 632 个仓库，Level-3 涉及 97 个仓库。Level-3 请求数量更少，相关性标注却更多，直接体现了目标集合变密。三个层级的数据与任务组成不同，因此它们适合展示能力迁移缺口，不能被当作只改变一个因素的严格对照实验。

## 四、Level-2 如何做到“答案来自补丁，检索只能看到修复前代码”？

图 2 的左半部分可以按五步理解。

**第一步，收集任务。** 作者从 SWE-bench 系列及类似 PR 数据中取得 issue、PR、仓库和提交等信息。最终 Level-2 包含 Verified 432 条、Pro 632 条、Live 1,623 条、++ 442 条、+ 207 条、Multi 1,449 条与 Multilingual 276 条。

**第二步，清理请求。** Qwen3.5-397B-A17B 对 5,550 条原始描述进行筛查，排除 489 条，留下 5,061 条。其中 380 条被判为答案泄露，109 条被判为没有可操作信息。答案泄露指描述已经给出明确位置和修复方案；普通 traceback 中出现路径、描述中提及函数，并不会自动构成泄露。空模板或只有“Fix #123”的描述则缺少独立检索所需的信息。

这一筛查很重要：一个检索器可能通过抄取描述中的答案取得高分，也可能因请求完全没有信息而被无意义地惩罚。Verified 从 500 条减为 432 条，其中 68 条因泄露被移除；不同来源被筛除的比例并不相同。

**第三步，回到修改前版本。** 仓库 checkout 到相应 PR 修改前的提交。这样候选代码对应开发者实际面对的状态，不会把修复后的实现塞进检索库。

**第四步，切块并保留定位信息。** 代码通过抽象语法树（AST，即源码的语法结构）切分，文档通过 LangChain 等切分方式处理，同时保留路径和行范围。块是模型检索与打分的单位，路径和行号则负责把块与补丁、轨迹重新连接。

**第五步，把补丁映射回旧代码。** 根据修改文件与行范围，将参考补丁涉及的内容对齐到修改前的块，形成正例。检索输入是 issue 和旧仓库，补丁只在离线构造标签时使用。

这一步使标签具有可验证的来源，但也带来明确边界：参考补丁记录了一次被采用的实现。没被修改的块可能很重要，另一种正确修复也可能选择不同的位置。这正是作者继续建立 Level-3 的原因。

## 五、Level-3：轨迹、相关性裁决与受限重跑各自负责什么？

这是最需要仔细读的部分。图 2 右侧看起来是一条自动标注流水线，实际包含三种不同证据。

### 5.1 轨迹提供候选：智能体真正看过什么？

作者使用搭载 Qwen3.5-397B-A17B 的 Mini-SWE-Agent 尝试处理任务，再从轨迹中抽取 `cat`、`grep`、`head`、`sed` 等浏览命令暴露的内容，把实际访问的片段对齐到 Level-2 的块。

这一设计的优势是候选来自任务执行过程，容易捕捉仅凭补丁看不到的调用链、测试与配置。它的局限也来自同一来源：智能体没有访问到的有用内容，可能永远进不了候选池。轨迹在此是候选生成器，访问行为本身还不等于相关性证明。

### 5.2 相关性裁决：两种模型、三次判断

附录给出裁决提示词。裁决器看到 issue、块的元信息与内容，将其分为：

- **high，分数 2**：直接的错误逻辑、可能修复的位置、紧密相关的数据流或关键失败测试。
- **partial，分数 1**：有助于理解或定位的邻近上下文。
- **irrelevant，分数 0**：不提供相应帮助的内容。

每个候选使用三次判断：Qwen3.5-397B-A17B 给两次独立判断，Claude Sonnet 4.6 给一次。准确说法是**两种模型给三票**。这不是三个独立模型家族的一致性验证，也不是最终代码定位时用多数投票决定答案。

算法 1 先用 Level-2 标注初始化 Level-3，再加入接受的分数大于 0 的候选。原文没有充分展开三票如何合成最终分数、遇到不同意见时如何处理，因此复现时需要继续核对发布实现，不能自行补一个多数规则。

### 5.3 文件白名单验证：只给这些文件，还能解决多少任务？

作者分别根据 Level-2 与 Level-3 标注生成文件级 allowlist，让智能体只能访问相应文件，再看修复成功率。操作限制也会影响测试等步骤，所以这是一种受限环境下的集合质量验证。

| 数据来源 | 完整上下文 | Level-3 文件白名单 | Level-2 文件白名单 |
|---|---:|---:|---:|
| Verified | 73.0 | 69.0 | 62.0 |
| Multilingual | 65.0 | 59.0 | 43.0 |
| Pro | 46.1 | 43.2 | 36.9 |
| Multi | 42.0 | 39.5 | 23.3 |

表 13，数值为解决率百分比。Level-3 相比 Level-2 提升 7.0、16.0、6.3 和 16.2 个百分点，并且总体更接近完整上下文条件。这为“补丁之外的上下文有集合层面的用途”提供了实际执行证据。

但检验单位是文件集合。把一个文件放进白名单，也可能同时暴露文件内没有被单独标注的其他块。因此，69% 的解决率不能转写为“每个 Level-3 块都必要”，也不能推出它找到了最小充分上下文。

### 5.4 反馈迭代与失败轨迹

遇到上下文不足的情况，流水线会继续执行、提取新浏览内容、对齐和裁决。算法的停止条件包括任务解决、没有新增上下文或预算耗尽。论文没有在方法叙述中完整交代数值预算与所有反馈细节。

作者也保留一部分未成功修复的轨迹，只要其中的片段通过相关性判断。这减少了“只有容易被当前智能体解出的任务才有标签”的偏向。它仍依赖这套智能体能够探索到什么。

回到 Django 的例子，Level-3 的价值是把迁移图和模型状态等支持代码纳入评价目标。类似地，`grpc-go-3201` 从 2 个编辑相关块扩展到 121 个相关块，涉及 DNS resolver、包装层、ClientConn 状态和默认 service config；`zstd-983` 从 1 个扩展到 79 个，涉及源大小、参数转换与字典内部逻辑。目标集合迅速扩大，随之而来的难题是：给定有限阅读预算，该优先保留哪些？

## 六、请求改写：同一个任务，换一种说法会怎样？

作者还用 Qwen3.5-397B-A17B 将原始 issue 改写为较简洁的开发者请求，删除模板与重复信息，同时要求保留错误消息、堆栈、标识符和代码线索，不新增事实。附录提示词建议约 50–300 词，并特别要求保留完整技术报错。

Level-2 平均请求长度从 1,558.5 字符降至 660.8；Level-3 从 1,074.4 降至 547.4。**候选库和标签保持不变。** 因而原始版和改写版是同一个底层任务的配对视图，不能在划分训练测试或统计独立样本时拆成两条互不相关任务。

这个设置不只测试冗余删除。改写也会改变关键词密度、信息顺序以及模型能利用的表面线索。结果如果变差，应解读为请求表达方式敏感性，不能直接称作“去噪反而有害”。

## 七、领域微调：训练检索器辨别同一仓库内的近似候选

论文另构造了与 SWE-bench 系列仓库不重叠的训练集：628 个仓库、53,301 条 PR 请求、29,171,451 个候选块，以及 1,218,875 条正例关系，平均每请求 22.87 个正例。

正例仍由 PR 补丁对齐得到。负例候选从同仓库非正例块中采样，每请求构造 64 个负例候选，训练采用 1:8 的正负比例，对 Qwen3 嵌入模型的 0.6B、4B、8B 版本训练三个 epoch。

为什么同仓库负例重要？从完全无关的项目中区分一个候选很容易；在相同命名风格、相近领域词汇和重复封装之间找对入口，才是代码智能体经常面对的检索问题。

训练使用多正例对比学习损失 InfoNCE。对请求 q，记正例集合为 P、负例为 N，相似度为 s，温度为 τ：

`L(q) = −log [ Σ(d∈P) exp(s(q,d)/τ) / Σ(d∈P∪N) exp(s(q,d)/τ) ]`

直观上，它增加请求分配给正例集合的总概率，让多个正确块共同贡献监督，避免强行只认一个“唯一答案”。

这里有一个与全文有关的张力：训练的“非正例”只表示没有被补丁标记，并不保证对理解任务无用。论文一方面用 Level-3 扩展相关性，另一方面仍主要用编辑信号训练。它报告了这种训练对 Level-3 的迁移收益，但没有证明负例中完全不存在支持上下文。

## 八、评测口径：排名靠前与覆盖完整，是两件不同的事

评测基于修改后的大规模文本嵌入基准（MTEB）框架。仓库快照之间可以合并去重以节省存储，但每个请求都通过仓库与提交元信息筛选到相应版本的候选，避免跨时间状态混检。不同模型使用其相应的输入指令或原始文本配置。

两个核心指标分别看排序与覆盖：

- **归一化折损累积增益（NDCG@10）**：看前十名的分级相关性及次序，高等级相关块排得更前，收益更高。标准增益为 `2^rel−1`，按 `log2(rank+1)` 折损，再除以理想排序得分。
- **Recall@100**：前一百个结果覆盖了全部已标注正例中的多少。

NDCG 不是准确率，Recall 也不是修复成功率。一个系统可以前十名很准，但漏掉许多支持上下文；也可以前一百覆盖较广，却把关键内容排得很后。

比较模型包括通用嵌入模型、代码专用检索模型、BM25，以及领域微调版本。这里的 SweRankEmbed 结果属于嵌入检索器评测，不能直接替代一个包含额外检索、重排与最终决策的完整流水线结果。

## 九、核心结果：传统检索成绩为什么不能直接搬到仓库任务？

### 9.1 能力排序部分迁移，但分数明显掉落

以下均为正文表 3，单元格格式是 NDCG@10 / Recall@100，单位为百分数。

| 模型 | Level-1 | Level-2 | Level-3 |
|---|---:|---:|---:|
| Qwen3-8B | 71.7 / 96.9 | 20.3 / 48.0 | 34.4 / 41.5 |
| SweRankEmbed-Large 7B | 45.4 / 79.1 | 22.4 / 52.1 | 34.4 / 42.4 |
| Qwen3-0.6B | 66.9 / 94.7 | 17.0 / 45.5 | 32.6 / 40.2 |
| Qwen3-0.6B-SFT | 58.1 / 90.3 | 26.5 / 59.4 | 44.5 / 54.4 |
| Qwen3-4B-SFT | 59.8 / 90.5 | 30.3 / 66.0 | 49.2 / 61.6 |
| Qwen3-8B-SFT | 63.0 / 92.5 | 32.8 / 66.4 | 50.2 / 61.4 |

图 3 展示了这种普遍的层级差距。Qwen3-8B 在 Level-1 的高分没有转化为接近完整的仓库上下文覆盖。SweRank 在 Level-1 明显低于它，但在 Level-2 两项指标反而更高。这说明传统任务的强弱不能直接决定真实仓库任务的强弱。

不过，图 4 的秩相关给出了更细的答案：Level-1 平均排名与 Level-2、Level-3 的 Spearman 相关分别为 0.64 和 0.69。传统评测仍有一定预测力，只是远非充分。不同 Level-1 任务的预测力也不同，代码到文本的相关只有 0.47/0.52，混合任务达到 0.74/0.75。

### 9.2 领域适配可以比单纯放大模型更有用

0.6B-SFT 在 Level-2 与 Level-3 的四个指标都超过未微调的 8B。8B 微调后，Level-2 从 20.3/48.0 升到 32.8/66.4，Level-3 从 34.4/41.5 升到 50.2/61.4。训练目标与仓库候选分布对齐，收益很明显。

代价也在同一张表里：8B 的 Level-1 NDCG 从 71.7 降到 63.0，0.6B 从 66.9 降到 58.1。领域微调提高了当前目标能力，同时牺牲了一部分传统任务表现。另外，4B-SFT 的 Level-3 Recall 为 61.6，略高于 8B-SFT 的 61.4，所以不能概括为更大模型处处最好。

BM25 的 Level-2 为 13.0/38.8，Level-3 为 20.5/30.1。它明显低于最佳领域模型，却高于一些通用嵌入模型，例如 BGE-M3 的 4.6/18.3 与 8.7/12.5。路径、标识符和错误文本中的精确词面匹配，仍是不可忽略的基线。

### 9.3 简洁请求不一定更容易检索

Qwen3-8B 的 Level-2 从原始请求的 20.3/48.0 降至改写后的 17.2/45.1；Level-3 从 34.4/41.5 降至 30.8/38.4。8B-SFT 也下降：Level-2 为 32.8/66.4 → 29.2/64.0，Level-3 为 50.2/61.4 → 44.4/57.4。

但 CodeRank 的方向相反：Level-2 为 12.1/32.9 → 13.8/37.9，Level-3 为 22.5/28.6 → 26.2/31.4。这表明请求表达与检索器之间存在交互，不能从某个模型的变化推出统一的“精简请求更好”或“更坏”。

## 十、分组结果与失败分析：哪些困难被平均数遮住了？

### 10.1 多语言：收益广泛，样本量不均衡

图 1 与表 4、附录语言表覆盖 11 种语言。Level-2 仓库分布中，Python 约占 48.7%，随后包括 Java、Go、JavaScript、TypeScript、Rust 等。

以 Qwen3-8B 的 Level-2 NDCG 为例，微调后 Python 从 21.9 升到 33.7，Go 从 14.6 升到 38.8，JavaScript 从 18.6 升到 39.8，Java 从 12.5 升到 21.8。收益跨越多种语言，但基线、增幅和最终上限都不相同。

稀有语言的极端数值需要结合样本量阅读。例如 Swift 的覆盖很小，Level-3 仅涉及一个仓库；某一配置取得很高分，并不能代表对 Swift 生态的稳定泛化。

### 10.2 任务意图：主要证据仍来自 bug 与 feature

Level-2 中 bug report 占 60.2%，feature request 占 32.8%；Level-3 分别为 56.9% 和 35.9%。两者合计超过九成。

表 23 中，8B-SFT 的 Level-2 bug 请求为 32.4/68.1，feature 为 36.9/66.2：feature 的前十排序较高，覆盖率却略低。Level-3 对应为 51.4/59.0 与 59.7/56.7，也有类似差别。这说明用一个“难度”词描述整组任务会损失信息。

问题咨询与文档请求数量较少，Level-3 只有 11 条 question 和 9 条 documentation，相关均值更适合探索性观察。

### 10.3 大仓库与密集目标：覆盖比前排更容易受压

作者按候选库大小和每请求相关块数量划分 focused/dense 与 small/large 四种情况。8B-SFT 在 Level-2 的四组 NDCG 都约为 33–35；Recall 则从 focused-small 的 73.2，降到 dense-large 的 60.4。

Level-3 的 dense-small 为 49.5/69.5，dense-large 为 55.4/56.5。大库组的前十排序反而更高，覆盖却更低。因此数据支持的结论是：大候选范围与密集目标尤其考验覆盖，不能写成“仓库变大后所有指标都下降”。固定 top-100 时，更多相关块也会直接增加召回率的分母。

附录 H 进一步观察到，候选小于 1,000 的组中，NDCG@10 为零的比例为 19.6%；候选在 5,000–20,000 的组为 33.9%。零分失败中，bug 请求占 74.3%。后一个数字是失败样本的构成，不能当作“74.3% 的 bug 请求失败”。这些关联也未隔离语言、任务复杂度等混杂因素。

## 十一、容易漏读的两组补充实验

### 11.1 密集检索与智能体浏览轨迹：支持上下文都不容易找全

附录 F 让只读 Mini-SWE-Agent 执行检索，将整个轨迹中访问到的块映射到相同标签，和固定 top-100 的密集检索比较。

在 Verified 上，Qwen3-8B-SFT 的 top-100 对 Level-2、Level-3 的 Recall 分别为 76.12 与 63.29。GPT-5.5-xhigh 轨迹为 88.38 与 63.21，平均访问 99.40 个块；Qwen3.6-27B 轨迹为 80.35 与 62.47。

智能体在改动位置覆盖上更强，但更广支持上下文的覆盖都停在约 63%。这是有价值的校准：主动探索也没有轻易解决完整上下文发现。

比较仍有预算差异。一个是固定一百个结果，另一个是全程浏览的并集；平均块数相近不保证每任务块数、token、时延与工具成本相同。不能据此直接认定某种方式在等预算下更优。

### 11.2 BM25 与语义融合：排序收益没有自动变成覆盖收益

附录 G 将 BM25 与 Qwen3-8B-SFT 做分数融合。Level-2 七个子集有六个 NDCG 提升，Level-3 四个子集有三个提升，但 Recall 并不总是改善。

Verified 的 Level-2 从语义检索的 33.91/76.12 变为融合后的 36.66/74.27，前排更好但覆盖下降；Pro 从 39.28/64.89 变为 40.80/65.29，两项均略升。Multilingual 的 Level-3 则从 41.49/61.96 降到 38.91/57.79。

这说明词面和语义信号可以互补，但收益依赖子集和目标。论文没有给出一个覆盖所有设置的完整因素消融：例如换标注智能体、去掉某次裁决、改变训练负例、匹配上下文预算，分别贡献多少，尚不能从现有表格中独立归因。

## 十二、它证明到了哪里，还有哪些证据缺口？

将局限集中起来看，可以得到五个层次。

**第一，相关性标签有生成路径偏差。** Level-3 候选来自特定智能体与探索策略，裁决又依赖两个模型。漏掉未访问的关键块、把貌似相关的块保留下来，以及同模型判断的相关错误，都有可能发生。保留失败轨迹缓解了一部分选择偏差，但没有消除它。

**第二，标签粒度与验证粒度不同。** 标签在块级，白名单验证在文件级；大文件会附带暴露同文件其他内容。Level-3 比 Level-2 解决率更高，支持集合级用途，但无法辨别哪些单块决定结果、哪些是冗余、哪些会干扰。

**第三，更多上下文与更好上下文没有完全分离。** Level-3 的集合通常大得多，论文没有在等 token、等块数下完成所有受限重跑比较。因此它提供的是扩充上下文后的效用证据，对信息质量的独立效应仍需额外控制。

**第四，评测和报告仍有复现空白。** 文中缺少充分的人类标注一致性检验、三次裁决的完整合成细则、部分循环预算以及结果不确定性分析。附录 H 的每请求平均标签数与正文表 1、附录统计表有轻微差异，本文采用详细统计表的 10.42 和 41.27。执行复现应核对具体数据版本、评测配置与聚合方式，而非混用不同表格。

**第五，适用范围取决于任务来源。** 数据主要来自 SWE-bench 家族与 PR，bug 和 feature 占主导，语言和仓库不均衡。仓库不重叠的训练设计减少了一类泄露，但不等于完全排除预训练污染或证明对任意私有仓库有效。发布数据、论文全部层级与每个内部校准实验也应分别核对，不能将一个下载包视为全部实验材料。

作者的核心结论仍然成立：仓库版本、局部相似干扰、多目标与辅助上下文，是传统代码片段检索评测覆盖不足的因素；领域适配能够明显改善这一场景。更强的因果性或普适性主张，需要更多实验。

## 十三、对当前 CPI 研究最直接的影响

### 13.1 先调整新颖性定位

CORE-Bench 已经包含“从智能体轨迹提取上下文 → LLM 相关性裁决 → 受限环境重跑验证”的组合。我们不能把这三个动作本身作为主要新意。

可继续推进的问题是：**语义上合理的上下文，何时真正支持最终定位，何时挤占预算或诱导错误？** CORE-Bench 的 high/partial 是相关性等级；我们的 C/P/I 区分关注任务证据角色及干扰效应。两者没有现成的一一对应关系。High 不自动等于 C，partial 不自动等于 P，补丁外代码也不能一概当干扰。

### 13.2 防止过滤器把真正支持代码一起删掉

Level-3 白名单比 Level-2 更有用，是对“只保留直接改动相关内容”的重要提醒。过滤策略如果只奖励与补丁近似的位置，可能提高表面精度，却删除决定推理正确性的配置、测试和调用关系。

因此，过滤实验应同时观察直接定位证据与支持证据的保留情况，再看最终定位输出。可以离线建立 high/partial 与 C/P/I 的交叉分析，但裁决输入必须只含部署时可见的 issue 与源码，避免把金标准答案偷偷提供给选择器。

### 13.3 等预算干预比再次做相关性判断更关键

对当前 RQ2/RQ3，最有区分度的证据来自固定候选、固定节点数或 token 预算后，改变上下文组合并观察最终决策。需要分别记录：

1. 检索实际暴露了哪些源码；
2. 过滤留下了哪些内容；
3. 最终裁决定位到了哪里；
4. 代价花在了多少调用和累计输入输出上。

只看到最终输出块数减少，不能说明真实开销减少；只看到相关性标签更纯，也不能说明最终定位更好。若某种过滤平均收益不稳定，CORE-Bench 恰好提供了一个可检验的解释方向：被删内容中可能混有任务需要的支持材料。但这个解释要通过干预与错误分析确认。

### 13.4 当前 38 个不同任务，首先守住统计单位

当前 RQ3 已收敛到 38 个不同任务，重复组按冻结顺序取第一个。CORE-Bench 的原始/改写请求说明了相同原则：底层任务不因换一种描述就成为独立样本。去重口径、样本顺序和所有方法共用的任务清单应固定，避免方法间悄悄换题。

CoSIL、LocAgent 的两模型与筛选裁决，以及随后 SweRank 本地实验，应在共同任务和预算口径下比较。CORE-Bench 可提供检索诊断与外部验证思路，但其 NDCG/Recall 与我们最终定位的 F1 不可直接横比。使用公开任务进一步验证时，还需核对仓库、具体修复任务和 base commit 的交集，避免把重合任务当成独立泛化证据。

## 十四、读完应带走的判断

CORE-Bench 最有价值的推进，是把代码检索的评价目标从传统语义匹配扩展到具体仓库版本中的编辑位置与支持上下文，并用真实执行结果说明：只覆盖参考补丁，往往不够。

它同时留下了一个很适合继续研究的缺口：**一个内容被访问、被判断相关、甚至属于有效上下文集合，都还不能单独确定它对最终结果的作用。** 从“有哪些相关内容”走到“在有限预算下哪些证据使决策更可靠”，正是 CPI 需要通过严格干预回答的问题。
