# Echoes of AI：AI 帮写的代码，换个人接手之后怎样？

> 精读日期：2026-11-24  
> 原题：Echoes of AI: Investigating the downstream effects of AI assistants on software maintainability  
> 作者：Markus Borg（一作、通讯）、Dave Hewett、Nadim Hagatulah、Noric Couderc、Emma Söderberg、Donald Graham、Uttam Kini、Dave Farley。  
> 发表：Empirical Software Engineering 31:161，2026 年 6 月 9 日。

## 一、把代码交给下一个人，才知道快在哪里

你用 AI 很快加了一个搜索筛选项。一周后同事打开仓库，要在同一段逻辑里再加一项。他会觉得前人铺好了路，还是觉得读懂那一堆分支比自己重写更慢？如果研究在第一位开发者点下提交按钮时就结束，这个成本永远不会进入报表。

过去的生产率研究通常看首轮的作业用时、提交数、完成率，或静态检查通过率。这些结果能回答“今天完成得多快”，很难直接回答“别人明天改起来多快”。本文让第二位开发者实际接手第一位的代码，用新增功能所需的时间、主观体验和成品特征一起衡量可维护性。图1因此把两件事分开：可维护性是代码工件的属性，生产率描述使用该工件的人在维护活动中的表现。两者相关，不能用一个工具分数来替代。

这篇实证软件工程期刊文章的第一作者与通讯作者均是 Markus Borg。其[隆德大学主页](https://portal.research.lu.se/en/persons/markus-borg/)列其为 CodeScene 首席研究员及该校软件工程兼职教师，研究涵盖实证软件工程、应用 AI 与技术债。他此前参与的 *Ghost Echoes Revealed* 已用人工评估对照可维护性指标；本文进一步让另一人完成真实的后续变更。Equal Experts 工程师参与设计任务与实验系统，团队还包括隆德大学和 Continuous Delivery 合作者。研究设计曾经 ICSME 2024 注册报告评审；这与后文所述的探索性第一阶段比较是两件事。

## 二、同一个食谱网站，先加时间筛选，再加价格筛选

正式原文图2先把问题拆成效率和质量。图3画的是实验流程，图4才是作者用于分析的有向无环图（DAG）。

实验用 RecipeFinder，一个有意留有质量缺陷和不完整测试的 Java/Spring Boot 小应用。图22显示用户的查找界面，图23把问题落在一段实际控制器代码：原有搜索方法已有多处分支嵌套，圈复杂度为13。每轮新功能都得在这个区域做事。附录A说明第一轮增加按总用时筛选并修正已有的时间展示缺陷，不预期改后端 API；第二轮接着加“每份成本”筛选。两轮各有三项验收检查，目标质量要求保持宽泛，以模拟需求方不会给出完整重构规范的情形。

1. **第一阶段生产代码。** 449份有效报名问卷用于筛查与分组。AI 组按既有使用经验和偏好形成，参与者可选熟悉的助手；对照组不用 AI。这是为减少强迫使用陌生工作流或禁止熟悉工具造成的不遵守，代价是两组原本就不同。表6中 GitHub Copilot 有21次报告、ChatGPT 13、Cursor 9，可多选。不能读成同一款模型的对照，也不是让自主 Agent 接管整个任务。
2. **第二阶段随机分配起点。** 一批新开发者被随机分给合格的第一阶段方案；处理组接到有 AI 协助的方案，对照组接到没有 AI 协助的方案。所有接手者均被要求不用 AI。作者给第一阶段的提交安排多个邀请，以免未响应就断掉整个交接。表7列第一阶段39份 AI 协作和37份非 AI 方案，第二阶段40份处理和35份对照；这是**方案/结果数**，不是四组独立人员都同时用过两套流程。第一阶段有一人交了两份不同方案；另一人被发现用了 AI 后更正分组。图9显示，只有51份第一阶段起点得到有效续作，部分起点有多个续作。
3. **统一读取指标。** 提交系统独立开 GitHub 仓库，自动跑验收、CodeScene 和 JaCoCo。四个结果是完成分钟、基于开发者生产率框架 SPACE 的感知生产率、全项目按文件代码行数加权的 CodeHealth（1–10分）和测试行覆盖率。CodeHealth 的复杂度和嵌套阈值为小任务调低，度量着重于文件级代码构造；行覆盖率是代码被执行到的比例，不表示断言覆盖了所有语义。

时间并非一律来自机器计时。系统原本从开放仓库算到最终交付，但约半数参与者未一次做完。作者以67个邮件回忆工时替代原记录，并剔除11个超过16小时的可疑值；因此第二阶段有75份合格方案、72个可用时间。感知生产率有十道等级题并允许不适用，频率派用题项均值，贝叶斯另用有序题项建模。表1–2给问卷，表5是质性编码表。任务共收到151份有效方案；论文结论部分报告约95%由职业开发者完成。收到有效方案的人远少于报名者。

## 三、图4真正讲了什么：操纵一个来源，与把来源随机发给别人

图4分左右两栏。左边，第一位开发者的特征同时影响其 Java 熟练度、使用偏好与 AI 习惯；偏好参与决定首轮是否用 AI。图里拟研究的路径是：

`首轮用 AI → 首次交付 Code1 → 接手者的 Code2 → 最终覆盖率或 CodeHealth`

`Code1` 也能直接影响接手者花多久、觉得多费劲。另一条路径从“是否用 AI”逆着偏好回到第一位开发者，再顺着 Java 熟练度、代码去到覆盖率。这是**后门路径**：例如两组原本就不一样熟 Java，组间差异会叠加到工具效果。图中还有经过 AI 习惯的替代路径。作者按这张图在模型中调整首轮 Java 熟练度和 AI 习惯；在耗时模型中再加入第二位开发者是否中断，其目的主要是改善估计精度。论文把交付物作为未完整观测的中介，没有为了让两组相似就把首轮代码质量当协变量塞回去，否则可能把 AI 经由代码产生的总效应挡住。

两种估量要分开。**第二轮随机的是接手者收到哪类已完成的工件**，因而提高了对“分配这批现成代码给接手者”的比较可信度。首轮开发者是否用 AI 没有随机；要进一步解释为“让同一类首轮开发者用 AI 产生的效果”，仍依赖图上对技能、习惯和其他未测差异的假设。试验流程图负责交代在哪里随机，DAG 负责交代变量之间的假定关系；随机化不需要画成每条箭头的含义。

频率派根据数据形状对时间与覆盖率用 Wilcoxon 秩和检验，对 CodeHealth 与感知生产率用 Welch t 检验，采用组内重抽样估计区间。事前计划第二阶段至少128人才能较稳地检出中等差异；75人对标准化差异约0.66才有约80%功效，对0.5约57%，对0.2约17%。这解释了为何文章还给出贝叶斯模型及不同先验的敏感性，而不把“未显著”当等效检验。

附录B给出运算。耗时取对数，因而比较可转回相对用时变化；覆盖率在 logit 尺度建模并用预测值翻译回百分点；CodeHealth 用线性回归。对主观题，图5、16、24展示一个潜在效率值怎样通过各题独立的分界映成1–5档，而不是假定“从1到2”和“从4到5”间距相等。AI 习惯和 Java 熟练度等有序变量用可以不同宽度的台阶表示；经验与 AI 使用相互作用，作者重点展示首轮习惯使用 AI 的画像，其他人仍纳入拟合。表4比较乐观、中性、悲观三组先验，让读者看到结果是否由先验主导。

## 四、实验结果：起步更快，没有可靠传到下一棒

### RQ1：接手更高效吗？

第二阶段接受相同功能要求、同样不用 AI，改变的是收到的既有代码。图13显示处理组中位数136分钟，对照173分钟，但分布长尾、组间区间宽、Cliff’s δ=−0.079，p=0.56。图14把两轮的贝叶斯后验放在一起：在习惯使用 AI 的首轮开发者画像下，第一轮更快的估计曲线明显在零左边，第二轮曲线向零移动、而且横跨零。论文报告第二轮相对时间变化后验均值−12.59%，95%可信区间−45.77%至+32.68%；换悲观先验后，“更快”的后验概率从76%跌至约38–39%。处理组少37分钟是描述统计，不是可以承诺的提速。

图15的主观生产率均值为3.95对4.06（p=0.37）。使用习惯人群画像的有序模型也只给不确定的负向倾向。图17把抽象的潜在分数转回示例题：高 Java 熟练度的习惯使用者对应的续作中，某道题给最高分的预测概率约51%降至47%。这是模型预测，不能当成实测比例。自由文本也揭示了用时噪声来自哪里：不熟悉 Spring Boot、搭环境时出问题，以及对“做到多好才可提交”有不同判断。有人只满足验收，有人主动重构多处。没有测得一致的下游效率差异，是这一轮试验的主要结果。

### RQ2：接手完成后的代码质量更高吗？

| 第二轮指标 | AI 来源 | 非 AI 来源 | 总体比较 |
| --- | ---: | ---: | --- |
| CodeHealth（图18，均值） | 8.49 | 8.44 | p=0.24，d=0.28 |
| 测试行覆盖率（图20，中位） | 70% | 70% | p=0.49，δ=0.09 |

图19按首轮 AI 习惯等级画出 CodeHealth 的模型后验，低习惯效应集中在零附近，高习惯稍向正侧移动。习惯使用者对应的第二轮估计提升为0.10分（95%可信区间+0.02至+0.19），三种先验变化下相对稳定。这是**按模型和使用者画像得到的细小质量信号**，与总体的8.49对8.44以及不显著并不矛盾。覆盖率后验也只给很小的正向信号：对高 Java 技能且习惯使用 AI 的首轮画像，第二轮预测约68%对69%。这不是两组实测各自的中位数。

表8拆开 CodeHealth 之后，平均分接近仍可掩盖不同维护路线：AI 来路组恶化复杂方法的方案为22/40，对照11/35；前组也较常移除已有复杂方法，8/40对3/35。引入长复合条件为7/40对1/35，手工检查关联到把新价格判断直接补进既有的关键字与时间过滤条件。反过来，新出现的原始类型滥用较少（3/40对9/35）；作者推测这和一些方案采用较集中的函数式写法、减少分拆后传递零散参数有关。不同指标能同时有好有坏；这些事后拆分宜作为机制线索。

### 单独看第一轮，会误读哪些现象？

图21的原始比较下，AI 组交付时间中位数短30.7%（p=0.0029，δ=−0.42），贝叶斯的习惯使用者画像估计更大，论文结论报55.9%。这里的30.7%是未经随机化的组间差，不是下游数字。第一阶段的 CodeHealth 差异没有统计显著性，覆盖率多数聚在70%附近，最高几份测试覆盖率和最积极的效率自评出现在有 AI 的组，也有明显离群值。

表7显示 AI 组新增行均值643、非 AI 组216，但中位数是123对166；最大值10,788对660。平均值受少数大改显著影响，不能说“典型 AI 方案多写三倍”。一份超万行方案增加大量测试、文档和前端库而非同等规模的新业务能力，却获得较高的 CodeHealth。该评分是按行数加权的文件级质量；大批良好代码会冲淡局部坏代码，并不降低需要理解的总量。表9–12分别拆出原项目与新方案的气味、气味的引入/移除、RefactoringMiner 检测到的重构及 PMD 静态规则告警。AI组比较常做变量内联、重命名等局部整理，也更常加入注释和新测试；非 AI 组较常提取类和移动方法。一些 AI 方案消除原方法的嵌套，另一些引进重复代码或复杂条件；PMD 的若干复杂度告警更少，代码风格告警波动却更大。附录C/D说明气味和 PMD 规则，不是事后把所有质量都合成一个成绩。

自由文本（§4.5）给了有帮助和会误导的例子：有人只把 AI 当陌生技术栈的入门手册，后来手写功能；也有人在排查问题时被引向错误方向。非 AI 使用者有人喜欢主动重构，也有人指出首次接触团队仓库，实际不会无沟通就深度改动。177条经编码的材料说明可能机制和环境摩擦，不给因果频率，也不代表未回复的人。

## 五、证据够回答什么，下一步怎样做得更清楚

- **条件明确的结论**：在一座小型 Java 应用、跨人交接一次、接手者不使用 AI 的情况下，四项指标都未发现稳定的大幅组间差异。小或中等差异仍有空间；时间的区间尤其宽，无法据此宣布等效。
- **试验单位的边界**：第一轮只把通过验收的方案交下一轮；第二轮较多退出或未通过，报告的主要是有效续作。多名接手者共享同一份起点，个体不交流也不意味着结果不存在起点内相关。如果复做，值得预先报告所有分配后的完成率和缺失，再按起点做聚类或给起点等权的敏感性估计。两阶段共151份方案不能理解为151个独立开发者后续效应。
- **测量与外推**：自报工时、不同完工标准、只有少量验收测试，都会影响解释。覆盖率高与检查全面不同，文件级 CodeHealth 与架构和长期协作也不同。旧一代补全、聊天工具和不同使用量组成一个混合处理，不足以对当下自主编码 Agent、百万行项目、长期技术债或个人认知能力做定论。
- **复现的分工**：公开分析仓库提供清洗、描述统计、频率派和贝叶斯代码；文中给出[配套归档](https://doi.org/10.5281/zenodo.17977295)及任务资料出处。CodeHealth 本身依赖商用 CodeScene，原文称学术可申请许可。预注册公开的是设计，未授权随意改写数据边界或把事后观察当预先假设。

最值得借鉴的是图3和图4的分工。如果比较同一任务在几种输入构造下的表现，可以先画一张分配图：同一任务、相同模型/评分协议，输入配置在哪一步发生变化。随后只在因果图中放真正需要辨认的路径：任务或模型若影响结果，但没有决定受控处理的分配，就不自动成为混杂因素；在构造时固定的预算写进图注和对照定义；由处理改变的实测用量或后续证据可见性则有可能处于中介路径。先写明要估的是同预算内的对照、还是允许机制自由改变的总效应，再决定哪些节点该画、哪些不该拿来调整。
