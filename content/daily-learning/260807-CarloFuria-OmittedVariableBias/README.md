## 一句话价值

用 DAG、调整集和 tipping-point 敏感性分析评估观察性软工结论对未测混杂的稳健性。

#### 一句话结论

扩大样本不能消除遗漏变量偏差；对于仓库挖掘研究，应先用因果图决定调整变量，再用 tipping-point sensitivity analysis 判断一个未测混杂因素需要多强，才能推翻结论。

#### 研究问题与动机

实证软件工程经常从 GitHub、Gerrit 等平台获得大量观察数据，然后使用回归模型解释某个因素对结果的影响。

问题是：如果一个未记录变量同时影响 treatment 和 outcome，回归系数会吸收它的作用。例如：

- 开发者能力影响其采用的编程语言；
- 开发者能力也影响代码质量；
- 如果模型没有测量能力，就可能把能力造成的质量差异错误归因于语言。

样本越大，只会让这个有偏估计显得越“精确”，并不会使其更接近真实因果效应。

#### 方法流程

论文提供了一个可操作的工作流：

1. 明确 treatment、outcome 和目标因果效应。
2. 根据领域知识及既有文献建立 DAG。
3. 从 DAG 推导最小或可行的调整集。
4. 检查调整集中的变量能否被可靠测量。
5. 对无法测量的混杂变量设定合理效应范围。
6. 进行 tipping-point sensitivity analysis。
7. 判断多强的未测混杂才能改变效应符号或统计结论。
8. 若很弱的混杂就能推翻结论，应重新设计研究、收集其他数据或缩小研究问题。

#### 数据、比较对象与评价方式

论文使用两个真实软件工程场景作方法演示：

- 编程语言对代码质量的影响；
- 团队规模对开发工作量的影响。

第一个案例使用既有 GitHub 项目数据的子集：

- 105个单语言项目；
- 45个 Java 项目、60个 Python 项目；
- 每个项目至少100次提交；
- 952名至少提交10次的开发者。

代码质量定义为：

\[
1-\frac{\text{bug-introducing commits}}{\text{all commits}}
\]

开发者能力则用其提交中未引入缺陷的比例近似。需要注意，这些指标只是方法演示所用代理变量，作者明确不把结果解释成 Java 或 Python 的一般性质量结论。

主要分析工具包括：

- DAG 与调整集；
- 线性统计模型；
- 标准化均值差；
- tipping-point sensitivity analysis；
- R 包 `tipr`。

#### 可核验结果

在语言—质量案例中：

- 同时控制开发者能力时，语言效应估计为 **−0.012**；
- 忽略能力时，估计变为 **−0.052**；
- 实际数据中，能力对语言选择关系的标准化均值差为 **−1.545**；
- 只需 **−0.062** 的相应标准化差异，就足以使观测效应翻转；
- 或者，能力对质量只需产生 **0.034** 的效应，也足以翻转结果；
- 假设存在多个较温和的未测混杂因素，两个这样的因素便可能推翻效应方向。

因此，这个案例的观测结论对遗漏变量非常脆弱。

#### 局限与威胁

- 论文主要是方法演示，不是对语言、质量或团队效率给出领域结论。
- 案例主要采用线性关系和横截面分析。
- 敏感性分析不能自动发现真正遗漏了哪个变量。
- tipping point 依赖研究者为未测混杂设定的合理范围。
- DAG 如果错误，调整集和最终估计也可能错误。
- 该方法不能替代对选择偏差、测量误差和时间依赖混杂的处理。
- 对代码审查这种纵向过程，可能需要边际结构模型等扩展方法，而不能直接把每个 PR 当作独立样本。

#### 与 Causality for Code Review 的具体联系

它非常适合作为你当前研究的核心方法论文。

假设研究：

> 使用自动化代码审查工具，是否提高 review-point hit rate？

一个初始局部 DAG 可以写成：

```text
变更复杂度 ─→ 是否使用工具 ─→ review-point hit
      └────────────────────→ review-point hit

审查者经验 ─→ 是否使用工具
      └─────→ review-point hit

项目成熟度 ─→ 是否使用工具
      └─────→ review-point hit
```

可能难以测量的变量包括：

- 审查者对模块的真实熟悉程度；
- 开发者主动采用工具的动机；
- 团队审查文化；
- PR 的隐性风险；
- 时间压力。

你不仅要报告“控制了哪些可观测协变量”，还应回答：

> 一个未观测因素需要同时多大程度影响工具使用和 review-point hit，才能使观察到的效应消失或翻转？

这会比仅增加更多控制变量、项目和模型更有说服力。

#### 可直接借鉴的实验或写作点

1. **把调整变量选择与预测特征选择分开。**
   不应按照相关性、显著性或模型性能选择混杂变量，而应由 DAG 和识别条件决定。

2. **增加遗漏变量敏感性分析。**
   主结果之后报告 tipping curve，并用审查者经验、PR复杂度等已测变量作为未测混杂强度的参照。

3. **解释大样本为什么不能解决偏差。**
   可以在 threats to validity 中指出：更窄的置信区间并不代表较小的因果偏差；它可能只是对错误估计更加确信。
