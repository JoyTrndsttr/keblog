# How Much Do Coding Agents Over-Edit, and Why? An Empirical Study of Unneeded Edits in Repository-Level Agent Patches

> 精读日期：2026-11-28  
> 作者：Aakash Goel、Benjamin Steenhoek（共同一作）、Yu Hu，均署名 Microsoft；原文未单列通讯作者。  
> 来源：[arXiv:2611.34875 v1](https://arxiv.org/abs/2611.34875) · [原文 PDF](https://arxiv.org/pdf/2611.34875)。2026 年预印本，未核实正式录用。

## 多改了一百行，究竟哪里多余？

一个 Agent 修好分页错误，同时加了回归测试、更新文档，还顺手改变了空输入的处理方式。它的补丁比维护者的长，可三种新增内容的性质完全不同：测试可能降低以后再修的成本，文档可能解释新约定，而空输入行为可能无端扩大改动范围。要判断 Agent 是否过度修改，关键不是数行，而是问：**把某块改动单独撤回，什么会坏？这块改动又在哪一步留进了最终补丁？**

这是 Microsoft 团队的仓库级实证研究。共同一作 [Aakash Goel](https://www.linkedin.com/in/goelaakash123) 公开介绍过加入 GitHub Copilot 团队；[Benjamin Steenhoek](https://benjijang.com/) 在 Microsoft Code|AI 从事 Copilot 编辑模型和 Agent 研究，同 [Yu Hu 等人的工作](https://arxiv.org/abs/2611.33314) 也涉及 Copilot 编辑模型。作者团队和评估所用 Copilot CLI 有直接关系，这给轨迹和评估数据提供了实际来源，也使跨运行框架的检验格外重要。对研究者而言，值得读的是：作者没有把一个方便统计的代理量直接当作研究构念，而是用可观察干预来定义它，再检验这个定义会在何处失灵。

## 把一个补丁真正拆开看

作者把方法称作 **Delta Residue Attribution（DRA，改动残留归因）**。图 1 和算法 1 可以顺着同一个教学例子理解。设分页补丁有 A（修正边界）、B（改变空输入行为）、C（回归测试）三块：

1. **重建轨迹。** 从任务起始快照按日志重放结构化文件编辑，为每行记录来源，再同最终提交比对。若重建结果与提交不一致，SWE-bench Verified 的相应轨迹不进入严格重放分析，避免把日志中没看见的内容猜成某一步写的。DeepSWE 另有精确来源缺失，归因用有精确来源的单元。
2. **拆成可以单独撤回的单元。** 同一文件相邻变更行合成一块，间隔至多一行未变代码也会合并；新增或删除文件作为一块。代码、测试、文档、配置、注释及格式变更分开处理。在 SWE-bench Verified 的评分设置中，测试文件会重置；像 C 这种新增测试不能用同一个通过门槛判断价值，所以主要分数只看代码。
3. **确定它留在补丁中的来源。** 一个块归给最后写入或删除其任一行的步骤。若 B 在探索时写出、修复时又被改过，最后归到修复。先用两条确定性规则，再用 GPT-6.1 Sol 按任务、历史和操作标成调试、修复或清理三组；这衡量的是最终留存的作者动作，不是概念第一次出现的时间。
4. **在同一份最终补丁上逐块撤回。** 把 A 恢复成改前写法，其他块保留，重跑任务测试。若从通过变失败，A 对这套检查是必要的。若单独还原 B 仍通过，B 暂时标成「任务测试不需要」。无法有效撤回或解析失败也按必要计。每块都从同一个最终状态开始，不把上一块的撤回累积进主分析。只有部署裁剪的实验才累积撤回。
5. **追问测试没看见什么。** 对被标为不需要的代码，作者让独立调用生成器看 issue 和局部撤回差异，不给任务测试或维护者补丁。探针同跑于 Agent 补丁、撤回后补丁和维护者补丁。若 B 确实改变行为，且保留 B 时的行为与维护者补丁一致，增强判据可以把 B 恢复为必要。这区别了「测试没覆盖」「有行为变化」和「有参考证据支持这个变化」。

代码必要率 NP_code 是「撤回会让判据拒绝的代码单元数 / 全部代码单元数」。例如三个代码单元只有撤回 A 会失败，分数是 1/3。调试残留占比则是「归给调试步骤的不必要代码数 / 所有不必要代码数」。分母不同，前者评估补丁构成，后者定位残留来源。NP=1 只表示没有单块可以按当前粒度撤去；两块替代实现各自撤掉都能通过、一起撤掉才失败时，单块判定同样无法描述它们的联合必要性。

## 为什么要两套任务和一条人类基线？

主分析用同一个 GitHub Copilot CLI 运行框架，覆盖四家供应商的 18 个模型。SWE-bench Verified 有 500 道 Python 任务，纳入 6,728 个已解且可精确重放的补丁（482 道不同任务，114 道由 18 个模型共同覆盖）；DeepSWE 有 113 道多语言长任务，纳入 932 个已解补丁，模型级统计用可评分任务至少 10 道的 17 个模型。对维护者补丁用同样的检查，分别有 470 道和 103 道任务可作比较；DeepSWE 的四份未过任务测试的维护者补丁被排除。主结果按任务测试评估，行为探针负责校验部分判定。模型差值在可比任务上估计，论文用实例自助法报告 95% 区间，另做共同任务、任务固定效应及粒度敏感性检查。附录 A 记录先验预期及调整：两模型试验发现测试占额外改动的大头，于是把代码设为主要分析对象，并加入维护者校准。

## 五个问题，分别看到了什么？

### 1. Agent 的补丁长，代码就更冗余吗？（图 2）

在 Verified，典型模型改动行数是维护者的 2.33 倍；排除测试文件，比例降到 1.09 倍；按代码块数量比则为 0.86，逐任务中位数为 1.00。任务测试下，代码必要率平均为 0.887 对 0.864：18 个模型中 11 个高于维护者基线且区间在零之上，4 个未发现差异，3 个 Gemini Flash 明显更低。仍有约 11% 的 Agent 代码单元在平均意义上可撤而不影响任务测试。

DeepSWE 中，必要率 0.797 对 0.785 是总体汇总；按共同任务并排的图 2b 中，没有模型显著高于维护者，两款 Gemini Flash 低于维护者。不能把两个总体数直接相减当作图上的配对效应。更关键的是，Verified 换成增强判据后，Agent 相对维护者的差由 +2.3 个百分点转成 −4.5 个百分点。附录 C/D 中按单元汇总，行为校验把约 84% 的已探查维护者「测试不需要」单元，以及 35% 的对应 Agent 单元重新判为必要。维护者写的东西更经常得到额外证据支持；结论会跟随判据变化。

### 2. 多出来的是哪类改动？有实际功能吗？（图 3）

Verified 的额外单元中约 61% 是未评分的测试、21% 是代码、13% 是文档、5% 是注释或格式；DeepSWE 则有 58% 是代码、26% 是测试、12% 是文档。这里的「额外」包括未评测试，不能把它统一读成「坏改动」。在 Verified 被任务测试判为不需要且跑了探针的 3,559 个 Agent 代码块中，约 89% 表现出行为变化；典型情形是邻近输入触发或吞掉不同异常。也就是说，这些块往往不是改空格，审查者仍需理解它改了什么。

作者另用变异测试衡量新增测试：对 271 个有效案例制造 1,962 个小人工程序错误，Agent 新增测试抓住 68.1%，触及文件的原回归测试抓住 45.6%，任务测试抓住 77.1%。任务测试漏掉的错误中 102 个（22.7%，占全部人工错误约 5.2%）被 Agent 新增或加强的测试抓住。不同套件抓到的集合并不一样，这正是把测试和业务代码分别评分的收益。人工变异检出不等于真实缺陷检出。

### 3. 残留是不是调试时顺手写进去的？

这条直觉在主分析里没得到支持。Verified 的 3,987 个不必要代码单元里，仅 154 个归于调试（约 3.9%）；约 83% 归于修复动作、11% 归于修订。以各阶段写出的代码为分母，修订代码中不必要的比例约 0.29，首次修复约 0.25，修订又不多。DeepSWE 在来源精确的单元中得到约 3.7% 的调试占比。另一个 LLM 对 10,000 步重标，细分角色一致率 84.4%（κ=0.69），调试／非调试 89.1%（κ=0.55）。这给归因提供了复核，但没有人类审计；也不能从最后写入归因推出调试对后续决定没有间接影响。

### 4. 能修更多题的模型，也更会控制改动吗？

Verified 上，解题率与代码必要率的模型间 Spearman 相关是 −0.10（原始 p=0.69）。例如 Sonnet 5 与 Gemini 3.7 Flash 解题率分别为 80.6% 和 81.4%，必要率却是 0.922 与 0.789，每题平均不必要代码单元约 0.34 与 1.23。用共同任务、控制任务或换成行权重后，三款 Flash 偏低的模式仍在。DeepSWE 相关为 −0.59（p=0.01），任务校正后 −0.52（p=0.03）。这是模型层面的关联，不能推出提高解题率会导致过度修改。

附录 D 在同模型、两框架均成功的任务上配对，例如 Verified 上 Opus 5 在 Copilot coding agent 为 0.903、同题 CLI 为 0.910；DeepSWE 的 Codex CLI 与 Claude Code 小样本配对区间都跨零。表 9 与附录文字对 Codex CLI 某组差值方向并不一致，宜只取「样本少、差异小」的判断。附录 E 的 SWE-bench Pro 只测到两款模型（分别 345 和 272 个完成评分的配对），两款模型的必要率约 0.609 和 0.597，同题维护者约 0.499 和 0.481；这个较弱的测试基线和两模型样本不能验证排名规律，也没有重放来验证来源。

### 5. Agent 可以自己把多余代码去掉吗？（表 1）

部署时看不到隐藏任务测试，作者用三种替代方式处理 Verified 的已成功补丁，再用增强判据评分。各列适用样本不同，不能把保留率当作同一批任务的绝对排名。

| 处理方式 | 删对的比例 | 找出不必要块的比例 | 仍通过任务测试 |
|---|---:|---:|---:|
| 回到 Agent 自己第一次全绿 | — | — | 97.3% |
| 要求模型逐块自审后删改 | 65.7% | 35.5% | 98.2% |
| 用 Agent 自测逐块累积撤回 | 39.6% | 66.5% | 86.6% |
| 自测加原有回归测试后累积撤回 | 46.3% | 67.3% | 89.1% |

第一次全绿只评后来还继续改的补丁，3,031 份可评；净少 150 个代码单元，NP 从 0.700 到 0.710，因为大量残留第一轮通过时已经在里面。自审覆盖 17 个模型，评了 6,345 份，删得相对准但漏得多。测试驱动的两列基于同一 2,495 份有独立命令且基线自测通过的补丁；加回归测试后，从 0.936 到 0.975。许多误删项实现了自测和既有测试都没覆盖的行为，这也是为什么「留存补丁更简洁」和「安全保住全部功能」要同时汇报。附录 H 的干预提示没有实际运行，不能据此宣称训练或新提示已经减少过度修改。

## 证据能支持到哪里？

- **操作定义有效，但对检查集敏感。** DRA 标记对「落在维护者没改过的函数之外」的区分能力为 AUROC 0.718，优于仅看块大小的 0.478；然而被标记块只有约 43% 在维护者改动函数外。写法不同可能一样好，写在同一个函数里也可能是多改。增强判据参考维护者行为，不能当独立人类审查标签。
- **单块撤回不是全局最小补丁。** 相邻但语义独立的变化会被并进同一块；互补或替代块的联合影响可能被漏掉。更细或按行加权能检验模型排名是否稳健，但不能证明每个块的语义必要性。
- **成功和可重放定义了样本。** 结论来自已解决的轨迹，不能代表所有尝试；Verified 有约 3.3% 重放不精确，DeepSWE 约 33.4% 的补丁至少一个单元无法定位来源，且 Verified 仅 Python、有数据污染风险。其他运行框架的小规模重叠样本不能消除这一限制。
- **来源归因和改动影响是两类证据。** 撤回比较直接测到单块对固定判据的影响；步骤归因与模型间相关性没有把「是否经历调试」「是否使用某个模型」随机化。人工维护评审、合并率与后续真实回归仍待检验。

## 读完记住什么？

1. 补丁体积是成本信号，不能代替对必要性的测量；尤其要拆开测试和代码。
2. 「测试不需要」比「行为无变化」弱得多；增强判据甚至能改变模型与人类对比的方向。
3. 调试不是主样本里最终残留的主要最后写入点，把清理开关机械设在第一次全绿收益很小。
4. 清理策略各有取舍。必须同时报告保留质量、删除准确性及适用样本，不能只报删了多少。

## 对当前研究的启发

这篇文章提供的借鉴是**把差值绑定到具体改变的对象和判据**。它撤回的是终态补丁，评估任务测试与行为；仓库上下文研究改变的是模型输入，评估的是定位结果。不能把「补丁中这个块可撤回」等同于「上下文中这个节点无用」。两个设计都可以呈现一条可审计的反事实链：先说明保持不变的部分，再指明替换或去除的单元，最后报告判据是否改变。

写作上，可把观察层和干预层分开：自然检索中某类上下文曝光更多，可以同时伴随更多核心证据；同题比较在核心证据不变、预算匹配的条件下，把表观上下文与无关上下文对照，才回答这两类补充输入之间的差异。它没有直接回答「加入表观上下文」相较于「完全不加」的效果。对方法评估也可借鉴表 1 的报告方式：同时展示保留关键证据、最终质量和成本，并交代三项使用的样本分母。最有启发的一处其实是判据更换导致方向翻转：证据定义与失效条件本身就是结果的一部分。
