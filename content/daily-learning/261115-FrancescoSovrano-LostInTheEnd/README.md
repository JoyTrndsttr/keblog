# Lost in the End：给模型整份代码，不等于它真的看到了后面的漏洞

> 今日精读：Francesco Sovrano、Adam Bauer、Alberto Bacchelli，**Large Language Models for In-File Vulnerability Localization Can Be “Lost in the End”**，FSE 2025。
>
> 最值得带走的不是“上下文越短越好”，而是：**代码是否被放进输入，与证据是否被模型有效利用，是两回事。缩短输入可以救回漏报，也可能切断判断所需的依赖，制造误报。**

## 1. 为什么不是把函数放大成文件就结束了？

只给模型一个函数，经常缺少关键事实：输入在哪里校验？调用者传入什么？变量是否已经清洗？最终落到哪个敏感操作？给整份文件，理论上能补齐其中一部分上下文。

但这引出另一个问题：文件变长以后，模型是否仍能找到需要的证据，尤其是靠后的证据？

论文图 1 用 CVE-2022-24715 的 PHP 文件说明为什么文件级上下文有意义。补丁既改变了私钥输入的检查，拒绝特定 `file://` 输入形式，也改变了后面构造 SSH 文件路径的方法，不再直接使用原来的用户字符串，而是使用其哈希。修复跨越文件中的不同函数。只盯某一处可疑字符串操作，很容易遗漏相关检查或路径生成过程。

这里要分清两个层次：

- **信息覆盖**：把相关函数一起提供，避免关键证据根本不在输入里。
- **信息利用**：即便证据在输入里，模型是否能定位并正确结合它。

本文主要追问第二层。它不是仓库级程序分析，也没有证明所有漏洞都能由一个文件判定。

## 3. 三个研究问题串成一条线

**RQ1：**现成 LLM 接收完整文件时，检测并定位漏洞的表现如何？

**RQ2：**失败是否与文件长度、漏洞在文件中的位置有关？真实文件上先观察相关性，再把相同漏洞移到不同位置进行构造实验。

**RQ3：**如果长输入和靠后位置确实不利，把文件切小能否改善？改善了什么，又损失了什么？

因此，这不是三个互不相干的实验，而是“发现问题 → 尝试解释 → 简单干预”的实证链条。

## 4. 数据和任务：到底让模型做什么？

### 4.1 794 个漏洞，前后两个版本

作者从 2018 年 3 月至 2024 年 3 月的 CVE 记录出发，选取由单个 GitHub 提交修复、且只修改一个源代码文件的案例。文档修改不算额外源文件。涵盖 PHP、JavaScript、TypeScript、HTML、Java、Go、Python、Ruby、C 等语言。

三类漏洞分别是：

- CWE-22，路径遍历：105 个；
- CWE-89，SQL 注入：146 个；
- CWE-79，跨站脚本 XSS：543 个。

修复前与修复后各取一次，共 1,588 个文件版本。作者把修复后的文件当作相应目标 CWE 的负例。注意，这是由补丁构建的标签，不是证明修复后整个文件不存在任何其他漏洞。

三类文件的字符数中位数分别为 7,534、6,255、8,654；每文件函数数中位数为 8、8、9。函数字符数中位数大约一千。数据里 PHP 最多，有 1,020 个文件版本，其后是 JavaScript 214、Python 112、Java 96。它不是语言均衡的数据集。

### 4.2 六个模型，不做微调

模型包括 Mixtral 8×7B、Mixtral 8×22B、Llama 3 70B、GPT-3.5 Turbo，以及 2024 年版本的 GPT-4 Turbo、GPT-4o。上下文容量从 Llama 的 8K token 到 GPT-4 系列的 128K token 不等。作者使用统一提示词、温度 0，不做任务微调。

提示词会告诉模型需要找的 CWE 类型，并要求输出：简短解释、原样复制的漏洞代码行、是否发现漏洞。所有类型使用同一个 XSS 示例。**这是知道漏洞类别后的定位任务，不是要求模型自由发现任意类型漏洞。**

六个模型能容纳的文件数量不同。例如 CWE-79 的 GPT-4 Turbo/4o 各评估 1,086 个文件版本，Llama 3 70B 只有 985 个。跨模型排名不能忘记样本覆盖差异。

### 4.3 “检测正确”还要求位置对得上

模型说“有漏洞”还不够：报告的代码行经空白归一化后，需要至少有一行与修复补丁中变化的行匹配。作者把它作为定位成功的代理。

这样做便于大规模自动评价，但也有两点风险：补丁变化行可能含重构；正确解释漏洞却没有复制到匹配行，也可能被判失败。

还有一个必须保留的原文问题：评分说明的相邻段落对“回答 yes，但没有匹配漏洞行”的分类不一致，一处称 false positive，另一处称 false negative。因此下文准确转录论文表格，但不自行重建其混淆矩阵。尤其不能把这里结合定位的 accuracy，直接当作普通平衡二分类准确率，与抛硬币机械比较。

## 5. RQ1：完整文件给进去了，表现仍然不高

先看表 3 的 F1。每列是一种漏洞，数值越高越好。

| 模型 | 路径遍历 | SQL 注入 | XSS |
|---|---:|---:|---:|
| Mixtral 8×7B | .305 | .281 | .173 |
| Mixtral 8×22B | .402 | .362 | .220 |
| Llama 3 70B | .360 | .400 | .226 |
| GPT-3.5 Turbo | .339 | .386 | .197 |
| GPT-4 Turbo | .470 | .383 | .246 |
| GPT-4o | .448 | .410 | .275 |

几个具体读法：

1. **没有一个模型在所有漏洞类别上都最好。**GPT-4 Turbo 在路径遍历上最高，GPT-4o 在 SQL 注入和 XSS 上最高。Llama 的 SQL 注入 F1 为 .400，也高于 GPT-4 Turbo 的 .383。
2. **数据最多的 XSS 反而最难。**不能因为一种漏洞在公开记录中常见，就推断模型一定更擅长。这也不是直接测量训练语料频率。
3. **漏报仍多。**GPT-4 Turbo 在路径遍历上的 recall 是 .600，GPT-4o 在 SQL 注入上为 .514、XSS 上为 .309。即便这几组表现相对好，也不是可以直接放心部署的程度。
4. 论文表中最高 accuracy 只有 .324。但它是这套包含定位匹配的任务指标，不应脱离评分口径解读。

作者还检验了语言差异，没有发现显著差异。这不意味着语言等价：样本明显不均衡，一些语言的数据量有限。

另外，正文有“Llama 在各类别均超过 Mixtral”的概括，但表格中的路径遍历并不支持它：Mixtral 8×22B 为 .402，Llama 为 .360。读论文时应以具体表格为准，不把作者自己的概括照搬成更强结论。

## 6. RQ2 第一层：真实文件中的长度与位置

作者只取 794 个修复前文件，对定位成功与否做 logistic regression。可以把模型写成：

`成功概率 = sigmoid(a + b × 文件长度)`

或者把输入变量换成漏洞位置。位置是漏洞之前的字符数，也就是绝对偏移，不是文件中的百分比。为了跨 tokenizer 比较，作者使用字符数而不是 token 数。

图 2 左侧首先提醒我们：实际数据主要集中在较短文件和靠前位置，分布很偏。右侧的拟合曲线显示，文件越长、漏洞越靠后，检测成功概率越低；真实文件这部分报告各模型与 CWE 组合的关系均显著。

不过，真实文件上的这一观察还不是干净的因果结论。长文件可能同时更复杂、包含更多函数和更多依赖；绝对靠后的位置也常常来自长文件。作者在复现材料中补充了同时纳入两种变量的回归，但单纯统计控制仍不能排除所有复杂度因素。

因此，关键不在“画出下降曲线”，而在下一步是否让同一个漏洞换位置。

## 7. RQ2 第二层：Code-in-the-Haystack 怎么控制变量？

### 7.1 把同一段漏洞移来移去

作者每类 CWE 选 5 个基础漏洞，共 15 个。若漏洞所在函数少于 500 字符，就移动整个函数；若太长，则抽取相关语句并重构成约 500 字符的函数。

然后构造四种长度：4,000、8,000、16,000、25,000 字符。每隔 500 字符安排一个漏洞位置。前后的填充代码来自原文件或同一仓库里的独立代码单元，不是让 LLM 临时生成一堆无关代码。

为了把代码块尽量塞进指定长度，使用类似 0/1 背包的选择过程：先填漏洞前面的容量，再填后面的容量。长度存在约 200 字符的容差，不是所有文件都精确等长。

每类共有 `5 × (8 + 16 + 32 + 50) = 530` 个构造配置，三类共 1,590 个。模型重复运行 5 次，以缓解非确定性。温度 0 并不保证调用结果永远一致。

这比真实文件的相关性更接近“同一漏洞，换长度和位置”的对照。不过，这些数目来自作者按预期较大效应进行的事前功效分析：每个回归至少 273 个构造观测，进而选取每类 5 个基础漏洞。它保证的是该设计假设下的观测量；1,590 个配置并不等于 1,590 个独立漏洞：它们只来自 15 个基础漏洞，统计外推必须记住这一点。

### 7.2 图 3：不是典型的 U 型，而是后半段持续掉队

热力图横轴为漏洞位置，不同行对应文件长度；成功记 +1，失败记 −1，最后平均。因此颜色分值 0 对应约一半成功，并不是“零成功”。

在很多长文件组合里，开头比较绿，往后逐渐变红，且末尾没有稳定回升。尤其 SQL 注入，在较长输入上恶化明显。这就是标题里“Lost in the End”的含义：不是简单套用常见的“中间差、两头好”，而是任务中后部也未必有优势。

但热图并不意味着每个模型、每个 CWE、每个位置都同样严重。例如 GPT-4o 的路径遍历比 GPT-4 Turbo 的长文件后段更稳；GPT-4 Turbo 的 XSS 图又没有 SQL 注入那样一致的变红模式。

### 7.3 图 4：总体趋势成立，不等于每格都显著

构造实验的回归大体也呈长度和位置增加时下降，但图中的 p 值有必须保留的例外：

- GPT-3.5 Turbo 的 XSS 位置关系：p = .897；
- GPT-4o 的 XSS 长度关系：p = .086；
- GPT-4o 的 XSS 位置关系：p = .123。

这些都没有达到常用 .05 阈值。不能把真实文件部分的“全部显著”，挪到构造实验里继续使用。也不能因为一条拟合线略微下降，就说相应组合已证明位置效应。

### 7.4 图 5：出错时，它常指向哪里？

这张图统计的是**错误预测出来的位置**，不是实际漏洞的位置。4K、8K 输入的错误位置较分散；16K、25K 时，错误预测大量集中在前面几千字符，后半段明显较少。

这与“模型过度关注开头”的解释相容，但并不能单独证明注意力机制或训练数据分布就是原因。论文提出的训练分布解释仍是假说，没有进行训练数据审计，也没有通过重训练验证。

### 7.5 构造实验还有什么不完美？

移动函数、抽取函数、替换填充代码都可能改变语义或依赖。作者也承认构造过程可能引入语法问题，例如 import 位置。这对验证位置敏感性很有价值，但还不能称作“仅改变位置，其他语义完全不变”的严格保证。

更稳妥的后续设计应检查可解析性、保留依赖闭包，并以基础漏洞为单位做配对分析或聚类统计，避免把同一个漏洞的许多变体当成完全独立证据。

## 8. RQ3：切块能救漏报，为什么又制造误报？

作者把文件按连续代码行切块，避免截断一行，并尝试最大 6,500、3,000、1,500、500 字符四种大小。它不是依赖感知切块，没有自动把远处的清洗函数一起带过来。

这部分只用 794 个漏洞文件。每个文件切成多块以后，大部分块自身不含漏洞，因此评价样本结构发生变化。作者主要比较 recall，而不是把切块后的 F1 或 accuracy 当成与原始文件设置完全同口径的数字。

下面是表 4 中“最高 recall 对应的块大小 / recall”。单位为字符。

| 模型 | 路径遍历 | SQL 注入 | XSS |
|---|---|---|---|
| Mixtral 8×7B | 500 / .428 | 1500 / .452 | 500 / .309 |
| Mixtral 8×22B | 3000 / .552 | 500 / .657 | 500 / .428 |
| Llama 3 70B | 1500 / .495 | 1500 / .554 | 1500 / .278 |
| GPT-3.5 Turbo | 1500 / .533 | 500 / .636 | 500 / .376 |
| GPT-4 Turbo | 6500 / .657 | 500 / .630 | 500 / .404 |
| GPT-4o | 6500 / .666 | 1500 / .650 | 500 / .407 |

三个结果值得连起来理解。

**第一，切块确实可以减少漏报。**论文报告平均相对 recall 提升超过 37%。但这不是提高 37 个百分点。例如 GPT-3.5 的 XSS 是 .192 → .376，相对增长 95.83%，绝对只增加 18.4 个百分点；GPT-4 Turbo 路径遍历是 .600 → .657，增加 5.7 个百分点。

**第二，没有统一的最佳长度。**同一个 GPT-4 Turbo，对路径遍历最高 recall 对应 6,500 字符，对 SQL 注入与 XSS 则是 500。不能从这篇文章推出一个普适的“安全上下文长度”。这还是在被评估的数据上挑最好的四选一，没有展示独立验证集上的长度选择效果。

**第三，precision 下降。**切得越细，不含漏洞的块越多；一些本来需要远处证据才能排除的问题会被误报。作者观察到，把 SQL 拼接所在的块单独交给模型时，模型可能指出注入风险，却看不到其他块中的输入清洗。这正是“减少噪声”和“丢失证据”之间的冲突。

所以这里不是“切块全面胜过整文件”，而是**召回改善，以更多误报为代价**。论文没有给出足够完整的成本与 precision 对照来证明最终部署收益，更不能据此说计算开销几乎不增加：多块通常意味着更多调用。

作者建议更智能的切块，例如带上相关定义和数据流。这是合理方向，但本文没有验证一个依赖感知新算法。

## 9. 我会怎么评价这篇论文？

### 做得好的地方

- 把“装得下”与“用得好”明确拆开，在实际代码任务中提供证据。
- 不满足于真实数据的相关性，加入同一漏洞的长度与位置变体。
- 用错误位置分布补充成功率，不只报告一个平均数。
- 报告了切块的负面后果，留下真正需要解决的任务：短而完整的证据，而非机械删字。

### 不能越过的边界

- 六个模型都是当时版本，不能代表 GPT-6.1、现在的 Qwen/DeepSeek，或工具增强 agent。
- 三类 CWE、以 PHP 为主、单源文件修复，与完整仓库推理有明显距离。
- 修复后标签、补丁行匹配和评分文字歧义影响指标解释。
- 构造实验仅每类 5 个基础漏洞，变体数量不等于独立样本数量。
- 用字符数便利了跨模型比较，却不等于严格匹配 token；长度、绝对位置和相对位置也不是同一个变量。
- 仅构造实验重复 5 次，其余实验没有同样的重复预算；作者报告相关重复花费超过 400 美元。
- 切块只试四个大小，且按最高 recall 选值；没有形成可直接迁移的最优策略。

一句话评价：**这是一篇值得借鉴实验设计的任务特定实证论文，不是一条“长上下文必坏、切短必好”的定律。**

## 10. 对 CPI 筛选、GraphLocator 和 SeerAgent，真正可迁移的是什么？

以下是结合研究问题提出的实验建议，不是论文已经验证的结论。

选题前读取了 GitHub master 的研究记录，当前远端内容末尾仍是 11 月 10 日的文件级 V2 试验，主要瓶颈包括证据未曝光、已读但未用于最终选择以及源码范围表达不足。下面沿这几个问题讨论迁移，不把该远端记录当作之后全部实验的最新状态。

这里的 C 候选是模型判断，不等于人工审定的真实核心证据；现有一些选择协议还会保留 P 待定，仅删除 I。实际比较必须写清保留规则，而不能统称为“只看 C”。

如果“先筛选再裁决”优于直接裁决，至少有几种不同解释：筛掉了干扰信息；让关键证据变靠前；减少长度后模型更易处理；或者保留的候选更接近真正的决定性证据。只比较两个最终分数，无法区分这些机制。

我会把下轮对照拆成四组：

1. **原始上下文**：作为共同基线，保存每例完整输入和 token 数。
2. **按既定规则筛选后的上下文**：测试实际方法收益，并记录 C 候选、P 待定、I 排除分别如何处理。
3. **等 token／等节点数量的随机或简单排序选择**：检验收益是否只是变短、节点变少。
4. **相同内容、不同顺序**：将关键证据放前／中／后，尽量只改变位置，不改变保留内容。

每组对相同实例配对评估，并在三个模型上分别报告。不要只说“GPT 好、其他不好”，而要指出是哪个任务、哪个基线、哪些实例和哪类错误。

尤其需要检查“原本正确，筛后错误”的样本：是否删掉了输入清洗、变量定义、调用约束或反例？这些正是本文切块误报给出的警示。对应地，“原本错误，筛后正确”也要区分找到新证据与仅改变输入布局。

若进一步集成到 GraphLocator，应先固定它提供的候选上下文，比较直接裁决与筛选后裁决，再考虑自主探索。否则同时换检索、筛选、工具、预算和推理过程，就很难知道提升来自哪里。

最终故事可以更清楚地表述为：**不是上下文越多越好，也不是越少越好；要保留能改变裁决的证据，同时控制无关内容和证据呈现方式。**这篇论文给“呈现方式会影响利用”提供了先例，但 CPI 的语义价值仍需要自己的公平对照来证明。
