# SWE-agent: Agent-Computer Interfaces Enable Automated Software Engineering

> **精读日期：2026-11-14｜NeurIPS 2024｜John Yang、Carlos E. Jimenez 等**
>
> 一句话：软件智能体不只需要更强的模型，还需要更适合模型使用的工具界面。SWE-agent 把搜索、阅读、编辑和反馈组织成简短、可恢复的操作，在同一个 GPT-4 Turbo 上，将 SWE-bench Lite 的问题解决率从 Shell-only 的 11% 提高到 18%。

原文：[NeurIPS 正式版 PDF](https://proceedings.neurips.cc/paper_files/paper/2024/file/5a7c947568c1b1328ccc5230172e1e7c-Paper-Conference.pdf)｜[论文页面](https://papers.nips.cc/paper_files/paper/2024/hash/5a7c947568c1b1328ccc5230172e1e7c-Abstract-Conference.html)｜[代码](https://github.com/SWE-agent/SWE-agent)｜[arXiv:2405.15793](https://arxiv.org/abs/2405.15793)

本文依据正式版正文及附录中的实现、参数搜索、行为分析、完整案例与局限组织；不混用今天的软件版本和 2024 年实验配置。

## 1. 同样会写代码，为什么换一组工具就能多修好问题？

想象你让模型修改一个仓库。它知道需要改某个函数，却仍要先找文件、查看行号、写一条不出错的 shell 替换命令，再重新打开文件确认结果。它可能在任何一步陷进去：搜索输出太长、逐条翻匹配结果、替换时缩进错了、改完没有输出所以不知道是否成功。

这篇论文把这些问题视为一个独立研究对象：**模型与计算机之间的接口**。Agent-Computer Interface（ACI，智能体—计算机接口）不仅是“有哪些工具”，还包括工具参数、输出格式、错误反馈，以及哪些历史信息继续进入下一次模型输入。

作者提出的研究问题是：**固定语言模型，不改权重，重新设计它操作计算机的方式，能否提高真实仓库问题的解决率？** 这与“模型能否生成补丁”不同。后者常将代码检索好，一次性要求模型回答；这里让模型自己探索、修改、执行，并根据结果调整。

当时已有非交互的仓库补丁生成，也有模型直接调用 Linux shell 的交互框架。前者没有执行反馈，后者沿用了为人类编程的通用命令。论文的缺口是：尚缺少面向模型特性设计、并通过消融验证的端到端软件工程接口。这个出发点来自开发集轨迹中的实际困难，再由实验检验；不是预先假定“工具越多越好”。

## 2. 先走完一个真实修复，再拆解方法

附录 Figure 33 的案例是 requests 中的 HTTP 方法名转换问题。输入方法为字节串 `b'GET'`，直接转成字符串会得到包含字节标记的 `"b'GET'"`，而不是合法方法名 `"GET"`，请求因而失败。

SWE-agent 的实际过程是：

1. **找文件。** 定位到 requests 目录的 `sessions.py`，而不是构建产物目录中的同名文件。
2. **找具体操作。** 打开文件，搜索 `builtin_str`，找到第 428 行附近的方法名转换。
3. **修改。** 在转换前判断是否为 bytes；如果是，先按 ASCII 解码。
4. **验证。** 创建复现脚本，用字节形式的方法发送请求，运行后得到 200 响应。
5. **提交。** 删除临时复现脚本，提交仓库修改；评测测试通过。

这里每一步产生的东西都能被下一步使用：搜索产出路径，阅读产出可操作的行号，编辑产出新代码，执行产出新的事实，最终产出 patch。不是先写一大段“修复计划”，再让模型凭记忆提交答案。

作者同时指出，仓库原有 `to_native_string` 工具函数能完成相同功能，而模型重新写了解码逻辑。这个案例说明它已完成测试意义上的修复，也留下了“会修”与“符合仓库惯例”之间的距离。

## 3. SWE-agent 到底改了哪些接口？

### 搜索：先得到可选择的结果集合，而不是不断翻页

工具包括按文件名找文件的 `find_file`、在单文件查字符串的 `search_file`、跨目录查字符串的 `search_dir`。返回格式尽量固定：在哪个文件、匹配多少次、对应位置是什么。

一次搜索最多返回 50 个结果；超过上限时不倾倒所有内容，而是要求缩小查询。它把“信息太多”变成一个明确的下一步：重写更具体的查询。

Figure 5 用 pvlib 中定位 `PVSystem` 的问题展示三种行为：

- 直接 shell：模型先列目录，再切目录，接着继续找文件，定位需要多次动作。
- 逐条搜索界面：搜到 15 个匹配后，从第一个开始反复调用 `next`。虽然每个结果带周围代码，但模型倾向看完所有匹配。
- 汇总搜索：查询 `class PVSystem`，得到 `pvlib/pvsystem.py` 的一个匹配，然后直接打开目标文件。

关键差别是**搜索结果怎样引导下一步动作**。逐条展示看起来贴近编辑器体验，却可能把模型带入穷举浏览；汇总结果更容易让它比较并选择。

### 阅读：100 行窗口，同时保留全局位置

`open` 打开文件后默认最多展示 100 行；`goto` 跳到指定行，`scroll_up/down` 移动窗口。输出包括完整路径、文件总行数、每行行号，以及窗口前后省略了多少行。

这解决两种相反的问题：整个文件太长，会占据上下文；只给一个过短片段，又看不到足以理解函数的邻近代码。保留路径和行号还能避免把“刚才看的是哪里”变成额外推理任务。

### 编辑：把替换、校验和回读合成一次操作

`edit` 接收开始行、结束行和替换文本，可以一次替换多行。编辑后自动展示新内容，模型无需再调用阅读工具。

Figure 3 中，模型在 `solvers/diophantine.py` 的第 404—407 行替换高次方程分类条件。输入是已经带行号的旧代码；动作是指定范围替换；输出是修改后的同一片段。真正有用的是这种稳定的“看见什么，就明确修改哪一段”的联系。

编辑还接入代码静态检查器（linter）：若引入所检查的严重错误，修改不落地，系统返回错误和相关代码，要求重试。Figure 6 的 SymPy 案例中，模型多写了一个右花括号；检查器指出不匹配，并保留原文件，模型随后修正编辑。**错误被拦在一次操作内，而不是污染后续全部测试与修改。**

### 上下文：旧观察可以缩短，动作链仍然保留

初始输入含环境说明、工具文档、可选成功示例和 issue。之后反复执行“思考 → 一条动作 → 环境反馈”。

仅最近 5 条观察保留完整内容，更早观察折叠成一行；这不是把所有历史思想与动作一并删除。这样既留下尝试过什么，又减少旧文件版本和冗长输出反复进入模型。

没有输出的成功命令也有明确成功反馈。动作格式不合法时系统要求重写，并清理重复的格式错误信息。整体仍基于 Linux shell，必要时可用通用命令，**并不是把模型完全锁进四个专用工具。**

## 4. 实验比较的是哪三类系统？

实验单位是一个 GitHub issue 与对应仓库状态，输出是修改补丁。评测将补丁应用后运行测试，用“该任务是否解决”计分，不要求补丁文本与人工答案相同。

- **SWE-bench 完整测试集：**2,294 个任务，12 个 Python 仓库。
- **SWE-bench Lite：**300 个较自包含的功能性 bug 修复任务，是主消融与行为分析对象。
- **HumanEvalFix：**每语言 164 个短程序修复题，本文评估 Python、JavaScript、Java；无需大仓库定位，侧重编辑和调试。

主要模型为 GPT-4 Turbo（`gpt-4-1106-preview`）与 Claude 3 Opus（`claude-3-opus-20240229`）。接口最初围绕 GPT-4 开发，再迁移至 Claude。默认温度 0、100 行阅读窗口、最近 5 条完整观察；这些选择来自 37 个开发集任务的参数搜索，每个配置统计 5 次采样。

三类对照分别是：

1. **RAG：**BM25 用 issue 检索文件，模型一次生成补丁。检索增强生成（Retrieval-Augmented Generation）在这里代表“提供代码，但不交互执行”。
2. **Shell-only：**模型可持续使用 Linux shell，最终从仓库状态提取补丁。
3. **SWE-agent：**仍可交互，但增加专用动作、结构化反馈和上下文管理。

每题 API 成本上限为 4 美元，超限时自动提交已有修改。论文报告 pass@1，即一次完整尝试能解决多少任务。主表的平均成本按正文定义是**成功解决实例的平均推理成本**，不应据此直接计算全项目账单。金额是当时模型价格下的统计。

## 5. 结果一：收益来自交互，也来自交互接口

论文未把实验编号为 RQ，下面按实际比较展开。

### 完整仓库修复：两个模型都获得提升

| 模型 | RAG，完整集解决率 | SWE-agent，完整集解决率 |
|---|---:|---:|
| GPT-4 Turbo | 1.31% | 12.47%（286/2,294） |
| Claude 3 Opus | 3.79% | 10.46% |

这说明能够探索、执行和修正的系统，比先取一批文件后直接写补丁，更能完成真实仓库任务。

更直接检验接口价值的是 **同一 GPT-4 Turbo 在 Lite 上的交互系统对照**：

| GPT-4 Turbo 设置 | Lite 解决率 | 主表平均成本 |
|---|---:|---:|
| RAG | 2.67% | $0.13 |
| Shell-only，无示例 | 7.33% | $0.79 |
| Shell-only，有示例 | 11.00% | $1.46 |
| SWE-agent | 18.00% | $1.67 |

对有示例的 Shell-only，提升为 **7 个百分点，约 64% 相对提升**；对无示例版本则是 10.67 个百分点。明确这一区别，就不会把“加接口”和“加示例”的收益混在一起。

Claude 在 Lite 的 SWE-agent 结果为 13%，高于其 RAG 的 4.33%，但低于 GPT-4 的 18%。这组接口有跨模型可用性，最佳模型与提升幅度仍会变化。

附录按仓库分解也显示异质性：GPT-4 在 Django 的 114 例中解决 26.32%，在 SymPy 的 77 例中解决 10.39%；xarray 的 5 例中 SWE-agent 为 0%，RAG 为 20%。总体提高，并不要求每个小仓库子集都同时提高。

**结论：是否交互是第一层差别，如何让模型有效交互是第二层差别。**

## 6. 结果二：不是堆工具，而是减少低效操作链

Table 3 固定 GPT-4 Turbo 和 Lite 任务，在完整配置上改变某项设计：

| 改变 | 解决率 | 相对完整配置 |
|---|---:|---:|
| 完整配置 | 18.0% | — |
| 不提供专用 edit | 10.3% | −7.7 点 |
| 编辑保留，但去掉 linting | 15.0% | −3.0 点 |
| 搜索改成逐条 next/prev | 12.0% | −6.0 点 |
| 去掉专用搜索 | 15.7% | −2.3 点 |
| 阅读窗口缩至 30 行 | 14.3% | −3.7 点 |
| 每次显示完整文件 | 12.7% | −5.3 点 |
| 保留完整观察历史 | 15.0% | −3.0 点 |
| 去掉成功示例 | 16.3% | −1.7 点 |

三个最有信息量的比较：

**第一，能直接做可靠的多行编辑非常重要。** 去掉 edit 后模型仍能用 shell 修改，并非失去修改权限；它只是要自己完成文本替换、转义和重新阅读，解决率降至 10.3%。对这组配置而言，这是单项改动中最大的下降。

**第二，设计不合适的工具比不加工具还差。** 逐条搜索 12%，低于没有专用搜索的 15.7%。作者观察到模型持续遍历匹配，耗尽预算。这是非常明确的负面结果：功能完整，不等于动作安排有效。

**第三，上下文不是越长越好，也不是越短越好。** 100 行窗口优于 30 行和完整文件；最近 5 条观察优于全历史。这里的目标是保留够用的当前信息，减少无效重复，而不是一味最小化 token。

这些消融是“在其余模块存在时改变一项”的效果，不能把各下降数字相加，得到各模块独立贡献总和。

## 7. 结果三：短程序调试同样受益

HumanEvalFix 直接给一个有 bug 的文件及可用示例测试。模型修改、运行、再修改，不需要跨仓库搜索。除语言对应的示例轨迹外，沿用 SWE-bench 配置。

| 方法 | Python | JavaScript | Java |
|---|---:|---:|---:|
| 原表 GPT-4 对照 | 47.0% | 48.2% | 50.0% |
| WaveCoder-DS-6.7B | 57.9% | 52.4% | 57.3% |
| SWE-agent + GPT-4 Turbo | 87.7% | 89.7% | 87.9% |

完整表还包含 CodeLlama-instruct 和 DeepSeekCoder-CodeAlpaca，均低于 SWE-agent。作者复用已有论文报告的非 SWE-agent 数字，并非统一重新运行全部模型；这里最清楚的发现是交互式编辑与验证在短程序上也很有效。

正文给出的三语言平均为约 88.3%；摘要的 87.7% 对应 Python 列，阅读时不要混为同一口径。Figure 25 显示大部分成功例在前 10 轮内完成，符合“短程序主要需要修正与验证，而非长距离导航”的任务特点。

## 8. 轨迹揭示了什么：成功有闭环，失败容易原地打转

### 成功轨迹的常见结构

Figure 7 统计完整集上 286 条成功 GPT-4 轨迹：开头通常是复现问题，或搜索相关文件；之后从目录定位收敛到文件和行；约第 5 轮起，最常见动作是编辑与 Python 执行。新执行结果有时又触发一次局部搜索。

因此它不是“一路搜索到末尾，再统一判断”，而是：**形成局部解释，尝试修改，用执行结果检验，再补足信息。** 附录动作序列统计也发现连续编辑、连续滚动容易继续自我重复。

### 失败究竟卡在哪里？

作者用 GPT-4o 对 Lite 中 248 条未解决轨迹分类，参考完整轨迹、模型补丁与人工补丁；在 15 条人工标注验证样本上，一致率为 87%。

主要类别为：
- 错误实现：39.9%；
- 过度针对特例的实现：12.1%；
- 无法从失败编辑恢复：23.4%。

前两者合计 52%，说明很多失败已经到达相关代码，却没有形成正确且足够一般的修复。其余还包括找不到相关文件、找到文件却没找到编辑点、复现失败、过早放弃和预算耗尽。

这也解释了为什么要同时观察**找到了什么**与**拿这些信息做对了什么**。只统计文件命中会漏掉后半段。

### 两个失败案例，比抽象的“推理不足”更具体

附录 Figure 35：SymPy 的 `Derivative.kind` 返回错误类型。模型成功复现，最终也找到 `Derivative` 类，却反复向下滚动几百行定义，耗尽预算。实际修复涉及覆盖继承属性。需要的不是把整文件再看一遍，而是定位属性从哪里继承、应在哪里覆盖。

Figure 36：Django 密码哈希只读控件输出文本，标签却带着不适用的 `for` 属性。模型找到控件和模板，随后在错误抽象层实现 `label_tag`，并以为无法启动服务器而未经测试提交。正确修复点是 Widget 的 `id_for_label`。这是“找到附近代码，但没理解调用/继承机制”的失败。

此外，Figure 34 的 pylint 标签匹配修复通过测试，但所用正则边界比人工方案更宽，可能包含测试未覆盖的行为。通过测试与完整语义等价不是同一件事。

### 一次失败之后，重试是否一定有效？

完整集 2,294 条 GPT-4 轨迹中，1,185 条（51.7%）至少发生一次失败编辑。作者报告一段编辑尝试最终成功的概率为 90.5%；发生一次失败后，相应恢复概率降至 57.2%，失败越多，恢复越困难。它提示错误循环值得尽早识别，而非默认每次追加尝试都有同样价值。

这些是轨迹统计，不是随机安排重试次数的实验。能直接采取的做法是记录错误类型与重复次数，让恢复动作与原动作不同。

## 9. 多跑几次与让同一次跑更久，要分开讨论

Table 10 在 Lite 上重复运行 6 次，单次解决率从 17.33% 到 18.67%，平均 17.94%，标准差约 0.49 个百分点。总体分数接近，但成功的具体任务并不完全重合：

| 每题最多尝试次数 | 至少一次成功的 pass@k |
|---|---:|
| 1 | 17.94% |
| 2 | 23.89% |
| 3 | 27.35% |
| 6 | 32.67% |

因此，“相同设置重复跑没有价值”并不成立。独立尝试能覆盖更多题；但需要额外运行成本，也需要在实际部署中辨别哪个补丁正确。

另一方面，成功轨迹往往较早提交，许多失败轨迹拖到预算上限。完整集成功的 GPT-4 轨迹中 266/286 由模型主动提交，其余 20 条因成本上限自动提交。这个现象使作者怀疑单纯增加每次预算的收益有限。**独立重试的已报告收益，与延长单条失败轨迹的推测收益，是两件事。**

## 10. 证据反思：结果最可靠的范围在哪里？

1. **接口整体有效，细机制仍有捆绑。** 与同模型 Shell-only 的比较最接近本文问题；但专用命令同时改变了动作粒度、反馈长度与所需轮数。若要证明纯粹由信息筛选而非预算节省导致，还需相同 token/轮数等进一步控制。
2. **最佳配置来自较小开发集。** 37 例调参后在独立测试集评估是合理流程，100 行与最近 5 条却不是跨模型、跨任务的普适常数。单项消融主要基于 GPT-4，Claude 的模块级效果没有同等覆盖。
3. **报告重复性，不等于完整显著性论证。** 六次重复支持主系统分数相对稳定；论文没有为每一组消融提供同样充分的重复与配对显著性结果。这里保留原始差值，不擅自称每项“统计显著”。
4. **成功指标是测试通过。** 案例已显示未复用仓库工具函数、正则边界不完全等价等问题；可维护性、通用正确性仍需另评估。
5. **失败分类有误差。** 15 例人工核对较小，87% 一致率足以辅助找常见模式，但不足以把各百分比当成精确故障普查。失败分析的 248 条也对应其分析运行，不应机械用主表 54 个成功推算成相同一轮。
6. **旧模型与任务范围。** 研究主要覆盖 Python 仓库以及三种语言的短程序；不能直接预测 GPT-6.1、Qwen、DeepSeek 或漏洞定位的提升幅度。按年份未发现明显成绩趋势，也不足以排除训练数据污染。
7. **安全与工程成本。** 作者采用临时 Docker 容器隔离执行，仍讨论恶意任务、工具代码和软件智能体滥用风险。容器隔离不是无限权限的理由；接口实验应固定权限与可访问资源。

## 11. 真正该记住的贡献

- 不训练模型，也能通过操作接口获得实质收益：同模型 Lite 从 Shell-only 的 11% 到 18%。
- 搜索输出应支持选择和收敛；逐条遍历式工具反而使结果低于不加专用搜索。
- 编辑、即时回读和错误阻断组成可恢复闭环，减少小错误扩散。
- 阅读与历史存在“够用而不冗余”的工作区间，而非越长越好。
- 错误实现、错误恢复和无效浏览需要分别诊断；单一总分无法指出该改哪里。
- 多次独立尝试确有覆盖收益，但本文没有证明无限延长单次探索有效，也没有证明这些设计自动迁移到所有模型。

## 12. 对 causal-review / SeerAgent 的直接启发

本次已读取 GitHub master 的 `documents/研究记录.md`，可见内容截至 11 月 10 日的文件级探索 V2 记录；这里仅据这份仓库记录讨论，不把本地后续实验冒充已同步结果。

记录中的关键现象是：格式与提交恢复提高了可执行性，但重复阅读和机制识别仍是瓶颈；部分先筛选上下文的设置会丢失真实相关证据。SWE-agent 提供的是**接口与证据使用机制的研究先例**，不是我们方法已有效的外部证明。

最值得分开的三层变量是：

**第一，证据获取。** 同一初始候选上下文下，比较整文件阅读与按符号/行区间阅读；记录新增有效片段、重复读取比例和搜索到相关实体的轮数。这样能回答“接口有没有更快取得必要信息”。

**第二，证据保留与送入裁决。** 将“所有已读内容”和“筛选后内容”作为明确对照，保留被排除证据的可恢复索引。最终裁决必须能访问相应证据，不能仅在探索过程里看过。把 GT 保留、裁决 F1、错误翻转分别统计，才能判断筛选省掉的是噪声还是必要前提。

**第三，基于失败类型恢复。** 重复同范围阅读，不等于产生新证据；连续格式错误也不同于语义分歧。可分别触发更具体搜索、追踪调用/继承关系、或结构化重新提交，而不是统一“再试一次”。

一个成本可控的下一步是，在固定模型、固定案例、固定初始上下文和预算下，只比较两个版本：现有探索接口，以及“范围阅读＋重复操作提示＋明确缺失条件”的接口。先逐例检查改善是否集中在获取瓶颈；再单独测试筛选与最终裁决，避免一次把接口、提示词、裁决策略全部改掉。

这能把前两个 RQ 与后续方法连起来：**先识别哪些上下文会影响判断，再验证怎样通过可观察、可恢复的操作，把真正有用的证据送到最终决策。** 核心不是让智能体忙得更久，而是让每一步产生能改变下一步判断的信息。
