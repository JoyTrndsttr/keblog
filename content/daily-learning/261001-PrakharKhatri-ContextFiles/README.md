# Do Context Files Help Coding Agents?：真实仓库中的双代理消融实验

> 精读日期：2026-10-01  
> 作者：Prakhar Khatri  
> 机构：Independent Researcher  
> Venue / 年份：arXiv / 2026  
> 原文：[arXiv:2607.27250](https://arxiv.org/abs/2607.27250) · [HTML 全文](https://arxiv.org/html/2607.27250v1) · [代码与数据](https://github.com/codeprakhar25/context-files-coding-agents)  
> Tags：Coding Agent · AGENTS.md · Repository Context · Controlled Experiment · Negative Result · Statistical Power

这篇论文问了一个看似简单、其实很容易被直觉带偏的问题：仓库里的 `AGENTS.md`、项目 wiki 或类似“上下文文件”，真的会让 coding agent 更容易完成真实软件任务吗？作者在三个 Python 仓库、17 个真实任务上，对 Claude Code 和 Codex 分别比较“无上下文”“每轮始终注入完整上下文”“按任务选择性注入上下文”三种条件。主要结果是：正确率没有出现稳定提升，少数过程指标发生了变化，但实验规模不足以证明小效应不存在。

这项工作的价值不在于给出“上下文文件无用”的终局答案，而在于把一个普遍的工程习惯变成了可检验的处理变量，并诚实展示了负结果、功效不足和实现差异。它也是一个很好的实验设计案例：当成功率大量落在全成或全败的地板/天花板区间时，再多重复同一任务，也未必能换来足够的信息。

## 一、先建立论文地图

### 核心矛盾

过去的实践逻辑是：代理不了解仓库约定，因此把构建命令、架构说明、测试流程和风格规范写入 `AGENTS.md`，就能减少探索成本和错误。这个说法听起来合理，但它混合了至少三个不同命题：代理有没有读到信息、信息是否改变过程、改变过程是否最终提高任务正确率。已有观察和厂商建议主要支持“信息可能被使用”，并不自动证明“任务成功率会提高”。

作者因此不再比较“有上下文的某个系统”和“没有上下文的另一个系统”，而是在同一个任务、同一个代理框架中只改变上下文处理条件。顶层证据链是：

```text
上下文文件被广泛推荐，但缺少真实仓库中的受控证据
    ↓
把仓库任务作为实验对象，把上下文注入策略作为处理变量
    ↓
同一任务 × 同一代理 × 三种策略 × 三次重复
    ↓
用隐藏测试判断正确性，用工具调用、token、时长等描述过程
    ↓
比较任务内配对差异，并审查负结果是否来自功效不足
    ↓
结论：未观察到可靠的正确率提升；过程效应可能存在；不能据此证明小效应为零
```

### 理解全文需要的四个概念

1. **上下文文件（context file）**：本文指项目级、相对稳定的说明材料，如 `AGENTS.md` 或整理后的 wiki。它提供仓库约定，而不是针对某一道题专门写出的解题提示。
2. **处理条件（treatment condition）**：实验主动改变的输入。本文有三档：完全不给；每轮都给完整文件；先根据任务检索，再给相关片段。它不是三个不同模型，而是同一代理在不同上下文策略下运行。
3. **任务内配对（within-task pairing）**：同一道任务在各个条件下都执行，比较时先看同一任务内的差异。这样可减弱任务难度差异造成的噪声。
4. **地板/天花板效应**：某任务在所有条件下都失败，或所有条件下都成功，就几乎不能告诉我们处理是否有效。真正有辨识力的是成功概率位于中间、且可能被处理推动的任务。

## 二、作者到底把“上下文有帮助”测成了什么

本文不是测“模型能否回答仓库知识问答”，也不是测“上下文片段能否覆盖补丁文件”。作者把现实问题操作化为：在真实仓库 issue 对应的修改任务上，改变上下文注入策略后，代理生成的补丁通过隐藏 gold tests 的比例是否变化。

实验输入是 issue 描述和仓库快照；代理可以正常浏览、编辑、运行命令；输出是一份补丁及运行轨迹；gold test 是根据已合并 PR 的预期行为构造、但不向代理公开的测试。这里的结果变量更接近“功能修复是否正确”，而不是文本相似度。它避免了“补丁和开发者写得不一样就算错”的问题，却仍只覆盖测试表达出来的需求。

因此本文检验的是一个较窄、但清楚的因果问题：**在这些被选中的仓库、任务、模型版本和运行框架下，注入这种自然形成的仓库说明，是否改变隐藏测试通过率以及若干过程指标。** 它没有检验专门为每个故障构造的最小充分证据，也没有检验图结构、调用链或反事实扰动的独立贡献。

## 三、实验材料怎样构建

### 3.1 从约四十个仓库缩到三个

作者先扫描约 40 个候选仓库，要求项目规模足够真实、历史中存在可复现的已合并 PR、能够在隔离环境中安装和测试，并且具备可用的仓库说明材料。经过可执行性、依赖和测试等筛选后，只剩 6 个符合基本条件，最终选中：

- `pdm`：Python 包和依赖管理工具；
- `firebase-admin-python`：Firebase Admin Python SDK；
- `opshin`：面向 Cardano 的 Python 智能合约语言工具链。

这一步的必要性很强：如果仓库不能稳定构建，失败就可能来自环境而不是上下文。然而它也制造了选择边界。能被纳入的项目本来就更容易容器化、测试更成熟，因此结果不能直接外推到依赖复杂、文档混乱或闭源的仓库。

### 3.2 任务来自已合并 PR，但不是简单重放开发者补丁

作者从真实 PR 中抽取 issue/任务，固定到修改前的仓库状态，再编写或整理隐藏 gold tests。初始任务集有 12 个任务；为了寻找更多“不是必成也不是必败”的任务，作者又用 Codex 筛查 84 个候选，并加入 4 个边界任务。最终 Codex 评估 17 个任务，Claude 因一个运行条件未满足而评估 15 个。

这里有一个值得注意的设计张力：寻找中等难度任务能提高实验辨识力，但如果根据处理后的结果来挑题，会引入选择偏差。作者的新增筛查主要依靠先导运行识别边界任务，并保留原始任务集与边界子集结果；这比只报告“最能显示差异”的任务透明，但仍说明任务抽样并非来自某个明确定义总体的随机样本。

### 3.3 三种上下文策略

| 条件 | 代理每次拿到什么 | 想检验的假设 |
|---|---|---|
| `none` | issue 与仓库，不额外注入上下文文件 | 代理依靠自行探索能做到什么 |
| `always_on` | 每一轮都注入完整上下文 | 持续暴露全部约定能否减少遗漏 |
| `selective` | 根据任务，从 wiki/说明中选择相关内容 | 降低无关信息和 token 负担是否更有效 |

`always_on` 不只是“一开始读一次文档”，而是反复把完整说明放进上下文。它保证高暴露，却可能放大重复和无关信息。`selective` 更接近检索增强：先匹配任务，再提供局部材料。若它成功，可以说明相关性筛选比全量注入更重要；若失败，则仍需区分“材料没用”和“选择器没找到决定性材料”。

三种条件并非在所有仓库中完全等价。`opshin` 的 selective 材料与任务匹配较细；`pdm` 和 `firebase-admin-python` 使用的 wiki 语料分别大约比基础上下文大 10 倍和 18 倍。因而 `selective` 同时改变了选择机制和候选语料库，不能被视为只删除无关 token 的纯消融。

## 四、代理、运行与评价坐标系

实验使用 Claude Code（`claude-sonnet-4-6`）和 Codex CLI（`gpt-5.5`）。每个任务在三种条件下各运行三次：Claude 完成 15×3×3=135 次，Codex 完成 17×3×3=153 次，合计 288 个进入主要评价的运行；论文还记录了 291 个完成运行，差异来自筛选和可评价性处理。

两个代理的上下文注入位置并不相同：Claude 的材料追加到 system 侧，Codex 则前置到 user prompt。这个差异意味着论文比较的不是模型本体的纯粹可互换反应，而是“模型 + CLI 框架 + 实际可用注入通道”的系统表现。它提高工程真实性，却限制跨代理的严格机制比较。

主要结果是隐藏测试是否全部通过。过程指标包括 token/缓存、工具调用、运行时长、测试行为和努力程度。统计分析以任务为单位，而不是把每次随机运行当作完全独立样本：作者使用置换检验、配对 Wilcoxon 检验并做 Holm 多重比较校正；对效应界限还给出 bootstrap 和探索性双单侧检验（TOST）。这个选择是对的，因为同一任务的三次重复共享相同需求和代码，若把 288 次运行都当独立样本，会严重夸大有效样本量。

## 五、RQ1：上下文文件提高正确率了吗

### 设计

同一任务、同一代理在三种条件下运行，固定仓库和任务定义，仅改变上下文注入。成功由隐藏测试统一判断。最关键的表格固定了代理，横向改变策略，因此应先比较同一行中的三个成功率，而不是先比较 Claude 与 Codex。

### 结果

| 代理 | 无上下文 | 全量常驻 | 选择性上下文 | 总体检验 |
|---|---:|---:|---:|---:|
| Claude Code | 53.3%（24/45） | 55.6%（25/45） | 55.6%（25/45） | p = 1.00 |
| Codex CLI | 58.8%（30/51） | 56.9%（29/51） | 52.9%（27/51） | p = 0.66 |

Claude 的两个上下文条件只比 `none` 多一次成功；Codex 反而分别少一次和三次。总体检验均不显著，方向也不跨代理一致。边界任务本来最可能呈现处理效应，但 Codex 四个边界任务的成功次数比例是 `none` 58%、`always_on` 42%、`selective` 42%，仍没有出现上下文带来的提升。

### 应该怎样解释

最稳健的表述是：**在这套样本和实现中，没有观察到上下文文件对正确率的可靠正效应。** 不能写成“证明上下文文件无效”。不显著可能意味着真实效应很小，也可能意味着任务数太少、处理强度不足、材料没有覆盖决定性知识，或者效应只出现在特定任务类型。

任务级结果大量聚集在地板和天花板：很多任务无论策略如何都成功，或无论策略如何都失败。三次重复能降低单次采样噪声，却不能让这种任务产生新的处理对比信息。这也是为什么 288 次运行看似很多，真正的统计单位仍只有 15 或 17 个任务。

**RQ1 Takeaway：** 自然形成的仓库级上下文并未在三个仓库和两个代理上稳定提高隐藏测试通过率；目前证据反对“默认注入就会普遍增益”的强说法，但不能排除较小或异质的效应。

## 六、RQ2：即使结果不变，过程会不会变

作者进一步检查 token、缓存创建、工具调用与时长。Claude 的 `selective` 条件显著减少 cache creation（Holm 校正后 p=.012），但这主要是输入更短导致的机械结果，不能被当作代理推理更高效的独立证据。Codex 的整体效率指标基本持平。

最有意思的过程信号来自 `opshin` 的探索性分析。Claude 在 `none`、`always_on`、`selective` 下平均盲目运行完整测试套件的次数约为 3.67、2.44、1.67，运行时长约为 2689、2066、2032 秒。也就是说，说明材料可能帮助代理更快找到合适的验证路径，却没有把最终正确率推高。

这个结果说明 outcome 与 mechanism 需要分开测。一个处理可能让路径更短、测试更有针对性，但如果真正卡点是功能设计或精确接线，最终 pass/fail 仍不动。反过来，仅看成功率会漏掉过程改变；仅看 token 或时长又可能把“更快失败”误认成改进。

这里的 `opshin` 分析是事后、样本小且没有充分功效，最多作为机制线索。论文没有证明“上下文普遍减少盲测”，更没有证明该过程变化因果中介了任务成功。

**RQ2 Takeaway：** 上下文可能改变代理怎样工作，尤其是缓存和测试行为，但现有过程证据不足以推出质量提升；过程指标必须和正确性联合解释。

## 七、任务难度为何比重复次数更关键

两个代理对任务难度的排序相当一致：任务级成功率的 Spearman 相关约 .75，Pearson 相关约 .77。这表明任务本身存在稳定难度结构。然而作者也估计，约 40% 的“信息带”具有代理特异性：对一个代理处于中等难度的题，对另一个代理可能已落到地板或天花板。

这解释了为什么不能只用一个模型筛出边界题，再假设它们对所有模型都同样有辨识力。实验应该先为每个代理估计 untreated success probability，再预先定义共同支持区间，或者把 agent×treatment 交互作为研究对象。否则，一个处理的真实异质效应会被大量没有可动空间的任务稀释。

作者的 Monte Carlo 功效分析进一步指出：以当前方差和任务结构，最小可检测差异超过 30 个百分点；若想以 80% 功效检测约 10 个百分点的差异，可能需要约 120–200 个任务。增加不同任务比在同一任务上继续堆重复更有效，因为前者扩大独立实验单位和难度覆盖，后者主要降低随机运行噪声。

论文还用 TOST 与 bootstrap 描述观测效应范围，给出 Claude 差异小于约 10 个百分点、Codex 小于约 15 个百分点的探索性界限。但作者明确提醒，这不是具有充分功效的等效性证明。正确读法是“当前数据与大而普遍的提升不相符”，不是“已排除所有实用大小的提升”。

## 八、失败案例和操纵检查告诉了什么

### 8.1 Near-miss 失败往往不是“少读了一份文档”

作者人工检查接近成功却未过测试的运行，常见障碍包括功能设计没有完全对齐、没有识别正确实现模式、或最后的精确 wiring 出错。它们更像任务技能问题，而不是缺少仓库约定。若错误的瓶颈不在 treatment 所操纵的知识上，再强的上下文暴露也很难救回任务。

这是一条关键的构念效度检查：实验不能只确认“给了上下文”，还应确认上下文中存在对该任务有决定性的、代理原本不易自行获得的信息。本文的材料是自然项目文档，不保证每题都有这样的信息，因此它更像测“把现有文档默认塞给代理”的政策，而不是测“决定性证据出现时代理能否利用”。

### 8.2 两任务、36 个单元格的 probe 没有显示救援效应

作者对两个任务做了更细的操纵探针，共观察 36 个 task×agent×condition×repeat 单元格。上下文没有把失败系统性救成成功。例如 Claude 在 task 907 上，`none` 成功 2/3，`always_on` 1/3，`selective` 0/3。这个局部结果甚至向负方向移动，但样本太小、只涉及两个任务，不能推出上下文有害。

探针的真正贡献是排除了一个过于方便的解释：主结果不是仅仅因为汇总表把明显的任务级救援平均掉了。与此同时，它仍没有直接测量代理是否注意、引用或正确归因了材料，因此“暴露成功”与“认知利用成功”仍未分开。

## 九、一个容易被忽略的工程发现：轨迹指标未必可跨代理移植

论文原本使用基于 turn 数的 effort 分类器。Claude 的轨迹有多轮事件，这个指标还能近似交互深度；Codex 日志却只发出一个 `turn.completed`，结果把 8 个实际上工具使用密集的任务错误标成低努力。工具调用数相对更可移植。

这不是主正确率结论，却是很有价值的测量警告：同名日志字段不代表同一语义，框架升级也可能改变事件粒度。跨代理实验若不先验证 telemetry schema，就可能把记录格式差异解释成行为差异。任何基于轨迹的中介分析，都应先建立 agent-specific measurement model，并用人工抽样核验。

## 十、重要表格和图应怎样读

1. **主正确率表**：先固定代理，看三列策略差异；再看方向是否跨代理一致。决定性事实不是某一列最高，而是差值只有 1–3 次成功、检验不显著且方向不一致。
2. **任务级热图/分布图**：先找所有条件都成功或都失败的行，它们体现地板/天花板；再看只有中间条件变化的少数行。后者才提供 treatment contrast。
3. **效率表**：区分输入长度机械造成的 cache/token 变化和行为改变造成的测试调用/时长变化。前者不能直接解释为“更聪明”。
4. **功效曲线**：横轴是任务数，纵轴是检测给定效应的概率。应该读出的是任务数从十几扩到百级后，小效应才有稳定可检测性，而不是从当前 p 值反推效应为零。

## 十一、Baseline、消融与公平性审查

`none` 是合理的现实基线：现代 coding agent 本来可以自己搜索仓库。`always_on` 代表常见配置实践，`selective` 代表检索式改进。三者共享任务、代理工具和评价测试，任务内配对也控制了大量难度差异。

但这并非完全“只改一个变量”的理想消融：

- `selective` 同时改变材料池、选择器和输入长度；
- 两个代理的注入角色不同；
- `always_on` 每轮重复注入并不等于真实用户只提供一次文件；
- 不同仓库的文档质量和与任务的关联强度差异很大；
- 上下文条件可能改变有效 token 分配，但论文没有将长度与内容完全正交化。

因此，若 `selective` 没提升，不能单独归因于检索策略；若 `always_on` 没提升，也不能推断所有上下文表达方式都无效。更严格的后续实验需要至少把“是否含决定性信息”“是否含干扰信息”“token 长度”“呈现位置/频率”拆成独立因素。

## 十二、证据审计：这篇论文证明了什么

### 有较直接证据支持

1. 在三个开源 Python 仓库、15/17 个任务和指定代理版本上，两种上下文策略都没有稳定提高隐藏测试通过率。
2. 任务内存在大量地板/天花板现象，任务选择比简单增加同题重复更决定统计辨识力。
3. 上下文可改变某些过程指标；至少 cache creation 的变化明确存在，`opshin` 测试行为提供了探索性信号。
4. 任务难度在两个代理间有较高相关，但“处于可被处理推动的中间区间”具有明显代理特异性。
5. 基于 turn 的轨迹指标不能未经验证地从 Claude 移植到 Codex。

### 论文没有证明

1. 没有证明所有 `AGENTS.md` 或仓库说明都无用；样本、语言、仓库和模型范围都很窄。
2. 没有证明上下文会降低正确率；Codex 的下降方向不具统计可靠性。
3. 没有证明小于 10–15 个百分点的效应不存在；当前实验不具备正式等效性检验所需功效。
4. 没有证明上下文通过某个具体机制改变结果。暴露、注意、使用、归因和正确性之间的链条未被直接测量。
5. 没有比较任务特制的决定性证据、最小充分上下文、调用图或反事实干扰，因此不能外推到这些处理。

### 主要威胁

- **外部效度**：三个项目均为 Python 生态，且是可稳定构建的开源仓库。
- **统计结论效度**：独立任务数很小，能排除的主要是超大且一致的效应。
- **构念效度**：自然文档可能并不包含解决具体任务所需的信息；“上下文条件”不等于“有效证据条件”。
- **实现混杂**：代理使用不同注入角色与日志协议，模型版本结论具有时间快照性质。
- **选择偏差**：仓库与任务经过执行可行性和先导难度筛选，不能代表所有真实任务。
- **测量边界**：gold tests 优于补丁相似度，但仍可能漏掉性能、维护性和未编码需求。

## 十三、作者与研究背景

论文与 arXiv 元数据将 Prakhar Khatri 标为独立研究者；公开原文没有给出单独的通讯作者标记，因此不应把作者顺序额外解释为通讯关系。项目仓库公开了实验代码和数据，研究积累在本文中主要体现为对 coding agent 实验基础设施、真实任务重放、隐藏测试和统计功效的系统处理。没有足够可靠的公开材料支持进一步归纳一个稳定课题组或长期机构方向，所以这里不做超出证据的背景包装。

## 十四、读完真正应记住什么

1. 给 coding agent 更多仓库说明，不等于给了它当前任务的决定性证据；“读到”“改变过程”“提高正确率”是三件事。
2. 负结果最怕把低功效写成无效证明。本文最诚实也最有用的部分，是把能排除的效应范围和任务数需求讲清楚。
3. coding agent 实验的有效样本量首先由独立任务数决定，而不是总运行次数；大量地板/天花板任务会吞掉处理信号。
4. 过程指标值得测，但要防止把输入长度的机械变化或日志 schema 差异误认为智能行为变化。
5. “上下文是否有用”不是单一问题。后续研究应明确上下文是否含决定性信息、是否被注意和使用、是否改变中介过程，以及效应对任务和代理是否异质。

## 十五、对当前研究的启发

当前研究正在区分真正有因果作用的仓库证据与 plausible/random 干扰，并观察到：oracle 上下文明显更强，而 plausible 与 random 暂时未形成稳定差异；同时，机制判断有时正确，补丁文件召回却不完整。本文为这条主线提供的不是“上下文无效”背书，而是四项更具体的设计提醒。

第一，**处理强度必须通过操纵检查定义**。建议把每个上下文条件拆成 exposure、attention、attribution、action 四层记录：材料是否出现；模型是否引用或访问；定位理由是否归因于它；后续工具调用或文件选择是否改变。否则 plausible≈random 既可能是二者同样无信息，也可能是模型根本没有利用处理。

第二，**预先管理地板和天花板，但不要按处理结果挑题**。可以先用无处理 pilot 为每个模型估计任务难度，预注册一个中间成功率区间，再在独立测试集比较 oracle/plausible/random。若要跨模型比较，需报告共同支持区间，并显式估计 agent×treatment 异质性。

第三，**优先增加独立 issue/实例和噪声种子，而不是只在一个 case 上堆调用**。当前五个案例适合机制探索，却不足以稳定区分 plausible 与 random 的小差异。论文给出的 120–200 任务量级不能直接照搬，因为结果变量和方差结构不同，但它提醒我们必须先做功效模拟，再决定要检测的最小实用效应。

第四，**同时报告终点与轨迹中介**。现有实验中的 patch-file recall、机制正确性、证据归因转移 `P(M=1,A=0)`、测试调用和定位路径应分别保留。上下文可能让代理更快锁定机制，却未提高文件召回；也可能改变注意分配但不改变答案。只有把这些中介按时间顺序记录，才能判断“没有终点增益”究竟是 treatment 无效，还是后续 action/implementation 环节截断了效应。

最后，这篇论文最适合被引用为一个**自然仓库说明未呈现普遍正确率增益、且任务动态范围决定实验辨识力的先例**。它不能用来证明专门构造的因果证据或调用图无效，也不能替代对 plausible context 现实性的独立验证。
