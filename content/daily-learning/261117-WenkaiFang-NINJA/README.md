# NINJA：把全局找路与局部查证分开，怎样才算真正节省上下文？

## 1. 一个 Agent 需要记住所有走过的弯路吗？

设想我们正在处理一个 Django 问题：合并三个以上的媒体资源对象时，系统报出不该出现的顺序冲突。搜索 `Media` 能找到基础表单组件、GIS 表单组件、资源列表及相关调用。最先读到的文件可能只是入口，真正决定合并行为的函数又藏在另一处。

一个单 Agent 可以继续搜索、读代码、追调用、记录判断。但随着过程推进，它的上下文同时装进了三种东西：仍然有效的全局线索、某个局部已经查清的细节，以及走错方向时留下的痕迹。下一次决定“还要去哪里”时，模型仍要带着这些内容一起走。粗粒度搜索需要看得广，函数推理需要钻得深，两者争用同一条不断增长的轨迹。

NINJA 的解法是让一个 navigator 负责找路，多个 inspector 负责查证。Navigator 记住候选入口、已经探索的区域和回传的可疑位置；inspector 从一个入口文件出发，在独立上下文里细读代码，必要时跨文件追踪，再把结论送回来。一个局部任务结束，它的全部阅读历史不必成为下一个局部任务的起点。

这篇论文有两条贡献线。第一条是这种多轮、可跨文件、带全局状态的分工结构。第二条是分别训练两类角色，让它们学会工具协议和长程探索。末尾还有一个特别值得细读的实验：除了“补丁改了哪里”，把“补丁依赖但没改的代码位置”交给修复 Agent，能否继续提高成功率？这与我们的支持证据问题有关，但它采用的是 **gold support 提示**，必须与实际预测能力分开。

## 3. 先确定它在预测什么：相关代码不等于评测答案

论文把代码位置写成 `(文件, 函数或类方法)`，例如 `(file1.py, Class1.method1)`。主要定位指标的 ground truth 来自解决 issue 的参考补丁：哪些函数被修改，哪些文件含有这些修改。

这里存在三个不同集合：

1. **编辑位置**：参考补丁实际改动的位置，是主实验的答案。
2. **支持位置**：理解或修复问题时有帮助，但参考补丁没有改动的位置。
3. **其他探索位置**：包括检索命中的候选、走过的错误分支和尚待查证的代码。

因此，探索期间读了一个未被修改的函数，不能自动算作无用；最终把它当成“要修改的函数”提交，则会受到编辑位置 F1 的惩罚。NINJA 的训练奖励主要针对第一类，支持位置的价值放在下游实验单独考察。

执行上，它采用推理与行动交替的 ReAct 框架：模型产生推理和动作，工具返回观察，再进入下一轮。退出可以由模型主动选择，也可以由步数或上下文上限触发；随后加上最终提交提示，生成定位集合。这里的终止与最终提交是明确的流程环节，不是假设模型最后一定会自然给出答案。

## 4. 核心机制：每个局部有自己的上下文，但整个搜索仍然连贯

### 4.1 Navigator 管理的是一张探索账本

Navigator 的初始输入是 issue 描述与仓库结构。它使用按文件名或内容搜索的工具寻找入口，并维护三部分全局状态：

- `S`：inspector 回报的可疑函数及相关信息；
- `E`：已经探索过的文件；
- `Q`：尚待探索的候选文件。

它可以继续搜索、派出 inspector，或结束并输出最终位置。角色的重点不是自己把每个函数钻到底，而是选择下一块值得花预算的区域，并把局部发现合并成全局决策。

这一状态设计能回答三个实际问题：我们已经有什么证据？哪些地方已经查过？还有哪些入口值得去？相比把这些信息埋在长篇自然语言轨迹里，显式状态便于避免重复派工。

### 4.2 Inspector 只有一个入口，但没有文件围墙

每个 inspector 收到 issue 和分配给它的入口文件，并建立独立上下文。它不继承 navigator 此前全部探索轨迹，因此不会先被其他分支的错误猜测占满工作空间。

Inspector 的工具允许列出文件中的函数、类和方法，读取具体源码，再通过 `get_callers`、`get_callees` 等沿调用关系向外探索。入口文件只是起点，不是它唯一可以读的文件。如果真正的逻辑位于依赖模块，它可以追过去。

完成后，它回传可疑函数、解释及已经访问的位置。这里要区分“完整轨迹作为日志保存”和“把整段轨迹继续塞进另一位 Agent 的工作上下文”。NINJA 的组织原则是局部轨迹独立、通过结果反馈协调，不是让所有模型共享同一段不断膨胀的历史。

这种独立性也不是统计意义上的独立投票。不同 inspector 可以使用同一模型、读到相同函数、作出相近判断；它们的作用是分摊探索与上下文，不是天然提供彼此独立的证据。

### 4.3 多轮调度：先派出去，再根据实际走到哪里修正计划

假设 navigator 找到若干入口，默认一次并行运行两个 inspector。入口集合按并行度分成小批，每一批完成后更新 `S/E/Q`，再处理后面的批次。

关键在于 inspector 会跨文件探索。原本待查的 B 文件，可能已经被从 A 出发的 inspector 顺路看过。更新全局状态后，后续派工就可以跳过 B，避免照着初始名单机械地查第二遍。

但同一个并行批次尚未返回时，两名 inspector 并不知道对方刚读了哪里，仍可能发生重叠。所以并行度越大不一定越省时，也不一定越准。后面的实验恰好显示：适度重叠可能补上遗漏，过度重叠会增加重复探索与反馈。

用一条流程概括原文图 1：**issue 与仓库结构 → 全局找入口 → 独立局部查证 → 回传位置和访问记录 → 更新全局账本 → 再派工或提交**。上下文被分隔了，搜索并没有被切成互不相干的静态任务。

## 5. 跟着原文案例走一遍：为什么第二条路径能补上第一条的遗漏？

附录 G 使用 `django__django-11019` 展示轨迹。问题是合并至少三个 media 对象时出现虚假的 `MediaOrderConflictWarning`：中间合并结果会引入原本不应存在的顺序约束。

Navigator 搜索后派出两个入口：`django/forms/widgets.py` 与 `django/contrib/gis/forms/widgets.py`。

**第一位 inspector 从核心 widgets 文件出发。** 它先查看类与方法，再检查 `Media` 的 `merge`、`__add__`、`_js`、`_css` 等。阅读中发现 `__add__` 只是拼接 `_css_lists` 与 `_js_lists`，并没有完成全部验证。它还尝试查询 `MediaOrderConflictWarning.__init__`，遇到了工具错误，随后转向 `media_property` 和 `MediaDefiningClass.__new__`。最终回报中包含 `merge`、`__add__`、警告类及媒体属性构造相关位置。

**第二位 inspector 从 GIS widgets 出发。** 它看到的初始化、序列化、反序列化和 `get_context` 并没有解释媒体合并，于是跨到核心 widgets。找到 `merge` 后，它继续查调用者，从而把 `_js` 与 `_css` 拉入分析，最后回报 `merge`、`_js`、`_css`、`__add__`、`media_property`。

Navigator 汇总后的前五个结果是 `merge`、`__add__`、`_js`、`_css`、`media_property`。参考补丁涉及的三个目标是 `merge`、`_js`、`_css`，因此全部进入 top 5。

这个案例最有意思的地方不是“两个人各查一个文件”。事实上，两条路径发生了重叠，第二位还离开了自己的入口。它展示的是：一条局部探索没有选全目标时，另一条路径可以通过调用关系补齐；全局汇总保留这种互补，而不要求所有局部路径都正确。

也可以借此理解指标。这个例子 top 5 覆盖全部三个 GT，所以函数 Acc@5 记为成功。若最终预测集合恰好就是上述五项，则集合 F1 为 `2×3/(5+3)=0.75`。这个 F1 是按文中定义对示例计算的说明值，不是论文额外报告的逐例测量。它解释了为什么“前五个全找到了”与“输出集合足够干净”是两个问题。

## 6. 训练不是把两个角色一起扔进一个奖励池

### 6.1 监督微调（SFT）先教会工具协议

作者用 Claude-Haiku-4.5 在 500 个 SWE-smith-py 任务上采集轨迹，保留成功且格式有效的样本，得到 462 条 navigator 轨迹与 275 条 inspector 轨迹，分别进行两轮 SFT。

训练只对 assistant 生成的 token 计算损失。工具观察和外部提示仍作为条件输入，但不会被当成模型应该自己编写的答案。直观地说，模型学的是“在看到这段源码和工具返回后怎样行动”，而不是背着输出整份工具返回。

这一阶段首先解决协议问题：怎样形成合法工具参数，怎样提交位置，什么时候继续探索。后面的消融表明，没有这个热身，直接 RL 并不稳。

### 6.2 先训练 inspector，再固定它训练 navigator

强化学习（RL）使用 24,209 个训练任务，每仓库最多 300 个；按仓库过滤掉与评测仓库重叠的训练数据。这样的隔离比只排除同一 issue 更严格，但仍不等于证明基础模型从未见过公开仓库或基准内容。

作者先优化局部 inspector，再把训练后的 inspector 固定成服务，训练 navigator。这样 navigator 学“派谁去哪里”时，收到的反馈来自相对稳定的局部执行者，避免两边策略同时改变、奖励含义不断漂移。

奖励包含两部分：

`R = F1(预测编辑位置, 目标编辑位置) + λ × 工具成功率`，其中 `λ=1`。

F1 的集合形式为 `2|预测∩GT|/(|预测|+|GT|)`，既奖励找到目标，也惩罚乱报。工具成功率是有效执行调用的比例，用来约束不存在的符号、异常调用等问题。两项均在 0 到 1 之间，奖励并没有直接给“少用 token”单独加分。

Navigator 对整个任务的编辑 GT 计算 F1。Inspector 则只面对它访问文件范围内的 GT，不因为未被派去的区域而被扣分。若某条 inspector 轨迹的访问范围内没有 GT，作者把它排除出训练。这使局部奖励更可学习，同时意味着训练信号对“查了一块确实无关区域后可靠退出”覆盖较弱，后面讨论迁移时要记住这一点。

### 6.3 为什么比较 PPO 和 DAPO？

长程搜索里，最终答对不代表每一步都对。近端策略优化（PPO）使用价值评估器（critic） 估计更细粒度的优势，帮助模型调整中间动作；裁剪更新幅度则避免策略一次改得过猛。论文对照的解耦裁剪与动态采样策略优化（DAPO）不使用同样的价值评估器设计。

作者把 PPO 的优势解释为长轨迹中的信用分配更细。但这不是只开关一个 critic 的纯消融：两套训练还有采样等设置差异。PPO rollout 为 256 个 prompt、每个一个样本，DAPO 为 64 个 prompt、每个四个样本。总样本规模相近，不代表所有变量相同。

计算上，SFT 使用 8 张 A800，RL 对 14B 使用 8 张 H100，对 30B 使用两台 H100 机器。这里不应该把论文方法理解成“只写两个提示词就复现了训练版模型”。不过架构本身可以直接接未训练的底模，论文也确实单独报告了这一层结果。

## 7. 评测怎样读：先分清三个预算与两种准确性

定位主实验覆盖 SWE-bench Lite 和 LocBench，下游修复使用 SWE-bench Verified。骨干包括 Claude-Haiku-4.5、Qwen3-14B，以及 Qwen3-Coder-30B-A3B-Instruct；后者的 30B 是总参数规模，A3B 表示约 3B 激活参数。

默认温度为 0.6，Qwen 的 top-p 为 0.95，每个独立 Agent 上下文上限 32,768，inspector 并行度为 2。定位结果报告三次运行的均值与标准差。下面表格为便于阅读主要列均值，不能把一次运行与这些均值直接混比。

**Acc@5 的要求是前五项覆盖该任务的全部 GT，不是命中任意一个就算成功。** 文件级先把位置映射到文件；函数级则保留具体函数。F1 是每个实例的集合 F1 再求平均，不是把所有实例合成一个大集合计算。

成本有三个不同层次：

- **单 Agent 上下文上限**：32K 对每个 navigator、每个 inspector 各自生效，不是整个系统共享 32K。
- **总轨迹 token**：把定位涉及的所有 Agent 轨迹统计起来。表中 `k` 是 1,000，`K` 是 1,024。它不应未经核对就换算为含重复输入、缓存折扣的 API 账单。
- **端到端推理时间**：含模型调用和中间处理，但不含离线 embedding、检索索引或调用图构建。依赖图工具不是免费凭空出现的。

因此，“context-efficient”首先指缓解单条上下文的累积压力，不能读成在所有设置下总 token 最少。

基线也不是同一种东西换个名字：CodeRankEmbed 是静态向量检索；SWERank+ 结合检索、重排与迭代查询；LocAgent 用图进行定位；CoSIL 组织分层搜索与上下文剪枝；OrcaLoca 调整探索动作优先级和上下文；RepoSearcher 使用专门的工具与训练方案。论文尽量在相同骨干下比较，但没有把所有工具、候选节点和上下文包装固定为一致。因此主表评价的是完整系统，而不是某一个上下文因素的纯效应。

## 8. 主结果：函数覆盖提升很明显，低成本与高精度不能打包宣称

### 8.1 SWE-bench Lite：同一个 Qwen 骨干下发生了什么？

原文表 1 的代表性结果如下，定位分数均为百分数：

| 方法，Qwen3-30B | 文件 Acc@5 | 文件 F1 | 函数 Acc@5 | 函数 F1 |
| --- | --- | --- | --- | --- |
| SWERank+ | 26.8 | 8.9 | 1.1 | 0.4 |
| LocAgent | 44.0 | 14.7 | 25.4 | 9.3 |
| CoSIL | 79.2 | 29.8 | 24.6 | 12.9 |
| OrcaLoca | 64.0 | 51.8 | 39.0 | 27.9 |
| RepoSearcher | 74.8 | 26.0 | 19.9 | 13.9 |
| NINJA，未训练 | 79.3 | 53.5 | 71.1 | 27.7 |
| NINJA，SFT+PPO | 90.6 | 59.7 | 77.3 | 29.4 |

对应成本：

| 方法，Qwen3-30B | 轨迹 token | 秒 |
| --- | --- | --- |
| SWERank+ | 53.2k | 140.0 |
| LocAgent | 46.7k | 52.6 |
| CoSIL | 24.3k | 33.3 |
| OrcaLoca | 30.5k | 121.7 |
| RepoSearcher | 26.7k | 61.3 |
| NINJA，未训练 | 51.7k | 85.4 |
| NINJA，SFT+PPO | 48.7k | 84.7 |


未经训练的 NINJA 已经把函数 Acc@5 拉到 71.1%，明显高于其他同骨干 Agent。但它的函数 F1 为 27.7%，略低于 OrcaLoca 的 27.9%。这恰好提醒我们：能把所有目标放进前几名，不等于最终输出集合最精简。

相对 CoSIL，未训练 NINJA 用了约 2.13 倍轨迹 token、2.56 倍时间。相对 OrcaLoca，它反而更快，但仍消耗更多轨迹 token。不能把不同参照系里的优势拼成“更准、更快、更省”。

静态 CodeRankEmbed 的文件 Acc@5 为 75.0%，函数 Acc@5 为 54.0%，运行 14.9 秒。这是一个值得保留的低成本参照。论文中一些更复杂 Agent 对 Qwen 的适配并不理想，例如 SWERank+；不能由此推断该方法在其他实现和模型上都同样弱。

训练后 30B 的文件 Acc@5 从 79.3 升到 90.6，函数 Acc@5 从 71.1 升到 77.3，token 还从 51.7k 降到 48.7k。后训练在这组设置下兼顾了结果与轨迹效率。

换成 Haiku，NINJA 为文件 Acc@5 84.0、文件 F1 59.7、函数 Acc@5 76.3、函数 F1 29.3；训练版 Qwen 在前一项与函数覆盖上超过它，文件 F1 持平，函数 F1 只高 0.1。对比同为 Haiku 的 CoSIL，函数 Acc@5 是 68.3、函数 F1 是 26.6，说明 NINJA 的收益不完全依赖某一个开源骨干。

14B 训练后文件 Acc@5 从 72.0 升到 83.3，函数 Acc@5 只从 50.3 升到 51.8；token 从 35.0k 降到 32.0k，时间从 57.4 降到 45.7 秒。模型规模会改变收益形态，不能直接把 30B 的函数定位增益套到更小模型。

### 8.2 LocBench：趋势延续，但“超过闭源模型”仍有维度差别

在附录表 6 中，Qwen 未训练 NINJA 的文件 F1/函数 Acc@5/函数 F1 为 58.4/60.3/33.6，训练后为 63.7/69.0/37.5。相同骨干的 CoSIL 是 30.7/19.1/15.8，OrcaLoca 是 51.3/24.8/23.6。

训练后 NINJA 的文件 Acc@5 为 86.7%，高于 Haiku NINJA 的 83.3%；但文件 F1 63.7% 仍低于 Haiku 的 65.1%。函数 Acc@5 与 F1 则分别高于 Haiku 的 65.8 与 35.8。论文所说的超过强闭源模型，应当理解为主要结果上的竞争力，不是每个指标全面胜出。

这里的总 token 仍不低：未训练/训练 Qwen NINJA 为 59.8k/57.9k，CoSIL 27.1k，OrcaLoca 26.6k。跨两个定位基准重复出现的强证据是函数目标覆盖能力，最节省总计算则不是它的统一结论。

## 9. 公平比较最关键的一张表：压到相近 token 后，还剩多少收益？

原文表 3 给 NINJA 加入更小的总体 token 预算，与两个较省的基线比较。这比只看默认主表更接近我们关心的公平问题。

| 同为 Qwen3-30B | 文件 Acc@5 | 文件 F1 | 函数 Acc@5 | 函数 F1 |
| --- | --- | --- | --- | --- |
| CoSIL | 79.2 | 29.8 | 24.6 | 12.9 |
| NINJA，25k 预算 | 74.2 | 48.4 | 63.4 | 22.5 |
| OrcaLoca | 64.0 | 51.8 | 39.0 | 27.9 |
| NINJA，30k 预算 | 77.6 | 51.9 | 66.4 | 24.8 |

对应成本：

| 同为 Qwen3-30B | 实际 token | 秒 |
| --- | --- | --- |
| CoSIL | 24.3k | 33.3 |
| NINJA，25k 预算 | 24.8k | 35.6 |

与 CoSIL 相比，NINJA 在相近总体 token 下仍有很大的函数 Acc@5 优势，24.6→63.4；文件 F1 也从 29.8 到 48.4。但文件 Acc@5 下降了五个百分点，79.2→74.2。对最终交付文件集合的任务，这个负向结果不能略过。

与 OrcaLoca 相比，NINJA 的函数 Acc@5 为 66.4 对 39.0，时间也更短；可是函数 F1 是 24.8 对 27.9。它更善于覆盖全部答案，不代表误报控制同样占优。

这张表支持“效果提升不全是多花 token 买来的”。它没有完成 CPI 所需的所有控制：实际均值只是接近，未固定逐实例候选数、节点粒度、输入源码、工具信息和回读机会，也没有证明 API 计费成本完全一致。对于我们的研究，最好把两层问题分开：端到端比较允许系统自主探索，但完整记账；受控上下文实验则固定曝光与打包，专门识别 P/I 或证据结构的作用。

## 10. 消融与敏感性：独立上下文重要，但原实验没有把它单独剥离出来

### 10.1 三项结构消融

原文表 2 的 Qwen3-30B 结果：

| 设置 | 文件 F1 | 函数 Acc@5 | 函数 F1 | token | 秒 |
|---|---:|---:|---:|---:|---:|
| 完整 NINJA | 53.5 | 71.1 | 27.7 | 51.7k | 85.4 |
| 合成单 Agent、共用上下文 | 31.4 | 41.5 | 18.1 | 24.6k | 17.2 |
| 只允许第一轮派工 | 48.7 | 65.6 | 23.5 | 41.7k | 63.4 |
| 取消全局探索文件跟踪 | 51.7 | 69.9 | 26.8 | 58.7k | 93.8 |

第一行与第二行差距最大，但“去掉独立上下文”同时把 navigator 与 inspector 合成一个 Agent，还改变了有效预算和执行结构。它证明完整分工系统优于这个合并版本，不能严格归因于上下文隔离一个因素。

取消多轮派工后，函数 Acc@5 下降 5.5 个百分点。这说明第一次找到的入口未必已经足够，回传结果之后继续探索有价值。

取消探索状态跟踪后，token 从 51.7k 增至 58.7k，准确性反而略降。全局账本的主要价值在这里更清晰：它减少无意的重复派工，而不是单纯增大模型阅读量。

### 10.2 并行度：三个人的峰值不是普遍的最优人数

原文图 2a 中，并行度从 1 到 5，文件 Acc@5 依次为 75.6、79.3、81.6、78.7、79.3；函数 Acc@5 为 69.9、71.1、71.9、69.9、69.9。token 与运行时间总体上升。

作者的解释是：小幅重叠可以救回漏掉的函数；并行过多时，尚未同步的局部搜索造成重复代码与反馈，扰乱全局判断。这个解释合理，但图本身没有把“有害重复”“有用第二次验证”和 CPI 的 plausible context 分别标注、干预。因此它是调度现象，不是 P 的因果证据。

### 10.3 上下文窗口：先解决提前终止，再谈更长是否有用

图 2b 把每个独立 Agent 的窗口从 8K 增到 128K。函数 Acc@5 从 37.3% 升到 16K 时的 68.2%、32K 时的 71.1%，之后 64K/128K 为 70.8/70.9，基本平台化。

附录表 7 给出原因线索：8K 时 navigator 有 82.19% 的轨迹超限，inspector 为 49.83%；16K 时分别为 13.04%/12.90%；32K 时仅 0.33%/0.46%；64K 与 128K 均为零。

所以前半段巨大提升很大程度上伴随“终于能做完探索”。32K 之后不再明显增益，说明对这一任务和配置，继续扩大工作窗口没有带来同等收益。它既不证明所有定位问题都只需 32K，也不证明长上下文普遍有害。

## 11. 后训练结果：先会用工具，再学搜索策略

原文表 4 对 Qwen3-30B 比较不同训练路径：

| 训练方式 | 文件 F1 | 函数 Acc@5 | 函数 F1 |
|---|---:|---:|---:|
| 无训练 | 53.5 | 71.1 | 27.7 |
| 直接 PPO | 54.1 | 69.5 | 25.2 |
| 仅 SFT | 53.8 | 71.8 | 27.6 |
| SFT + DAPO | 58.7 | 74.5 | 28.3 |
| SFT + PPO | 59.7 | 77.3 | 29.4 |

直接 PPO 没有稳定改进，函数两项反而下降。SFT 单独提升有限，主要价值在于给 RL 一个会遵守工具协议的起点。两者组合后效果才明显。

作者也训练了 OrcaLoca，避免把“只有 NINJA 获得后训练”当成全部优势来源。OrcaLoca 的文件 F1/函数 Acc@5/函数 F1 从 51.8/39.0/27.9 提升到 54.9/45.5/28.4。训练对另一架构同样有帮助，训练后的 OrcaLoca 文件 F1 还高于未训练 NINJA 的 53.5；但与同样训练后的 NINJA 相比仍有差距。

附录另测 MATH-500、AIME 2024/2025、AMC 2023、GPQA Diamond、MMLU STEM 等一般推理任务，每题平均四个样本。30B 原模型平均分为 58.0，训练后的 navigator/inspector 为 60.8/60.0；14B 则从 85.3 到 85.1/84.6。这支持“这组测验上没有明显灾难性遗忘”，不能扩写为所有通用能力均被完整保留。

## 12. 支持位置实验：有用的是 oracle 提示，不是已经学会了寻找 support

论文用 mini-SWE-agent 与 Claude-Haiku-4.5 在 SWE-bench Verified 上修复 issue，改变 user prompt 中提供的位置提示：

| 提示来源 | 提示内容 | 修复成功率 | 修复 Agent token |
|---|---|---:|---:|
| 无 | 无位置提示 | 28.8% | 39.3k |
| 参考答案 | 编辑位置 | 52.6% | 36.7k |
| 参考答案 | 编辑位置 + 支持位置 | 57.2% | 36.3k |
| NINJA 预测 | 编辑位置 | 45.2% | 37.8k |
| 合并单 Agent 版本预测 | 编辑位置 | 33.2% | 39.7k |

NINJA 预测的编辑位置把修复率从 28.8% 提高到 45.2%，是 16.4 个百分点，不是相对增长 16.4%。其实际价值超出了定位榜上的分数。

Gold edit 把结果进一步带到 52.6%，再加入 gold support 达到 57.2%，多了 4.6 个百分点。这里的 support 来自参考补丁中改动语句所引用的仓库内依赖，包含可解析的被调用函数、构造函数，以及适用时的 `__call__` 等；被修改的代码位置不重复算 support。它是依据补丁得到的操作化支持集合，不是通过严格反事实实验认证的最小必要因果集合。

提示形式也很重要：提供的是文件/函数**位置名称**，不是直接把全部支持源码粘进上下文。修复 Agent 可以据此自行读取代码。因此增益同时可能包含更好的导航、更少的搜索歧路和更有效的证据获取。

这组结果留下三个边界。第一，NINJA 的主方法仍预测 edit，并没有在该表展示 predicted support；代码仓库也把 support 当成分析资源，而非现有定位 GT。第二，gold edit+support 比 gold edit 给出更多信息，未匹配额外位置数或加入同规模干扰位置，所以不能把 4.6 点全部解释成支持代码的“纯因果效应”。第三，表里的 token 只统计修复 Agent，没有加上前置 NINJA 定位成本。39.3k→37.8k 说明下游探索变少，不等于端到端总账更低。

因此，最稳妥的研究结论是：**只把参考补丁修改位置当成所有有用上下文，可能低估未编辑依赖的价值；怎样在不知道补丁时发现这些依赖，仍是开放问题。**

## 13. 论文做到哪里，仍缺哪几块证据？

NINJA 的强项很集中：它给出了完整可运行的探索架构，在两个定位基准、多个骨干上显示出较强的函数覆盖；相近 token 的补充比较表明，优势不完全来自额外计算；下游预测提示确实提高修复率；训练、调度和窗口实验也提供了机制线索。

局限可以归为四组。

**任务与答案边界。** 编辑函数 GT 是可评测的目标，却不覆盖全部有用证据。普通 issue 文字通常比 CWE-only 漏洞定位提供更具体的症状。Python 仓库及其调用图工具上的结果，迁移到多语言安全任务需要重新验证。论文没有把“支持位置有用”推进为可部署的支持位置预测器。

**因果归因边界。** 独立上下文消融同时改变分工、预算和控制流；PPO/DAPO 也不只是单变量变化。结果支持整套设计，但不能精确告诉我们各因素各自贡献多少。并行度下降与重复信息有关是作者解释，并未形成对竞争证据的受控识别。

**成本与可复现边界。** 主表中 NINJA 常用更多总 token；离线索引成本被排除；下游表没有包含前置定位成本。公开代码提供数据、训练、推理、评测与轨迹查看入口，并复用了 LocAgent/RepoSearcher 的相关工具，但复现仍要核对模型版本、实际样本清单、索引与训练资源，不能只复制一条最终准确率。

**训练覆盖边界。** 局部 GT 为空的 inspector 轨迹被排除，可能弱化无关区域的可靠排除与停止学习。按仓库划分降低任务微调泄漏，不解决所有基础模型预训练污染问题。三次运行的均值与标准差比单次分数更可靠，但没有替代逐例配对分析、失败分类或对部署分布的验证。

论文没有提供系统性的失败类型统计。我们能直接看到的负结果包括预算匹配后文件覆盖或函数 F1 不占优、直接 PPO 退步、高并行无额外收益，以及案例中的工具错误；不宜额外编造一套作者已经验证过的失效机制。

## 14. 对 Seer 的具体启发：借用工作空间组织，保留自己的证据问题

结合当前 causal-review 的研究记录，Seer 已把本阶段最终交付收紧为 VLocBench 文件定位；节点、片段、竞争解释是帮助探索的内部证据。已有开发实验还提醒我们：文件命中不等于理解正确，读过文件一部分不等于看见漏洞机制，合法提交也不等于准确性提高。

NINJA 最值得借鉴的不是再增加几个角色名称，而是将四件事明确分开：发现一个入口、读取哪些源码、形成什么判断、哪些内容仍留在工作记忆中。

### 14.1 可先借鉴的工程原则

**全局账本记录覆盖，局部空间承载推理。** Navigator 的 `E` 可以减少重复派工，但对 Seer 还不够细。一个文件读过头部，不能被记成整文件已经查清；账本至少应保留文件、已读区间、查询来源和未解决的问题。同文件内 `set` 与 `merge` 这样的竞争机制，也不能被最后一次 file-level 标签互相覆盖。

**局部返回要带证据坐标，不只带结论。** NINJA 回传可疑函数和解释；Seer 可以把它收紧成“候选文件、源码范围、支持哪条机制、什么证据尚缺、下一步可回读哪里”。这是对现有证据账本的具体化，不应宣称光靠增加字段就是研究贡献。

**可恢复压缩优先于永久删除。** 独立工作空间让局部历史不持续占用全局窗口，但应保留可追溯日志和源码坐标。对于尚未确认决定性的候选，可以压缩成身份、签名、短证据，在机制冲突或覆盖缺口出现时有限回读。未查验、待补证与人工审定 P 必须分开，不能把不知道的内容直接称为 plausible context。

**结束阶段独立计量。** NINJA 有退出与最终提交环节。Seer 现有轨迹已经说明，增加合法提交机会能修复协议失败，却不能自动修复机制判断。应该同时报告合法率、定位分数和错误解释，不把三者混成一个成功率。

### 14.2 两类实验不要混在同一张“公平”表里

若做端到端文件定位，保留各系统自己的探索流程，以相同模型版本、题面、仓库快照和可用总预算重跑，记录全部模型调用、实际 API token、工具时间、索引成本与失败重试。不要把 Seer 最后一次裁决的成本与其他 Agent 的整条探索成本比较。

若要研究 CPI 的上下文效应，则单独固定曝光集、源码版本和打包器，控制 token 与节点数量，明确处理哪些 P/I 片段。相同输入应复用或配对响应，避免把重复调用波动误认成筛选收益。NINJA 的总预算匹配可以作为系统比较范例，但不能替代这种受控组件实验。

Gold edit+support 只能作为诊断上界。实际方法必须在无 GT、无补丁、无人工 CPI 标签的条件下寻找证据；预测支持位置与 oracle 支持位置分别列。尤其不能把通过参考补丁提取的 support 再送回所谓“自主探索”主实验。

### 14.3 优先验证的研究问题应当更窄

一个有价值但尚未验证的假设是：**当不同局部证据支持相似却不同的漏洞机制时，带来源的短证据和有界回读，是否比累计全部源码或一次性删除更能保住正确文件？**

这与 NINJA 的分工可以相容，也超出了它目前主要回答的问题。但验证时需要拆分处理：先比较工作上下文隔离，再比较证据回传，再比较按缺口触发回读，避免一口气修改账本、提示、并行度和结束协议后，把涨分归给其中一个。

当前已经反复用于设计的十例只能作为开发验证。真正判断是否比 CoSIL、OrcaLoca 或其他 Agent 更好，需要冻结新样本和协议，保留缺失 CWE、争议公告、新增 GT 文件等边界分层，而不是按结果筛掉难例。函数级指标适合作为内部诊断，最终文件任务仍应按官方文件分母计分。

## 15. 最后留下什么？

NINJA 说明，仓库定位不必让一个模型背着所有探索历史走到底。把全局调度与局部查证分开，再通过访问记录和可疑位置衔接，能明显提高函数级答案覆盖；训练能进一步增强这种架构，但不是每个模型、每个指标都同样受益。

对我们的工作，更重要的提醒是：**把上下文拆开解决的是工作空间组织，把证据分清解决的是为什么相信某个位置。** 前者已有强相关工作，后者仍需可追溯的机制证据与公平实验。支持代码的 oracle 增益提供了研究动机，却没有替我们完成无补丁条件下的证据发现。
