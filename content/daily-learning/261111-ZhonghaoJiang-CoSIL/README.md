## 一个知道“要去重”、却不知道“在哪里去重”的修复任务

程序员收到一个问题报告：Django 的表单下拉框出现重复选项。报告提到了外键、限制选项的条件和相关文件。代码助手顺着这些关键词找到了几个看起来非常合理的函数，也知道应该调用 `distinct()` 去重，却仍然改错了位置。

这里的困难不是模型完全不懂问题，而是**症状所在的代码、名字最像问题的代码和真正该修改的代码，不一定是同一处**。仓库很大，只看报告点名的文件容易漏掉目标；放开让助手随意搜索，又可能反复阅读同一批相关但不关键的函数，耗完预算。

CoSIL 研究的就是如何把这段“从问题描述走到具体修改位置”的过程组织好。它先利用文件间的导入关系扩展候选范围，再沿函数关系逐步读取实现，用一个独立的相关性判断环节控制接下来往哪儿走，最后把定位结果整理成程序能够消费的完整路径和函数签名。它输出的是可疑位置排序，不直接生成补丁。

## 从 Django 的失败例子看，搜索到底缺了哪一步

论文图1使用 Django-13315。问题是：给 `ForeignKey` 的 `limit_choices_to` 传入包含连接条件的 `Q` 对象后，表单可能出现重复选项。

可以把它理解成一个查询处理过程：先拿到候选记录，再按条件过滤；过滤中的连接让同一条记录出现了多次，最终显示到表单中。关键词很容易把助手引向 `ForeignKey` 类及 `get_limit_choices_to` 之类的函数，但真正需要修改的是：

`django/forms/models.py::apply_limit_choices_to_to_formfield`

它处在“把限制条件应用到表单字段”的环节。论文图4展示的正确补丁，是在 `complex_filter(limit_choices_to)` 之后调用 `distinct()`。另一个系统把 `distinct()` 加在 `ForeignKey.formfield` 中取得默认查询集的位置。两者都想到了去重，却改在不同函数：论文报告前一个补丁通过测试，后一个未通过。这个实例说明，知道该用什么操作之后，仍需要找到合适的修改位置。

下面只保留图4中决定机制的操作顺序，省略无关代码：

```python
# 正确修复位置：apply_limit_choices_to_to_formfield
formfield.queryset = (
    formfield.queryset.complex_filter(limit_choices_to).distinct()
)

# 另一个系统选择了更早的位置：ForeignKey.formfield
queryset = self.remote_field.model._default_manager.using(using).distinct()
```

作者检查了三种已有方法在这个实例上的轨迹，发现三个问题。

1. **范围选错。** 层级定位容易围绕报告点名的 `django/forms/fields.py`、`django/db/models/fields/related.py` 搜索，真正的 `django/forms/models.py` 没有被及时纳入。名字相近的函数则容易被反复选中。
2. **搜索方向失控。** LocAgent 多次读取或遍历 `ForeignKey` 相关内容，产生重复上下文，却没有把有限步骤花在关键分支上。
3. **结果接口出错。** 一次图遍历把应该是列表的 `start_entities` 传成字符串，触发工具错误；另一种输出只给 `related.py` 而不是完整路径，解析时出现 `KeyError`。找到候选与成功交付候选是两个环节。

图1从左到右画出问题描述、文件级结果、函数级结果。红叉对应上述错误或错误位置，绿色结果对应正确路径。下方的导入关系与函数关系解释了如何从症状文件走向修改位置。这是一个动机案例：它让设计取舍变得具体；方法是否普遍有效，随后用两个基准的整组实验回答。

相关工作已经能做的事情不少：Agentless 可按文件、函数、行逐层缩小范围；OrcaLoca 可使用队列调度和代码关系引导代理；LocAgent 可建立全仓库关系索引并多跳检索。本文要补的是**有限预算下，既扩展到必要位置，又避免在无关方向上反复消耗，同时稳定交付结构化定位结果**。

## CoSIL 怎样跑完一次定位

输入是问题描述和对应版本的代码仓库，输出是按可疑程度排序的函数或类列表。方法没有额外训练阶段，也不要求事先把整个仓库的函数关系全部建成索引；它仍需要读取目录、导入语句和被探索实体的源码。

图2以 Astropy 的 QDP 文件读取问题演示整体结构：左侧是问题与仓库目录树，中间是文件级候选扩展，右侧是函数级探索。灰色大区域代表文件，圆形节点表示函数，另一类节点表示类；蓝箭头是搜索步骤，绿色轮廓是接受的上下文，红色轮廓是裁剪对象。读这张图时，重点是**文件层先扩范围，函数层再逐步深入**，以及右上角搜索者、裁剪者和当前上下文之间的循环。

### 第一步：不要只相信报告点名的文件

作者先递归遍历仓库，得到目录树。模型读问题描述和目录树，预选一批相关文件。接着，系统解析这些文件的导入语句，得到以预选文件为起点的一阶邻接关系，再把问题、目录树、预选文件和导入关系一起交给模型，重新选出并排序最可疑的五个文件。

这里的“模块调用图”在文件层具体指**导入关系图**：节点是模块或文件，边表示 import。它告诉模型“这个模块依赖哪些模块”，不等于程序运行时实际发生过哪些调用。

在 Django 例子中，报告把注意力带到外键实现，导入关系则提供通往表单模型模块的线索。结果不是把全仓库源码塞入窗口，而是让原来较窄的候选范围获得结构化扩展。随后只对选出的文件建立类、方法和函数的骨架，交给下一阶段。

附录图8、图9分别给出预选与导入关系重排的提示词。前者要求完整路径和有序候选，后者额外提供 import 内容，返回五个文件，并要求排除测试文件。两次提示的输入不同：第二次有了新的依赖证据，才有机会纠正第一次的范围判断。

### 第二步：把“知道名字”变成“逐步读到实现”

文件骨架列出类、成员方法和文件级函数，但不等于函数正文。CoSIL 根据问题和骨架选出探索起点，然后维护两个状态：

- `visibleNodes`：当前可供选择的节点，类似待调查线索。
- `contextNodes`：已经读取并被接受的节点，其源码将用于最终判断。

每轮搜索者从可见节点中选择一个目标，调用对应工具读取代码。表I区分了读取类、类中方法、文件级函数，以及提前结束的 `exit` 工具。附录图10的提示词进一步要求使用给定骨架中的路径、类名和函数名，避免重复调用，并在预算内选择最可疑位置。

读到源码后，相关性裁剪者判断是否接受该节点。**按照论文方法描述**，接受则保存正文、开放它的邻居；拒绝则不把正文纳入最终上下文，也不沿这个节点继续扩展。每轮增加已使用的步骤数，最多十轮；如果目标不存在，系统提示重选；若模型判断证据已足够，可提前退出。

这样，状态变化就很清楚：

> 问题与骨架提供起点 → 选择一个节点 → 读取实现 → 判断相关性 → 接受并扩展，或拒绝这个方向 → 继续选择 → 汇总保留证据，输出位置排序。

它不是先遍历整个图再过滤。节点是否被接受，会影响下一轮哪些邻居进入视野。图2里红色分支被停下后，有限轮次便可用于其他分支。

### 函数关系从哪里来

函数层节点包括类与函数，边包括调用和继承。论文让大模型根据目标实体的源码以及所在文件的导入语句，分析向外的依赖，输出以当前实体为中心的一阶子图。

图3展示的是文本表示，不是必须渲染的图片：一侧记录文件及其 imports，另一侧记录目标函数关联的文件级函数、类方法等。模型消费这种结构化文本即可。附录算法1把构建过程拆成读取代码、提取 imports、组织提示、调用模型、解析关系输出。

附录图5进一步把三种表示连起来：左边是目录树，中间是 `M1` 导入 `M2`、`M3` 的文件图，右边把各模块展开为类和函数，显示更细粒度关系。**目录告诉你东西放在哪里，导入图告诉你相关模块可能在哪里，函数图帮助决定下一步读谁。** 三者承担不同职责。

### 第三步：让相关性裁剪者控制支路

裁剪者的输入是问题描述和刚读到的代码片段，输出是是否接受。附录图11的模板要求：相关且应加入上下文则返回 True，否则返回 False。它不是给函数打“正确补丁位置”的金标准标签，而是在搜索过程中判断“这段内容是否值得继续带着走”。

这一步同时具有两种作用：减少保留的源码，以及减少沿该节点继续扩展的机会。对于 Django 的例子，保留所有名字相关的类容易让十轮预算用在外围，而定向搜索有机会到达实际应用过滤条件的函数。

这里先按论文流程解释方法。公开代码的旧版、新版与这段描述有重要差异，后面给出固定版本链接，复现时应以选定版本的实际行为为准。

### 第四步：把长轨迹的最终判断交给一次短上下文复核

文件级和函数级阶段末尾，模型都需要提交定位结果。CoSIL 的 **Reflective Alignment（反思式对齐）**取最后一条包含决策信息的回复，而不是把整个交互历史再重放一遍；正文描述将它与问题一起放入一个新的短上下文查询，要求重新排序并规范输出。

这一步的直觉很朴素：前面可能进行了很多工具交互、出现过错误消息；最终交付时，单独检查“路径是否完整、格式能否被解析、候选排序是否合适”，比让长轨迹直接作为结果更稳。

它是一次独立查询，不是另训练了一个独立模型。附录图12实际展示的模板重点是格式修正：提供待修正结果和正确路径格式示例。正文还描述了重排作用，因而复现时不能仅凭“reflection”这个名称判断具体做了什么。

到这里，一次定位的完整产物是**有序、可解析的位置列表**。后续可以继续做行级定位，也可以把这些位置对应的代码交给修复模型。

## 实验先固定了什么，又比较了什么

作者提出四个 RQ：定位效果、组件贡献、对修复的帮助，以及跨模型泛化和费用。研究单位是一个仓库 issue，而不是一个孤立函数。

### 数据和答案怎样定义

SWE-bench 原始集合包含来自12个 Python 仓库的2,294个任务。本文主要使用：

- **SWE-bench Lite：300例。** 通过启发式筛选得到的较小子集，排除了一些依赖图片等非文本信息的问题。
- **SWE-bench Verified：500例。** 从1,699个人工审查实例中筛选，减少描述不充分、测试过于特定等问题。

定位评价与作者提供的文件、函数／类级目标位置比较；公开工件以[gt.json](https://github.com/ZJU-CTAG/CoSIL/blob/8e82b3f261db30c2d74095a70127b8079fe023c3/evaluation/gt.json)和[gt_verified.json](https://github.com/ZJU-CTAG/CoSIL/blob/8e82b3f261db30c2d74095a70127b8079fe023c3/evaluation/gt_verified.json)保存这些目标。模型根据问题与待修复仓库输出候选，再与目标比较；后面的修复实验则执行测试来判断问题是否解决。两种评价对象要分开：前者测“位置排名”，后者测“最终修复”。

### 三个基线代表三种组织方式

- **Agentless-FL：层级提示。** 取 Agentless 的定位部分，先文件再函数，主要依靠结构骨架缩小范围，代表低交互、低成本方案。
- **OrcaLoca：代理式调度。** 使用优先队列、动作分解、相关性评分和代码图，并根据距离裁剪已检索上下文。
- **LocAgent：全仓库图索引。** 先解析仓库依赖关系，借助索引和检索工具进行多跳定位。

这些基线合理地覆盖了轻量提示、动态代理和图索引方案。作者还考虑了微调方法 BugCerberus，但由于实现未公开，未完成比较。

### 模型、预算与运行设置

RQ1使用 Qwen2.5-Coder-7B、14B、32B，RQ2消融使用32B，经 vLLM 本地运行；定位时统一温度为0。CoSIL 最多搜索十轮；OrcaLoca、LocAgent 按默认设置最多重试三次、最长十五分钟。论文比较的是**相同基础模型下各自完整定位流程**，没有把所有方法强制限制为相同 token 或调用次数。

RQ3使用 RQ1 的 Qwen32B 定位结果，把前3个位置交给相同的 Agentless-1.5 修复和验证阶段。修复模型分别为 Qwen32B 与 GPT-4o-2024-08-06，每例生成十个候选补丁：一个贪心生成，九个温度0.8采样；再用模型选择的回归测试及生成的复现测试进行验证和选择。

RQ4换用 DeepSeek-v3-0324、GPT-4o-2024-08-06，在 Lite、Verified 各抽取50例，记录定位表现、token消耗与费用。这些是论文实验时的模型和价格，不是今天的报价。

### 怎样读这些指标

**Top-N** 问的是：前 N 个候选中，是否至少有一个目标位置？将命中的 issue 数除以总数，就得到 Top-1、Top-3、Top-5 命中率。即使一个 issue 需要改多个函数，只找中一个也可计为命中，因此它更接近“首批建议是否有用”，而不是完整缺陷集合的召回率。

**Mean Reciprocal Rank（MRR，平均倒数排名）**关注第一个正确候选有多靠前：第一位得1，第二位得1/2，第三位得1/3，没有命中得0，再对任务取平均。**Mean Average Precision（MAP，平均精度均值）**在每个正确候选的位置计算该截断点的精度，将这些精度相加，除以该任务的全部标准目标数，未命中的目标贡献0，再跨任务取平均，因此还考虑多个正确位置的排列。

例如，一个教学用列表依次是“错、对、错、对”，且目标有两个：Top-1失败，Top-3成功；倒数排名为1/2；两个命中位置的精度分别为1/2和2/4，所以该任务的平均精度为1/2。这说明命中率、首个正确位置和完整排序质量并不是同一个指标。

**Empty Rate（空结果率）**统计没有任何候选输出的任务比例。它反映流程交付失败，不等于所有输出非空的任务都定位正确。修复阶段的 **Applied%** 是补丁能成功应用且不出现语法错误的比例，**Resolved%** 是实际解决问题的比例。

## RQ1：函数定位是否真的更准

答案是肯定的：在表II、III的六个“模型规模×数据集”组合中，CoSIL 的函数 Top-1 都最好。差距随模型和数据集变化，不是一个固定增益。

下面把原表的函数 Top-1 转成百分数；同一行固定数据集和基础模型，变化的是定位流程。

| 数据集 / 模型 | Agentless | OrcaLoca | LocAgent | CoSIL |
|---|---:|---:|---:|---:|
| Lite / 7B | 17.3 | 15.7 | 4.7 | **21.3** |
| Lite / 14B | 18.7 | 17.0 | 9.0 | **20.3** |
| Lite / 32B | 24.7 | 21.7 | 10.3 | **43.3** |
| Verified / 7B | 25.6 | 20.6 | 12.0 | **28.2** |
| Verified / 14B | 26.0 | 23.2 | 17.6 | **43.0** |
| Verified / 32B | 32.6 | 25.4 | 25.0 | **44.6** |

32B上的提升最容易解释：Lite 相对最强基线提高18.6个百分点，Verified提高12.0个百分点。14B则很有异质性：在 Lite 上20.3%还略低于 CoSIL 的7B结果21.3%，但在 Verified 上已经达到43.0%。增大模型并不保证每个子集都平滑提升。

### 文件第一名并不是全面领先

文件层的结果很有解释力。32B时，LocAgent 的文件 Top-1 在 Lite、Verified 分别为64.7%、68.6%，高于 CoSIL 的61.3%、64.0%。但 CoSIL 的文件 Top-5 达到83.7%、86.4%，高于 LocAgent 的74.0%、81.6%。7B Lite 上也是 OrcaLoca 的文件第一名更准。

### 少了多少空结果

32B Lite 的空结果率分别是 Agentless 2.0%、OrcaLoca 2.67%、LocAgent 13.67%、CoSIL 0%；Verified 分别是3.0%、4.0%、12.8%、1.0%。7B和14B时，CoSIL 同样很少输出空列表。

作者结合轨迹观察，将一部分改善归于工具错误减少、最终结果更易解析。论文没有把所有错误类型的计数展开成完整表，但这些空结果率说明稳定交付确实是不同流程之间的重要差异。

摘要的“平均提升96.04%”是18个函数 Top-1 相对增幅的算术平均，即两个数据集、三个模型规模、三个基线的组合。它不是提升96个百分点，也不是32B相对最强对手几乎翻倍。上面的绝对数更能帮助判断实际收益。

**这一问应记住：CoSIL 最强的证据在函数级定位；文件层拓宽覆盖、函数层读取与排序、交付可靠性一起形成了端到端优势。**

这一问使用各50例的 Lite mini、Verified mini，而非完整300/500例。它一方面检查是否依赖 Qwen，另一方面记录实际token与调用费用。

## 论文还追问了一个重要问题：修复成功能当定位指标吗

作者在讨论部分补做了两组比较，不能把它们略过，因为它们限制了“定位好了，所以修复一定更好”的直觉。

### 表VIII：补丁改到了哪里，混合了定位与生成能力

有些工作不直接评价定位列表，而是看最终补丁修改的文件、函数是否与标准补丁匹配。这种 **file/function match rate（文件/函数修改位置匹配率）**已经受生成器与补丁选择流程影响。

作者使用 GPT-4o-0513 做 CoSIL定位，接 Agentless-1.5生成四组、每组十个候选补丁，再选择结果，称为 **CoSIL@40**。它与前面十补丁设置的 CoSIL@10不只是预算不同，定位模型也变了。

表VIII给出多种完整修复系统。挑几个最能解释问题的比较：

| 完整流程 | 函数修改匹配率 | 解决率 |
|---|---:|---:|
| OpenCSG Starship | 52.3% | **39.7%** |
| Agentless-1.5官方 | 51.7% | 32.0% |
| CoSIL@40 | 52.0% | 31.3% |
| Infant-Coder | **54.7%** | 30.0% |
| 作者复现Agentless-1.5 | 48.0% | 28.3% |

Infant-Coder的函数修改匹配率更高，解决率却比OpenCSG低9.7个百分点。定位候选相同，也可能因为生成器没选对、补丁写错或验证器选错，导致最终修改位置变化。作者因此主张，跨不同修复流程时，用最终补丁位置反推定位能力会混合多个因素。

在同一@10后半段流程中，OrcaLoca、LocAgent、Agentless、CoSIL的函数修改匹配率则从41.3%、44.7%、45.0%到48.3%，解决率也从19.7%、21.0%、22.3%到25.7%。保持后半段一致时，两种指标的关系更清楚。

### 表IX：定位明显更好，仍可能少修好几个问题

作者进一步把官方Agentless、自己复现的Agentless和CoSIL@40拆开比较。

- 官方Agentless的函数 Top-1 / Top-5为25.0% / 49.0%。
- 复现Agentless为25.0% / 43.7%。
- CoSIL@40为48.0% / 64.0%。

CoSIL函数首位命中明显更强，Top-5也比官方Agentless高15个百分点；但最终解决率为31.3%，略低于官方的32.0%。它高于作者复现版本报告的28.3%。

表IX还展示了四组补丁各自的解题数：官方Agentless为81、82、85、78；复现版本为72、72、70、70；CoSIL为76、75、77、77，分母均为300。这个拆分表明，定位效果之外，采样与补丁生成/选择仍带来波动。最终“All”是整套候选选择后的报告结果，不应把四组成功数简单相加。

作者提出温度0.8采样的随机性可能解释部分差异。这是合理解释，论文没有通过重复整套运行把各因素的方差进一步分解。

## 复现与证据审查：把需要保留的边界一次讲清

前面的结果支持 CoSIL 作为完整定位流程的价值。进一步使用这些结果设计研究或复现时，下面六点会改变解释。

### 1. 对比控制了模型，没有控制所有资源

主实验用相同基础模型和定位温度，但方法的工具次数、源码暴露量、失败重试、构图代价与提示长度不同。迭代搜索的消融同时移除了逐步读实现的能力，因而它说明该环节在完整系统中很有帮助；要拆出“图关系本身”相对“多读正文”的贡献，还需额外对照。

同理，反思式对齐混合了格式修正、一次额外查询及候选重排；裁剪同时改变保留内容和搜索方向。当前消融没有把这些处理逐一分离，也未做完整组件交互实验。费用表为部署取舍提供依据，但不是严格相等预算下的机制实验。

### 2. 论文、旧实现、新实现的裁剪不是同一件事

这是本次对公开工件作有限行级核对后发现的关键差别。以下代码观察独立于论文实验报告，没有运行工件，也没有据此重算结果。

**论文描述：**相关则保留正文并扩展邻居，不相关则排除正文并停止这个方向。附录算法2从 `visibleNodes` 移除被裁剪节点。不过，正文和提示词规定True表示接受，算法2的 `pruningFlag=True` 却进入删除分支，布尔命名不一致。讲方法时以“接受/拒绝”的语义理解，不能直接照抄这个极性。

**论文所链旧仓库：**README现在明确将自身标为旧实现。其拒绝分支虽然加入“该函数不相关，不要继续检查其调用函数”的提示，**仍将读取到的函数正文加入主对话**。这一行为已存在于2025-09-19的提交，见[固定版本AFL.py第610–628行](https://github.com/ZJU-CTAG/CoSIL/blob/8e82b3f261db30c2d74095a70127b8079fe023c3/afl/fl/AFL.py#L610-L628)。因此，这段实现更接近限制后续方向的提示，而不是已经从主上下文删除正文。

**当前新仓库：**截至核验，HEAD为2026-05-31的 `0568e423735b399d5b089996961fea9ae142e4c7`。其中裁剪者先自行检索最多三轮再裁定；拒绝时用一条拒绝提示替换工具结果正文，最终汇总又跳过这些拒绝提示。见[裁剪与替换逻辑](https://github.com/ZhonghaoJiang/CoSIL/blob/0568e423735b399d5b089996961fea9ae142e4c7/CoSIL/fl/CoSIL.py#L154-L230)、[汇总逻辑](https://github.com/ZhonghaoJiang/CoSIL/blob/0568e423735b399d5b089996961fea9ae142e4c7/CoSIL/fl/CoSIL.py#L284-L315)。它已增加新的检索判断与工具调用行为，不能拿今天代码的成本直接解释2025年的实验。

两版被检查的调度路径都没有展示一个按拒绝集合硬性禁止后续读取的全局机制；原始源码仍可通过名称读取。**源码仍在、理论上可重新取回，与系统明确保存拒绝状态并在证据不足时自动恢复，是两种能力。** 当前检查未发现后者的完整策略，也不应把论文概括成“永久删除后永远无法再访问”。

这一差别要求复现首先固定论文版本、仓库commit和具体入口，再确认“裁剪”实际改变的是正文、汇总、搜索指令，还是几项一起改变。它尚不足以确定论文每个表格具体对应哪个可执行版本。

### 3. 指标的含义也需要对齐到实现

Top-N只要求至少一个目标命中，不衡量找齐全部修改点。这种参考位置匹配评价也可能忽略某些同样有效、但修改位置不同的替代修复；论文未充分交代从原始修复到定位目标的完整构建规则。

此外，公开评估脚本的函数匹配路径会从“文件::函数”提取函数/类名再比较，未在这一步保留完整文件身份；跨文件同名函数可能因此被合并判断。见[固定版本评估脚本](https://github.com/ZhonghaoJiang/CoSIL/blob/0568e423735b399d5b089996961fea9ae142e4c7/evaluation/FLEvalNew.py#L46-L170)。这条实现观察提醒后续复现明确匹配规则，不直接证明论文表中有多少样本受影响。缺失输出仍计入分母。

### 4. 个别表格存在内部不一致

为了不把排版或报告差异误写成发现，本笔记采用明确可对照的数值，并保留以下疑点：

- GPT-4o Lite mini 的 LocAgent函数Top-1，表VII写0.44，而完整表X写0.10；0.44在表X对应Top-5。两表冲突，因此不据主表该值作结论。
- 同一设置下CoSIL的文件Top-5，表VII为0.90、表X为0.92。
- 表IX复现Agentless“All”写86/300，解决率写28.3%；两者算术上不一致。上文将28.3%标为论文报告值，不自行猜测哪个数字应被更正。
- 表IV完整版本Top-1为0.433，表V十轮为0.430。它们来自不同表的实验，原文未详细解释差别。

这些问题不改变主要函数定位结果的方向，却影响精确复现与汇总，值得在使用数据时记下来。

### 5. 不确定性与外推范围

主结果没有给出重复运行的置信区间或显著性检验。定位温度为0也不等于所有工具、服务和基础设施行为完全确定。小规模泛化集每组50例，少数实例就能改变几个百分点；尤其60%对58%的差距，应与额外费用一起审慎使用。

所有主数据都来自Python仓库，不能直接代表多语言安全漏洞定位、代码审查或缺乏详细issue描述的任务。模型发布晚于基准，GitHub又是常见训练来源，作者承认可能存在训练数据泄漏；相同模型对比改善了相对比较的可比性，但不消除绝对性能中的污染。

### 6. 图与相关性判断本身也会出错

函数图由模型根据源码与imports推断，论文没有独立量化图边准确率。相关性裁剪也可能错拒必要证据，且会连带影响后续可探索范围。作者提供了裁剪有利的案例和聚合消融，但没有完整报告误裁目标比例、拒绝后的恢复成功率或长期搜索状态。它为上下文管理提供了有效系统设计，尚未给出可恢复裁剪的充分验证。

## 读完真正应该记住什么

作者用实验支持了四个具体结论：

1. **分阶段图搜索在这组任务上提高了函数定位质量。** 六个模型与数据集组合的Top-1领先，32B上相对最强基线提高18.6和12.0个百分点。
2. **迭代读取实现是完整系统中的主要贡献。** 去掉它下降11.3个百分点，去裁剪下降2.0个百分点；不能把系统总收益都归给裁剪。
3. **稳定接口也是定位能力的一部分。** 少量格式错误就可能让已得到的候选变成空结果，短上下文复核改善了流程交付。
4. **统一后半段时，更好的定位能帮助修复。** 四种数据集与修复模型组合的解决率都提高；跨不同修复流程时，最终补丁位置与解决率又会混合生成和验证能力。

尚未被这组证据单独确定的是：严格同token条件下的纯图结构增益、独立的正文删除效应、最优搜索预算、误裁后的恢复能力，以及Python issue之外的泛化。

最值得带走的设计思想是：**先让搜索范围覆盖关键位置，再让逐步阅读把名字变成证据；对搜索路径、当前上下文和最终输出分别负责。** 不是所有任务都需要昂贵的代理，便宜的层级提示在高信息量问题上仍很有竞争力。

## 对当前研究的启发：从“判断后丢掉”走向“有理由地再读”

最新研究记录中的主线，已经从单纯增加仓库上下文，转向区分“目标从未被曝光”“曝光后被筛掉”“仍保留却没被选中”，并探索有限预算下的可恢复证据管理。CoSIL是这一方向必须认真区分的近邻：它已经把相关性判断放进探索过程，且影响后续搜索，因此“边搜索边分类、再裁剪”本身不足以成为新的核心贡献。

### 把三个损失位置分开，先知道要救哪一种失败

可以沿一次轨迹保留三层集合：搜索真正读到过的实体、管理后仍保留的证据、最终输出的位置。对同一个目标，依次判断：

- 是否根本没进入曝光集合？这主要要求改进入口或扩展策略。
- 是否读过但随后被剔除？这对应裁剪失误，恢复策略可能直接帮助。
- 是否仍在最终可用证据中却没有选中？这要求改善证据组织、判定或输出，而不是再多检索一遍。

这些标签可以用于离线分析；运行时系统不能直接得到标准答案。对CoSIL也应分别测，因为它的裁剪会改变后续探索，只有最终准确率很难定位收益或损失发生在哪一层。

### 将论文未展开的“可恢复”变成具体操作，而不是口号

一个可执行的研究设计是：被暂时排除的正文不常驻工作上下文，但保留实体身份、来源、判定依据、未解决的问题和可重新读取的入口。当后续出现机制证据缺口、不同候选解释冲突或必需调用链中断时，允许一次受预算约束的恢复读取。

这属于待验证设计，不是本文已实现的能力。它与“源码文件仍存在”相比，多了明确的状态、触发条件和恢复动作。也要区分三种运行时状态：尚未读过、需要补证、读过后暂时认为不关键。把所有未知内容一律贴上相同标签，会让模型失去选择下一步证据的依据。

### 先做同曝光集合的配对比较，再做完整代理比较

最清楚的第一层实验可以固定已经获得的源码曝光、任务描述、基础模型和最终读出器，比较：

1. 原始证据组织与读出；
2. 一次性删除；
3. 保留可检索身份的压缩表示，并允许有触发条件的有限回读。

这样先问“在已获得相同材料时，管理方式是否改善决策”。随后再放开搜索，使恢复行为反过来影响下一步探索，测完整系统效果。两个问题都重要，但适合分层回答。

若要解释回读机制，可以把相同额度的额外调用分配给随机回读或无触发的继续阅读，避免把单纯增加资源算成策略优势。端到端比较则应报告真实调用数、输入/输出token、源码读取、构图或索引成本、耗时及失败，而不是只报一个准确率。严格固定所有预算与展示实际成本收益是两类互补实验，不必混成一个设置。

### 比较对象必须对准任务信息和实现版本

CoSIL使用自然语言issue，其中常有文件名、报错与行为线索；当前以 Common Weakness Enumeration（CWE，通用弱点分类）为主要提示的漏洞定位，信息条件明显不同。Python SWE-bench与多语言漏洞任务的实体、目标和评分也不同，结果不能直接搬用。

作为基线时，应固定其实际可执行版本，并明确保留哪些组件：文件导入扩展、函数迭代、裁剪、反思式对齐。尤其要记录裁剪是否真的删正文、是否只改变汇总，以及额外检索是否计入成本。这个版本核对能避免把旧实现的方向提示、新实现的正文过滤与新研究的恢复策略混为一谈。

最终值得推进的问题是：**暂时判为不关键的证据，能否以低成本保留可恢复性，并在真正出现证据缺口时被可靠地重新利用？** CoSIL提供了搜索中管理上下文的扎实起点，也留下了这个可以被具体实验回答的缺口。
