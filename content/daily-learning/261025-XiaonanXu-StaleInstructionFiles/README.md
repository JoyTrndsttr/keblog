## 先把场景说清楚：这里比较的不是两套代理

一个仓库原来用 `print()` 输出进度，于是维护者在 `AGENTS.md` 或 `CLAUDE.md` 里写了“使用 `print()`”。后来代码已经全面迁移到 `logging`，但这句话忘了改。现在编码代理接到一个新增功能任务，同时看到两份互相冲突的证据：

- **说明文件**仍命令它用 `print()`；
- **当前代码**每个相似位置都在用 `logging`。

人通常会把当前代码理解为项目已经迁移后的现实，并把说明文件视为过期。代理却可能反过来：它把说明文件当成高优先级命令，把当前代码当成需要被纠正的对象。最严重时，它不只让新代码偏离项目，还会重写本来能通过测试的旧代码。

这篇论文没有提出一个复杂的新代理。它只比较同一代理在两个条件下完成同一任务：

| 条件 | 用户级说明文件里多了什么 | 代理应如何处理冲突 |
|---|---|---|
| 对照组 | 什么也不加 | 由现有代理自行判断 |
| 干预组 | 一句“文档与现有代码冲突时，以现有代码惯例为准，并在最终回复中指出冲突” | 把“代码优先”提升为同层级指令 |

研究者在 40 个小型 Python 项目上测试 Claude Code 与 Codex CLI；每个项目、每个代理、每个条件重复两次，共 320 次运行。核心问题不是“哪个代理更强”，而是：**当说明文件与代码冲突时，输入在上下文中的权威层级是否会系统性改变代理选择；一句更高层的优先级规则能否逆转它。**

## 为什么过期文档会变成“强命令”

论文把原因拆成三步。

第一，说明文件常用命令句描述项目现状，例如“金额使用浮点数”“错误时返回 `None`”。写下时它可能是事实；项目迁移后，事实已经失效，但命令语气不会自动消失。

第二，代理框架把 `AGENTS.md` 或 `CLAUDE.md` 的内容放入用户指令区域，而代码只有在代理读文件时才作为工具输出进入上下文。两者不是同一权限层级的普通证据。

第三，模型本来就被训练为让指令优先于工具输出。这是必要的安全设计：网页、日志或代码文件中的“忽略此前指令”不应劫持代理。问题在于，过期说明也借用了同一条安全规则。它虽然描述错了，却仍携带“指令”的权威。

所以这不是模型没看见冲突。Claude Code 在无修复句的 80 次运行中，有 79 次在最终回复里明确指出说明文件和代码不一致，但仍有 86.2% 的具体选择服从过期文件。它看见了证据，却把错误的一方当成应被服从的权威。

## 实验是怎样构造的

### 40 个项目不是从真实仓库随机抽样

研究者构造了 40 个小型 Python 项目。每个项目有 3–8 个能工作的模块、通过的原始测试、一个代理说明文件和一个新增功能请求。完成任务要做 4 或 5 个惯例选择。

研究共设计 16 类冲突，包括输出方式、路径处理、字符串格式、导入方式、异常信号、配置表示、金额表示和枚举表示等。每类冲突在 11 或 12 个项目出现，而且两个方向都出现：有些项目的代码用 A、说明要求 B；另一些反过来。这样可以抵消模型天然偏爱某种写法的影响。

功能请求只描述需要实现的行为，不透露应采用哪种惯例。说明文件在所有条件下都保持同一条过期规则，唯一变化是用户级文件里有没有那句优先级声明。

### 两个代理与四个运行条件

论文使用 Claude Code 2.1.302 + Claude Sonnet 5.5，以及 Codex CLI 0.163.0 + GPT-6 Sol。每次从项目的新副本开始，无人值守运行，自动批准文件编辑。40 个项目 × 2 个代理 × 2 个句子条件 × 2 次重复，得到 320 次有效运行。

这里有一个重要边界：模型与代理版本非常新，结果只对应论文记录的版本和提示结构。它不能自动外推到所有编码代理，也不能保证未来版本仍有相同比例。

### 评价的不只是测试是否通过

研究者用脚本检查新代码中的每一个惯例选择，把它分为：匹配说明文件、匹配现有代码、两者都不匹配。

另一个盲化的 Claude Opus 5.5 判断器只读取最终回复，不知道条件、代理和代码变更，用于记录代理有没有明确说出冲突。研究还定义“大规模重写”：如果运行删除了原有 Python 文件中的至少 20 行，就算重写旧代码。

最后，研究者恢复项目原始测试，再与新增功能的隐藏测试一起运行。这一步很关键：代理不能靠修改测试来让结果看起来成功。

## 六个核心结果

### 1. 没有修复句时，过期文件压倒当前代码

无修复句时，720 个具体选择中有 649 个（90.1%）匹配过期说明文件，只有 4.2% 匹配当前代码。Claude Code 的服从文件比例为 86.4%，Codex CLI 为 93.9%。16 类冲突中，有 14 类在两个代理上都由过期文件占上风。

这不是单一惯例偏好造成的。每类冲突都双向安排，如果模型只是偏爱 `logging` 或 `pathlib`，它会在一半项目里看似服从文件、另一半服从代码；结果却系统性地随说明文件方向移动。

### 2. “发现冲突”不等于“正确处理冲突”

Claude Code 在 79/80 次对照运行中说出了冲突，却仍然按过期说明实现。Figure 1 给出直观例子：代理在回复中承认原有模块都使用 logging、pathlib、`str.format()` 和绝对导入，同时仍让新功能遵循 CLAUDE.md 中相反的旧规则。

这区分了两种失败：

- **检索失败**：代理没有读到或没有注意到现有代码惯例；
- **裁决失败**：代理读到了冲突，但错误地判断哪一方应优先。

本文的主要现象属于后者。因此只增加更多相似代码上下文未必能修复；若权威排序不变，更多证据仍可能被解释为“更多需要改造的旧代码”。

### 3. 一句话把选择从 4.2% 翻到 91.4%

加入优先级句后，匹配当前代码的比例从 4.2% 升至 91.4%，增加 87.2 个百分点；按项目重采样得到的 95% 区间为 83.6–90.9 个百分点。

Claude Code 从 7.5% 升至 94.4%，Codex CLI 从 0.8% 升至 88.3%。两个代理在干预组的全部 160 次运行中都报告了冲突。

这一结果最有意思的地方不是句子措辞巧妙，而是它改变了冲突双方的层级关系：用户级说明里的“代码优先”与项目级旧规则同属指令，模型不再需要用低权威的工具输出去对抗高权威指令。

### 4. Codex 会把能工作的旧代码改坏

无修复句时，Codex CLI 在 80 次运行中的 20 次重写了原有代码，涉及 40 个项目中的 12 个。这些运行删除原有代码的中位数为 198 行、涉及 9 个文件；恢复原始测试后，其中 17 次失败。

Figure 7 展示一个 kanban 项目：AGENTS.md 要求字符串常量，现有代码用 `Column` 枚举。代理不是让新功能适应枚举，而是把现有枚举替换成字符串，导致原始测试无法再导入 `Column`。

有修复句时，Codex 的重写次数降为 0。Claude Code 在两个条件下都没有达到论文定义的“大规模重写”阈值，所以这一风险不能泛化为所有代理都会重构旧代码。

### 5. 测试通过率从 89.4% 升至 100%

无修复句时，总体测试通过率为 89.4%；加入句子后 160/160 全部通过。差异来自 Codex CLI：它从 78.8% 升到 100%，且所有失败都对应旧代码重写。Claude Code 的测试本来就全过，但它产生的新代码仍经常违反项目当前惯例。

因此测试通过不是充分指标。如果只看隐藏功能测试或最终“绿色”，会漏掉新旧代码风格分裂；反过来，Codex 的结果又说明这种不一致有时会升级成真实回归。

### 6. 修复没有明显增加成本

有修复句的运行使用的工具调用和时间还略少。论文没有把这解释为普遍效率提升，因为项目很小、每条件仅两次重复；但至少没有看到“先检查冲突并遵循代码”必须付出额外运行成本。

## 证据审查：哪些结论扎实，哪些仍是推断

### 较扎实的部分

1. **处理变量很清楚。**同一项目、任务、代理和过期文件只差一句用户级规则，适合解释选择翻转。
2. **冲突双向构造。**16 类惯例两边都做，减少模型固有写法偏好混淆。
3. **评价维度互补。**选择级、回复级、代码重写和测试回归同时记录，避免单指标讲故事。
4. **项目级重采样。**主要区间以 40 个项目为单位 bootstrap 2,000 次，没有把同项目中的多个选择伪装成独立样本。
5. **材料可复查。**论文发布项目、任务、运行记录和分析脚本，320 次运行也全部有效，仅一次沙箱失败按预先规则重跑。

### 必须降调的部分

1. **项目是合成的小型 Python 项目。**它们刻意让代码内部一致、说明文件确定错误；真实仓库可能同时存在迁移中的两套惯例，代码本身未必是唯一真值。
2. **只测两个代理和单一新版本。**强结果说明机制值得重视，不代表 90.1% 是行业稳定常数。
3. **一句话包含两个动作。**它既规定代码优先，又要求最终回复报告冲突。实验不能完全分离究竟哪一半促成行为改变；更细消融尚未做。
4. **“代码优先”也可能被滥用。**安全、合规、API 契约或待迁移规范有时应压过旧代码。论文针对的是文档确定过期的场景，不应把句子扩展成无条件忽略规范。
5. **机制解释与行为结果要区分。**实验直接证明优先级句能翻转行为；“因为模型训练的指令层级”与观察一致，也有系统结构证据，但论文没有对消息角色做完整随机化实验。
6. **冲突判断器本身是模型。**它被盲化并给出证据句，降低偏差，却没有报告大规模人工复核或判断器一致性。好在主要选择和测试结果不依赖这个判断器。
7. **重写阈值是操作化定义。**删除至少 20 行能抓住明显改造，但会漏掉小而危险的修改，也可能把合理重构算入；本文案例中 17/20 的旧测试失败为风险提供了更硬证据。

## 对当前 P/I 研究最直接的启发

当前研究已经看到：plausible context（P）平均比 irrelevant context（I）稍好，但效应集中在少数案例；P 有时减少漏掉的目标节点，同时增加额外定位；而且“不含缺陷”不等于“没有定位价值”。本文提供了一个更具体的解释轴：**上下文的作用不只取决于内容是否相关，还取决于它以什么权威身份进入，以及模型如何裁决冲突。**

### 1. 在 P/I 之外增加“权威层级”因子

同一段 plausible 代码可以作为普通检索块、工具输出摘要、用户声明，或项目说明文件出现。语义相同，权威不同。下一轮小规模实验可在固定 case 上做 2×2：

- 内容：P vs 匹配的 I；
- 注入位置：普通证据区 vs 明确的任务指令区。

如果只有指令区显著改变输出，说明观察到的是服从/阈值移动，不是代码证据利用；如果 P 在两个位置都优于 I，才更支持语义证据机制。

### 2. 把“有没有读到”与“如何裁决”分开标注

对每个 case 增加过程标签：模型是否引用了 P/I 中的节点、是否指出它与目标代码冲突、最终又跟随哪一方。本文的 Claude 例子说明“提到冲突”不能当利用成功。建议至少区分：未注意、注意且采纳、注意但拒绝、注意后扩大预测集合。

### 3. 设计冲突方向对称的配对样本

本文让每种惯例两个方向都出现，这是当前实验可以直接借用的控制。对于 repository context，可构造 A/B 两类配对：一类 P 支持 GT 而主文件表面线索支持非 GT；另一类把同样关系反转。若模型总追随被标为“相关”的上下文，不论其真实方向，就暴露的是标签权威效应。

### 4. 给 oracle 规则加例外，而不是无条件“P 优先”

HY security specification test 的复核已经说明：一段不含缺陷的代码仍可能提供调用契约或定位价值。因此不要把“含 GT 的上下文优先”写成硬规则。更稳妥的干预是：当文档/检索与现有调用链冲突时，先列出冲突及各自证据，再根据可执行测试、数据流或调用关系裁决；没有可验证依据时保留不确定性。

### 5. 结果继续拆成漏报与过度定位

这篇论文同时报告惯例选择、旧代码重写和测试结果，避免测试通过率掩盖风格偏离。当前实验也应继续并列报告 GT recall、extra predictions、集合大小与 F1。若高权威 P 只是让模型更愿意多报，它可能提高 recall，却不代表定位证据更准确。

### 6. 做一句话干预，但把它当机制探针

可尝试加入一句中性裁决规则：“仓库证据互相矛盾时，不按标签或呈现位置自动排序；先依据调用关系、数据流和测试验证，再说明冲突。”若这句话能显著缩小 P/I 差异或减少 extra predictions，它提示原效应部分来自上下文权威，而非内容本身。它首先是机制探针，不应未经真实仓库验证就当部署策略。

## 一句话抓住全文

这篇论文最重要的不是让所有项目都“代码永远优先”，而是揭示：

> **编码代理面对冲突证据时，会按输入的权威层级裁决，而不只是按证据与当前仓库事实的一致性裁决。**

在本文 40 个确定“说明已过期、代码仍一致”的小型 Python 项目上，两种代理无干预时 90.1% 的选择跟随过期文件；把“冲突时遵循现有代码”提升为用户级指令后，91.4% 的选择转而跟随代码，Codex 的旧代码重写从 20 次降到 0，全部测试通过。

它把当前研究中“上下文是否有帮助”的问题推进了一步：相关性、覆盖率和 token 数量之外，还要控制**上下文被赋予了多大权威，以及模型是否把证据冲突误处理成命令服从问题**。
