## 一、报错描述越长，就越需要一个会反复搜索的 Agent 吗？

用户报告“某个语言变体明明能回退到基础语言，系统检查却报错”。一个定位智能体很容易先找到语言转换函数，然后顺着调用关系反复读下去。真正需要修改的地方，却可能是另一个文件中的检查规则。

SweRank 问了一个很直接的问题：如果专门教模型把这类错误描述映射到“实际被修改的函数”，能否用检索和排序完成定位，省去多轮自主搜索？

传统代码检索擅长“找一个完成某功能的函数”，但真实 issue 往往写的是失败现象、日志和期望行为。论文引用的平均长度对比是 SWE-bench issue 约 460 token，而 CodeSearchNet 的功能查询约 12 token。差异同时涉及长度和任务意图：关键词与功能相似的函数，未必就是修复位置。

本文的办法是收集大量真实 issue 与修改函数的配对，训练两类模型：小模型负责从整个仓库召回候选，大模型负责在候选之间排序。主要创新落在**定位专用数据、困难负样本及不完整排序监督的训练方式**，总体架构仍是成熟的“先检索、再重排”。

## 二、作者为什么会从排序角度切入？

论文合作机构为 UIUC、Salesforce Research 与 KAIST AI。Revanth Gangi Reddy 的[个人主页](https://gangiswag.github.io/)列出其在 UIUC 随 Heng Ji 从事研究，兴趣包括智能体搜索、嵌入模型、重排和检索增强生成；本文工作在其 Salesforce 实习期间完成。

这条研究路线有直接积累：Revanth 与 Tarun Suresh 共同参与 CoRNStack，它用高质量对比数据训练代码检索与重排；Revanth 与 JaeHyeok Doo 参与 FIRST，研究利用首个候选标识符的输出信息进行高效列表重排。SweRank 将这些经验迁移到 issue-to-code，而非从头提出一个图搜索智能体。

Tarun 的[现主页](https://tarsur909.github.io/)已写为 Stanford 计算机博士生，不能拿当前身份覆盖论文署名时的 UIUC 归属。JaeHyeok 的本文归属为 KAIST，本文与 FIRST 的共同作者关系可由论文及 Revanth 的发表列表核对。原文没有指定通讯作者，本文不凭末位署名推定。

阅读价值在于，它为图导航和多智能体定位提供了一个很强的低交互基线：如果专门训练过的排序器已能找到大多数目标，多轮探索的价值就应体现在它解决了哪些排序器仍失败的任务。

## 三、先跟着一个真实例子走完方法

附录图 10 的 Django 示例正是开头的语言检查问题。LocAgent 的第一名是 `django/utils/translation/trans_real.py` 中的 `get_supported_language_variant`；SweRank 的第一名是 `django/core/checks/translation.py` 中的 `check_language_settings_consistent`。前者处理语言变体，后者直接检查配置并决定是否返回 E004。

模型运行时并不预先知道这两个位置。它得到 issue 文本及修复前仓库，按以下流程定位：

1. 将仓库内函数整理成候选代码片段，提前编码为向量。
2. 将 issue 编码为同一空间中的向量，以余弦相似度检索候选。
3. 重排模型同时阅读 issue 与一组带编号的候选代码，输出由高到低的编号序列。
4. 将排序后的函数映射到模块或文件。一个文件的得分取其中最高分函数的得分。

第三步为什么重要？单独比较 issue 与每个函数，只能判断各自像不像。把多个候选放到一起，模型可以比较“负责语言转换”与“负责抛出这个检查错误”哪个更像实际修改点。

这里没有强化学习，也没有多个角色的相互查证。检索器使用对比学习，重排器使用监督微调。**原始 SweRank 与后续 SweRank+ 是不同工作**，不能把后者的迭代搜索与记忆结构补进本篇方法。

## 四、SweLoc 数据：从修复记录里学“哪里被改过”

### 4.1 从仓库到训练样本

图 2 的流水线从热门 PyPI 包关联的 GitHub 仓库开始。作者检查前 11,000 个包，要求仓库至少 80% 为 Python，排除 SWE-bench 与 LocBench 已有仓库，再按源码重叠去重，留下 3,387 个仓库。

随后筛选满足两项要求的 pull request：关联并解决一个 issue，且修改测试文件。对于每个 PR，保存 issue 描述和 PR base commit 的代码快照，得到 67,341 个初始“PR、代码库”配对。测试变更是筛选信号；论文此处并未逐例证明新增测试在旧版失败、修复后通过。

一条 PR 可能改多个函数。作者将每个被修改函数各自展开为一个训练正例，同仓库未修改函数作为负例候选。因此 **67,341 是初始 PR 数，不是最终函数级训练样本数**。

图 3 进一步说明样本并非全是单点修改：74.0% 的 issue 只改一个文件，62.1% 只改一个模块，51.2% 只改一个函数。函数粒度下，18.0% 改两个、8.8% 改三个、5.5% 改四个、16.5% 超过四个。issue 长度均值为 382.56 token，分布有明显长尾。

### 4.2 为什么还要过滤“已有正确补丁”的数据？

真实 PR 可能同时包含清理、重构或描述不充分的修改。一个函数确实被改过，不保证仅凭 issue 文本就能合理定位到它。

作者先用已有 CodeRankEmbed 给所有函数排序，只保留正例排在前 20 的训练配对。这叫一致性过滤：要求问题与修改位置至少存在可被已有检索器识别的关联。

接着，从同仓库未修改函数中取最相似的 15 个，构造困难负样本。相比随机抽一段完全无关代码，这些负例更能迫使模型区分“看起来相关”与“实际被改”。大检索器的具体训练配置使用 7 个困难负例，小检索器使用 15 个，不能把数据挖掘数量与所有训练批配置混成一个数字。

这两步对应两个不同问题：过滤控制正例信号，困难负样本提高区分难度。它们都发生在训练数据构建阶段，不是部署时的 CPI 分类。

## 五、两个模型分别学什么？

### 5.1 检索器：把真正修改点拉近，把近似候选推开

双编码器分别编码 issue 与代码，得到向量。训练希望 issue 与对应修改函数的相似度高于批内其他函数和困难负例。

式 1 是 InfoNCE 对比损失，可写成：

`L = -log[exp(s(issue, positive)) / Σcandidate exp(s(issue, candidate))]`

分子是正例的相似度经指数变换后的值，分母包含正例与所有竞争项。正例得分相对提高，比例增大，损失下降；一个困难负例得分过高，分母增大，损失随之增大。训练因此给模型一个明确压力：不要只因共享几个语义特征就把错误函数排到前面。

小检索器从 137M 参数 CodeRankEmbed 初始化，大检索器从 7B 的 GTE-Qwen2-7B-Instruct 初始化。附录 A 给出不同 query prefix，说明部署时前缀也是模型输入协议的一部分。小模型训练两轮，大模型一轮；批大小均为 64，训练分别使用 8 张 GH200。这些是训练资源，不能当作推理部署的最低配置。

### 5.2 重排器：没有完整排名，只教它先选对第一名

普通列表重排训练需要完整目标顺序，比如 `3 > 1 > 4 > 2`。SweLoc 只知道哪个函数是修改目标，并不知道其余九个未改函数之间谁更相关。

作者因此只监督正例的编号。假设一个训练窗口有十个候选，真正修改点编号为 7，就提高模型首先生成 `7` 的概率，而不编造剩下九个候选的顺序。式 2 为：

`L = -log Pθ(正例编号 | issue, 带编号的候选集合)`

这种训练能成立，还依赖前置步骤：所有重排器先用通用文本列表排序数据训练过输出格式。定位微调不在正例编号后加入结束标记，以保留模型继续输出完整序列的能力。可以把它理解为，先学会“怎样写一张排序表”，再学“在定位任务中谁应该排第一”。

训练每组一个正例加随机抽取的九个困难负例，候选顺序打乱，防止模型依赖固定位置。每段代码最多 1,024 token，总输入上限按原文为 16,348；过长时截短 issue。7B 小重排器从 CodeRankLLM 初始化，32B 大重排器使用经过列表排序预训练的 Qwen2.5-32B-Instruct。微调使用一轮、全局批大小 128，以及 16 张 GH200。

### 5.3 “单轮检索框架”不等于一次大模型调用

论文将它称为 single-shot，是相对自主规划、调用工具、继续探索的 Agent 循环而言。官方推理脚本实际设置为 **top-100 候选、窗口 10、步长 5**，用多个重叠窗口完成排序。

这一区别关系到成本核算：完整一例的 reranking 可能累积多次模型输入，不能只记录某个窗口的 token，也不能把“只输出编号”理解成每例只生成一个 token。上述实现细节来自[固定版本运行脚本](https://github.com/SalesforceAIResearch/SweRank/blob/d3df5088485eda13c7eebfcd6250052fd276f1a3/script/run_rerank.sh)，而非自行推测。

## 六、实验究竟在比什么？先看样本与指标

主实验比较 Agent、未经定位微调的检索器、SweRank 检索器，以及在检索结果上运行的重排器。SWE-bench Lite 原本有 300 例，但作者排除没有修改既有函数的任务，保留 **274 例**。LocBench 为 **560 例**，包括 bug、功能请求、安全与性能问题。

关键指标 Acc@k 的定义很严格：**所有金标准位置都在前 k 个结果中，才算这一例成功。** 它并非只要命中一个目标就成功，也不等于逐函数召回率。

教学示例：目标函数为 A、B，前十名只有 A，Acc@10 为 0；前十名同时含 A、B，Acc@10 为 1，即使另外八个候选均非修改点。这个指标与精确率、F1 的惩罚方式明显不同。文件和模块层面则按函数最高分聚合，再以相应粒度计算。

表 1、2 的全部重排器固定使用 **大检索器** 的候选，因此可在相同召回入口上比较重排模型。Agent 对照包括 SWE-agent、OpenHands、MoatlessTools、LocAgent；LocBench 还包括 Agentless。不同方法的底层模型、训练数据及推理流程不同，这是一组系统能力比较，不是“固定同一模型后仅改变有无 Agent”的单变量实验。

## 七、主结果：排序器在这些数据上确实很强

### 7.1 SWE-bench Lite：大检索器已经超过 LocAgent 的函数前十覆盖

下面均为 274 例上的百分比，取自表 1：

| 方法 | 文件 Acc@1 | 函数 Acc@10 |
|---|---:|---:|
| SWE-agent，Claude-3.5 | 77.37 | 64.60 |
| LocAgent，Claude-3.5 | 77.74 | 77.37 |
| CodeRankEmbed，137M | 52.55 | 58.76 |
| SweRankEmbed，小 | 66.42 | 74.45 |
| SweRankEmbed，大 | 72.63 | 82.12 |
| 大检索器 + 7B SweRankLLM | 78.10 | 86.13 |
| 大检索器 + 32B SweRankLLM | 83.21 | 88.69 |

同为 137M，CodeRankEmbed 经定位训练后，函数 Acc@10 从 58.76% 到 74.45%，提高 15.69 个百分点。7B 检索器达到 82.12%，高于 Claude-3.5 LocAgent 的 77.37%；加入 32B 重排器进一步提高到 88.69%。

这也显示粒度之间的区别：大检索器的函数前十覆盖已很强，但文件第一名 72.63% 仍低于 LocAgent；重排将文件第一名提高到 83.21%。候选覆盖与最前面选谁，是两个不同瓶颈。

最强开源重排器也没有包揽所有指标。相同检索输入下，GPT-4.1 的文件 Acc@5 为 97.08%，高于 32B SweRankLLM 的 95.99%；函数 Acc@10 则为 87.96%，略低于 88.69%。

### 7.2 LocBench：收益并非只来自一种 bug 数据

表 2 的函数 Acc@10 / Acc@15 分别为：LocAgent Claude-3.5，59.29 / 60.71；大检索器，63.21 / 67.32；加 32B 重排器，71.25 / 76.25。

大重排器的文件 Acc@5 / Acc@10 为 86.61 / 89.82，LocAgent 为 83.39 / 86.07。GPT-4.1 的函数 Acc@10 为 71.61，仍略高于 SweRank 的 71.25，所以“总体很强”比“每格都最优”更准确。

图 4 将 LocBench 分为四类。大重排器在 bug、功能、性能、安全四组均有优势；从柱高估读，性能问题约从 LocAgent 的 0.37 到 0.54，安全问题约从 0.59 到 0.66。安全组的小检索器及大检索器单独运行并未都超过 LocAgent，优势主要在加入重排后体现。图中没有逐柱精确标值，这些只作为约数，不用来计算显著性。

**这一组实验的结论：专门训练的排序路线值得成为定位主基线，尤其不能用普通 BM25 或通用嵌入的弱结果代表整个检索范式。**

## 八、收益从哪里来？数据、负例、模型分别检查

### 8.1 数据越多不一定越好，筛选强度有折中

图 5a 固定小检索器，改变正例进入训练集的排名门槛 K。K 从 5 放宽到 20 时，数据变多且效果提高；继续放宽到 50 后回落。完全不筛选时，函数 Acc@10 约 54%，反而低于预训练基线约 59%。

图 5b 固定 K=20，再改变使用的数据比例。总体随数据增加而改善，但不是每个点严格单调；例如函数曲线在 5% 到 10% 之间小幅下降，之后提高到全量约 74.5%。所以更准确的经验是：先控制训练信号，再扩大数据，而非数据越多就必然更好。

这两项实验也提醒读者，改变 K 会同时改变数据数量、难度和样本构成，不是纯粹只操纵“噪声比例”。

### 8.2 别只教模型拒绝太容易的负例

附录 E、图 9 比较随机负例、首轮挖掘负例、用首轮训练后模型再次挖掘的负例。大模型函数 Acc@10 从约 73% 到约 81%，再到 82.12%；小模型从约 66% 到约 72%，再到 74.45%。约数来自曲线，最终值可对照主表。

第二轮负例由已经更强的模型挑选，代表第一轮训练后仍容易混淆的函数。结果支持迭代困难负例对排序训练有价值。它测量的是训练策略带来的最终能力，并未证明某个被采样负例在推理上下文中一定造成干扰。

### 8.3 换底座也有效，但提升幅度不同

表 3 用相同 SweLoc 数据对三个检索器微调一轮，函数 Acc@10 为：CodeRankEmbed 59.5→72.3，Arctic-Embed 53.7→71.9，多语言 Arctic-Embed-v2 62.0→70.1。表 3 是一轮适配实验，不要把它的 72.3 与主表两轮配置的 74.45 当作同一运行矛盾。

表 4 中，32B 通用文本 Qwen 重排器从 82.5→86.1，32B 代码版从 81.8→84.7；3B 文本版从 76.6→82.5，3B 代码版从 80.3→81.0。7B 的代码版略优于文本版，但 3B 和 32B 则是文本版更好。定位排序不必然随“代码专用”标签而变强。

附录 B 将验证扩展到 Llama-3.1-8B。通用列表排序训练后，再加 SweLoc，SWE-bench Lite 的函数 Acc@10 从 80.29→85.77，LocBench 从 70.00→73.04。通用排序训练本身在 Lite 的 Acc@10 甚至比零样本 81.39 略低，定位数据才带来进一步改善。

### 8.4 模型容量与向量维度不能混为一谈

附录 D 的表 9 比较更多编码器。Qwen3-Embedding-0.6B 微调后 Acc@10 为 75.18，8B 为 83.94；分别略高于 137M 和 7B SweRank 检索器。跨模型比较同时改变架构、预训练、宽度、深度与维度，不能将所有差距只归于向量维度。

更有控制力的是表 10：固定 Qwen3-0.6B，利用嵌套向量表示训练，让不同长度的向量都可用于检索。微调后，1,024/512/256/128/64 维的 Acc@10 分别为 75.18/74.09/69.71/66.79/60.22。512 维比 1,024 维只低 1.09 个百分点，继续压缩才明显损失；64 维经过适配仍从 38.32 提高到 60.22。它给出了索引存储与质量之间更具体的折中。

## 九、哪些任务仍然难？

### 9.1 多修改点：找到一个并不够

图 6 用参考补丁修改函数数作为复杂度代理。SWE-bench Lite 中，LocAgent 从单函数组的 82.0% 降到 2–3 函数组的 47.1%；大检索器在后一组仍有 77.1%。LocBench 中超过五个目标的任务非常困难，图中各方法约在 0%–10% 附近，正文概述为个位数；不将图上未精确标值的柱高当作更精细的数字。

这说明排序器对若干多目标任务有明显优势，也说明全部覆盖指标会随着目标数增加变得更苛刻。目标数量既反映任务结构，也改变评估难度。作者把重排改善解释为捕捉跨函数依赖，但实验没有单独操纵依赖关系，这一机制解释仍需额外验证。

### 9.2 词不像、语义距离远时，重排更有用

图 7 按 issue 与目标函数的词面重叠分组。最低 Rouge-1 区间 0–0.1 中，大检索器在 Lite 的 Acc@10 为 65.2%，LocAgent 为 60.9%；重排继续带来改善。方法因此不只依赖直接关键词重合。

图 8 改用 Gemini-Embedding 测得的平均余弦相似度分组。语义相似度超过 0.8 时各方法接近很高的覆盖率；0.65–0.75 的低相似度区间更难，而重排相对检索仍有明显提升。这个分层用的是金标准函数，适合事后诊断，不能直接作为部署时已知的难度标签。

### 9.3 上限在哪里：先检索到，才有机会重排上去

表 8 的大检索器在 Lite 上 Acc@10/20/50/100 为 82.12/86.50/90.88/93.43；LocBench 为 63.21/71.25/80.71/84.29。

对于只能重排这 100 个候选的系统，93.43% 与 84.29% 是“全目标已进入候选池”的上限。最后的 Acc@10 分别为 88.69% 与 71.25%，可见候选内部排序仍有改进空间，LocBench 尤其明显。另一方面，未进入候选池的那些任务，重排无法凭空救回。

这比只比较最终分数更有解释力：检索覆盖、重排损失以及后续修复失败，应分开记录。

### 9.4 多语言测试：迁移成立，离完美还有距离

附录 F 测试 SWE-bench Multilingual 的 234 个任务，覆盖 C、C++、Java、JavaScript、TypeScript、Rust、PHP、Ruby、Go。小检索器 Acc@10 从基座的 35.04→44.02，大检索器从 42.31→50.85；Gemini-Embedding 为 47.44。

这里的重排实验使用**小检索器**：加 CodeRankLLM 后 51.28%，加 SweRankLLM-Small 后 56.84%。不能把这一行写成“大检索器加重排”的结果。

Python 定位训练在其他语言上产生了迁移收益，但论文只给聚合结果，不能保证每种语言都有相同增益，更不能直接外推到只有 CWE 名称的漏洞查询。

## 十、能否真正修好？又省了多少？

### 10.1 定位优势能传到修复，但增幅更小

表 6 固定 SWE-Fixer 的代码编辑阶段，更换定位模块：

| 定位来源 | 文件 Acc@1 | 修复 Pass@1 |
|---|---:|---:|
| SWE-Fixer 自带 | 69.7 | 21.0 |
| LocAgent | 78.5 | 22.6 |
| SweRank | 83.2 | 24.5 |
| 正确文件 oracle | 100 | 25.9 |

SweRank 相对 LocAgent 的修复成功率提高 1.9 个百分点；即使直接给正确文件，编辑器也只有 25.9%。所以定位确有价值，但这个修复器下的大量失败还发生在后续编辑与测试阶段。

表 6 的 LocAgent 文件数值 78.5 与主表的 77.74 并不完全一致，正文没有充分解释差别。复现时应核对该下游流程的具体运行与样本，不能自行把两个表拼成同一条轨迹。

### 10.2 成本优势依赖离线索引与具体部署

表 5 报告每例推理费用：Claude-3.5 LocAgent 0.66 美元，微调 7B LocAgent 0.05 美元，7B SweRankLLM 0.011 美元，32B SweRankLLM 0.015 美元。代码向量可以预计算，论文把在线检索额外开销视为很小。图 1 将这组费用放到对数横轴、将函数 Acc@10 放到纵轴：SweRank 重排器处于约 1–1.5 美分、86%–89% 的区域，Claude-3.5 LocAgent 约 66 美分、77%。这张图强调的是特定部署下的质量与费用组合。

这些是论文配置的费用估计，不能直接当作今天任意平台报价，也未摊入首次编码新仓库、训练和长期存储的全部成本。成本效益表还混合了模型与系统差异；最清楚的说法是，作者配置下的排序流水线在线推理更便宜。

附录 G 在 50 个 Lite 实例上测时延。7B 重排器在单张 80GB A100 上平均 12.5 秒；同用 GPT-4o 时，SweRank 为 30.2 秒，LocAgent 为 85.3 秒，约 2.8 倍差距。后者控制了模型，更能支持“取消自主搜索循环能够减少时延”这一工程判断。

表 13 的每例累计输入/输出 token 为：SweRank 78,409/741，LocAgent 234,197/1,884。输入约减少三分之二，输出约减少六成。78,409 是累计输入，不应解释为单次窗口必须容纳这么多 token；与前面滑窗重排实现结合看，多个窗口的重复输入必须计入总成本。

## 十一、案例与数据分布补充了什么？

附录图 10 的第二个例子是 scikit-learn：`ColumnTransformer` 的 pandas 输出无法正确处理没有特征的 transformer。LocAgent 第一名是 `_iter`，SweRank 第一名是 `_hstack`，二者位于同一个 `_column_transformer.py` 文件。

这个例子非常适合解释粒度差异：文件指标可以把二者都视为命中，函数指标才能区分是否定位到负责拼接和输出处理的位置。图展示的是最终候选与源码片段，没有完整搜索过程，不能从图重构 LocAgent 为什么一步步走错。

两个案例都由作者挑选，帮助理解“表面相关函数与实际修改位置”的差别；它们不是全部失败的代表性抽样，也没有统计证明所有 LocAgent 错误都属于混淆症状与根因。

附录 I、图 11 从 SweLoc 随机取 10,000 条，用聚类关键词与语言模型生成主题。前三类为数据工程 10.3%、机器学习 9.2%、数据科学 8.6%，其后包括代码格式化、文档、地理空间分析等。它说明语料覆盖多种 Python 生态任务，同时也显示主题偏重；这些自动主题标签不是人工审定的漏洞类型分布。

## 十二、证据审查：强结果与尚未回答的问题

### 12.1 “未修改”不是“无用上下文”

SweLoc 用修改函数构造正例，用未修改函数构造负例，适合训练修改位置排序。但未修改调用者、校验函数和类型定义可能是理解修复所必需的支持材料。

因此本文的 hard negative 不能直接对应人工 CPI 的 P 或 I。排序目标低，并不意味着作为解释证据也应删除。把修改标签拿来训练最终候选排序，与拿来训练上下文清除器，是不同任务。

### 12.2 一致性过滤同时选择了“已有模型看得懂”的任务

只保留正例进入前 20 的训练配对，能减少描述与修改不匹配的样本，也可能排除很难但有效的非局部修改。图 5 支持它在当前测试集上的效果，却没有拆开“去噪”与“选择更容易学习的分布”各自贡献。

训练时排除两个评测集仓库是重要防泄漏措施；这仍不等于所有预训练底座从未接触相关公开代码。本文没有足够证据把最终优势全归于新数据，排除一切底座记忆影响。

### 12.3 系统排名不等于架构的纯因果效应

主表同时改变底层模型、定位监督、候选生成方式与交互协议。重排表内的候选入口较统一，适合研究重排选择；Agent 与检索系统之间则属于完整方案比较。附录同 GPT-4o 时延对照改善了资源解释，但并未把主表所有质量对照都变成同模型、同训练、同预算实验。

论文未提供足以支持所有小差距的重复运行方差或逐项置信区间。比如 LocBench 上 71.25 与 GPT-4.1 的 71.61，只应描述为接近，不能靠小数点宣布一方稳定胜出。

### 12.4 输出形式和数据筛选限定了适用范围

Lite 排除 26 个没有修改既有函数的任务后，结论适用于可映射到既有函数的定位。新增文件、模块顶层语句等情况，需要另行约定候选空间。

全覆盖 Acc@k 对多目标任务非常严格，却没有像 F1 一样连续惩罚额外候选。把它作为唯一指标，容易隐藏“多报很多、但把目标包进去”的行为。本文的很高 Acc@10 不能直接换算成很高的文件 F1。

### 12.5 公开代码值得读，不能只看命令退出码

本次只读核查官方代码发现：`run_rerank.sh` 默认传入 `--use_parallel_reranking`；对应 `src/rerank.py` 在可见 GPU 数大于 1 时才运行并行分支，只有一张卡时打印警告，没有在这一分支自动回退到串行执行。单卡复现应明确走不带该开关的串行路径，并核验实际结果文件，不能看到脚本结束就认为重排完成。这个隐患针对官方命令行入口；直接调用底层 `Reranker.rerank` 的独立适配器不必经过该分支，不能据此推断其他部署已经空跑。

README 也明确说，检索器训练脚本未包含在仓库；数据构造和重排训练代码有提供。这是复现材料范围，不能简化为“所有训练流程都已一键开源”。上述核查固定在本次记录的源码版本，未独立重跑模型。

## 十三、读完应该真正记住什么？

1. **任务适配的数据非常有力量。** 同一个 137M 检索器经过定位训练，函数前十覆盖提高约 15.7 个百分点；普通代码检索结果不能代表专用排序器的上限。
2. **没有完整排序标注也能训练列表重排。** 先学习通用排序格式，再只监督正确候选的首位编号，利用了真实 PR 标签的有限信息。
3. **候选召回和最后选谁要分开。** 高 Acc@100 是重排的机会，不是最终定位成功；LocBench 仍有明显候选内排序损失。
4. **多轮 Agent 的价值需要具体证明。** 本文表明部分定位可以被训练好的检索与重排高效覆盖，但没有证明自主探索在所有信息条件下都多余。
5. **低在线费用建立在预计算和专用模型上。** 多滑窗累计 token、建库成本、显存和首次启动开销，都应该保留在复现报告中。

作者证明的是这套数据与排序系统在指定基准、模型和指标下的有效性，以及部分修复收益；并未证明困难负例在上下文中必然有害，也未证明排序优势就是因果推理能力更强。

## 十四、对当前定位与 CPI 实验，最值得直接借用什么？

本次已读取 causal-review 的 GitHub 研究记录，公开版本最近内容到 11 月 10 日，主线是区分未曝光、筛掉和保留后漏选，并检查文件级定位的真实端到端成本。该文件不能代表此后本地实验的最新状态。下面是方法建议，不是新实验结论。

**第一，保留 SweRank 自己的身份。** 将原始 retriever 与 retriever+reranker 分别作为低交互基线。若把它的候选再交给另一模型筛选裁决，应单列为组合方法，不能把组合输出称为原生 SweRank。

**第二，38 个任务先固定同一候选与评分约定。** 原文主要使用详细 issue，而当前查询可能只有 CWE。这个信息差可能影响检索模型甚于多轮探索模型，必须如实描述。论文的 274 例 all-gold Acc@k 与当前文件 F1 应各报各的，不能将百分数直接拼成同一排名。

**第三，为每例保留四个阶段。** 全仓候选空间里是否存在目标，top-100 是否覆盖目标，重排后 top-k 是否仍覆盖，追加筛选后是否损失目标或支持材料。这样能够区分检索失败、排序失败与筛选损失，而不是把所有失败归到“模型理解不够”。

**第四，困难负样本提供的是候选来源，不是自动 P 标签。** 可以从高相似未改函数中提出待审候选，再由机制证据检查它是竞争解释、支持证据还是无关片段。若直接把未改函数全标 I，可能删掉真正需要的支撑代码。

**第五，总成本至少拆成建库、检索、滑窗重排和后续裁决。** 缓存可复用时报告稳态在线成本，首次处理新仓库时另报冷启动成本。不同方法的失败、未知 usage 与未执行槽位也应保留，缺失成本不能填零。

本文最重要的研究启发是：一个强排序器能减少大量探索开销，但“排序靠后”与“对理解无贡献”仍有距离。后者恰好是上下文作用研究可以继续回答的问题。
