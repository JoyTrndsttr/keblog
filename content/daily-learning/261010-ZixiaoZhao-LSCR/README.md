## 1. 先建立整篇论文的地图

这篇论文研究一个很现实的问题：安全代码评审需要跨函数、跨文件理解控制流、数据流和资源生命周期，但能做复杂推理的大模型昂贵、难以私有部署；7B 左右的轻量模型便宜，却容易只看局部表象，生成“听起来合理、实际找错根因”的评审评论。LSCR 的核心办法不是把大模型的最终答案直接拿来微调，而是让教师模型先抽取证据、再做静态分析式推理、最后生成结构化评审，并把整条“证据—推理—结论”轨迹蒸馏给轻量学生模型。

在基于 SeRe 构建的 5,329 条训练数据和 450 条人工质控测试数据上，LSCR 的三个 6.7B/7B 学生变体在安全类别识别、文本指标和人工效用评价上都优于对应学生模型及 SecureReviewer。最强的 LSCR-QW 达到 0.680 Accuracy、0.603 Balanced Accuracy；但失败分析也表明，加入仓库上下文和推理监督后，模型仍经常无法验证安全条件、追踪跨函数数据流或处理复杂控制流。

理解全文需要先掌握五个概念：

1. **安全代码评审（Security Code Review）**：不是检查格式或普通可维护性，而是识别可能形成漏洞的控制流、数据流、资源生命周期、输入校验和权限问题。
2. **上下文感知蒸馏（Context-Aware Distillation）**：教师和学生不仅看目标 diff/hunk，还接收仓库中检索到的符号定义；教师产生的中间推理也作为监督信号。
3. **安全推理轨迹（Security Rationale）**：先列出证据，再进行类似静态分析的传播与约束推理，最后输出问题类别、根因描述、影响和修复建议。
4. **Balanced Accuracy（平衡准确率）**：先分别计算各类别的召回率，再求平均，避免 30.4% 的大类把 3.1% 的小类表现掩盖掉。
5. **IHMU 人工评价**：把评论标为 Instrumental、Helpful、Misleading 或 Uncertain，用于区分“真正准确可行动”与“只有部分相关”。

全文的顶层证据链是：

```text
Research Gap
轻量模型便于部署，但缺少仓库语义和安全推理能力
    ↓
Research Object
结构化安全评审 R=(C,D,I,A)
    ↓
Operationalization
仓库符号上下文 + 证据抽取 + 静态分析式 rationale
    ↓
Method
Teacher 生成 K 条轨迹 → Judge 过滤 → Student 指令微调
    ↓
Evidence
450 条测试；自动指标、人工 IHMU、组件消融、教师替换、失败分析
    ↓
Claim
结构化 rationale 蒸馏能显著增强轻量模型，但精确程序语义仍是瓶颈
```

## 2. 为什么普通轻量微调仍然不够？

### 2.1 现实矛盾：高频评审需要低成本，安全判断却依赖全局语义

代码评审是持续发生的高频活动，工程落地关心延迟、成本可预测性、数据是否能留在内网，以及模型能否在有限显存上运行。直接调用闭源大模型或者部署几十、上百亿参数模型，在安全敏感或资源受限环境里未必可行。

但安全缺陷又恰恰不是只靠局部词法模式就能判断的。一个看似普通的赋值，可能因为上游调用允许并发而形成竞态；一次内存分配是否泄漏，取决于指针之前指向什么、跨函数如何传播、旧资源是否释放。轻量模型若只学“代码片段 → 评论”，很容易学到高频表面模式，而不是漏洞成立所需的执行语义。

### 2.2 Figure 1：没有仓库上下文，模型会给出合理但错误的解释

论文第一个动机案例展示了一段共享配置对象的条件初始化。局部看，它像是重复分配或初始化问题；仓库调用链却显示该函数可能被多个线程并发调用，而共享成员没有锁或原子保护，真正风险是竞态与不一致初始化。

这个案例支持“局部 hunk 可能不足”的动机，但还不是统计证据。它说明仓库上下文在某些案例中具有决定性信息，不代表自动检索到的所有仓库代码都有用。

### 2.3 Figure 2：拥有上下文仍不等于理解语义

第二个案例中，新增代码覆盖一个可能已指向旧分配区域的指针。表面评论建议先初始化为 `NULL`，但真实问题是覆盖前没有释放旧内存，属于资源生命周期管理错误。大模型通过显式证据和数据依赖推理才能将旧值、重新赋值和泄漏串起来。

因此作者提出两层 gap：

- **context deficiency**：缺少定义、调用关系和共享状态；
- **reasoning deficiency**：即使代码已经给出，轻量模型也未必能沿控制流、数据流和资源生命周期得出正确结论。

LSCR 分别用“仓库上下文检索”和“安全 rationale 蒸馏”处理这两层问题。

## 3. LSCR 怎样从输入运行到输出？

Figure 3 将方法分为三段：数据准备、相关上下文检索、安全 rationale 蒸馏。重要的是，这三段不是并排的模块清单，而是前一段产出的监督材料会进入后一段。

### 3.1 数据准备：先把人类评论变成可学习的结构

原始数据来自 SeRe。SeRe 不是靠几个安全关键词从通用评审中粗筛，而是依据 OWASP 和 Common Weakness Enumeration（CWE，常见弱点枚举）的安全定义，包含真实安全评审及仓库级信息。

LSCR 把每条安全评审写成：

\[
R=(C,D,I,A)
\]

其中：

- \(C\)：安全问题类别；
- \(D\)：问题及根因描述；
- \(I\)：可能造成的安全影响；
- \(A\)：可执行的修复建议。

这一结构来自 SecureReviewer。它迫使模型同时回答“是什么、为什么、会怎样、怎么修”，比一段自由评论更容易训练和评价。

SeRe 原本没有细粒度类别标签。作者以 CWE 的 Research Concepts 为上层空间，采用迭代式 taxonomy 构建：先让大模型把能覆盖的评论分到已有类别；无法可靠分类的样本进入未分配池；人工只检查其中是否出现值得新增的重复模式；扩充类别后继续迭代，直到形成与数据匹配的紧凑类别集合。最终测试集使用七个一级类别，而不是把大量稀疏 CWE 编号直接当标签。

作者用 Qwen3-32B 将人类评论重写为结构化格式，得到 **5,329 条训练数据**。对随机抽取的 337 条，两个专家在类别标注上的 Cohen's Kappa 为 0.76，在重写质量上的 Kappa 为 0.695；解决分歧后，94% 同时满足语义等价与结构要求。测试集则由两位领域专家逐条质控，最终包含 **450 条**。

### 3.2 上下文检索：把 hunk 中未知符号解析回仓库

给定目标片段 \(s\) 和仓库 \(G\)，LSCR 构造紧凑上下文 \(C(s)\)：

1. 从目标片段语法树中抽取标识符集合 \(I(s)\)；
2. 解析仓库抽象语法树，建立“符号名—类型—定义位置”索引；
3. 对每个标识符检索候选定义；
4. 若同名定义有多个，选择到目标片段文件依赖距离最短的一个，同文件距离为 0；
5. 对局部变量展开完整所在函数，以保留 definition-use 语义；
6. 拼接定义，达到预算后停止。

具体预算是：单个符号定义最多 200 行，所有定义合计不超过 2,000 行，最终输入最多 15,000 tokens，超出部分截断。

这里的设计有明确优点：它可复现、无需训练检索器、能把未定义符号落回代码。但“最近定义”只是启发式相关性，不保证该定义是漏洞判断的决定性证据；同名符号、动态分派、别名、宏和跨语言关系都可能破坏这个假设。论文把所有使用上下文的模型置于同一构造协议与预算下，保证了实验内一致性，却没有单独测检索 precision、recall 或最小充分性。

### 3.3 教师生成：先找证据，再做静态分析式推理

Teacher 的推理被拆成两步。

**第一步：Evidence Extraction。** 从 hunk 与 \(C(x)\) 中找安全相关元素，例如敏感标识符、关键 API、异常处理分支和具体语句。每条证据尽量只包含类别、行号和最小代码片段，避免一开始就生成泛泛长解释。

**第二步：Static-Analysis-Style Reasoning。** 教师围绕已抽取证据追踪函数内/函数间控制流和数据流，检查资源生命周期、认证、输入校验和典型误用模式，然后生成 \((C,D,I,A)\) 结构化评论。

形式上，教师先生成证据集：

\[
E=\{e_1,e_2,\ldots,e_m\}
\]

再生成推理链：

\[
R=(r_1,r_2,\ldots,r_n)
\]

最终输出：

\[
y=f(E,R),\quad y=(C,D,I,A)
\]

这个公式并不是一个可执行的静态分析算法，而是对生成顺序的约束：结论应当以证据和推理为中间状态。

### 3.4 多轨迹与 Judge：不是所有教师 rationale 都进入训练集

教师为每个输入采样 \(K=3\) 条候选 \((E_k,R_k,y_k)\)。Judge 只有在三项同时满足时才保留候选：

1. 输出符合 \((C,D,I,A)\) 结构；
2. 预测类别与参考答案一致；
3. 描述、影响和建议与参考答案语义等价。

通过的轨迹被序列化为“输入代码与上下文 → 证据 → 推理 → 结构化结论”，学生模型用指令微调学习整条生成顺序。

这一步能过滤最终答案明显错误的教师样本，但要注意：Judge 验证的是最终评论与参考答案的一致性，不是逐步核验每条证据、每个数据流边或每个 rationale 步骤是否忠实。因此 LSCR 蒸馏的是“能导向正确参考结论的解释轨迹”，论文没有证明这些自然语言 CoT 是教师内部真实机制，也没有证明中间链条逐项正确。

### 3.5 学生模型与部署

学生模型包括：

- CodeLlama-7B-Instruct（LSCR-CL）；
- DeepSeek-Coder-6.7B-Instruct（LSCR-DS）；
- Qwen2.5-Coder-7B（LSCR-QW）。

训练使用 Low-Rank Adaptation（LoRA，低秩适配）：rank 8、alpha 16、dropout 0.05，最大序列 15,000 tokens，两张 A800 80GB GPU。部署时只需运行微调后的轻量学生；主要教师推理成本发生在离线数据构建阶段。

## 4. 实验坐标系：结果是在什么条件下得到的？

### 4.1 数据与类别

测试集共 450 条，七个一级安全类别分布不均：

- 控制流管理不足：137（30.4%）；
- 资源生命周期控制不当：84（18.7%）；
- 编码规范遵循不当：75（16.7%）；
- 中和/校验不当：60（13.3%）；
- 异常条件检查或处理不当：43（9.6%）；
- 错误计算：37（8.2%）；
- 访问控制不当：14（3.1%）。

因此 Accuracy 与 Balanced Accuracy 必须同时看。一个总是预测大类的模型可能有尚可 Accuracy，却会在 Balanced Accuracy 上暴露对小类的失败。

数据采用时间切分：学生模型训练截止日期之后的样本只用于测试，以降低污染风险。这比随机切分更接近部署，但不能排除教师模型或通用预训练数据已经见过公开仓库内容。

### 4.2 Baselines

对照覆盖三种范式：

1. **原始轻量模型**：衡量不做任务适配时的起点；
2. **专门微调的评审模型**：CodeReviewer、LLaMA-Reviewer，以及与三个学生骨干一一对应的 SecureReviewer；
3. **通用大模型**：GPT-4o、Claude-3.5-Sonnet、DeepSeek-V3、DeepSeek-R1、Qwen3-32B。

SecureReviewer 是最关键对照：它使用相同学生骨干、相同训练数据，并采用与 LSCR 一致的 LoRA 配置。两者主要差别是 LSCR 加入仓库上下文与证据—分析 rationale 蒸馏。通用大模型没有经历同一任务训练，因此适合回答“开箱即用的大模型到什么水平”，不适合作为纯模型规模的严格因果对照。

### 4.3 指标和运行协议

类别识别使用 Accuracy 和 Balanced Accuracy；生成使用 BLEU-4、ROUGE-L、METEOR 以及面向安全评审的 SecureBLEU。推理使用 greedy decoding；API baseline 温度为 0；随机种子固定为 42。

人工评价将评论分为：

- **Instrumental (I)**：准确指出目标安全缺陷且描述完整；
- **Helpful (H)**：指出相关风险，但不够准确或具体；
- **Misleading (M)**：没有有用信息、否认缺陷或没有识别目标问题；
- **Uncertain (U)**：提出参考评审之外的其他风险，专家无法确认。

三位安全代码评审专家独立标注选定模型的输出，并报告 I-Score、IH-Score 与 M-Score。

## 5. RQ1：LSCR 的总体性能如何？

### 问题与设计

RQ1 同时问两件事：轻量模型能否识别正确安全类别，以及能否生成与参考评论一致、包含安全语义的结构化评论。Table 2 固定同一测试集，对比原始学生、通用大模型、传统评审微调模型、SecureReviewer 与 LSCR。

### 分类结果

最直观的比较是同一骨干的前后变化：

| 骨干 | 原始 Accuracy / B-Acc | LSCR Accuracy / B-Acc |
|---|---:|---:|
| CodeLlama-7B | 0.071 / 0.138 | **0.680 / 0.590** |
| DeepSeek-Coder-6.7B | 0.164 / 0.147 | **0.651 / 0.561** |
| Qwen2.5-Coder-7B | 0.262 / 0.316 | **0.680 / 0.603** |

与更强且更公平的 SecureReviewer 对照相比，LSCR-CL 为 0.680 vs 0.616，LSCR-DS 为 0.651 vs 0.611，LSCR-QW 为 0.680 vs 0.571。论文所说“平均超过 12%”是相对提升，不是 12 个百分点。

开箱即用的大模型中，GPT-4o 最好的 Accuracy 为 0.476，Qwen3-32B 的 B-Acc 为 0.404，均低于三个 LSCR 变体。这说明针对固定 taxonomy 的训练非常重要；但它不等于“7B 模型本质上超过大模型”，因为 LSCR 看过 5,329 条同任务监督，大模型没有。

作者报告 LSCR 对学生骨干及 SecureReviewer 的 Accuracy 提升达到 \(p<0.05\)，bootstrap 波动约为 ±0.02。不过正文没有说明所用显著性检验、配对单位、重复运行次数和多重比较处理方式，统计结论的可复核性弱于点估计本身。

### 生成结果

LSCR-CL 的 BLEU-4 最高，为 **14.169**；Qwen3-32B 的 SecureBLEU 和 METEOR 最高，分别为 **29.751** 和 **0.363**。LSCR 没有在所有指标上统治大模型，而是在多数指标上达到接近或更均衡的水平。

与 SecureReviewer 同骨干对照：

- CL：BLEU 12.123 → **14.169**；
- DS：12.627 → **13.570**；
- QW：11.077 → **12.808**。

作者概括的 BLEU 平均提升超过 13.3%同样是相对百分比。Table 2 最值得记住的不是某一列冠军，而是任务微调对类别识别影响极大；在文本相似度上，大模型、SecureReviewer 和 LSCR 的差距要小得多。

**Takeaway：** LSCR 能稳定增强三个轻量骨干，特别是在细分类别识别上；证据支持“该训练方案对当前 benchmark 有帮助”，不能单独证明 rationale 是唯一原因。

## 6. RQ2：生成的评论对人是否真正有用？

### 问题与设计

BLEU 高可能只是措辞更像参考答案。RQ2 让三位专家根据 hunk 与 gold review 判断评论属于 I/H/M/U，直接检查准确性、行动性和误导风险。作者选择 Qwen2.5-Coder-7B 作为原始学生代表，并排除各组最弱模型，以控制标注成本。

### Table 3 怎样读？

应先看 M-Score，因为安全评审中“自信但错误”的建议比缺少一条评论更危险；再看 I-Score，判断多少输出能准确指出目标缺陷。

- 原始 Qwen2.5-Coder：I=0.093，IH=0.447，M=0.553；
- SecureReviewer-QW：I=0.182，IH=0.558，M=0.442；
- **LSCR-QW：I=0.309，IH=0.656，M=0.344**；
- GPT-4o：I=0.184，IH=0.589，M=0.411；
- DeepSeek-V3：I=0.216，IH=0.649，M=0.351。

LSCR-QW 的完全准确评论比例是原始 Qwen 的 3.3 倍，误导比例降低 20.9 个百分点；相较同骨干 SecureReviewer，I-Score 增加约 69.8%，M-Score 相对降低约 22.2%。三个 LSCR 变体平均相对 SecureReviewer 将 Instrumental 比例提高约 52.6%，将 Misleading 比例降低约 22.6%。

自动指标与人工有用性的 Spearman 相关系数为：BLEU 0.516、ROUGE-L 0.603、METEOR 0.572。它们有中等正相关，却远非等价指标。较长评论的 perceived helpfulness 上升，但准确性下降，说明“写得多”可能增加可读解释，也可能引入更多不实断言。

论文还观察到：控制流管理不足类别的平均 helpfulness 为 50.1%；资源生命周期类别的平均 instrumentality 为 29.8%；超过平均长度的 hunk，其评论 helpfulness 比较短 hunk 低 17.4%。

需要注意，IHMU 以 gold reviewer 指出的目标问题为中心。标成 U 的其他问题并未通过程序分析或运行验证；因此 IH/M 能衡量与参考评审对齐程度，却不能完整测量所有输出的真实安全正确性。

**Takeaway：** LSCR 的收益不仅是文字更像参考答案，也体现在更少误导和更多可行动评论；但人工评价仍是 reference-aligned utility，不是漏洞存在性的独立 oracle。

## 7. RQ3：上下文、证据和推理各贡献了什么？

Table 4 在三个学生骨干上做七种条件：

- 完整 LSCR；
- 去掉 evidence；
- 去掉 analysis；
- 去掉整个 CoT；
- 去掉 context；
- 同时去掉 CoT 与 context；
- 不微调，只保留上下文和 CoT prompt。

### 微调是必要基础

LSCR-QW 去掉微调后，Accuracy 从 0.680 降到 0.331，BLEU 从 12.808 降到 7.105；CodeLlama 更从 0.680 降到 0.018。仅在 prompt 中要求小模型“找证据、做分析”远远不够，任务监督是最大基础差异。

### Evidence 与 analysis 都有帮助

LSCR-CL 去掉 evidence 后 Accuracy 为 0.618，去掉 analysis 后为 0.607；完整模型是 0.680。SecureBLEU 分别从 29.409 降到 27.930 和 28.314。两个阶段的去除都造成下降，但不同骨干降幅不一致：在 DeepSeek 上，去掉 evidence 或 analysis 的 Accuracy 只下降 0.004 和 0.007，而生成指标仍有更明显变化。

因此可以说二者整体有贡献，不能说每个模块在所有模型上都同样“不可或缺”。

### Context 有稳定但非独立的作用

去掉 context 后：

- CL Accuracy：0.680 → 0.613；
- DS：0.651 → 0.609；
- QW：0.680 → 0.611；
- QW B-Acc：0.603 → 0.516。

同时去掉 CoT 和 context 通常进一步下降，表明两者可能互补：上下文提供候选证据，CoT 监督模型如何使用证据。

但这个 ablation 不能完全回答“在部署时给同一个已训练模型额外 context 的因果效应”。上下文参与了训练数据、教师 rationale 生成和推理输入，删掉 context 改变的是整个训练—推理分布；而且没有用等 token 的无关或 plausible filler 对齐长度。因此它证明“LSCR 的完整 context-integrated 训练设计有贡献”，不是证明任意新增仓库上下文都会帮助。

**Takeaway：** 任务微调是最大前提；证据、分析和仓库上下文在完整管线中相互增强，但论文没有识别它们各自的纯中介效应。

## 8. RQ4：换教师以后还有效吗？

作者把默认教师 Qwen3-32B 换成 GPT-4o，保持相同蒸馏流程，并让对应教师同时充当 Judge。

Qwen3-32B 教师在三个学生上的自动指标通常更高。例如 LSCR-CL Accuracy 为 0.680，对 GPT-4o 教师为 0.624；BLEU 为 14.169 vs 12.923。LSCR-QW 的人工指标则出现另一种模式：GPT-4o 教师的 I-Score 0.311、IH-Score 0.682、M-Score 0.318，略优于 Qwen3-32B 教师的 0.309、0.656、0.344。

这说明方法没有在换教师后崩溃，且不同教师可能在自动相似度与人工效用上体现不同优势。但这里只比较两个教师，而且 Teacher 与 Judge 同时更换，无法把“生成质量”和“过滤标准”的影响分开。论文所谓 generalizability 更准确地说是“对两个教师配置具有鲁棒性”，还不是跨模型家族的广泛外部验证。

**Takeaway：** LSCR 不依赖唯一教师才能工作，但教师和 Judge 的耦合仍是未分离变量。

## 9. Negative Result：给大模型同样的仓库上下文，收益很有限

Table 6 把同一检索管线和相近输入预算用于五个大模型。与 Table 2 的无额外上下文结果对照：

| 模型 | Accuracy：原始 → 加 context | 变化 |
|---|---:|---:|
| GPT-4o | 0.476 → 0.462 | −0.014 |
| DeepSeek-V3 | 0.327 → 0.342 | +0.015 |
| DeepSeek-R1 | 0.404 → 0.407 | +0.003 |
| Claude-3.5-Sonnet | 0.311 → 0.251 | −0.060 |
| Qwen3-32B | 0.413 → 0.393 | −0.020 |

生成指标同样有升有降。最明显的是 GPT-4o SecureBLEU 从 26.245 升至 30.439，但 Accuracy 略降；Qwen3-32B SecureBLEU 从 29.751 升到 30.336，Accuracy 也略降。

这个结果限制了“上下文本身解释 LSCR 提升”的叙事：更多相关定义可能让评论文字更贴近安全语义，却不保证类别判断更准。LSCR 的优势更可能来自任务微调、结构化输出、rationale 监督与 context 的组合。

同时，这个比较也不是严格配对的因果实验：论文只给汇总点估计，没有逐实例 context 有益/有害分布或等长 filler 对照。但它是一项重要负结果——即使大模型有更强推理能力，简单增加仓库符号上下文也不会稳定改善安全评审。

## 10. Figure 6 与系统性失败：模型仍会把“相关模式”当成真实根因

Figure 6 的代码对 `newEnvReader(proc)` 返回值解构后直接执行 `defer er.finish()`。如果文件打开失败，`newEnvReader` 返回 `nil, err`，后续 defer 会在函数返回时解引用 nil。

LSCR-QW 确实注意到 `defer` 和资源清理，却错误声称 panic 时 defer 不会运行，从而把问题归因于“异常路径不执行清理”。正确根因是没有检查 `er` 是否为 nil。这个案例非常典型：模型找到主题相关的语句，却没有建立返回值传播与安全条件之间的精确关系。

作者对 196 条 misleading 样本进行人工分析：

- 30%–35%：没有验证关键安全条件是否已实施；
- 20%–25%：无法追踪数据流和变量传播；
- 15%–20%：无法分析复杂控制流。

这说明 LSCR 主要改善了评审结构、证据意识和平均可用性，却没有解决精确程序语义。自然语言 rationale 仍可能把表面相关模式包装成连贯但错误的因果解释。

## 12. 证据审计：论文证明了什么，又没有证明什么？

### 12.1 论文有充分证据支持的结论

1. 在当前 SeRe 派生 benchmark、三个轻量骨干和统一 LoRA 设置下，LSCR 的自动指标稳定高于相应原始模型和 SecureReviewer。
2. 人工 IHMU 评价显示 LSCR 生成的评论更常达到 Instrumental/Helpful，且更少 Misleading。
3. 完整管线中的任务微调、evidence、analysis 与 repository context 都与性能增益有关；联合去除会进一步退化。
4. 把教师从 Qwen3-32B 换为 GPT-4o 后，方法仍保持可用，没有灾难性下降。
5. 仓库上下文直接提供给通用大模型时，类别准确率没有稳定改善；上下文不是充分条件。

### 12.2 论文没有证明的内容

1. **没有证明 rationale 是忠实因果机制。** Judge 依据 gold 最终评论过滤，未逐步验证中间证据与推理。
2. **没有证明所有仓库上下文都有益。** 检索只按符号与依赖距离，未标注 context 是否决定任务、是否冗余或误导。
3. **没有隔离 context 的纯因果效应。** context 同时影响教师生成、训练和推理，且没有等 token filler。
4. **没有证明 7B 普遍优于大模型。** 小模型接受了专门任务训练，大模型主要是 zero-shot/直接推理。
5. **没有完整报告统计检验细节。** 文中给出 \(p<0.05\) 与 bootstrap 波动，但未交代检验名称、独立单位和多重比较。
6. **没有证明更细 CWE 或其他安全场景同样有效。** 当前标签是七个一级 Research Concepts，最小类只有 14 条。
7. **没有计入完整离线成本。** 部署学生轻量，但三轨迹教师生成、Judge 过滤、数据重写和人工质控的总 token、时间与费用未报告。

## 13. 读完真正应记住什么？

- 轻量模型的短板不只是“参数少”，还包括缺少任务结构与证据推理监督。
- 将评审拆为类别、描述、影响、建议，并要求先证据、后分析、再结论，是比直接蒸馏最终评论更强的训练信号。
- Repository context 和 CoT 在该训练管线中互补，但更多上下文单独给大模型并不稳定提高准确率。
- BLEU/ROUGE 与人工效用只有中等相关；安全评审必须显式报告误导比例。
- 模型最顽固的错误是找到相关代码却没验证安全条件，或无法追踪跨函数数据流——“相关证据”与“正确机制”之间仍有鸿沟。
- LSCR 更适合作为 evidence-grounded training 的方法先例，而不是“仓库上下文必然有益”的现实性证据。

## 14. 对当前研究的启发

最新研究记录已经把评估拆成文件命中、真实读取、机制解释与行级位置，并在 Antares 原生轨迹中找到一个可重复的源码支持候选：同一任务三条轨迹完整读取 `sanitize.js` 并指出递归无深度上限。LSCR 最值得借鉴的正是输出分层，而不是直接照搬其检索器。

### 14.1 把当前输出正式写成 Evidence → Mechanism → Location

可将现有 EvidenceLoc-Line 输出扩展为：

```text
Evidence
- 文件、行区间、最小代码片段

Mechanism
- 状态/数据如何跨语句或函数传播
- 缺失了哪个安全条件

Attribution
- 最终归因到哪个作用域、实体和位置
```

这与 LSCR 的 \(E\rightarrow R\rightarrow y\) 对应，但评分必须分开：证据命中不认证机制，机制正确也不认证行级范围。特别适合继续跟踪已经暴露的 \(M=1,A=0\)。

### 14.2 用冻结成功输入做配对 context 干预

当前最可靠的候选不是再扩充六例平均分，而是对同一个稳定可解任务冻结：

- 原始任务与模型；
- 已确认完整包含关键源码的核心 evidence；
- 输出 schema 与预算；
- 多次重复种子。

随后只改变新增上下文：无新增、随机等预算、plausible 等预算。这样才能回答“plausible context 是否让 Evidence、Mechanism 或 Attribution 中哪一层退化”。LSCR 的 w/o-context ablation 可作为方法先例，但不能替代这项配对因果实验。

### 14.3 审计检索候选的增量证据价值

LSCR 按“同名定义 + 最短依赖距离”选 context，正是现实系统产生 plausible-but-non-decisive context 的机制之一。可以在现有图探索/RAG 候选上记录：

- 是否解析目标 hunk 中真实未知符号；
- 是否增加新的 mechanism edge；
- 是否只是重复已有事实；
- 是否引入同名跨作用域实体；
- 是否被模型引用但未参与正确机制链。

这能把 plausible 的定义从“看起来相关”推进到可审计的“语义邻近但增量证据为零”。

### 14.4 Judge 不应只检查与 gold 结论一致

LSCR 的 Judge 要求类别与 gold 一致、文本语义等价，却没有验证 rationale。当前研究可以更严格：

1. Evidence Judge：代码片段是否真实存在、行号和作用域是否正确；
2. Mechanism Judge：传播边和缺失条件是否能由源码支持；
3. Attribution Judge：最终位置是否落在预先冻结的机制位置集合；
4. Outcome Judge：最终漏洞判断是否正确。

只有四层同时通过，才能称“evidence-grounded success”。这比单一行 F1 或文件 F1 更贴合最新研究记录的结论：先分开认证运行、读取、机制和预测，再讨论 context 的伤害或帮助。
