## 一个迁移文件缺少 import，为什么最后要去看序列化器？

用户报告 Django 生成的数据库迁移文件少了一条 import，还猜测问题在“写迁移文件”的模块。定位工具顺着这个猜测找到相关类，却可能一直在这里打转：真正决定某个对象应当产生哪些 import 的代码，藏在另一个文件的序列化器里。

这就是 OrcaLoca 要解决的问题：**语言模型已经会提出可疑位置，也能调用代码搜索工具，但怎样安排接下来的搜索，并把有用证据留到最后，仍然是两个独立难题。** 多读代码未必找得更准；只给一个简短的类骨架，又可能看不到真正有问题的方法。

论文的答案像一套有组织的调查工作流：模型提出线索，调度器安排先后，大对象拆成值得追查的小对象，工作上下文随当前嫌疑位置更新。最后把定位结果交给现成的修复器，检查定位改进是否真的帮助修复。

## 1. 作者观察到了什么缺口？

论文 Figure 1 把当时 SWE-bench Lite 榜单各系统的三个指标放在一起：文件匹配率均值为 **72.08%**，函数匹配率为 **53.50%**，最终解决率为 **33.10%**。这条逐层下降的链很直观：找到相关文件后，还要找对函数；找到函数后，还要生成通过测试的补丁。

作者引用的 SWE-bench 仓库平均规模约为 3,010 个文件、43.8 万行代码。面向这么大的空间，已有工具主要提供了两类能力：AutoCodeRover 等系统让模型调用结构化查询，Agentless 等系统采用从文件到符号的分层定位；RepoGraph 一类工作则把代码关系组织成图，为检索提供结构。

OrcaLoca 认为缺的不是又一个搜索入口，而是三个连接环节。

**第一，提出多个动作以后，谁来决定先做哪个？** 单纯按模型输出顺序执行，容易在次要线索上消耗很多步；完全按预先规定的图遍历走，又难以响应后来出现的新线索。

**第二，从骨架到正文之间，怎样有选择地展开？** 大文件全部返回会淹没重点，只返回函数签名又看不到逻辑。让主模型自己反复要求展开，会增加遗漏和重复调用。

**第三，读过的东西怎样进入下一轮？** 早期怀疑过的位置后来可能已不再重要。把所有结果不断叠加，会让旧线索与新证据争夺注意力。

Figure 1 提供的是定位仍有改进空间的经验背景；上述三个具体故障模式主要构成作者的设计诊断。论文随后用完整系统比较和消融，检查这些设计是否有用。

## 2. 先走一遍 Figure 2 的 Django 例子

Figure 2 使用 `django_14580` 演示工作流。报告说，生成的迁移文件缺少 import，文本强调了 `CreateModel` 和 `MigrationWriter`，还把怀疑指向 `django.db.migrations.writer`。

图中明确给出的探索序列如下。它是作者的演示轨迹，图注也说明正式实验配置可能不同。

1. 先查 `MigrationWriter`。这是一个类，系统把查询拆成更细的方法查询，依次查看 `serialize` 和 `as_string`，而没有优先展开 `basedir`。
2. 接着看 `writer.py`、`OperationWriter` 和 `CreateModel`。这些对象都与迁移文件生成有关，因而是合理的初始嫌疑。
3. 新证据把注意力引到 `serializer_factory`。这个动作已被模型多次提出，优先级累计到 3，超过原本待看的 `models.py` 的 2，于是先执行它。
4. 查到工厂函数后，关联文件 `serializer.py` 被优先加入搜索。文件分解又挑出 `TypeSerializer` 与 `DeconstructableSerializer`，而不是无差别遍历所有序列化器。
5. 接下来实际查看 `TypeSerializer`、它的 `serialize` 方法和 `DeconstructableSerializer`，最后才执行此前排队的 `models.py` 查询。
6. 到形成结论时，当前可疑位置已经转为 `TypeSerializer` 与 `TypeSerializer.serialize`。上下文管理器保留与它们更近的代码结果，把 `OperationWriter`、`MigrationWriter` 的两个方法和 `CreateModel` 等较远内容移出当前搜索上下文。

最后输出是 `django/db/migrations/serializer.py` 中的 **`TypeSerializer.serialize`**。图中的解释也给了具体机制：处理 `models.Model` 的特例把表示形式设为 `models.Model`，却配了一个空 import 列表，导致生成的迁移文件没有相应导入。

这个例子把三个设计的分工讲清楚了。**调度改变“先看哪里”，分解改变“看多细”，裁剪改变“做下一次判断时还能直接看到什么”。** 真正的错误位置并不等于报告者点名最多的位置；搜索必须允许证据把系统带离初始猜测。

## 3. 系统如何把这个过程跑起来？

### 3.1 代码图提供地址和关系，模型负责解释线索

CodeGraph 是仓库的结构化索引。它把文件、类、方法、函数表示为节点，用两类关系连接：一类是“某方法属于某类、某类属于某文件”的包含关系，另一类是调用、引用等依赖关系。目录层级也被纳入，以保留仓库结构。构建主要依靠抽象语法树，也就是把源代码解析成语法结构后识别实体和关系。

每个代码实体都有稳定的标识符（UID）。例如，一个类方法可以用“文件路径::类名::方法名”定位。这样，名称相同但位于不同文件的类不会被误当作同一个实体；两个写法不同但最终指向同一实体的查询，也能被识别为重复。

搜索接口沿用并调整了 AutoCodeRover 的设计：可以查看文件内容、查类、查类中的方法、查尚不确定类型的 callable，或用文件内的一段源码定位所属实体。大文件超过 200 行时返回骨架，大类超过 100 行时也返回骨架，再由后续动作取出方法正文。一个方法的精确查询则返回路径和代码片段。

骨架的作用是展示“里面有什么”，正文的作用是展示“具体怎么做”。系统同时保留这两种访问方式，避免在一次调用里被迫二选一。

### 3.2 每轮产生三个东西，而不是立即认定最终答案

一次常规搜索轮次，模型输出：

- **Observation，观察与分析**：新结果带来了什么信息，现有判断应怎样更新。
- **Potential Bug Locations，当前可疑位置**：截至这一轮，最值得怀疑的文件、类或方法。
- **Search Actions，下一步搜索动作**：还需要执行哪些查询。

问题描述和可用的复现信息会持续提供；历史观察和候选位置用于串起调查，代码搜索结果则经过上下文管理器筛选。动作调度队列从所有待执行动作中取出一个，执行后产生新的代码结果，再触发分解、去重和上下文更新。

可疑位置是中间判断，最终位置由一个单独的结论步骤输出。读者可以把它理解为“随时修订的嫌疑清单”和“最后交付的定位报告”的区别。论文采用推理与行动交替的工作流，没有通过奖励训练这个策略。讨论部分还提供一种可选的 top-k 输出方式：利用上下文管理器保留的搜索结果形成候选列表，而非只依靠最终生成的位置；主结果没有单列这一选项的对照实验。

正常情况下，待执行队列耗尽后结束。附录 E 还提供提前收敛条件：用 BERT 文本向量比较连续两轮观察，余弦相似度大于 0.97 算作近似相同，连续 15 次满足后停止。这是在识别“分析已长时间不再变化”，而不是对定位正确性作证明。

### 3.3 动态队列：不要让新线索排在旧任务后面等太久

动作调度队列（Action Scheduler Queue，ASQ）是一个带优先级的待办集合，用堆维护。普通新动作的默认优先级为 1；和已查实体紧密关联的文件，以及从大对象分解出来的动作，可以赋予更高优先级，例如 2。

更特别的是，系统记录模型重复提出同一动作的次数。一个仍待执行的动作如果持续被提出，计数会替换原优先级，让它更快被执行。Django 例子中，`serializer_factory` 的计数达到 3，因而越过了优先级为 2 的 `models.py`。

这里有一个容易混淆的点：**待办动作多次被提出会被提权，已经执行过的同一实体查询则应被去重。** 这是两个不同的集合和操作。

Figure 3(a) 展示了去重的必要性。先用 `search_class(ModelChoiceField)` 查到类，再把路径补全后查一次，虽然 API 调用参数不同，读到的仍是同一段代码。系统先获取实体 UID，在动作数据库中核对，第二次就不用重复执行。图示路径少写了 `models.py` 中的一个 s，正文和 API 示例使用的是 `django/forms/models.py`；这里按正文路径解释。

### 3.4 动作分解：返回“有这些候选”之后，还要真的去查

文件或类太大时，系统让一个评分子 Agent 判断其中哪些成员与问题更相关，再把它们转为精确查询。实验中，每个类挑 **3 个方法**，每个文件挑 **2 个实体**，并把这些动作以较高优先级放回队列。

比如 Figure 2 从 `MigrationWriter` 展开到 `serialize`、`as_string`，从 `serializer.py` 展开到 `TypeSerializer` 和 `DeconstructableSerializer`。分解的输出不是一句“建议看看这些方法”，而是调度器接下来可以真正执行的搜索任务。主 Agent 因而能继续获得正文证据。

名称歧义也用类似方式处理。Figure 3(b) 查询 `SQLCompiler`，倒排索引找到了两个候选位置：`django/db/backends/mysql/compiler.py` 和 `django/db/models/sql/compiler.py`。系统既向模型说明存在多个匹配，也为两个准确位置各自创建查询。这样就把“名字相同”转成了可核查的具体对象。

这一步比单纯把歧义列表塞回对话更进一步：它承担了继续展开的执行责任，降低模型看见列表后遗漏某个分支的机会。

### 3.5 上下文裁剪：保留离当前嫌疑集合较近的12份代码

上下文管理器只长期保留能映射到有效 UID 的代码搜索结果。歧义提示和骨架消息可以帮助当下生成动作，但不作为持久代码证据继续堆积。随后，根据这些代码实体与当前可疑位置的图距离排序，保留前 12 项。

核心直觉是：如果我们目前怀疑 `TypeSerializer.serialize`，那么它所属类、相关工厂函数等结构上相邻的代码，更值得直接放在下一轮输入里；早期查看过的远处写文件逻辑，可以先移出去。

具体怎么算“近”？对一份搜索结果 SR，先取它对应的图节点。对每个当前可疑节点 v，分别计算“SR 到 v”和“v 到 SR”的有向最短路径长度，取两者中较短的一个；最后对所有可疑节点求平均：

`距离(SR, PB) = 所有 v∈PB 的 min(路径长度(SR→v), 路径长度(v→SR)) 的平均值`

PB 是当前可疑位置集合。分数越小，代码整体上越接近这组嫌疑位置，就越容易留下。这里算的是**对所有候选的平均距离**，不是只看离某一个候选最近的距离，也不是按照代码文本相似度打分。

举一个教学示例：有两个可疑函数，代码 A 到它们的距离分别为 1 和 7，代码 B 的距离为 3 和 3，那么 A 的平均距离为 4，B 为 3，B 会更靠前。这个例子说明，规则倾向保留能兼顾多个当前假设的结构邻近内容。

裁剪作用于每一轮提供给模型的搜索结果。仓库图仍然存在，历史观察也继续传递，所以“某段代码不在本轮正文上下文里”与“这个节点从仓库永久删除”是两回事。

## 4. 不只是静态搜索：复现器怎样提供额外线索？

附录 C 和 Figure 5 给出一个辅助 Reproducer Agent。静态代码搜索知道函数怎样组织，却看不到某次失败实际经过了哪些路径；复现器尝试补上运行信息。

它先把 issue 拆成自然语言、源码片段、traceback 等部分，分别提取可疑文件和符号。然后在 Docker 内的 conda 环境中生成并执行复现片段，用 VizTracer 记录执行轨迹。日志交给模型判断：是否出现与报告相同的错误或异常输出；如果只是运行出无关错误，或问题应当出现但没有出现，就继续修正复现片段。

Figure 5 中，复现成功后，日志和复现代码继续进入解析分支，与 issue 中原有的线索一起交给轨迹过滤器。轨迹通常很大，作者先利用三个启发式筛选：与可疑符号位于同一文件、在调用轨迹中是它的近邻后代、靠近轨迹根部。先留下 25 个候选，再结合模型对代码相关性的评分重排，保留超过阈值且排名前 5 的候选，作为搜索线索。

附录 D 公开的提示词也体现了这一分工：文本切分、关键词提取、日志判断、问题概括、代码打分和主搜索分别承担不同输出。代码评分器输出 0–100 的整数；主搜索器明确区分常规轮次与最后的定位输出。

**复现成功率只有 38.0%。** 因而这条路径是增强信息来源，主要搜索设计仍须在没有成功复现的情况下工作。它也解释了为什么复现器不宜被当作论文中所有定位结果都必需的前置条件。

## 5. 实验到底测的是“找到了”，还是“修好了”？

论文没有编号 RQ，实际围绕四件事展开：与现有系统比定位能力；固定修复流程后看收益；检查不同系统的互补性；删除模块看贡献。附录再补成本分析。

### 数据、模型和比较单位

主实验用 **SWE-bench Lite 的300个真实仓库 issue**。SWE-bench 的任务包括问题描述、对应仓库版本、人工修复及验证测试；论文以人工补丁涉及的代码位置作为定位参照，以基准测试是否通过作为修复判据。

消融使用作者命名的 **SWE-bench Common，93题**，即 Lite 与人工核验过的 Verified 子集的交集。Verified 原有500题，但本文没有把完整500题作为主实验。

搜索器使用 **Claude-3.5-Sonnet-20241022，温度0.1**，主实验每步执行一个动作。类分解取3项、文件分解取2项、上下文保留12条，是这里的固定配置。

Table 1 汇总截至 **2025-01-13** 的17种方法及其不同模型配置，比较材料来自公开提交的补丁；其中 AutoCodeRover 由完整 SWE-bench 提交过滤到 Lite，Agentless-1.5 则由作者复现。它提供历史横向坐标。更直接的对照是随后固定相同模型和修复后端的 Agentless 比较。

### 四个指标各回答什么

**文件匹配率**：这一题人工补丁涉及的全部文件，是否都被预测覆盖。**函数匹配率**：全部人工修改函数是否都被预测覆盖，方法也计入函数。二者都是按题判断，再计算满足条件的题目比例。

例如，人工补丁涉及 A、B 两个函数，预测 A、C，函数匹配记为失败；预测 A、B、C，才算成功。这与“命中了一个函数”或 Top-1 命中不同。

只用完整覆盖率会鼓励多报。因此作者加入**函数匹配精度**：每题“预测函数中确实属于人工修改集合的比例”，再对题目求平均。上述两个预测的精度分别为 1/2 与 2/3。它惩罚多报，但与完整覆盖率衡量的是不同性质。

最后的**解决率**由 SWE-bench 的测试评估决定：补丁应用到指定仓库版本后，是否满足修复要求并通过相应回归测试。定位比较与修复比较分开，读数字时才不会把“找对地方”误读为“完成修复”。

## 6. 定位更强，修复也确实受益了吗？

### 6.1 历史横向比较：定位突出，解决率不是所有系统中最高

Table 1 的三个决定性开源比较如下，数字均以300题为分母。

| 系统 | 函数匹配 | 文件匹配 | 解决率 |
|---|---:|---:|---:|
| Agentless-1.5，作者复现 | 58.67% | 78.67% | 34.67% |
| OpenHands + CodeAct v2.1 | 63.67% | 81.67% | 41.67% |
| OrcaLoca | **65.33%** | **83.33%** | 41.00% |

OrcaLoca 的函数匹配是196题，文件匹配250题，解决123题。在该表的开源系统中，它的定位指标最好，但 OpenHands 多解决2题；Kodu 的解决率更达到44.67%，同时函数匹配只有52.00%。

这组结果很有启发性：系统对人工补丁位置的覆盖程度与最终测试成功有关，却不是同一个排序。修复策略、候选补丁选择，以及与人工补丁不同但有效的修改方式，都可能改变最后结果。

表中闭源 Globant 的函数匹配为67.33%，devlo 为66.67%，也高于 OrcaLoca。因此作者的突出结果应准确表述为**该历史比较中开源定位表现领先**，而不是今天的总体最好成绩。

### 6.2 更直接的实验：换定位器，保留相同修复流程

作者把 OrcaLoca 的输出转成 Agentless 格式，补充相关代码依赖，再接入 Agentless-1.5 的修复、验证、补丁选择组件。两边使用同一 Claude 模型，每题生成 **40个补丁**，其中第一个温度0，其余39个温度0.8，采用字符串替换式编辑。

验证同时使用回归测试和复现测试：回归测试筛选温度为0；复现测试也生成40个样本，温度安排同样是1个0加39个0.8，再依据验证结果选择补丁。Agentless 原定位流程每题有4次采样，每个定位结果分配10个补丁，总量也是40。

为了公平描述这4次定位，作者报告了两种汇总方法：先把四次函数集合求并集，再算指标，称为 Union of Locs；或逐次计算后求均值，称为 Mean of Locs。前者覆盖更宽，通常也更杂。

Table 2 的关键数值是：

| 定位结果口径 | 函数匹配率 | 函数匹配精度 |
|---|---:|---:|
| Agentless，四次结果取并集 | 58.67% | 29.01% |
| Agentless，四次指标取均值 | 47.33% | 33.72% |
| OrcaLoca | **65.33%** | **38.34%** |

对并集口径，OrcaLoca 的完整匹配高约6.67个百分点，精度高9.33个百分点；对逐次均值口径，分别高18.00与4.62个百分点。它并不是靠多报函数换覆盖：两种指标都提高了。

同一修复流程下，解决率从 **34.67%（104题）提升到41.00%（123题）**，多解决19题，即约6.33个百分点。这个实验给出的实际结论是：**OrcaLoca 这套定位及上下文准备流程，不仅改善了位置指标，也能给既有修复器带来收益。**

### 6.3 Figure 4：新系统还补上了别人的盲点吗？

作者把 OrcaLoca、Agentless、AutoCodeRover、OpenHands 的成功题目画成集合交叉图。共同函数定位成功的中心区域为113题，共同修复成功为65题；OrcaLoca 自己独有的区域分别是 **6个定位成功、8个修复成功**。另一方面，OpenHands 也有16个独有修复成功，Agentless 有3个，AutoCodeRover 有2个。

所以互补性是真实值得注意的现象：OrcaLoca 并不是把其他方法成功的题目简单重复一遍，其他方法也仍有它未覆盖的能力。这是研究组合策略的动机，但论文没有进一步运行“按题选最合适系统”的集成器。

## 7. 哪个机制有帮助？93题消融给出的答案

Table 3 在同一 Common 子集上保留其余系统，分别取消优先级、文件/类分解、歧义分解、上下文裁剪，比较函数完整匹配率。

| 配置 | 函数匹配率 | 对应成功题数 |
|---|---:|---:|
| 完整系统 | **76.34%** | **71/93** |
| 去掉动作优先级 | 73.12% | 68/93 |
| 去掉文件/类分解 | 72.04% | 67/93 |
| 去掉歧义分解 | 70.97% | 66/93 |
| 去掉上下文裁剪 | 72.04% | 67/93 |

成功题数由原 Table 3 直接报告。四种删除分别少成功3、4、5、4题。

从方法逻辑看，取消优先级会让当前最急迫的线索更难被及时追踪；取消文件/类分解会削弱由粗到细获取正文的过程；取消歧义分解会使名字匹配停留在候选列表；取消裁剪则让累积上下文继续膨胀。结果与这些设计动机一致。

**最直接的 takeaway 是四个机制在这套系统中都提供了正向增量。** 最大的单项下降来自取消歧义分解，说明“同名实体列出来”与“逐个准确查到”之间的执行环节值得认真设计。3–5题的差距也提醒我们保留实验规模感：这是指定配置下的组件比较，不是已经排好了所有场景中的模块重要性。

## 8. 性能提升付出了什么成本？

正文给出的每题搜索调用费用约 **0.87美元**，修复部分约 **0.90美元**，合计 **1.77美元**。附录 F 的 Table 4 将其与 Agentless-1.5 的1.05、OpenHands 的1.14、AutoCodeRover 的1.30、SWE-agent 的1.62作比较。虽然表题称 token cost，正文的费用口径表明这些是基于 token 的金额，而不是“1.77个 token”。

这张表的实际信息是：OrcaLoca 主配置优先提高定位质量，**总费用并不比所列基线更低**。把“上下文裁剪”直接等同于“整个系统更便宜”，会漏掉额外搜索、评分和修复的成本。

作者另外尝试每轮同时执行队列里前两个动作，让模型一次处理多个新结果。Table 5 只抽样10个 issue：例如 `pytest-8906` 的费用由1.93降至0.87，`sympy-14774` 由0.53降至0.15；也有 `django-16255` 从0.17升至0.18。

作者按费用分桶加权，**估计**平均定位费用从0.87降至0.58，减少约34%，总费用相应估计为1.48，并报告抽样中定位正确性没有受损。这说明减少轮次有优化空间，同时也呈现了一个小反例：批处理并非每题都会省钱。这个估计不是300题完整重跑的统一成本结果。

计算开销还包括按仓库和 commit 建图，以及裁剪时计算最短路径。论文讨论了未来缓存图、减少重复建图和使用推理缓存的可能性，没有给出覆盖这些部分的端到端墙钟时间对照。

## 9. 证据审查：哪些结论已经站稳，哪些仍值得补？

### 更扎实的是系统收益，尚待拆开的是具体机制

同模型、同修复后端、同40补丁总量的对照，比把不同公司榜单成绩直接相比更有解释力。但改变的是整套定位工作流，包括搜索路径、上下文选择、依赖补充和相关调用成本。它支持“这套方案有效”，尚不能把19题收益单独分配给某一种裁剪语义。

同样，去掉裁剪会同时改变上下文内容和长度；去掉分解会改变探索覆盖和动作数；优先级会影响后续看到了哪些证据。消融没有通过等 token、等调用或析因设计将这些因素分离。若要研究具体中介机制，还需要进一步控制。

### 指标是人工补丁覆盖，而不是唯一正确答案

函数完整匹配要求全部 gold 函数都出现，精度又惩罚 gold 之外的预测。这个组合能避免无限多报，但人工补丁并不一定囊括所有有效修复位置，也未必涵盖理解问题所需的全部证据。定位时值得读的调用者，不一定需要被修改。因此最好同时看完整匹配、预测精度、解决率及实际失败轨迹。

排行榜材料还受到模型、工具、预算和提交版本差异影响。Agentless 复现成绩与其官方提交不同，作者把可能原因归于公开复现脚本版本。论文没有给出多随机种子或置信区间，也没有系统分层报告哪些项目、错误类型受益最大。

### 裁剪存在“错误假设影响下一轮证据”的潜在反馈

裁剪的参照是模型当前提出的可疑位置。如果最初怀疑错了，那么真正重要但结构上较远的代码可能更难留在下一轮输入里；多个候选分散时，平均距离也可能偏爱折中位置。这是从规则推导出的潜在风险，论文没有专门的受控失败实验去量化它。

CodeGraph 也不是完整程序语义：当前实现面向 Python，附录承认引用解析仍有不足；跨语言边界和复杂动态关系需要更强的分析支持。论文主要验证一个 Claude 模型，讨论中的开源模型和跨语言推广仍待实验。

### 复现与实现细节还有可审计空间

复现成功由模型对日志作判断，38%的成功率之外，没有系统报告这个判断器的误报率，也没有单独消融复现线索的贡献。早停阈值、保留12项和分解取2/3项都没有敏感性曲线。正文给出了工作流，但 Algorithm 1 先把队列初始化为空、再要求队列非空进入循环，省略了实际启动动作如何进入队列；复现时应结合实现补齐这一步。

论文也没有系统失败案例分类。上面的 Django 成功例、10题成本抽样和定性限制，各自提供了线索，不应被当作已经覆盖所有失败模式。

### 两处数表口径要按实际数据读

Table 2 下方文字把约6.67个百分点的匹配增量与4.62个百分点的精度增量并列为“两种口径都如此”，实际上它们分别对应并集与逐次均值两个不同基线。本文已按各行重新比较。

Figure 4 左侧标注 OrcaLoca 函数匹配总数为194，而 Table 1 的65.33%对应196题。论文没有解释这2题的差异；因此总体成绩采用 Table 1，独有6题和8题仅按 Figure 4 的集合分析报告，不将两套计数强行拼成一致结果。

## 10. 读完真正该留下什么？

1. **搜索 Agent 需要管理尚未执行的动作。** 模型提出多个线索之后，动态调度能把新出现的重要线索提前，减少按旧顺序机械搜索。
2. **骨架的价值在于引导精确读取。** 大对象分解和名称消歧，不应只产生更多说明文字，还应转成可执行查询。
3. **仓库可检索空间与当前工作上下文可以分开。** CodeGraph 提供地址和关系，裁剪管理本轮看见的代码，两者不是同一种删除操作。
4. **定位收益要由下游结果验收。** 这里既有更高的覆盖和精度，也有同修复流程下多解决19题的证据。
5. **系统收益已有支持，普遍机制仍需检验。** 当前证据覆盖指定 Python 基准、Claude 配置和93题消融；最优距离规则、跨模型普适性以及每个模块的独立因果贡献仍是开放问题。

最值得记住的一句话是：**好的定位流程不仅要决定下一段代码去哪里找，还要保证查到的证据能在恰当的时刻参与判断。**

## 11. 对当前 SeerAgent 研究的启发

最新研究记录的主线已经转为自主端到端的文件级漏洞定位。V2 改善了多范围证据记录、目录导航、工具反馈和最终输出协议，但“最终能合法交卷”之后，更棘手的问题浮现出来：正确文件读到了却没进入最终结果；文件选对了，解释的漏洞机制却没有对应到实际代码。

OrcaLoca 提供的是直接的机制先例，也帮助把后续实验问得更具体。

### 11.1 把“已发现、已读、仍可见、最终选中”分开记录

OrcaLoca 已经区分动作队列、历史查询、当前代码上下文和最终定位。SeerAgent 可以进一步把同一文件的多个读取区间与不同假设显式关联，记录每份证据何时进入、退出、恢复，以及最终选择究竟引用了哪一份代码。

最省成本的第一步是离线分析已有轨迹：真实相关文件在哪个阶段被遗漏？发现后没读、读了但关键范围没覆盖、证据后来不再可见、还是结论阶段没有使用？这些阶段分别指向不同改进，比一个总文件 F1 更能指导下一版。

### 11.2 重复读取应按“是否增加证据”判定

OrcaLoca 用实体 UID 消除重复访问，对于静态的类或函数查询很自然。但范围级定位里，同一文件的第二次读取可能打开了新的行区间，或是在新假设下核实先前看过的语句。仅按文件名去重，会把有价值的核查也挡住。

因此可以把重复读取拆成：同范围且无新证据、范围扩展、为区分竞争机制而复核。先统计已有轨迹，再决定哪类值得压缩。被移出工作上下文的证据保留来源指针和恢复通道，有利于把省上下文与永久遗忘分开。

### 11.3 研究对象应包含“同文件内的机制区分”

文件级正确只说明空间位置对了。例如临时文件清理缺陷与大小限制逻辑可能同在一个文件，读到后一部分不能证明理解了前一种漏洞。可为同一文件维护多个候选解释及其支持、反证区间，再检查最终结论有没有指向实际读到的关键控制流。

这会把新工作的重点从“加一个图、搜索、再剪枝”的已有组合，推进到**证据如何支持或推翻假设，以及如何传到最终文件选择**。OrcaLoca 的可疑节点集合没有系统处理这个更细的语义层。

### 11.4 主实验与机制诊断可以分别做好

主结果仍应是自主端到端文件定位，在合理成本下比较文件精度、召回、F1、合法完成率与调用/token开销。问题输入、仓库版本、可见工具和预算应交代清楚；OrcaLoca 有时使用 issue 复现信息，不能把这类额外信息静默迁移到只给漏洞类型或受限线索的设置。

如果后来要解释具体机制，再对相同实例和可比较状态做配对或随机干预，例如是否保留证据来源、是否保留竞争假设、裁剪后是否可恢复，同时记录内容量和实际成本。历史轨迹回放适合诊断组件，端到端重跑适合回答整体收益，两种问题不必硬塞进同一个评估规则。

当前小规模开发集能帮助发现故障，尚不适合把一次整套协议改动的变化归功于某一个模块。先把“证据在哪一环丢了”量化清楚，会比继续添加更多搜索入口更接近眼下的瓶颈。
