## 一、给你整个仓库和一种漏洞名称，你会从哪里开始？

安全工程师收到的任务可能只有一句：“请检查这个项目有没有跨站脚本问题。”仓库却有几十、几百甚至几千个文件。模型即使知道什么是跨站脚本，也不等于知道应该打开哪个文件；而打开了相关文件，也不等于能判断修复之后原来的问题已经消失。

论文附录中的真实例子很小：`yahoo/serialize-javascript`，仓库约134 KB，任务ID为 `T0aMD9EF`，输入只有CWE-79的通用描述。正确文件是 `index.js`。GPT-5.5 xhigh逐步查看目录、读取带行号的源码片段、搜索序列化与转义相关实现，最终命中文件；另一条Llama轨迹停留在广泛搜索，未形成足够的目标源码阅读，耗完预算后没有提交。这不是考模型能否背出XSS定义，而是考它能否把一个抽象安全问题变成仓库内的有效调查。

VLoc Bench把这一步单独提出来评测。以往不少安全基准直接把可疑函数给模型，或以最终能否修好、能否生成有效攻击来评分。前者已经替模型完成了寻找代码，后者把寻找、理解、执行、修复混在一起。本文要测的是更窄但更基础的能力：**从弱线索出发，在完整仓库中找到安全补丁涉及的实现文件；再面对修复后的同一仓库，能否停止报告这个问题。**

它值得读，不仅因为有500个样本和27个模型，而是因为前后两种状态把一个常被平均分掩盖的矛盾显露出来：有的模型很会报位置，却几乎不会说“没有”；有的模型经常什么也不交，看起来误报极低，却根本不具备定位能力。

## 三、先把一个样本拆开：题目、答案与两次考试

### 3.1 从安全公告构造前后两个仓库

图1的核心不是两个模型，而是**同一任务的两份代码状态**。作者从GitHub Security Advisory中提取仓库、CWE分类、安全修复提交和相关元数据：

1. 修复前的仓库快照构成Phase A。模型寻找与目标弱点相关的实现文件。
2. 修复提交对应的仓库快照构成Phase B。模型需要识别记录中的漏洞已被处理。
3. 安全补丁触及的实现文件形成文件级参考答案；测试、文档和配置等文件被排除。

Phase B不是把A阶段的发现拿给模型复核。两阶段沿用同样提示、工具和预算，单独运行，不把A的探索历史传给B。这样改变的是仓库状态，而不是额外赠送一份定位答案。

模型实际获得的是CWE的**通用类别描述**，例如“跨站脚本”所属弱点的解释，而非这条公告的具体攻击路径。GHSA描述、CVE编号、版本影响范围、严重程度、补丁和文件提示不进入任务输入。其意义是削弱可直接定位到项目特定实现的信息，让模型必须探索仓库。它也意味着这不是现实中所有安全调查场景的平均难度：收到详细漏洞报告、PoC或运行时堆栈的工程师有更多线索。

### 3.2 标准答案测的是修复位置，不是完整漏洞机制

设补丁改了两个实现文件，模型交了其中一个，便获得部分召回；如果模型指出的是攻击触发处，却不在补丁文件中，文件评分可能不给分。

这个选择有实际理由：安全修复者最终需要知道哪些实现文件要改，而公开补丁可大规模提供可复现标签。代价是标签与“所有和漏洞有关的代码”不是一回事。补丁可能包含防御性增强、重构或关联修改；漏洞所依赖的调用者、数据流和运行时条件可能根本未改。**补丁文件集合既不是完整支持证据集合，也不是已经证明的最小因果充分集合。**

官方评分代码进一步把实现文件操作化为扩展名白名单，加测试路径过滤。核查时，`is_test_file`不只是识别测试目录，而会检查路径中是否含有 `test`、`_spec`、`spec/`、`__tests__/` 等字符串。这种启发式可规模化运行，也可能误排名字里恰好含相关片段的生产代码。研究者复用标签时应冻结规则，而不是凭“实现文件”四个字假定人工逐项审定。

### 3.3 样本规模不等于信息独立性

最终数据有500条漏洞、290个仓库、147种CWE。附录图5给出生态分布：Go 215、Maven 104、npm 88、pip 52、Rust 40、Composer 1。Go占43%，所以一个整体均值在很大程度上也反映Go任务表现；不能据此宣称六生态获得了同等充分验证。

图6对应严重程度：Critical 57、High 219、Medium 194、Low 30。约78%带CVE，年份覆盖2016至2026，其中2026年21条。仓库大小从约12 KB到840 MB，中位数4.2 MB；参考答案中位数3个文件，单文件任务占28.4%，至少10个文件的任务占14.8%。这比“给定一个函数判有无漏洞”多了显著的搜索与多目标覆盖负担。

论文描述的过滤包括：排除只改测试、文档、CI或锁文件的公告；排除无法访问的仓库；排除补丁触及超过50个文件的情况；排除缺失CWE的任务。公开manifest与最后一项存在差异，后文会给出本次只读核查结果，不能把论文文字自动当作发行数据已经满足的保证。

## 四、Agent究竟怎样跑，什么被控制住了？

### 4.1 统一的是调查接口，不是所有计算资源

每个任务使用全新的Ubuntu 24.04隔离环境，2 CPU、4 GB内存，仓库只读、禁用网络、不允许修改代码或运行项目程序。模型通过终端做目录浏览、文本检索、源码阅读等操作。单命令超时10秒，结束后销毁环境。因而这里主要测静态阅读与推理，不测编译、动态复现或测试执行能力。

预算为最多15次终端调用和20个生成回合，连续3轮没有工具调用也会停止。提交答案是独立的工具动作，不能把“15次终端调用”误写成“整个交互最多15步”。附录成功案例用15次终端调用、17轮模型生成，正好说明了这种区别。

比较覆盖27个语言模型，以及Semgrep、按CWE选择规则的Semgrep-CWE、CodeQL、Horusec四类静态工具。静态工具代表固定规则的代码分析，不是另外四个语言模型；它们使用自己的分析器和规则集，不能把统一Agent循环理解成所有系统都采用相同内部算法。

语言模型每个任务独立运行3次。论文主体概述温度0.3，但附录D更准确地区分了服务方式：本地开源模型用vLLM 0.19.1、H100、bfloat16、32768上下文上限，每轮最多16384生成token，温度和frequency penalty均为0.3；闭源API使用提供方默认温度及惩罚配置，xhigh还指定更高推理强度。原生工具模板也并非完全一样，Antares使用定制Granite模板。

因此本文较好控制了**题面、工具定义、Agent循环和命令预算**，没有把所有模型内部推理量、默认解码和模板统一。这是解释排名时必须保留的实验坐标。

### 4.2 Phase A如何评分？

直觉上，既要找到应该报的文件，也不能把整个仓库都报上去。令预测集合为S，参考集合为G：

- Precision = |S∩G| / |S|，回答“报出的文件有多少落在补丁标签内”。
- Recall = |S∩G| / |G|，回答“参考文件找到了多少”。
- File F1 = 2PR / (P+R)，同时惩罚漏报与多报。

教学例子：G有3个文件，模型报2个且都正确，则P=1、R=2/3、F1=0.8。它不是三分之二“完全成功”，而是部分覆盖。提交多一批无关文件会降低P，即使R不变。

各任务先各自计分，再宏平均，最后汇总3次运行。因而一个10文件任务不会简单按文件数获得一个1文件任务的十倍权重。输出虽然可以包含顺序，评分按集合比较，不是检索排序的MRR或Recall@k。没有提交的A阶段结果计0，包括主动说未找到和预算内没能结束。

### 4.3 Phase B的TNR需要读到实现层

Phase B希望测“修好之后别再报这个漏洞”，论文报告True Negative Rate，即不报告漏洞的比例。最重要的细节是，**评分并不只认可有充分证据的明确无漏洞判断**。文中的操作定义与官方 `score_phase_b` 都围绕 `submitted_nothing`：没有提交位置的运行会被计为真阴性，包括未完成、预算耗尽，以及部分API错误或拒答等情况。

Agent代码在API错误退出后，若没有已提交文件，也可能留下这种状态。这不是说所有高TNR都由错误组成，而是说仅凭TNR不能区分“读懂补丁后确认问题消失”和“根本没交卷”。实现对显式空列表等终态还有特定处理，复现时应直接使用终态字段，不要只按结果文件列表为空自行重构评分。

另外，修复后仓库可能还有其他未标注漏洞。模型报告了一个真实但不同的问题，在这个针对已知补丁的协议中仍可能记为误报。因此，TNR是**这个任务与评分规则下的操作性阴性率**，不是整个仓库被证明安全的概率。

## 五、第一组结果：最强模型也远未解决仓库级定位

表2固定500个Phase A任务，比较不同模型和工具的宏平均文件定位表现。以下保留决定主要结论的对照：

| 系统 | File F1 | Precision | Recall |
|---|---:|---:|---:|
| GPT-5.5 xhigh | 0.229 | 0.310 | 0.221 |
| GPT-5.5默认 | 0.221 | 0.305 | 0.211 |
| Antares-3B | 0.223 | 0.298 | 0.219 |
| Antares-1B | 0.209 | 0.268 | 0.221 |
| GLM-5.2 | 0.186 | 0.226 | 0.186 |
| Gemini-3-Pro | 0.152 | 0.190 | 0.153 |
| Antares-350M | 0.135 | 0.144 | 0.176 |
| Gemma-4-31B | 0.101 | 0.131 | 0.097 |
| GPT-5-Mini | 0.098 | 0.115 | 0.096 |
| Qwen3.5-122B | 0.091 | 0.124 | 0.083 |
| Semgrep | 0.086 | 0.091 | 0.155 |
| Semgrep-CWE | 0.052 | 0.057 | 0.071 |
| CodeQL | 0.023 | 0.025 | 0.030 |
| Horusec | 0.020 | 0.021 | 0.038 |

第一，0.229是宏F1，不是22.9%的任务全部找对，也不是漏洞检测准确率。即便最强系统，完整仓库搜索与多文件定位仍相当困难。

第二，专用小模型是重要反例。Antares-3B与GPT-5.5默认接近，Antares-1B也明显超过多数通用开源模型；但是Granite基础模型接近零，不能把结论改写成“小模型天然更适合安全”。比较同时改变了训练、模型家族和对工具任务的适配，不是仅改变参数量的控制实验。

第三，更强的通用品牌或更多参数不保证这个协议里更强。Qwen3.5的27B和122B同为约0.091，35B-A3B为0.085，9B为0.043；GPT-OSS 20B/120B约0.070/0.069；Llama-3.3-70B约0.012。GPT-5在此表为0.048，明显落后于Mini。作者讨论安全对齐、拒答和探索行为作为可能原因，但没有单独操纵这些机制，不能把每一个差距都解释成“模型不懂安全”或“安全对齐导致退化”。

第四，更精确的规则提示不必然改善标签F1。Semgrep-CWE比默认Semgrep更低，可能反映规则覆盖与任务标签的适配问题；它不能证明CWE信息对任何系统都无用。CodeQL等工具在这个评分与运行配置下的低分，也不等于它们在工业告警、查询开发或动态工作流中没有价值。

**这一组结果最稳妥的结论：专用训练可以显著改变仓库安全定位的能力画像，而现有系统整体仍有很大未解决空间。**

## 六、第二组结果：会报，不代表会收回；不报，也不代表验证成功

表3把同一批方法移到修复后仓库，排名发生明显变化：

| 系统 | Phase A F1 | Phase B TNR |
|---|---:|---:|
| GPT-5.5 xhigh | 0.229 | 0.279 |
| GPT-5.5默认 | 0.221 | 0.192 |
| Antares-3B | 0.223 | 0.034 |
| Antares-1B | 0.209 | 0.008 |
| Qwen3.5-122B | 0.091 | 0.750 |
| GPT-5-Nano | 0.024 | 0.868 |
| Granite-1B | 0.000 | 1.000 |
| Semgrep | 0.086 | 0.912 |
| Semgrep-CWE | 0.052 | 0.996 |

Antares-3B的A成绩相当有竞争力，但B的TNR只有3.4%；1B甚至只有0.8%。这说明学会积极定位的系统未必学会在补丁之后停止提交可疑位置。反过来，Granite-1B在A中为零、B中却达到1.000，正说明不能把阴性率独立包装成安全验证能力。

GPT-5.5提高推理强度后A与B均略有提高，但B仍远未达到可靠验证水平。Qwen和部分小型闭源模型的阴性率更高，至少有一部分应结合它们在A中的未提交与失败行为解释。静态工具往往更克制，不过默认Semgrep的A召回高于精确率，说明也不能简单把它们概括成“绝不多报”。

这组实验的价值，是把**定位积极性与停止报告能力**放在一起展示，而非宣布有一条模型排名通吃两个任务。若真要测“知道自己不知道”或“确认漏洞消失”，后续还需分开明确无漏洞、运行故障、超预算和拒答，并核查负例的有效性。两个边际均值也没有直接回答：究竟有多少任务，是同一系统在A定位正确、在B又明确正确收回？这需要任务配对的联合成功指标。

## 七、参数和成本：专用小模型为何值得关注，又不能夸大什么？

### 7.1 图2不是参数量决定能力的定律

图2以总参数量的对数为横轴，File F1为纵轴；13个具有参数信息的通用开源模型拟合线性趋势，Pearson相关约0.50。专用模型另行展示，MoE使用总参数而非激活参数。

总体上更大模型有一些优势，但散点离趋势线很远，同等规模之间差异明显，Antares这类小型专用模型则偏离通用缩放直觉。图所支持的是跨系统相关，不是把一个模型扩大十倍必然得到多少提升。架构、训练与适配都随模型变化，总参数也不等于单次激活计算量。

### 7.2 附录D与表8把成本定义讲清楚

完成500个A阶段任务，表8报告：Antares-350M约11分钟、0.60美元；1B约13分钟、0.71美元；3B约15分钟、0.82美元；GLM-5.2约50分钟、12.50美元；GPT-5.5 xhigh约5小时、141美元。

本地模型使用单H100、16并发worker，费用依据每小时2至4美元的租赁估算；API使用评测时即2026年6月的价格。这是历史评测成本，不是今日报价，也不包含模型训练。3B与xhigh的费用比约172倍；正文的约170倍可按这一对理解，不能把最低0.60与最高141两个端点也算成170倍。

Claude没有纳入主表，是预算覆盖不足：标准接口全量评估估计超过600美元，另一个不受同样限制、可使用子Agent的原生配置估计约1658美元。后者并不是本表同接口的成绩或可直接比较的基线。

因此成本结论不是“任何场景3B都能替代前沿模型”，而是：在这个有限工具、有限调用、文件级任务中，专用后训练有可能以明显较低的服务成本取得相近A阶段F1，但其B阶段行为是另一项必须付出的质量代价。

## 八、仓库为什么难：回归分析回答的是关联，不是干预收益

### 8.1 先理解作者想从约四万次运行中学什么

一个大仓库可能难在文件多、层级深，也可能难在逻辑分散。仅报告“某模型平均更强”解释不了哪些任务所有模型都失败。作者把模型、任务和重复运行组合成约四万条观测，用Lasso回归分析运行F1与特征的关系。

Lasso可以理解为带收缩的线性预测：每个标准化特征乘一个系数，组合起来预测分数，同时惩罚过多、过大的系数。正系数表示在这个线性模型中与较高F1关联，负系数相反；它不是“人为改变该特征后F1必然改变多少”的因果量。

仓库侧52个特征包括结构与大小、漏洞元数据、生态和严重程度；模型侧15个特征包括参数规模、类别与家族。表9给出完整分组，总计67项。作者用5折交叉验证选择正则参数，并报告拟合和交叉验证R²。R²反映解释了多少结果变异，不是预测准确率。

### 8.2 表4：代码是否集中，比严重程度标签更能预测难度

仅使用仓库侧特征，训练R²=0.188、交叉验证R²=0.164，52项保留48个非零系数。最大的正系数是最大五个文件占总源码行数的比例 `top5_loc_share`，约+0.082；其100次bootstrap均非零，95%区间约[0.072,0.091]。

直觉是，在相同短预算里，核心代码集中在少数大文件中的仓库更容易被覆盖，分散在大量位置的仓库更难。但这只是与分数的关系，不代表把代码机械合并为五个文件就能提升定位。

其余较大系数包括大小桶+0.038、压缩包大小对数−0.037、总源码行数+0.025、最大文件长度−0.023、浅层文件比例+0.018。大小桶与连续大小正负相反，不是“作者同时证明仓库大既好又坏”，而是共线变量与非线性残差共同作用的结果。参考文件数系数约−0.006，严重程度及相关分类的总权重较低，也不能据此说多文件定位没有负担。

### 8.3 图3：结构组的重要性较高，仍有大量问题没解释

加入模型特征后，67项保留57项，训练R²=0.241、交叉验证R²=0.192。图3把同组系数绝对值相加：结构0.285、模型类别0.063、仓库大小0.055、模型规模0.043、漏洞元数据0.034、生态0.031、模型家族0.030、严重程度0.010。

这就是“仓库结构权重约为模型类别4.5倍”的出处。换ElasticNet，该比值约5.7；按特征组置换带来的R²下降衡量，约3.2。替代分析说明趋势不完全依赖某一种惩罚函数，但这些比值不是结构因果效应是模型效应的几倍。

只用15个模型侧特征时，表5给出训练R²=0.053、交叉验证R²=0.007；专用模型类别和参数规模仍有正系数，但不足以预测某一次任务成败。这与图2的参数相关不矛盾：图2看模型均值，回归看单次任务结果，分析单位不同。

更应该记住的是，组合模型在样本内仍有约76%的变异没解释。代码语义、安全机制、模型具体决策和交互动态，都不是这些静态统计充分描述的对象。

### 8.4 图4：仓库规模与生态的分层现象

小于100 KB的20个任务，在所有27个模型上平均F1约0.598；大于10 MB的223个任务约0.058，相差约十倍。63%的任务落在至少2 MB的两个困难区间。这里每个柱子是跨模型的平均值，并非最强模型从0.598下降到0.058。

生态上Maven平均更难，pip与npm较容易，Go居中但样本最多。生态同时包含语言习惯、项目结构、仓库大小和漏洞类型，不能把生态均值直接当语言的因果作用。

尤其值得注意的是，38.4%的任务，即192个任务，在所评估系统中没有获得正确文件命中，论文按File F1=0描述。这不是“没有系统达到满分”，而是更强的失败现象。未解决任务中Go约47%、Maven约31%。增加模型规模或更换一个模型并没有自然消除这批共同难题。

## 九、搜索过程与失败终态：工具调用多一点就会更好吗？

作者把终端动作概括为搜索、读取和探索结构。模型平均工具调用次数与平均F1的Pearson相关约0.72，p<0.001。较强系统通常把有目标的搜索和源码阅读组合起来，而不是一直列目录或广泛搜索；错误率低的模型表现更好，错误率高于15%的模型通常较差。

这些现象与开头的 `serialize-javascript` 案例相呼应：成功轨迹把抽象CWE问题逐渐收敛到一个可读、可判断的实现，失败轨迹消耗了调用却没建立有效证据。命令执行错误也占用稀缺预算。

但这里并没有“强制同一个模型多调用三次”的干预实验。较强模型可能本来就既能有效使用工具又能推理；容易任务也可能更早结束。作者的模型级相关不能证明增加调用一定提高分数，更不能推出一个最佳搜索/阅读比例。

### 9.1 表6的失败分类是可复现的终态规则

为避免只凭挑选案例解释失败，作者对所有F1<1的运行按确定性规则分类：

- 未交文件且调用不超过3次：premature abstention，过早停止。
- 未交文件且调用至少13次：budget exhausted，接近预算耗尽。
- 其余未交文件：inconclusive，未形成结论。
- 有交文件且召回大于0、精度至少0.5：partial recall。
- 有交文件且召回大于0、精度低于0.5：broad submission。
- 完全没命中，且预测文件数超过参考数两倍：broad submission、zero recall。
- 剩余零命中提交：wrong localization。

这些名字需要与规则一起看。`budget exhausted`从13次起算，不是每条都恰好用满15次；`partial recall`在规则上可能包含召回已满但有少量误报的情况，不宜只按名称理解。它们是输出行为标签，不是对模型内在原因的人工语义鉴定。

约38500条非满分运行中，接近预算耗尽占32.3%，过早停止16.9%，未形成结论9.9%；合计59.1%没有交文件。有提交但定位错占27.4%，部分命中8.5%，广泛提交2.6%，广泛提交且零命中2.4%。因此失败不只是“找到错误文件”，还有相当多是不能交付可评分答案。

### 9.2 表7让相似均分的不同弱点浮现出来

表7换成“每个模型所有任务运行”的百分比，包含完美成功，与表6只看失败的分母不同。GPT-5.5约10.0%完美、15.6%接近耗尽、46.4%错误定位、23.2%部分命中；Antares-3B约9.8%完美、2.4%接近耗尽、57.2%错误定位、22.6%部分命中。两者平均F1接近，但Antares更愿意提交，因此也更容易报错。

Qwen3.5-122B约66.2%接近耗尽，Llama约75.3%过早停止，CodeScout约52%未形成结论。这提示工程改进方向可能不同：延长预算未必解决过早停止，改善JSON格式也不必然修复机制误判，而鼓励积极提交可能抬高A分数同时损害B表现。

表7中标作F1=1的10.0%是**完美任务比例**，不能与表2的平均F1=0.221混用。分清这个细节，才能正确解释“总体有部分收益”和“多少任务完整解决”两类结论。

## 十、把证据集中审一遍：哪些结论扎实，哪些仍缺一步？

### 10.1 任务设计有价值，但补丁不是机制真值

两阶段、相同弱线索和有限工具使任务边界清楚，公开快照与manifest也便于复现。然而补丁标签仍有三类限制：某些改动不一定是漏洞必要位置；某些必要理解证据不在补丁中；某些补丁新增文件在漏洞前根本不存在。若一个定位器只允许输出已读取的现存文件，遇到最后一种任务时可能天然无法满召回。

文件级命中还允许“找对文件、解释错函数”。在同一文件有多个相似机制时，F1无法判定模型究竟理解了哪个。这并不否定文件级任务，只是不能把文件F1等价成机制正确率，更不能把未改动源码全部当作干扰。

### 10.2 Phase B应把“不提交”与“验证成功”拆开

当前TNR包含失败终态，会奖励某些不工作的系统。更合适的补充是并列报告：明确有证据的无漏洞提交、正常定位提交、超预算、格式失败、API失败、拒答；再报告A正确且B明确正确的配对成功率。后者仍需要注意修复后其它漏洞与标签不完备。

这属于从评分实现推出的测量建议，不是作者已经执行的新实验。不能在复用论文时悄悄改评分，再拿新分数与其主表直接排名。

### 10.3 回归尚不能支持“结构比模型重要”的强因果版本

结构组本来包含更多特征，仓库特征在500个任务间变化，模型特征只在27个系统间变化；标准化与分组置换缓解不了所有可比性问题。约四万条运行也不是约四万个独立仓库，同一任务、仓库和模型重复出现。

本次只读核查官方 `docs/code/lasso_regressor.py`，看到普通 `LassoCV(cv=5)` 与 `cross_val_score(..., cv=5)`，没有按任务或仓库使用GroupKFold，且标准化在交叉验证之前完成。公开脚本与论文的特征表也并非可以不经核对就逐项等同。这不足以断言每一折究竟有何具体重合，但足以说明：**所报CV分数不能自动解释成对全新仓库的泛化性能**。任务/仓库分组划分、训练折内标准化和分层bootstrap会是更严格的复核方向。

另一个容易漏掉的细节在表9：部分“仓库侧特征”包括修复后压缩包大小、前后大小变化和参考文件数量。它们用于离线解释难度可以成立，却不是部署前面对未知漏洞都能获得的信息。因此不要把这套分析直接包装成不需要补丁的在线难度预测器。

### 10.4 官方manifest的只读核查：发行版本确实值得单独审计

本次读取官方仓库 `fa50b671aa0b954d73691d6ef8d592d42a2ac1e0` 版本的 `data/manifest.csv`，对应blob `278cdb180541439c17b36d61d915dd6486eae8fa`，没有运行模型或改动实验数据。结果如下：

- 共500条，六生态计数与论文一致。
- **19条的CWE ID与描述均为空列表**，与论文所述排除缺失CWE不一致。官方Agent对此会采用“Unknown vulnerability class”一类回退，而非获得具体弱点提示。
- 按 `(repo_full_name, vulnerable_commit_sha, 原始cwe_description)` 精确分组，500条形成**469个输入签名组**，其中19组包含多条记录。
- 这19个重复输入签名组里，有1组的原始参考文件列表字段并不完全相同。这里只核对字段，不把列表文本不同直接断言成语义冲突；具体集合、补丁和公告关系仍需逐组审查。

469是本次明确规则下的计算，不是论文宣称的“独立漏洞数”，也不是用所有模型实际wire内容去重后的最终独立输入数。相同输入可对应不同公告记录，是否应合并取决于研究问题；关键是不要把多条记录默认当成完全独立的观察。

这些发现不是因分数不好而删除样本的理由。严谨做法是保留原协议主表，另报缺CWE、重复签名和标签争议的分层结果，事先规定独立任务代表的选择。否则质量过滤也会变成事后挑样本。

### 10.5 还需要保留的外部效度边界

公共安全公告与公开补丁存在模型训练污染可能；年份跨度或21条2026样本不能单独证明无污染。专用Antares与该基准出自同一研究线，也不构成独立外部复制。15次终端预算、无网络、无执行定义了一种受限工作流，不能直接外推到长时间、可复现攻击、可运行测试的安全Agent。

作者有模型比较、替代回归和失败分析，但没有对工具组合、上下文语义竞争或训练组件做足够的独立因果消融。不要把观察到的搜索方式、模型类别或结构系数写成已证明的改进机制。

## 十一、读完后真正应带走什么？

本文最有说服力的贡献，是让“仓库级漏洞定位”成为一个独立、可重复测量的对象，并把修复前积极发现与修复后克制报告并列起来。最强系统平均File F1约0.229，192个任务对所评估系统仍是零命中；专用小模型可以在A阶段很强，但这不保证B阶段可信。

仓库结构、规模和探索行为与难度有明确关联，说明问题远不只是模型参数量。与此同时，补丁文件真值、未提交即阴性的定义、样本输入重复和回归划分，限制了我们能从这些分数推出多强的语义、泛化与因果结论。

一句话概括：**这是值得直接借用协议并认真审计的定位基准，不是已经认证“模型理解漏洞机制”或“过滤某类上下文有效”的证据。**

## 十二、与causal-review / CPI研究的具体接点

### 12.1 首先区分“同数据”“同协议”和“独立验证”

官方manifest确实包含 `NXIHKkeO`，对应 `mmaitre314/picklescan` 的Python任务，参考文件为 `src/picklescan/scanner.py`；也包含 `MgW6tpfT`，对应 `sidorares/node-mysql2` 的JavaScript任务，参考文件为 `lib/helpers.js`、`lib/parsers/binary_parser.js`、`lib/parsers/text_parser.js`。它们可作为与项目既有实例对照的两个已知例子。

这只能证明这些ID属于官方数据，**不能据此宣称当前38个独立任务全部重合，更不能把JavaScript的第二例算入Python子集**。本次未核实冻结38例的完整清单，因此不报告其重合数。若本地实例源自VLoc Bench，那么引用本篇是说明来源与协议，不是声称新增独立外部验证。

研究记录已经指出CWE缺失、漏洞前不存在的新增参考文件和相似函数同文件等问题，本次官方数据与评分核查使这些问题有了更直接的源头对照。重复组选第一个可以减少同输入重复计算，但必须固定排序、保留组成员和参考答案差异；不能把“第一个”改成“表现最好的那个”。

### 12.2 CWE-only与issue localization不能未经适配就同榜比较

CoSIL、LocAgent、SweRank等常以自然语言issue为搜索线索。把它们适配到只有CWE类别的任务，是合理的跨任务比较，但输入信息密度与原论文不同，原论文排行榜不能直接搬来作为预期性能。

更不能把具体CVE、PoC、公告描述、补丁路径或oracle方向提示混入某一方法，再把收益解释成图搜索或筛选更好。应明确分开：CWE-only主协议、增加任务方向提示的线索敏感性，以及使用人工CPI的oracle诊断。知道“目标大致在哪里”本身就是强处理，不是免费的实现细节。

### 12.3 文件F1之外，需要一条证据传递链

本篇的结果和项目已有复盘共同提示，可以把端到端失败分为：

1. 未发现目标身份。
2. 发现了身份，但没读到相关源码范围。
3. 已读到证据，但筛选或打包丢掉了它。
4. 证据仍在，最终却选了竞争文件或相似机制。
5. 本来能判断，但交互协议或结束阶段没有合法提交。

这五类不是本文已发布的CPI分类，而是由其终态统计延伸出的测量设计。论文的“wrong localization”不能直接替代第4类，因为它不检查是否真正看到了目标证据；“budget exhausted”也不能告诉我们预算浪费在重复读取还是必要补证。

对筛选组件，应在相同真实曝光和相同终裁器下，测目标文件、关键源码范围和支持证据的保留，再看最终F1。对完整Agent，则保留自身探索机制，报告建图、检索、筛选、终裁的全链路成本。一次末端裁决的便宜不能替代上游Agent的端到端效率。

### 12.4 补丁标签与CPI承担不同工作

CPI中的Core可以包含不需修改、却支撑漏洞判断的代码；Plausible描述经审查后看似相关但不决定目标机制的竞争上下文；Irrelevant也不能仅由“不在补丁中”自动得到。因此官方GT只能评分修改位置，不能直接给源码块划C/P/I。

尤其同文件中同时存在目标函数与貌似相似的旁支时，文件F1可能完全不变，机制解释却发生偏移。若研究要说明P如何影响判断，应保持C证据充分并控制位置、长度与处理量，执行相应反事实；本篇仓库结构回归与模型级调用相关都不能代替这种证据。

部署中的“未查验”“待补证”“暂时压缩”也应与离线审定P区别开。把未知节点初始化为P是一个运行状态选择，不代表它已经被证明是plausible干扰。

### 12.5 最值得借鉴的不是单个分数，而是失败也要成为可解释结果

将合法无发现、工具失败、API失败、预算耗尽和错误定位分别计数，可以防止把不交卷包装成稳健性。保留同输入重复组、缺CWE和新增文件标签的审计，可以防止把样本口径变化包装成方法收益。最后，将命中正确文件与给出正确机制区分，才有可能说明一个上下文管理方法究竟改善了什么。

这些都是下一步实验设计的约束与启发，不是新的实验结果。本文没有证明筛选已经有效，也没有证明图方法天然优于排序方法；它提供了一个更清楚的地方，让这些命题接受检验。
