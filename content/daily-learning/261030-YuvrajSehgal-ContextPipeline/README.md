## 先看一个反直觉故障：窗口还有 94% 空闲，证据却已经消失了

设想一个诊断 Agent 调用工具，工具返回如下 JSON：

```json
{
  "new_processes": [...],
  "running_containers": [...]
}
```

第一组记录描述跟踪开始后新出现的进程，第二组记录描述跟踪开始前已经运行的容器。某个真实故障恰好藏在第二组。

模型支持 400k token，上一次完整提示只有 23k token。仅看“窗口使用率”，系统显然还有大量空间。然而 Harness 为单次工具输出设置了 6,000 字符上限，并直接执行类似 `serialized_result[:6000]` 的前缀切片。结果不是两组各保留一部分，而是前面的字段几乎完整、后面的字段整体消失，剩下的文本还失去了合法 JSON 的闭合结构。

于是出现本文的核心区别：

- **模型窗口容量**回答最多能放多少内容；
- **Harness 交付管线**决定工具产生的内容中，究竟有什么真正到达模型。

如果只记录最终 prompt 或 Agent transcript，我们甚至看不到被删掉的证据，因为日志记录的通常也是“交付后”内容。论文因此主张：Agent 的上下文不是一个静态窗口，而是多次序列化、裁剪、保留和交接后剩下的管线输出。

## 论文值不值得读

这是一篇刚发布的五页 arXiv 预印本，样本和场景都不大，不能把它当作“工具截断普遍降低 Coding Agent 准确率”的定论。它值得精读，主要因为研究设计把一个很容易停留在工程经验层面的现象拆成了可测机制。

第一作者 Yuvraj Sehgal 是 Brock University 的硕士生，所在 THREADS Lab 长期研究软件可观测性、执行跟踪、性能诊断与可信 Agent。共同作者 Mahsa Panahandeh 来自 University of Ottawa，公开研究方向包括 AIOps、分布式跟踪、日志分析和软件可观测性。Naser Ezzati-Jivan 是 Brock University 副教授、THREADS Lab 负责人，长期从应用层到内核层研究运行跟踪、性能工程与根因分析。本文使用 Linux kernel trace 诊断 Agent，和团队既有积累高度一致，不是临时换题包装。

对当前研究也有一个直接价值：我们正在比较不同 Context 输入与成功/失败轨迹，却容易默认“构造好的输入就是模型看到的输入”。本文提醒必须另外审计 SDK、工具结果、候选目录、序列化和截断；否则一次漏报可能来自证据本来没进入模型，而不是模型受到 Plausible Context 干扰。

## 作者怎样把上下文画成五个边界

一轮 Agent 运行不是“把上下文塞进模型”这么简单。论文把信息路径拆成五个边界：

| 边界 | 从哪里到哪里 | Harness 做了什么 | 本文观察到的风险 |
|---|---|---|---|
| S1 | produce → deliver | 工具结果序列化并装入单次预算 | 前缀切片删除后部字段并破坏 JSON |
| S2 | deliver → act | Worker 在步数预算内读取并继续调用工具 | 51% Worker 恰好撞上步数上限，尚未完成的工作根本不会发生 |
| S3 | act → retain | 历史消息跨轮保留或重发 | 保留上限从 80k 提到 150k 字符，单次运行 token 从 303k 增至 545k |
| S4 | retain → transfer | Worker 把发现交给最终决策阶段 | 554 个 Worker 中 98 个没有交接任何内容，沉默会被误读成“没有发现” |
| S5 | transfer → persist | 信息是否跨运行持久化 | 本系统为保持运行独立而主动关闭，不是测得的故障 |

这五项不能被统称为同一种“丢失”。S1 和 S4 会销毁已经产生的证据；S2 是预算让某些计算尚未来得及发生；S3 可能不损失内容，却会反复重发历史、增加成本；S5 在本文中是实验隔离选择。

论文提出的测量思想也很克制：每个边界使用适合它的单位。S1 以顶层字段或记录是否送达计数，同时另报 JSON 是否可解析；S4 以已计算发现是否进入最终决策阶段计数。摘要指标 `yield` 定义为：

`yield = 最终被记录的发现数 / 已执行的计算数`

它只表示多少计算真正转化为决策可见发现，不表示发现是否相关或正确。作者明确没有把这个代理指标吹成“证据质量”。

## 现场测量：窗口没有满，管线已经坏了多少

作者研究的是一个基于 Linux kernel trace 的根因诊断 Agent。Agent 需要从进程和容器行为中找出注入的资源限制故障。

在 720 次部署评估中：

- 共得到 11,189 个工具结果；
- 其中 3,827 个，即 34%，在 S1 被截断；
- 所有被截断结果都变成不合法 JSON；
- 同一个 payload 中，靠前字段的送达率为 99.3%，靠后字段只有 4.7%；
- 最大单次 prompt 为约 23k token，只占 400k 窗口的 5.75%。

字段位置又恰好与故障类型绑定。跟踪开始后才启动的 `spawned` 故障会出现在靠前列表；跟踪开始前已经运行的 `resident` 故障只出现在靠后列表。两个应用上的诊断分数也呈相同分裂：前者为 40–55/60，后者只有 0–24/60。

这是一条很强的机制线索，却仍不是因果结论。故障类型可能同时影响可观测性、事件占比、工具策略和诊断难度。作者没有把“字段送达率与准确率同向”直接写成“截断导致准确率下降”，而是继续做回放和受控实验。

## Figure 1：为什么前缀切片会形成交付悬崖

论文唯一一张图把真实工具结果按工作负载规模逐渐放大，再分别通过两种裁剪器：

1. **prefix slice**：把序列化后的字符直接截到固定长度；
2. **row-aware bound**：按完整记录和结构边界裁剪，保证每个字段仍存在、结果仍可解析。

在 6,000 字符以内，两者都能交付后部字段。结果一旦越过上限，前缀切片下后部字段不是逐渐减少，而是从完整送达突然跌到完全消失，同时 JSON 损坏。这就是“delivery cliff”。结构感知裁剪则在不同规模下保留各字段和完整记录。

图中的生产实例有 33,370 字符、128 条后部记录，大小是上限的 5.6 倍。前缀切片保留了靠前列表 118 条中的 30 条，却把后部 128 条全部删除。故障容器所在的整个证据类别在模型读取前消失。

这里尤其需要区分两个量：工具输出很长，不等于模型上下文窗口满；单工具上限和全局窗口是两套独立预算。提高模型窗口并不会自动修复 6,000 字符的 Harness 切片。

## 864 次确定性回放：先证明机制真的按代码发生

作者保存了工具产生的完整结果以及最终交付给模型的文本，因此可以把同一结果重新送入不同裁剪规则，完全不调用模型。

他们从 31 次运行中取出 864 个真实结果：

- 所有超过预算的结果，在前缀切片下每次都损坏；
- 在 row-aware 裁剪下，没有一个损坏；
- 进程列表工具有 50% 调用损坏；
- Agent 自己的分析输出有 43% 损坏；
- 小摘要只有 1% 损坏；
- 从全部调用看只有 2.5% 受影响。

最后一个比例解释了为什么缺陷长期不容易被发现：绝大多数工具调用都正常，只有少数“列举大量对象”的调用越界，而这些调用又可能携带最关键证据。平均错误率很低，并不代表关键路径安全。

确定性回放证明了“相同输入 + 相同切片代码必然删除相同字段”。它仍没有证明 Agent 最终一定答错，因为 Agent 也许能从其他工具或摘要中重新获得同一事实。

## 七个框架调查：这不是孤立写法，但也不能夸大为全行业结论

论文检查七个当时版本的 Agent 框架：LangChain、smolagents、OpenAI Agents、AutoGen 两个包和 CrewAI 等。

作者找到两个通用输出裁剪器采用位置切片：

- `langchain-core` 把序列化工具输出保留前 500 字符；
- `smolagents` 对超过 20k 字符的 observation 删除中间部分。

二者都没有理解 JSON、行或记录结构。另有三个框架不主动裁剪工具输出，这只是把压力继续推向后续上下文组装；一个只裁剪自身 tracing 数据；作者只找到一个按完整行裁剪、并明确告知用户的结构感知实现。

这项调查只能说明“位置裁剪这一缺陷类别出现在多个框架”，不能说明这些框架在真实端到端任务中已经造成同样准确率损失。作者也没有跑七个框架的统一 Benchmark。

## 受控实验：固定什么、改变什么、观察什么

现场版本升级时，作者不仅修复了交付，还加入两个新分析工具。因此现场准确率提升存在混杂：究竟来自裁剪修复，还是来自新增工具？

受控实验重新把各个缺陷逐个放回去，固定诊断 Agent、模型、temperature 0、工具、任务和症状提示。实验包含两类故障：

- `spawned`：故障进程在跟踪中途出现；
- `resident`：故障容器在跟踪开始前已经运行；
- 健康 trace 作为负对照。

核心配置包括：

- **Repaired**：结构感知裁剪 + 自动交接；
- **S1 defect**：只恢复前缀切片；
- **S1 reversed**：仍做前缀切片，但反转字段顺序，让另一类字段落在后部；
- **order-only**：只反转字段，不裁剪，用于排除顺序本身的影响；
- S2、S3、S4 单缺陷臂；
- **all defects**：恢复原 Harness 的全部缺陷。

每类有 5 个不同 trace 记录，每个重复 3 次，以承认 temperature 0 也不完全可重复；总计 145 次运行。正确答案必须在结构化 answer 字段中明确提交罪魁祸首，只在推理中随口提到不算正确。

这个评分规则不是小事。早期评分器把“提到过”当作命中，曾把一个条件从 2/15 膨胀到 14/15。作者在第 46 次运行审计时发现并更换评分器。它提醒我们：节点是否进入最终选择，与轨迹中是否曾讨论该节点，是两个不同结果变量。

## Table II：截断改变了代价，却没有改变这组答案

对 `spawned` 故障的关键结果如下：

| 配置 | 正确 | 中位工具调用 | 每轮被截结果 | 计算数 | Yield | 输入 token 变化 |
|---|---:|---:|---:|---:|---:|---:|
| Repaired | 14/15 | 53 | 0 | 18 | 0.61 | 567k 中位总输入 |
| S1 defect | 15/15 | 68 | 27 | 32 | 0.34 | +5% |
| S1 reversed | 15/15 | 76 | 30 | 36 | 0.31 | +14% |
| order-only | 10/10 | 48 | 0 | 16 | 0.61 | −12% |

首先，S1 defect 中每轮中位丢失 27 个结果，占工具调用约 40%，且全部损坏。但正确率是 15/15，与 Repaired 的 14/15 没有可解释的优势或伤害；这个一例差异在当前样本下只能视为噪声。

真正稳定变化的是工作量：相对 Repaired，工具调用从 53 增至 68，再到反转字段后的 76，最高增加 43%；计算数从 18 增至 32 和 36，约翻倍；yield 从 0.61 降到 0.34 和 0.31。最终发现数仍为 11，说明 Agent 做了更多计算，却没有获得更多有效发现。

这就是作者提出的 **compensation tax（补偿税）**：信息通路被破坏后，Agent 可能通过其他工具、排序表或重复计算找回应有答案。端到端准确率看起来不变，token 和工具调用已经显著增加。

还需注意论文的 token 口径：单轮中位 prompt 约 10k，只占 400k 窗口约 2.5%；但一整次 Agent 运行包含约 53 次调用，所以累计输入达到中位 567k。窗口容量和累计计费量不能混为一谈。

## 最有价值的反例：字段真的删掉了，模型为什么仍然答对

作者预注册的预测是：反转键顺序后，故障容器所在列表会从完整送达变成完全删除，准确率应该下降。

操作确实成功：transcript 中每一个列表 payload 都没有罪魁祸首。然而 Agent 仍然 15/15 答对。

原因是这个 `spawned` 故障非常“响亮”：它占内核事件的 14.0%，在 Agent 后续构造的多个排序表中都排在前几行，而这些前部行仍能通过裁剪。原证据路径被删除，第二条路径仍然恢复了名字。

这个反例让论文结论变得更精确：

1. 截断的机械损害可以确定地测量；
2. 有冗余证据路径时，首先出现的是补偿成本；
3. 只有当关键事实没有第二条可恢复路径时，才更可能转化为最终错误；
4. 当前受控实验没有完成对“安静故障准确率因果效应”的充分证明。

这比宣称“截断会让 Agent 变差”更有研究价值，因为它把证据冗余和可恢复性变成了潜在调节变量。

## 生产规模复跑：方向一致，仍不足以完成因果证明

作者又在真实生产规模 trace 上比较修复与 S1 缺陷：

- Repaired：6 次中 3 次正确，0 个损坏 payload；
- S1 defect：5 次中 0 次正确，每次都有 10–14 个损坏 payload。

方向与假设一致，但 Repaired 自身也只有一半成功，说明仍存在与数据交付无关的失败。更重要的是，这次修复同时调整了交付和 Worker 步数预算，未做到只改变 S1。因此作者把它定位为机制在部署规模上的重复观察，而不是“截断单独导致现场准确率分裂”的最终证据。

## 为什么团队平常看不见这种故障

论文给出三个原因。

第一，墙钟时间几乎不敏感。十次未限额运行中，模型等待占总时间中位 84%，网络与排队掩盖了本地切片和重复计算的开销。

第二，窗口指标制造安全感。模型每轮只用 2.5%–5.75% 容量，但上游单工具预算早已删除证据。

第三，流程化提示可能掩盖根因。给 Agent 一份书面诊断程序，可以用自由探索约 35% 的 token 得到相同结论。团队看到成本下降，可能以为“上下文太长”已经解决；实际上新流程只是减少了对被破坏交付通路的依赖。

## 论文证明了什么，没有证明什么

### 已经得到较强支持的结论

- Agent 上下文确实需要按多阶段管线测量，不能只报窗口和最终准确率。
- 前缀字符切片会按字段位置确定性删除信息并破坏结构。
- 这一缺陷在真实工具结果与生产规模 payload 上都能重复。
- 在存在替代证据路径的任务中，缺陷首先表现为更多调用、更多计算和更低 yield。
- 多个公开框架存在类似的位置裁剪，结构感知裁剪并未成为一致默认值。

### 仍未得到证明的主张

- 不能由本文推出所有位置裁剪都会降低最终准确率。
- 不能推出现场 `resident` 故障的全部性能差距由 S1 单独造成。
- 七框架源码调查没有给出七框架端到端效果比较。
- 一个内核跟踪诊断 Agent、一个模型和少量故障记录不能代表一般 Coding Agent。
- 5 个记录各重复 3 次不等于 15 个独立故障实例。

作者把下一步实验写得很清楚：选择修复版已经稳定成功、且罪魁祸首“安静”的故障族；固定 trace、fault、prompt、model 和 tools，只改变完整交付、前缀截断、反转键、结构裁剪和按需分页；逐次记录罪魁祸首是否可见、payload 是否有效、是否存在替代通路以及最终答案。这个设计才有机会识别准确率因果效应。

## 对当前研究的深入启发

### 1. 把“构造输入”与“模型实际可见输入”分开存档

当前 P/I/R/E 实验至少需要三个版本：原始证据对象、送入 SDK 前的序列化消息、模型调用实际记录的最终请求。若只能保存最后一个，就无法发现上游已经删除的候选正文或后部字段。

每轮至少记录：

- 每个 context 单元的原始字符/token；
- 序列化后长度与字段顺序；
- 单工具、单消息与整窗口的各级上限；
- 是否在结构边界截断；
- JSON/代码块是否仍完整；
- GT、P、I 各自实际送达比例。

### 2. 成功/失败轨迹相减时增加“交付差异”层

轨迹相减不能直接从“工具调用过什么”跳到“模型为什么选了谁”。建议依次比较：

1. **Produced**：工具或输入构造器产生了什么；
2. **Delivered**：模型实际看见了什么；
3. **Discussed**：轨迹中分析过哪些对象与机制；
4. **Transferred**：子任务发现是否进入最终汇总；
5. **Selected**：最终答案提交了哪些节点。

这样可以区分“没找到 C”“找到了但没交付”“看到了但未理解”“理解了但交接丢失”“最终被 P 候选挤掉”。这比只比较最终 CPI 集合更能形成可审计机制链。

### 3. 不要只用最终 F1 判断上下文是否无害

论文中正确率持平，工具调用增加 43%、计算翻倍、yield 减半。对应当前实验，即使 Core 与 Core+P 最终节点 F1 相同，P 也可能引起重复阅读、更多搜索、更多 token 或更晚提交。建议把调用数、累计输入、重取同一文件次数、发现转交率与最终 F1 一起报告。

### 4. 把“第二条证据路径”作为异质性变量

Pinot、go-proxyproto、claircore 等案例不能只按 P 数量分层。更有解释力的问题是：GT 机制是否有多条独立可见证据？新增 P 是补充第二条正确路径，还是提供竞争解释？当主路径被遮蔽时，Agent 能否从测试、调用点、错误消息或相似实现恢复？

这与昨天的 Context Sufficiency Probe 可以组合：Probe 不仅问 Core 能否回答，还要记录答案依赖哪个证据字段，以及该字段在每个实验臂是否真的送达模型。

### 5. 超长恢复输入先做 Harness 预检

当前 19万至35万 token 大包虽然没有超过模型窗口，却可能在候选目录、工具回显或消息适配器处遇到更小上限。正式运行前可用无需模型的 CI 检查：序列化前后节点数是否一致、每类字段是否仍存在、代码单元是否闭合、GT/P/I 实际交付率是多少。机械失败应先在模型调用前被拒绝，避免把基础设施0分写成语义干扰。

## 最后用一句话记住这篇论文

**模型的上下文窗口只是管线末端的容器；真正应该审计的是证据从产生、交付、行动、保留、交接到持久化的每一道边界，以及丢失后 Agent 是否还有另一条路找回答案。**
