# Talking to Itself While Coding：注释为什么能改变模型写出的代码？

> [ACL Anthology](https://aclanthology.org/2026.findings-emnlp.916/) · [25页正式PDF](https://aclanthology.org/2026.findings-emnlp.916.pdf) · [作者公开工件](https://github.com/pdfCN/What-Makes-Comments-Help-Code-Generation)

## 一、眼前两句注释差不多，为什么结果完全不同？

想象一道 Two Sum 题。模型边写边给自己留下两句注释：“用哈希表在一遍循环中找答案”“先查补数，后插入当前数”。第一句给算法，第二句保住不能拿同一元素配对的不变量。如果只把第二句颠倒，注释依然专业、长度差不多，接下来的实现却可能变错。这个例子借用图2中的任务，颠倒步骤是为解释机制的教学例子，非原文独立实验样本。

过去的做法通常比较有注释还是没注释、解释为什么还是描述做什么。但注释既有外形，也携带算法决策。一个模型擅长题目，本身就更有机会同时写对注释和代码。仅从输出观察，无法分开“本来就会写”和“注释真的帮了它”。

本文的关键办法很干净：从更强模型已生成的代码里，只取最前面的自然语言注释，不给它的源代码；把注释放到较弱模型的生成开头，再用相同题目和同样的接收模型比较不同版本。为了进一步排除题目难度，用同一批题、同一块注释，尽量只改一个会让算法出错的决策。这样就能问：**变的是写法，还是写法所携带的判断？**

第一作者 Dangfeng Pan 的[个人主页](https://pdfcn.github.io/)列明其蒙纳士大学博士研究方向；通讯作者 Zhensu Sun 的[会议自述](https://conf.researchr.org/profile/ase-2026/zhensusun)聚焦软件工程与 AI。本文五位作者还共同研究过代码格式和模型 token 费用，[ICSE 2026 项目页](https://conf.researchr.org/details/icse-2026/icse-2026-research-track/39/The-Hidden-Cost-of-Readability-How-Code-Formatting-Silently-Consumes-Your-LLM-Budget)可核实。这里真正值得读的是两组对照：固定表面、改变语义，以及固定任务但让模型自己写提示。相关思想也适用于较一般的代码上下文评估。作者仓库公开了生成输出、逐题结果和校准数据，本笔记核对公开内容及全文两幅图、表1–19与附录A–D，未重新运行作者实验。

## 二、图1的四块不是四套答案，而是四个逐步变准的问题

1. **形态是否预测正确？** 先统计模型自然写的注释比例和摆放位置。
2. **意图是否预测正确？** 区分注释在解释为什么，还是描述做什么。
3. **内容干预是否改变正确率？** 将强模型注释作为前缀，分别放入正确、改错、乱序、错题和等长噪声。
4. **模型自己能不能获得同样收益？** 改指令让原模型自己写注释，再看它能否提供同样有效的内容。

主要数据是 LiveCodeBench v6 的单文件 Python 竞赛题，完整提示对照覆盖1055题。pass@1 是每道题只提交一个候选，通过测试的题比例，不是多次试答的任一次成功率。作者自跑14个模型、汇入74个排行榜提交做形态观察；干预则使用明确控制的接收模型与匹配提示基线。表8记载作者控制实验按题一个样本、温度0，主要生成实验输出上限4096 token，本地接收模型上下文上限16384。排行榜来源不因此变成相同服务和解码配置；观测与干预证据不能同等解读。

### 先看形态：注释多的模型没有稳定做得更好

共同分词器统计注释 token 占全部输出 token 的比例，再把注释内部划成完整注释行、同一行内的注释和文档字符串三种。表10–12的模型剖面显示，16个 pass@1 至少80%的模型中，4个注释占比不到2%，5个超过30%，全范围约0.1%–71.4%。

跨模型比较可能受模型能力和提交设置影响，因此作者还在单模型内部按题计算 Spearman 秩相关。表13中，三类摆放方式的最大绝对相关只有0.32；总注释量有少数相关较高，最高0.53，约22%的模型超过0.20。结论是没有稳定的共同预测关系，不是每个模型都毫无相关。

### 再看意图：有 WHY 趋势，但没有过多重检验门槛

13个模型的自然注释按行分类：WHY 对应设计理由，WHAT 包括算法、步骤、机制与定义，OTHER 合并装饰及误导。分类器是 Gemini，作者人工标了100个分层样本作校准。表5显示理由、算法单类的 Cohen κ 分别0.74和0.72，但具体步骤只有0.02；表6的聚合 WHY κ=0.74，WHAT 原始一致率0.85、κ=0.36、Gwet AC1=0.80，OTHER κ=0.10、AC1=0.35。这些指标在校正偶然一致和类别不均衡时口径不同，OTHER 因一致性不足不宜作定量依据。

作者用有注释的样本来比较意图比例，避免把没写注释直接算作没有 WHY。WHY 与模型成绩的秩相关为0.61，原始 p=0.027；WHAT 为−0.20、p=0.52。三项 Bonferroni 校正阈值是0.0167，未发现稳健关联。一种注释“在解释为什么”，也不保证它解释的是正确不变量。表7中成绩都约60%的两个模型，WHY 比例可分别为18.1%和40.7%。

## 三、真正的干预：对同一题换掉前缀

三个强来源是 Grok-4.1-Fast、Gemini-3.1-Flash-Lite 和 Claude-Opus-4.7。它们先回答原题；实验只截第一段代码最前面的连续注释行，丢弃导入和可执行代码。四个接收者为 Gemma-4-E4B-IT、Qwen3-8B、Seed-Coder-8B-Instruct 和 CodeGeeX4-9B。接收者在自己的输出开头已有该注释，继续生成代码；这与在用户消息里说“写注释”不是一个位置或处理。

| 对照 | 实际改变什么 | 排除哪种解释 |
|---|---|---|
| 匹配提示，不加注释 | 保留同题和源模型所用的注释提示模板 | 把系统提示差异当成外部内容收益 |
| 所有源注释 | 照单使用，不按源代码测试结果挑选 | 区分混合输入与事后挑中的理想子集 |
| 源成功或源失败 | 分别按源代码是否过测试分组 | 描述两种实际来源，但组间题难并不等同 |
| 同题最小改错 | 保留大部分原话和形态，改关键算法决策 | 在同一批题排除难度和粗粒度风格差异 |
| 乱序、错题、等长噪声 | 分别破坏顺序、任务对应、连贯语义 | 分开检查线索顺序和无关文本 |

表1每个变化用同一批题、同一个提示但不喂注释作基线。配对 McNemar 检验依据同题由错变对、由对变错的次数；五条件×12组源与接收者配对，共60项，做 Holm 校正。这比直接用全题成绩减去源成功子集成绩公平。附录给三个来源的源成功子集分别为757、892、870题。

### 表1：正确注释平均加17.2个百分点，源失败的近零不能当等效

源成功子集上，12组正确前缀平均提高17.2个百分点且都显著；所有源注释不挑选时，12组也都显著提高，但数值与筛选后的理想对照不同。例：Qwen3-8B 用 Gemini 在全体题的匹配基线为39.2%，所有源注释52.0%；只看 Gemini 源成功题则是53.6%到70.8%。不能把70.8%减39.2%。

源失败子集上没有任何一组达到显著，部分基线已经只有约1%–10%。这是难题地板和内容错误缠在一起的情形：一个原本很少做对的模型，掉分空间本来就很窄；源失败也不等于其中每句提示都错。作者没有让这一组承担最强机制结论，随后用同一批源成功题替换内容。

### 表2：同一批题只改一个关键决策，四个模型失去收益

用 Gemini 作源，在源代码通过的同一批题上，改写器保持语气、行数、缩进和大致长度，只破坏一个中心承诺，例如换成不适用的算法或颠倒关键条件。平均约10行中动2.3行，作者人工核查50个改写。结果如下：

| 接收模型 | 无外部前缀 | 原正确注释 | 最小改错 |
|---|---:|---:|---:|
| Qwen3-8B | 53.6% | 70.8% | 48.2% |
| Seed-Coder-8B | 43.9% | 58.3% | 41.9% |
| CodeGeeX4-9B | 26.4% | 52.3% | 28.4% |
| Gemma-4-E4B-IT | 71.3% | 85.2% | 74.2% |

原正确到改错四组均为 Holm 校正 p<0.001；改错相对无前缀，只有 Qwen 的负差达到显著。这两个比较回答不同问题：“拿掉正确语义会失去收益”有很强证据，“同题错误注释必然比没有注释更伤”没有得到相同程度支持。

附录表9换了另一个角度：保持正确语义，分别改措辞、压缩、加缓和用语，或把明确算法替换成模糊说法。Qwen 与 Seed 的模糊版分别比正确版差7.0、5.3个百分点；其余风格变化大多不显著，不过压缩版在 Seed 有+3.4个百分点，附录标为 p<0.05。这并不意味着长度永远无关。改写还需通过自动表面约束验证，每条件保留618–724条，四种改写的结果不可直接当一个完全平衡的全题析因。

### 错题比随机字串更有害，顺序并非全不重要

在源成功子集上，错题注释平均降20.8个百分点，长度匹配随机文本平均降17.9个百分点。把两者在公共任务上直接配对，10,076条任务×配置的观察中，946条仅随机文本过、650条仅错题过；12个独立配置比较里5组校正后显著，方向都一致。这个 pooled 分母包含同一题的多个模型或来源，不能误写成一万道独立题。

打乱正确注释的行序后，平均仍有+11.7个百分点，约留住68%原收益，12组中10组显著。合理解释是其中不少句子是可独立使用的算法线索，另有一部分依赖顺序。不是说算法步骤无序也正确，更没有证明可以无损砍掉32%。表15显示正确前缀提升多集中于中等题，错题和随机噪声主要伤容易题。附录D.7的89对3是870个 Grok 源成功问题中，至少3/4个接收者同向翻转且无反向翻转的题数，并非所有逐次运行的胜负；56个中等、18个容易、15个困难。D.8展示一个普通字符串计数题，正确提示明确应加总而非连乘，未受益的模型往往恰好选了后者。它说明具体机制，但案例是事后选出来的。

## 四、换真实仓库后，统计结论有多强？

RepoClassBench 要在已有项目中依据文字说明生成完整的类。接收者得到类说明、路径和既有文件头，输出回填后须通过构建与目标测试。用 Claude-Opus-4.7 产出前缀，重复四个接收者。原文列 C# 61题和 Java 130题，并注明排除两个各条件均失败于构建环境的 Java 任务。它比算法题更接近日常布局，不过仍是固定位置的类生成，不包含自主仓库探索。

表3中，同一模型单格经24项 Holm 校正，只有 Qwen Java 的错题前缀下降13.8个百分点显著；它的正确注释在 Java 子集上提高16.7点，未单格过校正。把 Java 接收者的匹配配对汇总，正确前缀41次改善、16次恶化；错误主题在 Java、C# 的汇总比较均更差。在完全相同的源成功任务上直接比正确注释和错题，Java 75对9、C# 20对2，均 p<0.001。这些汇总更支持内容方向的迁移，不足以证明各模型和语言都有同样提升，也应留意同题跨接收者复用带来的依赖。

## 五、图2与表4：要它多写、写在前面，能否换回同样效果？

图2在同一个 Two Sum 代码体上展示八种可见注释样式：少量、密集、几个 WHAT 步骤、解释 WHY、两者混合、文档字符串、顶部大纲和行内注释。它让读者看到同一算法可以写成多个样子。全格还有默认和不准写注释，共14模型×10策略。改变的是系统指令，而非把外部答案前缀交给它。去掉14个默认格后，全局 Holm 校正126个模型与策略比较，其中38格显著。

遵从表面要求确实有效：表17–18中无注释指令使平均注释比例22.7%降到6.3%；密集、WHY、混合和顶部策略都可大幅提高比例。但 pass@1 没出现跨模型统一提升。Qwen3-8B 的密集策略约+4.4个百分点，是四个接收者中唯一获得显著正向恢复者；对比其三个来源约18.1点的正确前缀平均收益，只恢复约24%。这两项的题集不同，24%是作者用来量级比较的比例，不是严格同批次的因果中介份额。

更有意思的是同一提示反向作用：不许写注释使 Gemma −14.5点、GPT-5.4-Nano 约−13.6点、Gemini −6.9点，GPT-OSS-120B 的点估计反而上升；要求顶部说明使 DeepSeek-V3.2 约+6.2点、GPT-OSS-120B −13.7点。表19中不写注释13/14模型输出缩短，Gemma −59%，MiMo却+46%；Mistral缩约43%的同时成绩未显著变。作者的−21.8%是各模型相对变化的平均，不要拿表17的总体均值直接重算。遵从形式、输出长度和正确率是三类观察。

作者另外对 Gemini 和 GPT-OSS-120B 做显式自拟计划和先拟计划再把计划交还给同一模型的两阶段对照，四格约+1.6、+1.9、−0.6和+0.9点，均未达显著。不能因此宣称所有规划范式无效；已测试的是这两种提示和这些模型。也不能把“未来可能需要训练”复述成本文已验证的解决方案。

## 六、证据最强在哪里，结论应停在哪里？

1. **同题最小语义修改是最强证据。** 它减少了源成功/失败分组混杂，方向在四个接收者上一致。50条人工核查和约束不等于逐条正确性证明；语言细节也不可能完全固定。
2. **对错来自源成品的测试结果。** 这是实验选择条件，不是部署时就能识别的证据信号；自然自写过程也不等同于外部前缀。来源成本不能从接收端独立通过率推出来。作者报告整个研究约500美元 API 和约200 A100小时，非每次加前缀的产品成本。
3. **观察性意图标签不是正确性标签。** 人工校准是单名作者，OTHER 信度较低，来源模型兼任若干评价与改写角色，排行榜与受控组条件也不同。观察不到稳健相关，不能证明没有机制。
4. **显著、有害和有实用价值要分开。** 源失败近零不代表等效，大规模配对的显著也不能代替效应量和独立任务口径。小样本仓库复现适合机制验证，不适合概括所有仓库和长程智能体。
5. **注释继承一个合理但错误的决定，可能比增加无效 token 更糟。** 然而本论文的“错题”是不同任务，“最小改错”是同题错误关键语义，这两组并未在完全相同的全面析因设计中互比。因此它没有建立某种通用噪声类型总比另一种有害。

真正应该记住：先问上下文提供了哪一个可以改变决定的事实，再问它是否正确、模型是否实际看到了；注释多、语气像分析甚至题目相关，都只是间接迹象。

### 对仓库级上下文研究的启发

对常规代码生成或审查，可以借鉴本文的同任务配对思想：比较上下文内容时尽量匹配表面形式和长度，记录实际展示的文本，并把信息是否真正确、任务基线与额外成本分开。尤其要把用于解释现有结果的诊断样本和用于检验新策略的留出样本明确分列，避免把已知结果帮助选出的优质上下文写成部署时可自动获得。这个经验可帮助安排消融和写清证据边界，不能把竞赛题 pass@1 晋升为仓库审查或定位效果的直接证据。
