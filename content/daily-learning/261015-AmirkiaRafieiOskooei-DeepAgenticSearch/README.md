## 先说结论：把搜索交给隔离子 Agent，并没有免费获得“干净上下文”

这篇论文比较两种已经进入实际 coding-agent 产品的仓库搜索范式。第一种是**语义检索**：提前把仓库切块、嵌入并建立向量索引，主 Agent 反复检索候选片段。第二种是**深度 Agentic 搜索**：主 Agent 不使用索引，而是把 grep、读文件等探索委派给拥有独立上下文的子 Agent，只接收其压缩后的结论。

作者在 SWE-QA 的 15 个 Python 仓库、每个仓库 48 个问题上，用 4 个模型分别运行两种架构。语义检索总体通过率为 65.2%，深度 Agentic 搜索为 46.2%；每个正确答案的平均成本约为 0.32 美元对 0.74 美元。差距不只来自“搜不到”：Deep 失败中 41.8% 是规划器与子 Agent 的协调断裂，而 91% 的此类失败仍给出流畅、自信的答案。

论文真正有价值的结论不是“向量数据库永远胜过 Agent”，而是：**隔离原始搜索输出虽然保护了主上下文，也新增了一条信息压缩和交接链路；如果没有测量交接内容是否保真，主 Agent 得到的“干净上下文”可能只是干净地丢掉了关键证据。**

## 论文地图：作者如何把一个工程争论变成可测比较

### 核心矛盾

仓库级代码问答需要先找到相关代码，再组合成解释。把整个仓库塞进上下文既不现实，也容易产生 context pollution：相关证据在大量无关文本中被稀释。业界由此形成两条路线：

- 语义检索在搜索前用 embedding 过滤，只把少量相似片段送入主上下文；
- Deep Agentic 搜索让子 Agent 吞下原始目录、grep 和文件内容，再把摘要交给主 Agent。

后一种架构常被视为更先进的 context engineering，因为主 Agent 不直接承受探索噪声。但“隔离噪声”与“保留必要证据”不是同一件事。论文的 research gap 是：人们知道两种架构在工程上怎样工作，却缺少在相同模型、相同问题和相同仓库上的配对证据，不知道额外的规划与委派到底换来准确率、成本还是新的失败。

### 顶层证据链

```text
大仓库不能整体放入上下文，检索与探索各有潜在风险
    ↓
研究对象：语义索引 ReAct Agent vs. 委派式 Deep Agent
    ↓
Operationalization：同一模型回答同一 SWE-QA 问题
    ↓
测量答案质量、token、成本、延迟、工具调用与完整轨迹
    ↓
配对统计检验 + 人类验证 judge + 全失败轨迹分类
    ↓
判断哪种架构在“单问题、只读、可索引仓库”中更准确、更经济，以及为何失败
```

注意最后的适用条件。论文研究的是固定快照上的仓库问答，不是补丁生成、测试执行、持续多轮开发或高速变化的工作区。作者在讨论中主动把结论限制在这一区间。

## 理解全文需要的五个概念

### 1. Repository-level Code Question Answering

仓库级代码问答要求回答“某个配置如何一路生效”“某个类为什么采用这种验证逻辑”之类跨文件问题。难点分为两段：先定位证据，再综合证据。若最终答案错了，可能是没找到、找到了没读、读了误解，或不同 Agent 之间交接时丢失。

### 2. ReAct Agent

Reasoning and Acting（ReAct）让模型在“思考—调用工具—观察结果”之间循环。本文的 ReAct Agent 只有三个工具：仓库结构查询、向量检索、读文件。它没有 shell、写文件、任务规划或子 Agent。

### 3. Deep Agentic Search

主 Agent 维护计划和任务清单，把仓库探索交给隔离子 Agent。子 Agent 用 grep、glob、目录列表和读文件完成探索，再返回摘要。优势是主上下文不堆积原始输出；风险是主 Agent 看不到大部分证据，只能相信摘要。

### 4. Context pollution / context rot

它描述无关或低价值内容累积后，模型更难利用少量关键证据的现象。Deep Agent 的隔离设计正是为了把污染留在子上下文，但本文提醒：删除噪声需要一个压缩者，压缩者本身会成为新的信息瓶颈。

### 5. 机制与症状

作者把失败分成两个正交维度。机制回答“过程哪里坏了”，如没定位到、交接断裂、循环不终止；症状回答“最终答案怎么错”，如答错对象、事实错误、前提否认或没有答案。相同的错误答案可能由完全不同的过程产生，不能只从输出倒推原因。

## 两种系统究竟怎样运行

### 语义检索臂：先建索引，再让 Agent 迭代查询

仓库文件先由面向源码配置的 `RecursiveCharacterTextSplitter` 切成约 500-token 片段，相邻片段重叠 50 tokens。每个片段使用 OpenAI `text-embedding-3-small` 生成 1,536 维、L2 归一化的向量，存入 Chroma。一次检索返回余弦相似度最高的 10 个片段。

回答问题时，ReAct Agent 可以查看仓库结构、发起多轮向量查询、读取完整文件，再生成答案。索引只需按仓库建立一次；后续每个问题共享同一索引。

这条路线的潜在损失包括：固定切块打断函数或类结构；相似词不等于真实依赖；Top-10 可能漏掉关键实体；为补偿低精度而反复检索会让候选变多。

### Deep Agentic 臂：主 Agent 规划，子 Agent 在隔离上下文搜索

Deep Agent 使用 LangChain `deep-agents` 默认工具集合，包括 `write_todos`、`task` 委派、`grep`、`ls`、`glob` 和 `read_file`。主 Agent 与子 Agent 使用同一个模型。

一个典型流程是：主 Agent理解问题并创建任务，调用 `task` 把某段探索交给子 Agent；子 Agent 在自己的上下文里搜索符号、列目录和读取文件；子 Agent生成压缩结果；主 Agent接收摘要，决定继续委派还是直接回答。

Figure 1 应按“什么进入最终回答者上下文”来读。语义臂的主 Agent直接看到检索片段；Deep 臂的主 Agent只看到子 Agent整理后的结果。两条路线都在过滤仓库，但过滤位置不同：一个在 embedding/index 层，一个在 Agent-to-Agent hand-off 层。

### 为什么工具集没有被做成完全相同

作者认为工具和编排正是范式的构成部分。若给 ReAct Agent加入计划、任务清单和可委派子 Agent，它已经变成 Deep Agent；若移除 Deep Agent的这些能力并接上索引，它又接近语义检索 Agent。因此主实验比较的是两个完整系统包，而非某个孤立模块。

这个决定适合回答实践中的“我该采用哪类系统”，却无法回答“究竟是 grep、任务规划、上下文隔离还是摘要造成差异”。论文对此没有做析因消融。

## 实验坐标系

### 数据集与实验单位

SWE-QA 覆盖 15 个开源 Python 仓库，每个仓库 48 个问题，共 720 个问题。12 个仓库来自 SWE-bench，3 个来自较新的 SWE-bench-Live；规模约从 1.3 万到 86.1 万行 Python。问题大致均分为 What、Why、Where 和 How。

每个“模型×搜索范式”都是一个条件，共 8 个条件；每个条件回答相同的 720 个问题，因此跨范式比较能按问题配对。每个问题使用全新线程，只能访问目标仓库，避免问题之间串扰。

### 模型与预算

四个回答模型为 Gemini 2.5 Flash、Gemini 2.5 Pro、Gemini 3 Flash 和 Qwen3-235B。Deep 架构中的主 Agent和子 Agent使用相同模型。温度固定为 0；每个问题最多运行 900 秒、Agent graph 最多递归 80 步。达到任一限制就按失败保留，不重试。

温度 0 只减少采样随机性，不等同于系统完全确定。论文没有为同一条件重复运行，因此不能像《What Does a Harness Buy?》那样估计同配置任务翻转率。这是其配对统计之外仍缺的一层噪声基线。

### 答案评分与人类校验

Claude Sonnet 4.6 按 correctness、completeness、relevance、clarity 和 reasoning 五维各打 0—10 分，总分是五维之和的两倍。70 分及以上为 Pass，50—69 为 Partial，低于 50 为 Fail。

自动 judge 与所有回答模型来自不同供应商。三名至少有两年经验、且非论文作者的软件工程师盲评 800 个分层抽样答案，每条件 100 个：

- 三位人类的 verdict 一致性 Fleiss' κ=0.81；
- 人类多数与 LLM judge 的 verdict 一致性 Cohen's κ=0.74，精确一致率 84%；
- 人类平均分与 judge 分数 Pearson r=0.83，平均绝对差 5.2 分。

Deep 答案上的一致性略低：verdict κ=0.69、分数平均绝对差 6.8；语义臂分别是 0.78 和 4.1。整体支持使用自动 judge，但也说明 judge 对更长、更复杂的 Deep 输出把握较弱。

### 统计检验

Pass 差异使用精确 McNemar 检验，连续分数用 Wilcoxon signed-rank 检验，并报告 Cliff's delta、bootstrap 95% 区间和配对标准化均差。四模型比较使用 Benjamini-Hochberg 假发现率校正。作者还按仓库整体重采样，并扫描 50—90 的不同 Pass 阈值，检查结论是否由问题嵌套或 70 分阈值造成。

## RQ1：哪种范式回答得更准确

### 总体结果

四模型汇总后，语义检索 Pass=65.2%、Deep=46.2%；Fail 分别为 21.9% 和 34.4%。方向在四个模型上一致，但效应大小高度异质：

| 模型 | Semantic Pass | Deep Pass | 配对差值 |
|---|---:|---:|---:|
| Gemini 2.5 Flash | 48.4% | 42.8% | +5.6pp |
| Gemini 2.5 Pro | 54.2% | 44.2% | +10.0pp |
| Gemini 3 Flash | 89.3% | 39.7% | +49.6pp |
| Qwen3-235B | 68.8% | 58.2% | +10.6pp |

所有 McNemar 与 Wilcoxon 结果在校正后仍显著。Cliff's delta 在两个 Gemini 2.5 模型上约 0.14，Qwen 为 0.235，Gemini 3 Flash 则高达 0.760。因此“方向一致”可信，但不能把 Gemini 3 的极端差距当成所有模型的典型幅度；它更像强烈的 model×harness 交互信号。

### Table 3 和 Table 4 怎样读

Table 3 把准确率、token、工具调用、延迟和成本放在同一行，适合看“系统整体”。Table 4 固定模型做配对差异和显著性检验，适合回答差值是否稳定。

最有解释力的不是总体 19pp，而是同模型差异跨度从 5.6pp 到 49.6pp。它说明架构效果不能脱离模型谈。Gemini 3 Flash 的 Deep 条件平均 44.6 次工具调用，远高于 Semantic 的 8.6 次，也比 Gemini 2.5 的 Deep 条件更长；论文没有进一步隔离这是模型对 Deep Agents 工具协议的不适配、循环控制问题，还是其摘要能力不足。

### Pass 阈值是不是人为制造了差距

Figure 4 横轴把 Pass 阈值从 50 扫到 90，纵轴是 Semantic Pass 减 Deep Pass。四条线全程高于 0，最小差值仍为 3.8pp；Wilcoxon 和 Cliff's delta 又直接比较完整分数，不依赖 70 分门槛。

所以结论方向不是阈值产物。但差值幅度会随阈值大幅变化，例如 Gemini 3 Flash 从 27.8pp 到 63.1pp。论文正确地把阈值无关的分数检验作为主要证据。

### 仓库规模和问题类型

Semantic 在 15 个仓库中的 14 个领先；Deep 只在 Django 上高 3.0 分。随着仓库规模增加，Semantic 的优势有缩小趋势，Spearman ρ=-0.69、p=.004，但最大仓库 SymPy 仍领先 13.7 分，没有观察到交叉点。这个趋势只能说“差距缩小”，不能外推“大到某个规模 Deep 会反超”。

What、Why、Where、How 四类问题上，Semantic 都领先约 17—20pp。两种范式都觉得 Why 最容易、How 最难，问题类型改变绝对难度，却没有改变本样本中的排序。

## RQ2：额外编排是否值得它的成本

### token 与每题成本

Deep 在四个模型上都使用更多输入 token、每题美元成本也更高。差异最夸张的是 Qwen3-235B：Semantic 平均约 34k 输入 token，Deep 为 761k；每题成本为 0.0085 对 0.1693 美元。

Gemini 3 Flash 的每正确答案成本是 0.179 对 0.858 美元；Qwen 是 0.012 对 0.291 美元。四模型汇总后，每个 Pass 的成本约 0.32 对 0.74 美元，Deep 高约 2.3 倍。

向量索引并没有把隐藏成本吞掉。15 个仓库约 2,100 万 embedding tokens，总索引成本估算 0.43 美元；即使全部摊到单个 Semantic 条件，每题也只增加约 0.0006 美元。这个数字只覆盖金钱，不覆盖索引更新、失效检测和运维成本。

### Figure 13：准确率—成本前沿

Figure 13 下半部分横轴是每题美元成本的对数，纵轴是 Pass rate。8 个条件中，Semantic 点都位于相同模型 Deep 点的左上方，即更便宜且更准确；虚线效率前沿没有经过任何 Deep 点。上半部分按仓库展开，方向仍一致。

这张图支持“当前设置下 Deep 被支配”，但不能推出“所有 Agentic search 都浪费”。两臂没有做 compute matching，Deep 使用默认工具和更长轨迹；论文回答的是默认系统包的效果，不是相同 token 下搜索策略的纯效应。

### 延迟和“更多努力”

延迟没有统一排序：Deep 在 Gemini 2.5 上更快，在 Gemini 3 和 Qwen 上更慢，且分布重尾、受环境影响。作者因此把 token 和美元作为主要成本证据。

Figure 15 显示每题分数与输入 token/工具调用的拟合斜率平坦或为负。这个关联不能解释为“多搜索导致低分”，因为困难问题既会触发更多搜索，也更容易答错。它只能说明：在观察数据中，额外努力没有伴随额外准确率，无法为 Deep 的成本辩护。

## RQ3：两种架构怎样行动、又怎样失败

### 工具调用分布

Semantic 的调用几乎均分给向量检索 43.6% 和读文件 43.2%，仓库结构查询占 13.3%。Deep 表面上工具更多，但仍主要是读文件 41.6% 和 grep 29.1%；其余为任务清单 10.9%、目录列表 8.3%、委派 7.0% 和 glob 3.1%。

委派只占 7% 容易误导，因为一次委派会展开一整条子轨迹。在 2,878 个 Deep run 中，2,395 个至少委派一次，平均每 run 2.1 次，每次约再运行 10 个工具调用。最终 68.8% 的 Deep 工具调用发生在子 Agent 上下文中，主规划器看不到这些原始观察。

Figure 17 最应该关注的不是“task 只有 7%”，而是信息可见性的断层：大部分真实阅读发生在隔离环境，主 Agent 只能消费压缩结果。这正是后续协调失败的结构基础。

### 轨迹长度

Figure 18 横轴为分桶后的工具调用数，纵轴为 Pass rate。除 Deep 最短轨迹常因根本未启动工作而低分外，两种架构总体都随轨迹变长而下降；Deep 的轨迹延伸到 50 次以上。

这仍是相关而非因果：长轨迹可能是问题困难的结果。论文没有随机限制步骤数，也没有对相同问题做“截短/放宽”干预，因此不能说缩短轨迹本身会提高准确率。

## 失败分类：过程在哪里断，和答案怎样错

作者把所有 Fail run 共 1,621 个全部编码，其中 Semantic 631、Deep 990。每个失败的压缩记录包含问题、参考答案、judge 理由、Agent 答案和清洗后的工具序列；Claude Sonnet 4.6 自动标注机制与症状。

两名作者独立人工标注 400 个分层抽样失败。机制 Cohen's κ=0.78，症状 κ=0.86；人工共识与自动编码 κ=0.82。这一验证比只让 LLM 自评可靠得多，但仍有一个限制：自动标注输入是“清洗后的工具序列”，未必保留每段证据的完整内容，且其余约四分之三失败未被人工复核。

### 六种机制

1. **协调断裂**：主 Agent 与子 Agent 的委派、返回或整合没有产生可用证据，仅 Deep 架构可能发生。
2. **检索/定位遗漏**：投入了显著搜索和阅读，仍没找到正确文件或实体。
3. **grounding 不足**：几乎没读代码就自信回答。
4. **证据误解**：读到了正确文件，却在综合时误报或过度推断。
5. **不终止循环**：控制循环反复搜索或停滞，最终无答案。
6. **证据获取失败**：工具报错，运行始终拿不到所需材料。

### 五种答案症状

无答案、否认问题前提、答错实体或机制、围绕正确实体给出错误事实，以及不完整/浅层回答。症状分类不依赖产生答案的过程，因此可与机制交叉。

### Figure 19—21 与 Table 5 的核心发现

Semantic 的 53.6% 失败属于检索/定位遗漏，18.1% 是 grounding 不足，17.1% 是读到正确文件后仍误解。它的典型风险是**没有把正确证据送到推理阶段**。

Deep 的 41.8% 失败属于协调断裂，13.5% 是不终止循环，检索/定位遗漏降到 24.4%。更关键的是，协调断裂并不总是可见错误：91% 仍生成流畅、自信的答案，通常答错实体或机制。它的典型风险是**子 Agent 可能做了大量搜索，但关键结果没有可靠进入主 Agent 的判断**。

机制与架构的关联很强，Cramer's V=0.56；即便删去仅 Deep 可能出现的协调断裂，余下共同机制的 V 仍为 0.35。相比之下，最终答案症状与架构关联只有 V=0.16。换句话说，只看答案怎么错，很难识别背后的系统故障；过程日志确实提供了额外信息。

非终止循环的平均分只有 3.3，98.7% 没有答案；证据获取失败平均 18.8，62.4% 没答案。协调断裂平均分却有 30.5，只有 9.4% 无答案。它比显式崩溃更危险，因为输出表面完整。

## Baseline、公平性与替代解释

### 合理之处

- 同一问题、同一仓库、同一模型做配对，避免把模型能力差异误算成搜索差异。
- 两臂都基于 LangChain 开源框架，没有把研究原型与成熟商业产品直接比较。
- 使用默认工具契约而非为某一模型特别调参，贴近“开箱即用”的实践决策。
- 结论同时通过阈值扫描、整仓 bootstrap 和跨供应商模型方向一致性检查。

### 仍然捆绑的变量

Semantic 不只多了向量索引，也少了任务规划和 Agent-to-Agent 摘要；Deep 不只改了搜索，也改变工具、系统提示、步数结构和上下文可见性。因此 65.2% 对 46.2% 是两个 bundle 的总体差，不是“embedding 相似度”对“grep”的单因素因果效应。

两臂也没有 token/调用次数匹配。Deep 平均投入更多计算却更差，足以支持“默认系统不划算”，却不能说明在严格相同预算下哪个搜索动作更有效。作者把 compute-matched baseline 列为后续工作是必要的。

### Semantic 也使用了外部模型能力

语义臂的检索器依赖 `text-embedding-3-small`，而 Deep 臂的探索与压缩依赖回答模型本身。因此比较并非纯粹“四个模型各自搜索”：Semantic 获得一个固定的专用 embedding 模型，Deep 获得同模型子 Agent。这个设计符合实际架构，但解释上应称“系统比较”，不能归结为回答模型自身的搜索能力。

## 论文证明了什么

1. 在 SWE-QA、15 个可索引 Python 仓库、单问题只读会话中，所实现的 Semantic 系统在四个模型上均显著优于所实现的 Deep Agent系统。
2. 方向对 50—90 的评分阈值、整仓重采样和四种问题类型保持稳定；差距不是单一 Pass 门槛造成。
3. Deep 在四模型上都消耗更多输入 token、每题成本和每个正确答案成本，当前比较中不在准确率—成本效率前沿。
4. 两种架构有不同失败签名：Semantic 主要漏定位，Deep 主要增加协调断裂和不终止循环。
5. 最终答案症状不足以识别过程机制；大量协调断裂会伪装成流畅、自信的错误答案。

## 论文没有证明什么

- 没有证明语义检索普遍优于所有 grep/search Agent。每种范式只使用一个具体 harness，工具、提示和编排共同变化。
- 没有证明结果能迁移到代码编辑、测试执行、修复或长时间多任务会话。恰恰在这些任务中，隔离主上下文可能产生本文测不到的收益。
- 没有证明快速变化、无法预索引的工作区仍应使用向量索引。固定 benchmark 快照是最有利于索引的场景。
- 没有测量同配置重跑波动；温度 0 不能替代重复实验。
- 没有直接构造逐阶段的 gold exposure：候选返回、真实读取、子 Agent 摘要和最终答案引用之间的召回损失没有被分别量化。
- 没有给出 planner→subagent→planner 交接的受控消融，因此 41.8% 的分类说明故障集中在哪里，却不能识别摘要长度、指令质量、上下文窗口还是整合策略中的具体原因。

## 读完真正应该记住的六件事

1. **上下文隔离是一种有损信道。** 它减少主上下文噪声，也可能把必要证据挡在主 Agent 之外。
2. **工具调用比例不能代表信息影响。** 7% 的委派触发了 68.8% 的全部 Deep 工具调用。
3. **最终答对/答错不足以诊断搜索系统。** 同一“答错实体”症状可能来自没检索到、子 Agent没传回来或主 Agent误解。
4. **复杂编排必须用成本—质量联合指标评价。** 本文 Deep 多花 token 却没有进入效率前沿。
5. **模型与 harness 有强交互。** Gemini 3 Flash 的 49.6pp 极端差距不应被当成通用平均效果。
6. **结论必须绑定任务制度。** “单问题、只读、可索引”是本文结果成立的核心边界。

## 对当前研究的启发

当前 `causal-review` 已完成 13 例 BM25、GraphLocator 与 SWE-agent 的真实检索暴露，并把 73 个 union 已读文件审计为关键、支持、暂定 plausible、unknown 和无关。本文最直接的价值不是提供“语义检索一定更好”的先验，而是给出一套应加入真实暴露实验的**交接层测量**。

### 1. 把五阶段 exposure ledger 固定下来

每种方法至少区分：

```text
方法返回候选
    → Agent 实际选择
    → 工具实际读取
    → 中间摘要/计划保留
    → 最终定位或回答引用
```

当前 GraphLocator 的候选、SWE-agent 的真实读取和最终行定位已经能覆盖前三层；下一步应补“中间判断是否保留了关键/支持/P 证据”和“最终理由是否引用”。否则会把“子过程确实读过”误当成“主决策实际利用”。

### 2. 为 SWE-agent 的 8 个预算耗尽槽位单独定义机制

这 8 个结果是 N/A 而非 0，不能与有提交但答错混为一类。可借用本文机制/症状双轴：机制记为非终止、工具失败、未形成提交或预算耗尽；症状再记无答案、错定位或理由不完整。这样既保留工程故障，也不把它伪装成检索质量。

### 3. 不把“答案未覆盖 P”直接解释成“P 误导”

本文协调断裂的关键证据来自完整轨迹，而非看到最终答案错就倒推。当前 16 个暂定 P 文件也应分别检查：是否被返回、是否被实际读取、是否进入中间总结、是否与错误实体/过宽行范围存在时间先后和内容对应。只有处理真正暴露在决策链上，才有资格成为后续干预候选。

### 4. 受控干预时冻结交接内容，而不只匹配 token

若比较 BM25、Graph 与主动搜索，除了新增 token、文件数和源码长度，还应控制 evidence packaging：完整源码、截取片段、文件列表、子 Agent 摘要不是同一种处理。可以增加两阶段实验：先固定同一批已读文件，只改变交给主模型的表示；再固定表示，只改变文件身份。这样才能分离“检索来源效应”和“压缩/交接效应”。

### 5. 同时保留 rerun control

本文缺少同配置重复，是当前研究可以做得更强的地方。对关键/P/unknown 暴露分别保留原样重跑，估计实际读取、最终引用和定位结果的翻转率；只有 treatment swap 超过 rerun noise，才讨论真实方法差异或 plausible-context 效应。

### 6. 当前更合适的 RQ 表述

基于最新数据，RQ 不宜直接写“哪种方法更容易引入误导代码”。更稳妥的是：

> 不同仓库检索范式在候选返回、实际选择、主动阅读和最终证据利用上产生怎样的 exposure funnel？其中哪些 evidence identity 与 representation 会在控制核心证据和预算后改变定位精度、范围宽度与机制判断？

这能容纳零效应、预算耗尽、unknown 文件和方法不支持案例，也不会先验地把 Core 外代码标成噪声。

## 总评

这篇论文的优势是把一个流行的架构直觉放到同模型配对实验中，并用全失败轨迹解释结果。人类验证 judge、阈值敏感性、整仓 bootstrap、成本前沿和机制/症状双轴，使“Semantic 领先”不只是一个总分表。尤其是 41.8% 协调断裂与 91% 静默输出，提供了一个强烈而具体的反例：**主 Agent 看起来回答正常，并不意味着搜索证据完成了可靠交接。**

它的主要不足同样清楚。两种范式是完整系统包，工具、提示、编排和预算同时改变；没有 compute-matched 消融、重复运行或逐阶段 gold exposure；Gemini 3 Flash 的异常大差距提示 harness 兼容性可能主导部分结果。因而这篇论文适合作为“过程交接是独立失败层”的机制证据，不适合作为“向量检索普遍优于 Agent 搜索”的最终裁决。

对当前研究而言，最值得带走的不是 65.2% 对 46.2%，而是一个测量原则：**真实检索实验必须记录证据在每一道边界上是否被保留；候选出现、文件被读、中间摘要保留和最终判断使用，是四个不同事件。**
