## 先说结论：先定义交接契约，再讨论“定位够不够好”

这篇论文问了一个很实用的问题：在修复 Agent 动手以前，能否用更小、更便宜的模型完成仓库探索，并保留大部分定位质量？作者建立 IssueLoc-Bench，让五个模型在相同的只读仓库接口下，根据 issue 返回排序后的文件路径，再比较质量、时间、token 与估算 API 成本。

答案不是“某个小模型普遍最好”。GLM-4.7-Flash 的定位质量最高，但在 SWE-bench Verified 衍生任务上平均约用 233k token、242 秒；Qwen3-30B-A3B 只保留其约 89% 的 Hit@3，却减少约 95% token 和 73% 时间。Qwen3-Coder-30B-A3B 的 Hit@3 保留率更高，约 94%，但输出更长、严格集合指标更差。模型选择取决于下游怎样消费定位结果。

论文最值得带走的是两个交接契约。若修复 Agent 仍能访问整个仓库，定位器只需给出“可恢复的候选列表”，Hit@3、Recall@3、MRR 更重要；若系统把预测文件变成访问白名单，定位就成了“硬门禁”，F1 与 exact match 才是关键。没有先写清契约，把任一指标当成统一目标都会误导工程决策。

对当前研究而言，它补上了 SHERLOC 前面的一层：SHERLOC 讨论候选内部应交付什么诊断，而 IssueLoc-Bench 讨论候选集合应以什么权限和失败恢复方式交给下游。它仍未做固定 repairer 的端到端实验，因此只能校准检索输出契约，不能证明便宜定位器会提高最终修复率。

## 理解全文所需的五个概念

### 1. Repository explorer

Explorer 是修复前的只读 Agent：接收 issue 与 pre-fix 仓库，可用 `ls`、`find`、`grep`、`cat`、`nl`、`sed` 等命令浏览，最后返回排序后的、不重复的仓库相对文件路径。它不编辑代码，也不运行完整修复流程。

### 2. Gold file set

论文把历史修复 commit 中修改过、且通过过滤的文件视为 gold。这个集合是开发者当时的修改足迹，不保证是最小充分文件集，更不保证每个文件都具有因果必要性。尤其在多文件修复中，辅助测试或重构文件可能被计入 gold。

### 3. Soft handoff

下游把定位结果当导航提示，仍可继续搜索整个仓库。只要前三名里出现一个有用文件，就可能启动正确诊断。因此 Hit@3、Recall@3 和 MRR 对这种可恢复流程更贴切。

### 4. Hard gate

下游只能读定位器返回的文件。此时漏掉任何必要文件都会造成不可恢复失败，而多报文件又会扩大噪声与成本，所以 F1 和 exact match 更重要。硬门禁若没有 escape hatch，会把上游一次失误永久放大。

### 5. Operating point

论文测到的不是纯粹的“模型能力”，而是模型连同停止策略、工具调用习惯、轮数、读文件量和输出长度形成的整条轨迹。相同接口不等于相同计算量；因此时间与 token 只能解释为完整配置的运行点。

## 研究问题与证据链

```text
问题：高质量探索是否必须使用昂贵模型？
  ↓
基准：499 个 SWE-bench 衍生任务 + 500 个随机仓库任务
  ↓
控制：同一只读接口、同一超时、统一文件路径输出
  ↓
质量：候选排名指标 + 集合指标 + 错误率
  ↓
成本：步骤、时间、输入/输出/总 token、价格快照
  ↓
推论：按 handoff 契约选择 explorer，并设置失败升级
  ↓
边界：未把 explorer 接到固定 repairer 上测最终成功率
```

## IssueLoc-Bench 怎样构造

### 两个互补数据臂

第一臂来自 SWE-bench Verified，共 499 个可用任务、12 个仓库，平均 gold 文件数 1.24，平均仓库路径数约 3,899。它贴近真实 issue 修复，但仓库高度集中，也可能受到公开数据污染。

第二臂从随机 GitHub 仓库构造 500 个任务，覆盖 153 个互不重叠的仓库，平均 gold 文件数 2.27、路径数约 614。它提升仓库多样性，却不等同于真实 issue 的难度分布。两个数据臂不是谁替代谁，而是分别强调真实任务结构与跨仓库外部效度。

### Gold 过滤

作者从历史解决 commit 的修改文件出发，移除新建、删除、二进制式、空 gold、以及全部为 Markdown/纯文本的任务。这样能让“在 pre-fix 仓库中查找文件”成为可执行问题，但也把需要新增文件或纯文档修复排除在外。

### 统一交互协议

五个模型看到同一 issue、同一仓库快照和同一只读命令集合，单实例超时 600 秒。最终答案解析为排序文件列表；无效路径计作 false positive，执行错误或空答案按空预测、质量记零。这个处理避免把失败实例从分母删除而美化平均数。

## 指标为何必须分成两组

### 候选导航指标

- **Hit@k**：前 k 个候选是否至少命中一个 gold 文件；
- **Recall@3**：前三个候选覆盖 gold 集合的比例；
- **MRR**：第一个 gold 文件出现位置的倒数。

这些指标适用于 soft handoff。它们奖励“快速给下游一个正确入口”，并不要求候选集合完全精确。

### 集合门禁指标

- **Macro F1**：每个实例的文件集合 precision 与 recall 的调和平均，再跨实例平均；
- **Exact match**：预测集合与 gold 集合完全相同。

这些指标适用于 hard gate。exact match 很苛刻，但当访问权限被上游结果限制时，这种苛刻恰好反映不可恢复风险。

## 实验对象与统计设计

作者比较 GLM-4.7-Flash、Gemma-4-E4B、Qwen3-30B-A3B、Qwen3-Coder-30B-A3B 与 Qwen3-4B。GLM 是高质量参考点，其余模型代表不同规模、专门化与成本的候选 explorer。

质量差异使用实例配对的 10,000 次 bootstrap，固定随机种子 1729；二元指标用 exact McNemar 检验，并对 32 项比较做 Holm 校正。作者还按仓库聚类 bootstrap，以免 499 个任务来自 12 个仓库造成伪精确。后者确实使部分 SWE 臂差异变弱，说明“实例很多”不等于独立环境很多。

每个模型只运行一次，没有重复随机轨迹。因此置信区间主要反映任务抽样不确定性，不包含模型同一任务多次运行的波动。这是阅读显著性结果时必须保留的限定。

## 结果一：质量最高的 explorer 显著更贵

在 SWE 臂上，GLM 的 Hit@3 为 **0.7756**、Recall@3 为 **0.7291**、MRR 为 **0.7642**、F1 为 **0.6965**、exact match 为 **0.5691**。代价是平均 **27.02** 步、**241.58 秒**、约 **233,294** token，错误率 6.6%。

四个轻量候选的取舍不同：

| 模型 | Hit@3 | F1 | Exact match | 平均时间 | 总 token |
|---|---:|---:|---:|---:|---:|
| GLM-4.7-Flash | 0.7756 | 0.6965 | 0.5691 | 241.58s | 233,294 |
| Gemma-4-E4B | 0.6774 | 0.6281 | 0.5551 | 43.09s | 26,640 |
| Qwen3-30B-A3B | 0.6934 | 0.6400 | 0.5571 | 66.28s | 11,123 |
| Qwen3-Coder-30B-A3B | 0.7315 | 0.6173 | 0.4449 | 81.29s | 27,116 |
| Qwen3-4B | 0.6453 | 0.5711 | 0.4629 | 30.15s | 14,976 |

Qwen3-Coder 最接近 GLM 的候选命中率，却在 exact match 上明显落后，说明它更像“宽松召回型” explorer；Qwen3-30B 的 token 最低且集合质量更均衡。模型名称中的“Coder”不能替代针对交接契约的实测。

## 结果二：跨仓库后，没有一个排序能保持不变

随机仓库臂上，GLM 仍领先，Hit@3 为 **0.8400**、F1 为 **0.6724**，但 exact match 只有 **0.4300**。Qwen3-30B 的 Hit@3/F1 为 **0.7560/0.5963**，Gemma 为 **0.7420/0.5787**，Qwen3-Coder 为 **0.7460/0.5730**，Qwen3-4B 为 **0.6540/0.4880**。

随机臂平均 gold 文件更多，因此“至少命中一个”的 Hit@3 可能提高，而完全匹配整个集合反而更难。这个反向变化说明单一数字不能脱离任务的 gold-set 基数解释。

## 结果三：保留率比绝对分数更适合成本决策

论文把轻量模型质量除以 GLM 质量，并同时报告资源降幅。在 SWE 臂：

- Gemma 保留 87.3% Hit@3、90.2% F1，时间减少 82.2%、token 减少 88.6%；
- Qwen3-30B 保留 89.4% Hit@3、91.9% F1，时间减少 72.6%、token 减少 95.2%；
- Qwen3-Coder 保留 94.3% Hit@3、88.6% F1，时间减少 66.4%、token 减少 88.4%；
- Qwen3-4B 保留 83.2% Hit@3、82.0% F1，时间减少 87.5%、token 减少 93.6%。

这形成三个不同推荐：soft handoff 优先 Qwen3-Coder 的候选召回；严格集合或 token 预算优先 Qwen3-30B；极端低时延才考虑 Qwen3-4B。它们不是统一排行榜的第一、第二、第三，而是不同约束下的 Pareto 点。

## 失败升级：论文最可落地的系统建议

作者建议先用便宜 explorer，出现空候选、无效路径，或下游无法形成诊断时再升级到强模型。这个路由要满足两点：

1. 失败信号必须在没有 gold 的线上环境中可观测；
2. hard gate 必须保留 escape hatch，让下游在候选不够时恢复全仓库访问或重新探索。

“置信度低就升级”听起来简单，但论文并未训练或校准置信度模型。它提供的是系统设计方向，不是已经验证的最优路由策略。

## Evidence Audit：证明了什么

1. **证明了同一只读接口下存在显著质量—成本 Pareto 前沿。** 轻量 explorer 可减少约 84%–95% token，同时保留大部分定位质量。
2. **证明了指标选择必须服从 handoff contract。** 同一模型在候选排名与集合门禁指标上的相对表现明显不同。
3. **证明了错误实例不能从均值中删除。** 空答案、执行错误和无效路径被明确计入，成本与可靠性共同构成运行点。
4. **证明了仓库聚类会改变不确定性判断。** SWE 臂只有 12 个仓库，按实例独立计算会高估部分质量差异的精度。
5. **证明了专门化模型不自动主导。** Qwen3-Coder 更偏召回，通用 Qwen3-30B 在 token 与严格集合质量上更均衡。

## 没有证明什么

1. **没有证明便宜 explorer 能维持最终修复率。** 没有固定 repairer、固定下游预算的端到端对照。
2. **没有证明 gold 文件是因果必要或最小充分集合。** 它只是历史 resolving commit 的过滤后足迹。
3. **没有隔离模型与轨迹策略的贡献。** 步数、停止、文件读取量和输出长度同时变化。
4. **没有估计重复采样稳定性。** 单次运行无法覆盖温度和工具决策带来的 run-to-run variance。
5. **没有验证线上升级门控。** 空/无效候选容易检测，‘下游无法形成诊断’仍需要可校准的判据。

## 对当前研究的直接启发

### 1. 冻结“检索输出契约”，再比较方法

当前 BM25、GraphLocator、SWE-agent 的输出不能只统一成一个文件/函数命中表。应明确每种方法交给下游的是：排序候选、可读取行块，还是访问白名单。若下游仍可自由探索，主要看 Hit@k、first-hit rank 与实际可见关键块；若候选限制访问，则必须报告集合 recall、exact match 与 escape 次数。

### 2. 把预算耗尽定义为运行结果，不是零质量

现有 13-case 实验里 SWE-agent 的 8 个预算耗尽继续记为 N/A 是正确的；但系统层评估还应单列 failure rate，并在部署效用中惩罚。论文把错误计零适合统一 benchmark 平均，当前因果分析则要保留“没产生处理”和“产生了无效处理”的区别。

### 3. Peripheral 增量实验保持 downstream access 一致

下一步等 token、等位置的 Core + Peripheral 对照，不能一组允许回查仓库、另一组把上下文当硬门禁。访问权限本身会改变处理。建议固定为 soft handoff：Core 始终可见，Peripheral 是额外随机暴露，下游仍有相同工具权限；另开独立实验研究 hard gate，不混在同一个效应里。

### 4. 同时记录 explorer 成本与 consumer 补偿成本

便宜 explorer 可能把成本转移给下游：候选更宽时，修复 Agent 需要额外阅读和验证。主表应同时报告 retrieval token、handoff token、consumer search token 与总 wall-clock，避免只优化上游账单。

### 5. 用可观测信号设计升级，而不是事后 gold

可以预注册三类升级条件：空/无效路径；候选间证据冲突；消费者在固定步数内未形成可执行诊断。条件必须不读取 gold patch，并报告触发率、额外成本和最终收益。这样才能把论文的路由建议变成可识别实验。

## 最终评价

IssueLoc-Bench 没有发明新的仓库搜索算法，它做的是更基础也更容易被忽视的工作：把探索阶段从修复 Agent 中拆出来，并让质量、成本与交接契约进入同一张表。其结果足以否定“定位器越强越好”这种无预算排序，也否定用单一 file hit 指标评价所有下游架构。

对当前研究，最直接的价值是规范实验接口：真实检索输出必须带排序、可见范围、预算状态和访问权限；Core/Peripheral 的因果对照必须在相同 handoff contract 下进行。论文没有验证最终修复效应，反而清楚划出了下一步应补的证据：固定消费者、固定总预算、显式 escape hatch，并对端到端成功率做配对比较。
