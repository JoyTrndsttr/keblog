## 1. 这篇论文在问什么：判断正确以后，还需要检查什么？

一个 Agent 被交给一次代码提交，它认为“这次改动引入了漏洞”。常见评估只检查这句话对不对。VulContextBench 进一步问：**它有没有找到支持这个判断的代码，以及有没有把找到的代码正确地交代给用户？** 作者构建 111 个经过人工审计的漏洞引入提交，标注 464 个带证据角色的代码块，然后分别评分 Agent 探索时打开的代码和最终报告引用的代码。

最重要的发现不是模型完全不会查仓库。七个模型在探索时都覆盖了大部分 gold context，但最终证据声明只覆盖其中一部分；块级召回的下降约为 37—73 个百分点。与此同时，“引用了正确文件”和“引用了文件里的正确代码”差别很大，“引用了正确位置”和“正确认识这段代码的证据角色”也差别很大。

过去的评价主要围绕最终 verdict，即是否引入漏洞的判断。具体问题有两个：一个模型可能记住了公开漏洞公告而给出正确答案，另一个模型可能沿着源码追踪输入、危险操作和约束，两者得到相同分数；而数据集认定的“引入漏洞的提交”本身还可能追错。作者因此先审计任务，再标注证据，最后把结果判断和外显证据分开评价。这是 benchmark 与评估协议论文，不是提出一种新的检索算法，也不是给 Agent 增加新模块后证明性能提升的论文。

### 理解全文需要的五个概念

**漏洞引入提交（Vulnerability-Introducing Commit，VIC）**是让某种漏洞行为开始存在的提交。它不是“修复之前最近一次碰过这行的提交”。如果一次提交只把早已存在的危险代码重新排版，它可以出现在版本追踪结果里，却不应该被当成真正引入者。

**漏洞修复提交（Vulnerability-Fixing Commit，VFC）**是移除漏洞的提交。作者通过它确定需要回溯的代码，但修复改了某行，并不自动证明那行的最后修改者就是漏洞引入者。漏洞行为还依赖入口、调用关系和周围约束。

**Gold context**是人工审核后认为支持该漏洞判断的源码区域。本文将它表示为具体仓库快照中的文件与行范围，并标注证据角色。Gold 是评估参照；“某块不在 gold 中”和“某块没有用”不能自动画等号，因为可能存在其他充分证据路径。

**Viewed context 与 declared evidence**分别是运行轨迹里实际打开的源码和最终报告声明的证据。检索命中、工具打开、模型理解、最终引用是不同环节；本文直接观察打开与引用，不直接观察模型内部理解。

**证据角色**回答“这段代码为什么重要”，包括引入漏洞的核心代码、产生危害的操作、攻击者可达路径和支持性定义/约束。找对位置却分错角色，也可能让读者无法检查报告的逻辑。

### 顶层证据链

| 层次 | 本文如何落实 |
|---|---|
| Research gap | 最终二元判断不能显示证据获取与选择质量；自动追踪的 VIC 标签可能错误 |
| Research object | 在引入提交快照上，Agent 对漏洞判断所搜集和声明的源码证据 |
| Operationalization | 审计后的 VIC、带角色的 gold 区域、轨迹中的 viewed 区域、报告中的 declared 区域 |
| Method / experiment | 两来源任务池、四条件审计、双 Agent 提案加人工审核、盲化验证、统一 harness 的七模型评估 |
| Evidence | 两阶段三粒度 P/R/F1，角色匹配与忽略角色的对比，diff-only 与 diff+gold 验证 |
| Claim | 大部分模型并非找不到源码，而是最终证据选择和角色识别存在明显缺口 |

这条链有两个需要始终记住的边界。第一，源码被打开，不等于它确实影响了模型决策。第二，最终引用缺少 gold，不等于 verdict 必然错。作者正是在测量最终准确率之外的一个独立质量维度。

## 2. Research gap：为什么只看 verdict 不够？

### 2.1 正确答案可能来自记忆，也可能来自推理

Common Vulnerabilities and Exposures（CVE，公开漏洞编号体系）通常连接着公告、修复、讨论和代码。若这些材料进入预训练，模型可能识别仓库或改动模式而回忆出答案。作者将这作为现实威胁提出，并引用既有研究说明漏洞检测会受到标签质量、重复数据和与真实漏洞无关的信号影响。

但本文没有对每次运行检测“答案究竟是记住的还是推导的”，也没有量化自己的七个模型有多少污染。它的贡献是提供另一种测量：即使 verdict 正确，也能检查报告是否提供了可核查的源码支持。隐藏 CVE 等信息降低直接提示答案的机会，并不能消除模型通过代码认出历史案例的可能。

### 2.2 标签回溯与行为引入不是同一个问题

SZZ 是以提出者姓氏命名的版本历史回溯方法；V-SZZ 是面向漏洞的扩展。基本思路是从修复修改的行回头查其历史来源。困难在于：版本历史记录的是文本变化，而漏洞是行为与可达条件的组合。

例如，危险函数一直存在，但直到后来某次提交增加了外部可控入口才形成攻击面。只追危险语句的历史，可能把时间点定得太早；反过来，格式化提交最后修改了该语句，也可能把时间点定得太晚。这是教学例子，不是论文报告的具体案例。

因此不能直接用“不可靠的引入提交 + 精细的证据打分”得到可信 benchmark。若快照时根本没有攻击者可达路径，Agent 无论怎么搜索，都找不出评估期望的 reachability evidence。

### 2.3 为什么安全任务尤其需要证据评价？

Issue resolution 往往还能通过测试看补丁是否解决问题。历史提交是否引入安全漏洞，则没有天然的同等执行信号：普通测试可能一直通过。安全报告还要交给人工复核，读者需要知道输入从哪里来、怎样到达危险操作、哪个约束被破坏。只给结论无法承担这项检查工作。

作者因此采用 ContextBench 的多粒度检索评价思想，扩展到安全场景，并补上 VIC 审计和角色标注。它并没有宣称检索分数能够替代全部安全验证；结论中的下一步仍包括运行 exploit 的概念验证。

## 3. Benchmark 怎么构建：从候选提交到可评分证据

整体流程是：

**既有 VIC 数据集 + OSV 近期公告 → 去重与候选池 → 逐例检查四项 VIC 条件 → 两个知情 Agent 独立提出证据 → 人工审查所有提案 → 快照行范围与角色 gold → 盲化模型验证 → 统一 Agent 协议评估。**

Figure 2 从左到右分成三块：左侧蓝灰色区域是两类任务池，中间黄色区域是四个审计条件，右侧绿色区域是双提案、人工标注与 verifier。图中的 proposer 汇合到候选上下文，人工与 verifier 再参与质量控制；具体谁看得到哪些信息，要以 §2.4 的文字协议为准。图是构建流程示意，不是证明标注完全可靠的实验结果。

### 3.1 Step 1：为什么需要两个候选来源？

第一来源是六个已发布数据源，分为两类：

| 来源类别 | 数据源 | 作者如何使用 |
|---|---|---|
| 人工审查过的来源 | V-SZZ-C、V-SZZ-Java、VCC-Eval、Vulnerability History Project 的最高审核等级 | 使用已发表的候选 VIC 标签，随后仍统一重新审计 |
| V-SZZ 标注来源 | ICVul，以及 Aladics 等人的 Java 数据集 | 接收来源发布的追踪标签，不重新运行它们的 V-SZZ；仍统一审计 |

池内按 CVE 去重。这里的“人工审查过”不是免检通行证，不同来源原来的引入定义和审查标准可能不同。

第二来源来自 OSV.dev 的近期漏洞公告。OSV 是 Open Source Vulnerabilities，即开源漏洞信息服务。作者选择 2026 年分配 CVE、并引用修复提交的公告，覆盖 PyPI、npm、Go 和 Maven 生态，再自行运行 V-SZZ 追踪候选引入提交。

这样补池有两层目的：已有来源主要覆盖 C 和 Java，语言范围不足；已有六来源最新到 2024 年，人工来源最新到 2022 年，历史公告更可能被模型见过。近期池增加语言和时间覆盖。注意“2026 年分配 CVE”不保证漏洞代码本身也是 2026 年写的，更不能保证它未进入训练语料。

该步骤输出的是候选，不是金标。原文没有给出完整可复现的采样率、各池逐项候选数量或所有去重规则细节；不能把最终 111 例理解为真实漏洞总体的随机代表样本。

### 3.2 Step 2：四项审计条件为什么缺一不可？

307 个候选进入审计，最后保留 111 个，约 36.2%。其余 196 个没有进入最终 corpus。这个比例反映所收集候选通过本文条件的比例，不是对所有上游数据集准确率的总体估计；作者明确说本文不是上游标签准确率研究。

| 条件 | 需要确认的事实 | 它防止什么错误 |
|---|---|---|
| 真实漏洞与真实修复 | 存在 CVE，且 VFC 移除了该漏洞 | 用没有可靠修复参照的案例做 gold |
| 真正引入者 | 历史回溯关联该提交，漏洞行为此前不存在 | 把最后触碰文本的提交当成行为引入点 |
| 实际改变漏洞代码 | 不是重命名、格式化、整体导入/搬移、早期不完整修复或仅触碰别处 | 把文本迁移和非目标改动误当引入 |
| 快照时攻击者可达 | 在给 Agent 的提交快照上，攻击者可以到达漏洞 | 要求模型找出后来才出现的入口或 sink |

四项检查都借助完整仓库历史。第二项偏“历史上谁改变了行为”，第三项偏“当前提交到底做了何种变化”，两者相关但用途不同。第四项则使任务在该快照上具有可回答性。

如果移除最后一项，gold 可能来自修复时的仓库，而 Agent 看的是更早的仓库。这不是模型能力问题，而是任务信息不对称。论文用审计减少这种问题，但没有提供逐类拒绝数量、完整审计者一致性或执行式可达性验证，所以不能把流程图的四个框等同于四项已有独立实验证明。

### 3.3 Step 3：先让 Agent 广泛提案，再由人作判断

对于每个保留案例，两个 proposer 独立工作：

- Claude Code，运行 Claude Opus 4.8；
- OpenAI Codex，运行 GPT-5.5。

它们看得到仓库快照、引入 diff、修复 diff、CVE 编号、Common Weakness Enumeration（CWE，漏洞弱点类别）、漏洞描述。两者在隔离 sandbox 中工作，不能查看对方输出。

这种知情设计合理的原因是：提案阶段目标是尽可能找全证据，而不是测模型是否能在未知情况下发现漏洞。若标注工具也必须从零猜测，gold 会混入“提案模型没搜到”造成的漏标。知情提案不构成被评估 Agent 的信息权限。

之后用行范围重叠作确定性 diff，分开“两者都提出”和“只有一个提出”的区域。人工标注者审核两类中的每一个块，回到快照检查，最终写出精确行范围。这一步不是只保留模型交集：只保留交集会把两模型各自发现的独有证据丢掉。

Gold block 采用包围证据的语法单元，可是函数、方法、类、struct、macro、顶层语句，或者明确命名的文件区域。因此“block”不等于“函数”；如果只以函数为检索语料，可能先天覆盖不到本文需要的类型或宏证据。每行还标记是否由当前提交 authored，这有助于区分改动本身与已有周边源码。

### 3.4 四种角色：位置之外，还要说清证据的用途

| 角色 | 本文含义 | 教学例子：路径穿越场景 |
|---|---|---|
| VIC Core | 引入漏洞的核心改动 | 删除文件路径限制检查的改动 |
| Sink | 缺陷产生安全危害的操作 | 使用拼接路径读取文件 |
| Reachability | 攻击者可控入口到漏洞的路径 | 请求参数进入处理函数再传入文件操作 |
| Dependency | 改动依赖的外部定义、不变量、配置 | 基目录定义、路径标准化契约或权限配置 |

右列是说明概念的假设场景，不是论文案例。Dependency 不是软件包依赖清单。它可以是一段类型定义、一条配置或某个函数保证的约束；若没有这些，就不能判断改动是否真的破坏了安全条件。

严格说，只有后三类是漏洞核心之外的 context。作者仍把 VIC Core 纳入 gold，并把它作为第四角色，因为找到核心本身也需要定位。理解这一点可以避免把“上下文召回”全部解释成跨文件推理能力：一部分 gold 是 diff 已经提示的核心代码。

这些角色不是把真实漏洞机制强行简化成一条固定链。它们是统一评分的类别，能让研究者看到模型覆盖的是显眼改动还是支持性证据；角色得分仍不能完整衡量报告逻辑的严密程度。

### 3.5 Gold 是否足够：盲化 verifier 与 diff-only 对照

标注结束后，另用 GPT-5.5 作为 verifier。它只收到引入 diff 和 gold 源码，判断是否引入漏洞以及漏洞是什么；不看 CVE 描述、编号、CWE、修复提交或完整仓库。对照组同一 verifier 只看引入 diff。

结果是：

| verifier 输入 | 识别漏洞比例 |
|---|---:|
| diff-only | 27.0% |
| diff + gold context | 75.1% |
| 差值 | +48.1 个百分点 |

遮蔽漏洞描述尤其关键：描述会直接说出问题，CWE 也会提示漏洞类别。如果 verifier 看过这些再答对，就无法知道是否是代码证据起作用。对照则检查 gold 比 diff 多提供了什么可用信息。

**这支持 gold 在该 verifier 和该 corpus 上整体上有帮助，不能证明每例充分。** 仍约四分之一未被识别；失败可能来自 gold 不足，也可能来自 verifier 能力或判定问题，本文没有进一步拆分。成功也不能证明 gold 最小充分、唯一充分，或每块都必不可少。

还有一个限制：GPT-5.5 同时出现在提案模型和 verifier 中，独立运行与盲化减少信息泄露，但不能消除同系列模型共享偏好的可能。原文没有多 verifier、逐块移除或 exploit-based 验证结果。这里的 diff+gold 还同时增加了信息与输入长度，因此不宜把 48.1pp 全解释为某种特定语义内容相对等长 filler 的因果贡献。

Table 1 固定最终审计 corpus，展示语言分布和 gold 规模。242 是按任务累计的标注文件数量，13,370 是这些块覆盖的行数，不是 13,370 条精确漏洞语句。语言内 CWE 数可重叠，总数 63 是并集，不能把各行 CWE 数相加当总数。

几个有解释力的比较：

1. C/C++ 与 Java 合计 82/111，约 73.9%。虽然跨五语言，总体结果仍主要反映这两类任务。
2. 平均约 4.18 块、2.18 个标注文件、120.45 块行/任务。这些是由总数算出的均值，不是论文报告的分布或中位数；不能据此断言每例只有四块。
3. 83 个仓库、最大仓库 7 例，减少单个项目占据大量任务的情况，但不等于完全消除仓库内相关性。
4. CVE 年份跨 2008—2026；2024 年 35 例，2026 年 34 例。最近案例降低全体均为历史资料的局限，历史案例仍占多数。

最常见 CWE 是 CWE-22 路径穿越（11 例）、CWE-125 越界读（6 例）、CWE-416 释放后使用（5 例）。“覆盖 63 类”体现多样性，却也意味着许多类别样本很少，不能据总体均值得出每个 CWE 都有同样模式。本文没有报告完整的语言/时间/CWE 分层效果或显著性检验。

## 5. Agent 怎样运行，什么信息能看，最终提交什么？

任务形式是 \((S,d_{vic})\)：只读仓库快照 \(S\) 加引入提交的 diff \(d_{vic}\)。被评估 Agent **没有** CVE、漏洞描述、CWE 或修复提交，它必须自主探索，再提交结构化安全报告。

最终报告包含 verdict、根因和安全影响解释，以及证据列表：

\[
C^A=\{(f_i,s_i,e_i,c_i,r_i)\}_{i=1}^{n}.
\]

这里 \(f_i\) 是快照内相对路径，\([s_i,e_i]\) 是包含首尾的行范围，\(c_i\) 是角色，\(r_i\) 是简短理由。假设它提交 `src/handler.py:40–65`、Reachability、解释请求参数流入危险函数；评估器就可以检查位置重叠和角色是否对应 gold。这个例子只说明输出格式。

七模型运行在相同 mini-SWE-agent harness 中，使用相同 prompt，通过 final submission tool 提交报告。Prompt 要求只引用实际检查过的代码，并用带行号的源码输出确认引用边界。Viewed 区域另从轨迹恢复，不能用最终报告反推“它看过什么”。

统一 harness 控制了工具包装和题面形式，避免把不同产品默认工作流的差异全归给模型。但论文正文未明确报告 temperature、重复运行数、每模型完整版本、统一 token/turn/time 上限、模型输入窗口、费用或运行失败处理分母。不能因此声称七模型成本等同，也不能把小分数差异解释为稳定统计优势。

整个 corpus 是审计通过的 VIC。正文未描述匹配的非漏洞提交对照组，因此 Table 2 的 verdict accuracy 不能被解读为完整安全检测场景的二分类准确率、特异度或误报能力。在这个正例 corpus 上答对，不证明能在大量普通提交中筛出稀少漏洞。

## 6. 三粒度与两阶段：分数到底测什么？

### 6.1 为什么同时有 File、Block、Line？

File 问“有没有进入正确文件”。Block 问“有没有把支持证据的函数或语法区域找出来，而不是把文件整段搬进报告”。Line 问“有没有覆盖修复改动对应的精确漏洞位置”。

这三者不是三个可互换实现。只命中正确文件，会给同文件错误函数带来表面成功；只用精确行，返回完整函数又会被许多非目标行稀释 precision。作者因此同时报告。

注意本文明确将 block gold 的范围与 line 层的修复位置区别开。不要把 Table 1 的 13,370 block 行直接当作 line-level 精确漏洞 GT。修复位置又是漏洞位置的操作化代理，不自动等于全部根因或全部决定性证据。

### 6.2 先理解 P/R/F1，再看公式

Precision（P）是“交出的区域有多少符合参照”，Recall（R）是“参照证据有多少被覆盖”。如果多交大量不属于参照的代码，P 会下降；漏交 gold，R 会下降。F1 把两者折中，不能用特别高的其中一项掩盖另一项特别低。

按当前粒度对齐集合，设 overlap 为 \(I=|C^A\cap C^G|\)，则：

\[
P=\frac{I}{|C^A|},\qquad
R=\frac{I}{|C^G|},\qquad
F_1=\frac{2PR}{P+R}.
\]

File 集合元素是路径；更细粒度需按区域与目标行对齐。论文用这些集合式表达，并报告 task macro-average。实际复现仍应检查发布实现的块重叠、去重、空集和行映射细节，正文没有给出完整伪代码，不能自行补成“函数命中就算整块正确”。

一个简化教学例子：gold 有 10 个目标单位，Agent 提交 20 个，交集 6 个，P=.30、R=.60、F1=.40。若把整文件都交出，Recall 可能升高而 Precision 大幅下降。这说明“更多检索”不能直接等同于“更好的证据选择”。

Macro-average 是先逐任务算分，再平均。**Table 2 的平均 F1 不是用表里的平均 P 和平均 R 重新算出来的 F1。** 难例、易例各占一份任务权重，也不能通过宏均值看出单例分布。

### 6.3 为什么探索低 precision 不一定是坏事？

Viewed context 包含探索时所有打开的代码。一个 Agent 不可能在打开之前就知道每个文件是否重要，宽探索自然带来低 P。Declared evidence 则是已经做过判断后给人的精炼证据，精确性和完整性都应更高。

本文认为低精确性的证据会增加人工排除负担，也可能增加下游模型使用困难。但本文没有直接测量审查时间或对下游性能的干预效果。Gold 外区域也不能全部认证为“无用”：它们可能是检查后排除的替代假设，或未标入 gold 的另一种证据。

关键是两个阶段各自有不同功能。用 Viewed 的 F1 排名，可能奖励少开文件而惩罚合理排查；用 Declared 的 F1 排名，测的是最终呈现质量，仍需和 verdict、解释支持度一起看。

Figure 1 是两个并排的雷达图，左边 Viewed，右边 Declared；没有常规横纵轴。每条辐射轴对应 File/Block/Line 的 P、R、F1，圆形刻度从中心向外增大，外圈为 1。七种颜色/线型对应七模型：GPT 为深蓝实线，Claude 为橙红实线，Kimi 为绿色实线，DeepSeek 为浅橙实线，Gemini 为深色虚线，Qwen 为红色虚线，Llama 为浅绿虚线。

### 7.4 这项实验没有说明什么？

最终引用少，可能是证据识别不足、压缩报告时遗漏、引用格式约束、输出预算或模型认为某些证据冗余。**论文没有在这些机制之间做干预分辨。** Viewed 区域存在也不代表模型真的理解或利用过它，Declared 区域存在也不代表其理由支持根因。

所以可以说“存在外显的证据选择缺口”，不能进一步说“模型明知证据正确却忘了”，更不能说“那些未引用块对结果没有因果贡献”。

## 9. Baseline、对照、负结果与已有工作的位置

### 9.1 本文实际有哪些对照？

七模型是同框架的模型 baseline，代表不同模型在统一安全检索任务上的表现，不是七种独立检索算法。全文没有提出一个新 Agent 再与现有 Agent 比性能，也没有 BM25、图检索、随机上下文等算法对照。

最明确的输入对照是 gold 验证中的 diff-only 与 diff+gold。它说明补充 gold 能显著增加点估计上的识别比例，但不做等长控制，不认证每块必要性。

另外两个诊断是同一轨迹的 Viewed/Declared 与同一声明的 role-aware/role-ignored。前者拆流程阶段，后者拆评分要求。二者都不是控制某个 treatment 后重新运行的因果消融。

### 9.2 哪些负结果和异常需要保留？

- 所有模型最终证据都不完整，即使 verdict 排名前列；不能只写最强模型的成功。
- 探索召回最高的系统并不最终引用最好。
- Kimi 的证据召回比 Gemini 高，verdict 却低；不能把证据 Recall 简化为答案正确率代理。
- Dependency 的 P/R 没有明显跨模型相关，不能假设所有证据角色具有相同能力结构。
- Gold+diff verifier 只有 75.1%，不能把总体提升写成全部 gold 已认证。
- 精确行 P 低部分来自返回完整块与目标行细小的设计，不应全部归为模型定位失败。

原文没有逐例漏洞 failure case、完整错误类型计数、实际 exploit 或新增 mitigation 的结果。本文的具体案例教学必须明确标注为说明性假设，不能虚构作者案例。

## 10. Evidence audit：这些结果支持多强的结论？

### 10.1 Gold 的构念与完整性

双 Agent 加人工审核提高候选发现与校验能力，但不是全空间证据完备性证明。不同漏洞可能存在多种充分解释，gold 外块被当作不匹配，会降低 P，却不自动说明该块无法支持正确报告。

整体 sufficiency lift 是有价值的检验，仍缺少逐例、多 verifier、替代证据路径、最小性和人工一致性报告。这个限制影响如何解释 retrieval precision，也影响未来用 gold 划分“决定性”和“非决定性”时的有效性。

### 10.2 位置、角色与逻辑支持仍是三层

位置 overlap 评价“在哪”，role match 评价“用来说明什么”，报告解释是否真正构成正确根因与安全影响，还需要语义审查。一个 citation 的行号正确、role 正确，理由仍可能错误。论文输出含理由，但主要表格没有提供逐声明 support correctness 的独立评分。

相反，一个报告引用较少而论证充分，也可能在 gold Recall 下得分低。因此证据完整性与报告可验证性相关，却不是同一构念。

### 10.3 Viewed 是行为记录，不是心智读取

轨迹可以证明某段代码进入了工具输出。它不能证明模型记住、理解或基于该段做判断。Viewed→Declared 的差值把问题缩小到探索后流程，但不唯一定位到“认知识别失败”，更不是步骤级因果归因。

同样，Declaring gold 也可能是事后整理而非真正推理依据。若要证明某段 context 的贡献，需要移除、替换等受控干预；本文没有这样做。

### 10.4 控制、统计与外推

相同 prompt/harness 是重要控制，但模型自带能力、窗口、输出习惯和实际执行成本不相同。全文未给足预算与重复细节，不能称所有成本公平或结果已稳定复现。

宏平均掩盖语言、角色频率、漏洞类型、年份和仓库难度。111 例来自 83 仓库，仍有同项目多个任务；若做显著性检验，应考虑任务配对和仓库内相关。论文没有给置信区间，多模型差值不宜夸大。

隐藏标签和近期 pool 减少直接泄漏，但旧 CVE 多、代码可被识别，污染没有被排除。近期与历史子集也没有分开报告，不能证明 2026 任务上缺口同样大。

只有审计成功的正例是有目的的样本选择。结果能够诊断这些安全证据任务，不能替代真实提交流中的误报/漏报评价，也不能外推到“所有 coding agent 都有同等严重证据丢失”。

### 10.5 哪些关键内容原文没有报告？

没有独立 Threats to Validity 章节并不表示没有威胁。11 页 PDF 中未给出完整模型预算表、重复种子、拒绝类别分布、人工一致性数值、逐语言结果、显著性检验、exploit validation、新改进方法及其消融。笔记不替作者补齐它们；未来复现时应检查 replication package 对哪些项目有补充。

## 12. 作者证明了什么，没证明什么？

### 有实证支持的四点

1. 在本文 111 例、统一 harness 的七模型评估中，探索 gold 覆盖明显高于最终声明覆盖，块 R 缺口约 37—73pp。
2. 文件指标会掩盖内部代码覆盖差异：GPT/Gemini 文件 F1 近似，块 F1 相差 .173。
3. 四类证据的角色匹配召回不均，支持性角色特别是 Dependency 普遍困难；去掉 role 限制后召回上升，证明位置覆盖之外还存在标签错配。
4. 对盲化 GPT verifier，diff+gold 相比 diff-only 从 27.0% 提高到 75.1%，支持 gold 的总体可用性。

### 仍没有被证明的内容

- Gold 每例都充分、完整、最小或唯一；
- Viewed 区域是模型实际决策原因，Declared 是忠实的内部推理解释；
- Recall 缺口由遗忘、attention dilution 或某个具体机制导致；
- 更高 retrieval score 因果地带来更好 verdict，或补充某类证据必然提高结果；
- 非 gold 是无用或有害 context；
- 某个模型的微小 F1 领先具有统计显著性；
- Agent 在真实混合提交流中的误报能力，或已通过执行证明漏洞可利用。

真正应记住的是：**找到代码、选择证据、识别角色、形成正确判断，是四个需要分别测量的环节。** 对安全报告来说，正确 verdict 不能替代可核查证据；而证据 overlap 也不能替代漏洞机制或因果贡献验证。Benchmark 的重要贡献是让这些缺口可见，改进它们仍是后续工作。

## 13. 对当前研究的启发：结合最新第 100 节，而不是停在旧五例结论

本节依据 `JoyTrndsttr/causal-review/documents/研究记录.md` 最新第 99—100 节。最新状态已是五十例、九来源的行级扩展，不应再只引用早期五例 random/plausible 均值。第 100 节有 436 合法、14 不可用配置，主行 GT 有效 409 配置中 181 个输入 GT 行为零；候选占比与行 F1 同例相关约 .0029。现阶段自然来源可计量，但尚无受控伤害证据。

### 13.1 可以直接借鉴：把证据链拆成可观测阶段

保留 retrieval-returned、实际 read、打包进入共同定位器输入、最终 declared 四个集合。本文的 Viewed/Declared 设计提醒我们：检索返回了候选不等于它进入模型输入，进入了也不等于最终引用。历史回放和新 Agent 的实际读取要继续分开，不能把历史记录当新独立重复。

EvidenceLoc-Line 是共同定位包装，输入代码到最终声明之间与真实探索 Agent 仍有区别。应按源码行集合明确计量：`G ∩ input` 衡量可见覆盖，`G ∩ declared` 衡量最终引用。只有输入有关键证据时，选择缺口才更容易解释；181 个输入零覆盖配置不能作为模型被外围误导的主要证据。

可以另报“已可见 gold 的最终引用比例”，但保留完整 gold 分母的主分数。输入覆盖条件分数是诊断，不能通过缩分母把不可见目标从主评价中删除。

### 13.2 对归因指标的帮助：A_loc 与 A_role 可以分开

本文直接提供位置与角色的操作化思路：

- `A_loc`：最终证据位置是否匹配人工审计的机制证据；
- `A_role`：同一位置是否正确标为核心、sink、可达路径或依赖；
- `A_support`：引用及说明是否真能支撑具体根因判断，仍需额外人工或执行检查。

这三者不能全部叫“证据真实因果贡献”。前两者是外显声明正确性，第三者是论证支持度；要研究 context 的因果影响，还要固定任务、核心、输入组织和实际 budget，改变外围 context 后配对比较。

先做 role-aware 与 role-ignored 两套评分，能区分“没引用到”和“引用到了却用途说错”。但 VLocBench 的删除/替换行是 patch 代理，不能未经人工机制审计直接充当四角色金标。

### 13.3 当前语料缺口：Dependency 不一定在函数里

最新实验已发现 import、全局赋值等语料缺口。本文的 block 允许类型、宏、顶层语句和文件 section，且 Dependency R 最低，这提示仅函数检索可能错过关键定义。fOb 的目标输入仍 0/118，是入口/语料与输入覆盖问题，不能解释为 P 干扰。

旧 Oracle 窗口裁剪也可能漏掉桥接函数后段的真实机制。研究记录已发现完整 63 行只保留前 16 行的情况，因此 `R−O` 只能叫检索残余，不自动认证 plausible/non-decisive。本文 gold 的审计与总体验证值得借鉴，不能替代当前 O 的独立机制核查。

### 13.4 怎样转成可检验实验？

优先在核心可见的冻结案例上做 core-only、core+P、core+random 的任务内配对；P 与 random 匹配实际 token、块数、文件身份/数量及输入表示。保留负向、正向和无效结果，不用降分筛选“真正 P”。

同时报告最终质量、位置覆盖、角色正确性、支持度与实际执行成本。若 P 主要改变声明角色而不改变位置，才有依据提出“归因用途错位”；若只是漏掉核心或增加截断，应该先归入可见性/预算机制。自然检索相关接近零不能否定所有条件效应，也不能由负相关宣布因果伤害。

Gold-only 的 verifier 对照可用于检查核心是否基本可识别，但本文 75.1% 的边界说明：单模型答对不能自动认证规则有效，答错也不自动证明 gold 不足。当前按假设推进 P 的计划可以保持，但论文叙事必须把该假设和已观察到的来源暴露分开。

### 13.5 这篇论文在我们的证据链中属于什么？

它提供了安全领域“找到证据与声明证据脱节”的实证先例和一套可借鉴的测量协议。它**没有**研究 plausible context 相对 random 的伤害，也没有证明静态图外围是非决定性上下文。可以作为指标与机制诊断的参考，不能作为我们干扰假设已经成立的证据。
