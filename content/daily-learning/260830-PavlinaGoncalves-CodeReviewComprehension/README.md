## 历史精读正文

## 专家到底是怎样完成代码审查的？

- **论文**：*Code Review Comprehension: Reviewing Strategies Seen Through Code Comprehension Theories*
- **作者**：Pavlína Wurzel Gonçalves、Pooja Rani、Margaret-Anne Storey、Diomidis Spinellis、Alberto Bacchelli
- **Venue**：ICPC 2025
- **DOI**：[10.1109/ICPC66645.2025.00068](https://doi.org/10.1109/ICPC66645.2025.00068)
- **研究材料**：[Zenodo replication package](https://doi.org/10.5281/zenodo.14748996)

### 论文地图

这篇论文真正想回答的是：**审查者面对一个真实 PR 时，如何逐步建立理解，并把这种理解转化成审查意见和最终决策？**

作者观察了10名经验丰富的审查者完成25次真实代码审查，通过思维出声和访谈重建其认知过程。在此基础上，他们扩展了 Letovsky 的代码理解模型，提出 **Code Review Comprehension Model，CRCM**。

最重要的发现不是某一种阅读顺序最好，而是：

> 专家代码审查是一种机会式、可调整的理解过程。审查者先建立上下文，再根据复杂度、已有知识和审查目标，组合线性阅读、难度优先、分块、测试和讨论等活动。

#### 核心矛盾

**过去：** 很多实验和仓库研究把代码审查表现为按文件顺序阅读 diff 的过程。

**问题：** 真实 PR 可能横跨几十个文件、数千行代码，还包含历史讨论、issue、测试和多轮修改。审查者不可能永远逐行完整阅读。

**作者的方案：** 直接观察专家完成日常工作中的真实审查，用代码理解理论解释他们如何控制审查范围、选择策略、建立 mental model，并最终评价代码。

### 理解全文需要抓住的四个概念

#### 1. Mental model：审查者脑中的“这项修改是怎么回事”

Mental model 不是对代码的逐行记忆，而是审查者在脑中形成的结构化表示：修改要解决什么问题、代码怎样实现它、不同实现部分如何对应目标。

审查者不必记住所有代码，但必须形成足以支持判断的模型。

#### 2. Opportunistic strategy：根据当前需要临时调整策略

“机会式”并不是随意或不严谨。它指审查者不固定采用一种阅读顺序，而是根据当前信息选择成本最低、价值最高的下一步。

例如，看到一个大型 PR 时，审查者可能先找核心逻辑；看到熟悉的小修改时，则直接线性读完。

#### 3. Review scope：这一次审查准备理解到什么程度

作者发现，审查者不一定在一次 session 中追求完整理解。他可能只审查自己擅长的部分、只检查高风险代码，或者把剩余问题留给下一轮。

所以，“没有完整读完”并不自动意味着审查失败，也可能是一个主动的范围决策。

#### 4. Expected 与 ideal mental model

审查者不仅建立“实际代码做了什么”的模型，还会形成两个参照物：

- **Expected model**：根据需求、讨论和已有约定，预计作者应该怎样实现。
- **Ideal model**：审查者心目中更优雅、更稳健的实现。

审查意见往往来自实际实现与这两个参照模型之间的差异。

### 为什么过去的代码审查研究还不够？

过去研究已经发现：

- 文件越靠后，收到的审查评论越少；
- 小型实验中的审查者常按界面顺序阅读；
- 测试可以帮助审查者理解修改；
- 复杂修改更难审查。

但是，这些结果没有充分解释一个更基础的问题：

> 当修改大到无法线性完整处理时，审查者究竟依据什么决定先看哪里、看多深以及何时停止？

以往受控实验通常采用陌生项目中的小型修改，适合测量缺陷发现，却很难观察真实审查中的以下因素：

- 审查者已经掌握的项目知识；
- 与作者的前期沟通；
- 多轮 review iteration；
- 其他审查者已经留下的评论；
- 审查者对自身职责范围的判断；
- 时间、精力和认知负担。

因此，本文的 research gap 有两层：

1. 真实代码审查中的理解过程缺少细粒度观察；
2. 现有代码理解模型没有涵盖审查的增量性、互动性和评价目标。

第一点有既有研究设计作为证据支持；第二点则是作者基于观察提出并论证的理论扩展，并不是已经经过量化验证的事实。

### 作者怎样研究一个看不见的认知过程？

认知过程无法直接从 GitHub 日志中恢复。仓库只能告诉我们审查者打开过什么、评论了什么，却不能说明他为什么这样做。

作者采用如下流程：

```text
招募被同事认为擅长审查的经验型开发者
        ↓
观察他们审查自己工作队列中的真实 PR
        ↓
要求审查者边操作边说出正在想什么
        ↓
审查结束后访谈，澄清动作顺序和决策理由
        ↓
转录审查行为、口头解释和访谈
        ↓
以 Letovsky 等代码理解理论建立初始编码框架
        ↓
在理论框架内继续自底向上提取具体策略
        ↓
形成 Code Review Comprehension Model
```

#### 为什么一定要观察真实 PR？

因为作者关注的不是“一个人能否找到预埋缺陷”，而是“他怎样管理真实审查的复杂度”。

真实 PR 让以下行为自然出现：

- 利用已经熟悉的代码库；
- 跟随此前的评论；
- 根据其他审查者的专长缩小范围；
- 查看 issue、CI、文档和历史 PR；
- 把大型修改拆成多个认知单元；
- 在不同 review iteration 中逐步形成理解。

如果换成人工小任务，这些机制很可能根本不会发生。

#### 数据规模意味着什么？

- 10名经验丰富的审查者；
- 25次真实审查；
- 14小时42分钟录制材料；
- PR 从2行修改到34,520行修改；
- 15次开源项目审查，10次闭源项目审查；
- 使用 GitHub、GitLab、Gerrit 和 Phabricator；
- 最终形成846个 codes 和3,792个引用片段。

这个规模足以支撑深入的质性机制描述，但不适合估计某种策略的平均效果。

### CRCM：理解并不是审查前的准备，而是审查本身

传统 Letovsky 模型可以简化为：

```text
知识基础 + 信息来源
        ↓
代码理解
        ↓
代码的 mental model
```

作者认为，这还不足以描述代码审查。审查者不仅理解代码，还需要：

1. 决定此次审查的范围；
2. 选择具体审查策略；
3. 用理解评价修改；
4. 生成评论或者提出替代方案；
5. 通过多轮互动继续更新理解。

CRCM 因而形成一个循环：

```text
已有知识 + PR及外围信息
            ↓
选择审查范围和策略
            ↓
构建实际PR的mental model
            ↓
与expected / ideal model比较
            ↓
发现差异、提出评论、测试或询问作者
            ↓
获得新信息
            ↓
继续更新mental model与长期知识
```

这里最值得注意的是：**理解和评价不是两个完全分离的阶段。**

审查者在理解代码的同时，会不断拿它与预期实现比较；发现不一致又会触发新的导航、测试或提问。

### RQ1：审查者真的会完整理解整个 PR 吗？

作者观察到四种审查范围：

| 类型           | 实际含义                                     |
| -------------- | -------------------------------------------- |
| Full review    | 审查者认为自己完整理解了修改                 |
| Focused review | 只审查某些质量维度或专业领域                 |
| Partial review | 只处理修改中的部分区域                       |
| Shallow review | 主要依赖测试、CI或其他审查者，只形成浅层理解 |

#### 为什么会主动缩小范围？

主要原因不是“审查者懒”，而是一次完整理解可能并不经济，甚至不可能：

- PR 太大，无法一次全部放入工作记忆；
- 审查是多轮过程，本轮问题可以留到下一轮确认；
- 其他审查者在特定模块上更有经验；
- 当前只需要判断高层设计是否合理；
- CI和测试已经覆盖部分低风险问题；
- 继续投入时间带来的边际价值已经很低。

一位参与者对大型 PR 的解释非常直接：它“不可能全部装进脑子里”。

#### 这个发现真正改变了什么？

它挑战了一个隐含假设：

> 好的审查者应该在一次 review session 中完整理解全部修改。

论文观察到的现实更接近：

> 整个审查团队通过多轮、多人互动逐渐形成足够的集体理解。

但必须区分事实与解释：

- **论文观察到的事实**：专家确实会主动限定范围，并把部分理解留给后续迭代或其他审查者。
- **作者的合理解释**：这是应对复杂度的有效策略。
- **论文没有验证**：缩小范围是否保持、提高或降低了最终缺陷发现率。

因此，它提出了一个机制模型，却没有证明 shallow 或 partial review 在什么条件下是安全的。

### RQ2：专家不是“读代码”，而是在组合一套策略

作者发现，大多数审查首先经历上下文构建，然后进入代码检查，最后形成决策：

```text
Context Building
        ↓
Code Inspection
  ├─ Code Reading
  ├─ Testing
  └─ Discussion Management
        ↓
Decision
```

25次审查中有23次以某种 context-building 活动开始。

#### 第一步：先建立上下文，而不是立刻看 diff

审查者通常先查看：

- PR 标题和描述；
- 关联 issue；
- commit 信息；
- CI/CD 状态；
- 已有审查讨论；
- 修改规模和文件分布。

这一步的输出是一个初步 mental model：

- 为什么改？
- 改动范围多大？
- 哪一部分可能是核心？
- 这次审查需要重点检查什么？
- 作者提供的信息是否足够？

如果审查者此前参与过 issue 定义或方案讨论，这一步可能很短，甚至被跳过。不是因为上下文不重要，而是上下文已经存在于他的长期记忆中。

#### 第二步：代码越复杂，阅读方式越不线性

作者总结了三种主要阅读方式。

##### 线性阅读

适合规模较小、结构简单的修改。审查者基本按照工具呈现顺序阅读。

观察材料中，线性方式主要出现在不超过约6个文件、176行变更的较小 review 中。

这不是严格阈值，只是当前25次观察呈现出的分界，论文没有证明超过176行就应改变策略。

##### 难度优先

面对大修改时，审查者会先判断哪里最需要认知投入。

它包含两种相反但都合理的方式：

- **Easy-first**：先清理简单部分，再集中精力处理难点；
- **Core-first**：直接找到修改核心，再沿数据流或执行流理解外围代码。

为什么两种方式都存在？因为它们优化的目标不同：

- Easy-first 降低待处理任务数量，减少心理负担；
- Core-first 尽快建立决定整体理解的主干模型。

论文没有比较二者孰优孰劣。

##### Chunking

审查者把大 PR 拆成若干可管理单元，例如：

- commit；
- 文件；
- issue；
- 功能区域；
-测试；
- 之前留下的评论。

分块可以降低瞬时认知负担，但也会损失全局一致性。作者观察到，一些审查者在分块完成后，又线性通读整个修改，以补偿局部阅读造成的全局信息缺失。

这揭示了一种很重要的策略组合：

> Chunking 负责让任务可处理，最终的整体扫描负责恢复跨块一致性。

#### 第三步：测试和讨论也是理解活动

测试在这里不只是验证正确性，还用于建立 mental model：

- 运行修改后的系统；
- 检查函数实际输出；
- 手动体验 UI；
- 排查 CI 失败；
- 从测试用例推断作者意图。

类似地，阅读已有评论也不是额外的社交流程。评论可能解释设计选择、指出已经处理的区域，或者告诉审查者当前不需要重复投入。

但评论也可能产生 anchoring 或 priming。论文中的审查者自己也意识到已有意见可能影响判断，因此作者建议工具允许切换评论可见性。

### RQ3：审查判断来自“实际实现”与“脑中参照物”的比较

CRCM 中的 mental model 分为三个层次。

#### Specification：修改想完成什么

包括：

- 解决什么问题；
- 为什么需要修改；
- 哪些使用场景应被覆盖；
- PR 的边界是什么。

#### Implementation：代码实际上怎样实现

包括：

- 修改了哪些数据结构；
- 控制流和数据流如何变化；
- 输出行为是什么；
- 实现放在当前模块是否合理。

#### Annotation：目标和实现如何对应

Annotation 把“为什么改”和“哪段代码实现了它”连接起来。

良好的 issue、PR 描述、commit message、变量命名和测试，可以让这种映射更容易建立。如果这些线索缺失，审查者只能从实现反向猜测其目的。

#### 审查评论究竟从哪里来？

作者提出一个很有解释力的观点：审查者同时维护实际、预期和理想三个 mental models。

```text
实际模型：作者现在写了什么
预期模型：根据需求和此前约定，应该看到什么
理想模型：按照我的经验，最好怎样实现
```

审查反馈通常来自它们之间的 discrepancy：

- 实际模型偏离预期模型，可能意味着实现错误或需求遗漏；
- 实际模型偏离理想模型，可能产生改进建议；
- 实际模型符合预期但不是最理想，审查者可能仍选择接受。

这很好地解释了为什么代码审查不只是 bug detection。审查者还在进行需求一致性判断、维护性判断和工程折中。

### Figure 3 和 Figure 4 真正说明了什么？

#### Figure 3：CRCM 不是线性流水线

图中的箭头包括 supply、guide、construct、compare、evaluate 和 update。它想表达的是：

- 信息来源为理解提供材料；
- 知识基础指导审查策略；
- 理解过程构建 mental model；
- mental model 与预期及理想模型比较；
- 比较结果产生评价和反馈；
- 新理解再更新长期知识。

这张图证明不了这些关系的因果强度。它是对质性观察的理论整合，不是用结构方程或实验估计得到的 causal graph。

#### Figure 4：真实策略是模块组合，不是一条固定路线

Figure 4(b) 把25次审查按规模排列，并用颜色展示每次 review 中出现的活动。

最值得看的不是某个参与者具体走了哪条路径，而是三个总体模式：

1. 大多数 review 先建立上下文；
2. 小型修改更多采用线性阅读；
3. 规模和复杂度上升后，分块及难度优先策略开始增加，而且会与测试、讨论和线性扫描交错出现。

一种可能解释是复杂度迫使审查者改变策略。但论文没有操纵复杂度，也没有排除项目、参与者经验、修改类型和工具等替代解释。

所以更准确的表述是：

> 在这组观察材料中，复杂 review 与更多非线性策略共同出现。

不能写成：

> 复杂度导致审查者采用 chunking。

### 这项研究的证据边界

#### 作者做得好的地方

- 观察真实工作队列，而不是人工构造的小任务；
- 同时使用行为观察、思维出声和事后访谈；
- 涵盖开源与闭源项目、四种审查平台；
- 使用理论驱动编码，同时保留自底向上发现新策略的空间；
- 提供转录、编码框架和其他研究材料；
- 第二作者检查部分转录和编码，研究团队反复讨论解释。

#### 需要警惕的地方

##### 1. 样本刻意偏向专家

参与者主要是被他人推荐的优秀审查者，很多具有领导或 mentoring 职责。

这有助于发现成熟策略，但不能说明：

- 普通开发者同样使用这些策略；
- 初学者能够正确使用这些策略；
- 专家采用的每个策略都值得直接推广。

##### 2. 观察到策略，不等于证明策略有效

论文没有测量统一的缺陷发现率，也没有把参与者随机分配到不同策略。

因此不能从该研究推出：

- context building 提高多少准确率；
- core-first 优于 easy-first；
- chunking 能减少多少漏报；
- expected mental model 会改善还是损害审查质量。

这些都需要后续实验。

##### 3. 理论框架可能影响看见了什么

作者先采用 Letovsky、Piaget 和 self-discrepancy theory 建立编码框架，再解释材料。这有助于形成系统模型，也可能让分析更容易发现符合理论的现象。

研究主要由第一作者完成，第二作者只验证部分转录和编码。论文没有提供传统意义上的独立双人全量编码一致性。

##### 4. 思维出声可能改变审查行为

参与者知道自己被观察，还要把思考过程说出来。这可能让审查更加仔细或结构化。至少一名参与者明确感觉自己因观察而更认真。

##### 5. “复杂度”没有被标准化测量

论文根据真实 PR 的规模和参与者描述讨论复杂性，但没有统一的 complexity treatment 或量表。因此 Figure 4 展示的是自然情境中的模式，而不是复杂度的因果效应。

### 作者证明了什么？

1. 在这25次专家真实审查中，理解代码变化是形成评论和决策的核心活动。
2. 专家会主动限定一次审查的理解范围，而不是总追求单次完整理解。
3. 审查策略通常从上下文构建开始，再机会式组合阅读、测试和讨论。
4. 大型或困难 review 中出现了分块和难度优先等非线性策略。
5. 实际、预期和理想 mental models 能解释审查者如何评价代码并形成反馈。

### 作者没有证明什么？

1. 没有证明某一种策略能提高缺陷发现率或审查质量。
2. 没有证明复杂度因果性地导致 chunking 或 shallow review。
3. 没有证明专家策略适合初学者。
4. 没有证明 CRCM 是完整或唯一正确的代码审查认知模型。
5. 没有证明使用 LLM 自动补充上下文一定能帮助审查者；这只是未来工具方向。

### 对 Causality for Code Review 的启发

这篇论文最适合用来建立**机制假设和变量体系**，而不是直接提供因果效应。

#### 可以转化成哪些 Treatment？

- 是否提供结构化 PR 上下文；
- 是否展示 issue、测试、历史评论或 call graph；
- 是否允许隐藏已有审查评论；
- 是否把大型修改自动分块；
- 是否标识核心修改区域；
- 是否提供预期行为或 acceptance criteria。

#### 可以测量哪些中介变量？

- context-building 时间；
- 首次形成正确 change rationale 的时间；
- 代码导航路径；
- mental model 准确度；
- 实际实现与需求目标的映射质量；
- 审查者主观认知负荷；
- 是否进入 shallow、focused 或 full review。

#### 可能的重要 Moderator

- PR 复杂度；
- 审查者对项目的熟悉度；
- review iteration；
- 作者与审查者是否提前对齐；
- 是否存在其他专家审查者；
- 缺陷是否跨文件；
- call graph 深度和跨模块依赖强度。

#### 一个可直接实施的实验

可以做一个析因实验：

```text
结构化上下文：无 / PR描述 / PR描述+Call Graph
×
已有评论：隐藏 / 可见
×
任务复杂度：低 / 高
```

主要 Outcome：

- 缺陷发现率；
- 错误评论率；
- 审查时间；
- mental model 准确度；
- 对错误 AI 建议的 over-compliance。

中介假设可以是：

> Repository context 首先改善 mental model，再提高审查表现。

这比直接比较“有上下文模型”和“无上下文模型”的最终准确率更接近真正的机制研究。

### 真正应该记住什么

- 代码审查不是读完 diff 后再判断，而是在理解过程中持续评价。
- 专家会控制理解范围；“没有完整阅读”有时是策略，有时也可能是风险。
- Repository context 的价值可能不只是提供更多代码，而是帮助建立 specification—implementation 映射。
- 分块可以降低认知负担，也可能破坏全局一致性；两者需要同时测量。
- CRCM 是一个机制模型和变量来源，不是已经得到因果验证的理论。
- 对你的研究最重要的问题是：**某种上下文干预是否通过改善 mental model，最终改变代码审查质量？**
