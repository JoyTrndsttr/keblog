## 一句话价值

归纳代码审查中的七类解释并验证按类型生成的可行性，但尚未检验解释对实际结果的效果。

### 论文地图

这篇论文真正研究的是：

> 审查者在要求作者修改代码时，会不会解释“为什么要改”？如果解释，会采用什么形式？LLM 能否按需补充不同类型的解释？

作者分析了五个 Google 开源项目中 793 条被自动筛选为“有用”的首轮行内审查评论，从中归纳出七种解释类型。结果显示，42% 的评论只告诉作者怎么改，没有说明原因；GPT-3.5 则能在一个小规模人工评价中较准确地将评论改写为指定解释类型。

不过，这篇论文证明的是**解释的分布和生成可行性**，不是解释产生的实际效果。它并没有证明增加解释会减少沟通轮次、提高采纳率或者改善最终代码。

### 核心矛盾：审查意见经常只有答案，没有推理过程

过去的自动代码审查研究主要关心：

- 能不能找到问题；
- 能不能生成修改建议；
- 评论是否与人类评论相似；
- 作者是否根据评论修改代码。

但在真实沟通中，“改什么”和“为什么改”是两种不同的信息。

例如：

> 改成 `PowerButton`。

这是建议，告诉作者应该采取什么动作。

> 改成 `PowerButton`，因为代码库中并不存在 `power_button` 这个符号。

后半句才是解释。它让作者知道建议来自一个可验证的技术原因，而不只是审查者的个人偏好。

作者认为，只给建议可能导致作者追问、误解或者机械服从。于是论文尝试先建立一套解释分类，再观察 LLM 是否能够生成相应类型。

这里存在一个尚未验证的前提：

> 评论中明确写出解释，会比只提供建议带来更好的审查结果。

这个前提很合理，论文中的案例也具有说服力，但本研究没有直接检验它。

### 理解论文需要抓住的四个概念

#### 建议与解释

- **建议**回答“代码应该怎样修改”。
- **解释**回答“为什么当前代码需要修改”。

一条评论可以只有建议、只有解释、二者兼有，也可能二者都没有。

#### 首轮行内评论

作者只分析每个评论线程中的第一条 reviewer inline comment。

这样做能保证样本单位比较一致，也能观察审查者一开始提供了多少信息。但它忽略了后续讨论：有些审查者可能有意先提出简短建议，在作者追问后才解释。

#### 开放式卡片分类

研究者没有预先规定解释类型，而是阅读样本，把相似解释放在一起，最后为每一组命名。这适合探索新现象，但分类结果会受到研究者判断影响。

#### 解释类型与解释效果

论文主要测量某段文字是否符合指定解释类型，以及内容是否正确、清楚、信息充分。

这与“作者看完后能否正确修改代码”不是同一个 Outcome。

### 数据是怎样产生的？

论文的研究流程可以概括为：

```text
抓取八个 Google Gerrit 项目的代码审查
                    ↓
使用既有决策树筛选“有用评论”
                    ↓
只保留首轮行内评论，并处理项目间样本失衡
                    ↓
得到 793 条评论，用于判断建议与解释是否出现
                    ↓
从包含解释的评论中分层抽样 298 条
                    ↓
开放式卡片分类，归纳七种解释
                    ↓
按审查者历史审查次数区分 novice / experienced
                    ↓
比较两个群体的解释频率和类型
                    ↓
用 GPT-3.5 把原始评论改写成指定类型的解释
                    ↓
人工评价类型、正确性、清晰度和信息量
```

### 第一步：筛选数据时已经引入了一个重要选择条件

作者最初抓取了八个 Google 开源项目在 Gerrit 上的 4,617 次审查、9,169 个 revision，覆盖 Android、Bazel、Chromium、Dart、Flutter、Fuchsia、Gerrit 和 Go。

随后使用基于 Bosu 等人研究改造的决策树筛选“有用”评论。模型依赖的信息包括：

- 评论是否 resolved；
- 评论之后是否发生代码修改；
- 评论情感；
- 评论数量和迭代轮次等。

Bazel、Flutter 和 Fuchsia 在筛选后没有留下满足条件的评论，因此最终只保留五个项目。

Android 的评论数量明显更多，作者从 789 条候选评论中抽取了 259 条；其他项目保留全部符合条件的行内评论，最终形成 793 条样本。

#### 为什么这个选择很重要？

论文研究的是：

> 在已经被模型判定为“有用”的首轮行内评论中，解释如何出现。

它并没有研究所有代码审查评论。

如果解释本身会提高评论被解决、被采纳或者触发修改的概率，那么“先筛选有用评论”相当于先根据可能受到 Treatment 影响的变量选择样本。这会改变解释在总体评论中的真实分布。

更直观地说：

```text
是否提供解释 ──→ 评论是否被采纳/解决
                         ↓
                 是否进入研究样本
```

当研究只观察被采纳或解决的评论时，解释与其他因素之间的关系可能受到选择偏差影响。

### RQ1：审查者多大程度上会主动解释？

#### 作者真正想问什么？

作者要区分四种首轮评论：

1. 只有建议；
2. 只有解释；
3. 建议和解释都有；
4. 二者都没有。

#### 实验单位和数据

- 实验单位：每个行内讨论线程的第一条审查者评论；
- 样本：793 条；
- 研究者同时阅读目标代码行和完整讨论线程；
- 两位作者完成标注，分歧通过讨论解决。

#### 结果

Table 1 和 Figure 6 给出的总体分布是：

| 类型             | 数量 | 比例 |
| ---------------- | ---: | ---: |
| 既无解释也无建议 |   84 |  10% |
| 只有解释         |   81 |  10% |
| 只有建议         |  331 |  42% |
| 解释＋建议       |  297 |  38% |

其中有 378 条评论包含解释，297 条同时包含建议。也就是说：

> 当审查者确实解释时，**79%** 的解释与具体建议一起出现。

跨项目趋势也比较稳定：仅含建议的比例在 Dart 的 36% 到 Gerrit 的 45% 之间。

#### 这个结果能支持什么？

它能支持：

- 在这批经过筛选的首轮行内评论中，只提供建议非常常见；
- 解释通常不是独立出现，而是作为修改建议的理由；
- 这种分布没有完全由单个项目驱动。

它不能支持：

- 42% 的所有真实代码审查都缺少解释；
- 缺少解释一定造成额外讨论；
- 每条建议都应该附带显式解释。

有些项目惯例可能是团队共同知识，一句简短建议已经足够。是否需要解释，可能由作者经验、问题复杂度和双方共享知识共同决定。

> **RQ1 真正告诉我们：在已经被判为有用的首轮行内评论中，“只告诉作者怎么改”与“同时解释为什么”几乎同样常见。**

### RQ2：作者归纳出的七类解释是什么？

作者对 298 条包含解释的评论进行分层抽样和开放式卡片分类，得到七种解释。

#### 1. 引用规则或原则

审查者援引：

- 项目规范；
- 语言标准；
- 编码约定；
- 团队规则。

例如，“Chromium style guide 规定不应处理 DCHECK 失败”。

这种解释的核心不是描述眼前错误，而是说明修改要求来自一个可以复用的规则。

#### 2. 提供相似示例

审查者指出代码库中已有的实现，让作者与其保持一致。

这是仓库级上下文最直接的体现：解释依赖的不只是当前 diff，还需要找到真正具有可比性的代码。

#### 3. 提供测试条件或失败场景

审查者构造一个“如果……会怎样”的具体情境，例如：

- 某个值为空时测试会崩溃；
- 特定输入会触发错误；
- 某个分支没有被覆盖。

这种解释接近局部反事实推理：改变输入条件，观察当前实现会产生什么结果。

#### 4. 讨论未来影响

它不一定描述当前就会发生的失败，而是说明今天的设计可能怎样限制未来修改。

这要求审查者理解演化趋势、扩展路径或潜在功能，因此比指出当前错误需要更多仓库和领域知识。

#### 5. 表达个人偏好或感受

例如某个名称“让我困惑”，或某种写法不易理解。

这类解释未必对应客观缺陷，但能表达代码对阅读者造成的认知影响。

#### 6. 指出当前代码的问题或原因

这是最常见类型，占包含解释样本的 **40%**。

审查者直接说明：

- 当前代码哪里不正确；
- 某个符号不存在；
- 某段逻辑为何多余；
- 问题的可能根因是什么。

#### 7. 说明采纳建议后的收益

占比 **25%**，是第二常见类型。

它强调建议带来的好处，例如：

- 更清晰；
- 更快；
- 更容易维护；
- 更容易保持同步。

#### 最值得看的分布

Figure 8 显示：

- 指出当前问题：40%；
- 描述建议收益：25%；
- 引用规则或原则：10%；
- 未来影响：只有3%。

这说明大多数解释集中在当前代码和当前建议，较少涉及未来演化。

但这不代表“未来影响”价值较低。它也可能意味着：

- 这种解释需要更深的系统知识；
- 未来影响更难从单个代码片段中可靠判断；
- 复杂设计讨论更可能发生在非行内评论中；
- 数据筛选方式不利于捕获这类解释。

> **RQ2 真正告诉我们：人类审查解释存在多个可操作的功能类别，不能只把解释视为一段没有内部结构的自然语言。**

### RQ3：经验会让审查者更爱解释吗？

#### 经验是怎样定义的？

作者以历史上完成的审查数量衡量经验，将排名前 27% 的审查者设为 experienced：

- 67 名 experienced reviewer；
- 185 名 novice reviewer。

这里的“novice”只是相对于当前样本的审查次数较少，并不等于编程新手。

#### 频率上：没有差异

Figure 9 显示，经验组与新手组只有解释的比例都约为 **10.2%**；其他类别差异也很小。

卡方检验结果为 \(p=0.9\)，没有发现解释出现频率与经验等级之间的统计关联。

换句话说：

> 审查经验更多的人并不一定更频繁地解释。

#### 类型上：存在差异

Figure 10 显示：

- 新手比经验组更集中使用“指出当前问题”，差约 14 个百分点；
- 经验组使用“解释建议收益”多约6个百分点；
- 经验组使用规则、相似示例、测试场景和未来影响的分布更广；
- 类型分布的卡方检验为 \(p=0.02\)。

作者由此认为经验丰富的审查者具有更广泛的解释能力。

#### 证据能支持多强的结论？

可以说：

- 按历史审查次数分组后，两组使用的解释类型分布不同；
- 经验组在样本中表现出更高的类型多样性。

不能说：

- 审查经验导致解释能力提升；
- 增加审查次数会使一个人学会讨论未来影响；
- 解释类型多样一定代表评论质量更高。

潜在混杂包括：

- 经验组负责的模块和任务可能更复杂；
- 经验组可能拥有更高代码所有权；
- 项目、编程语言和缺陷类型分布可能不同；
- 只有更复杂的问题才需要规则、场景或未来影响解释。

论文只比较了聚合分布，没有在相同任务和相同问题类型下匹配新手与资深审查者。

> **RQ3 真正告诉我们：经验主要与“怎样解释”相关，而不是与“是否解释”相关；但这种关系仍是观察性关联。**

### RQ4：LLM 真能生成不同类型的解释吗？

### 第一阶段：四种 Prompt 的比较

论文使用 2023 年 7 月版本的 ChatGPT，即 GPT-3.5。基础输入包括：

- 原始代码审查评论；
- 代码片段；
- 目标解释类别。

在此基础上比较：

| Prompt      | 增加的信息                  |
| ----------- | --------------------------- |
| Base        | 不增加                      |
| Base+Commit | commit message              |
| Base+Line   | 被评论的具体代码行          |
| All         | commit message 与目标代码行 |

每种 Prompt 生成30条评论，总计120条。评价者判断：

- 是否符合要求的解释类型；
- 解释内容是否正确。

Table 3 中：

- Base+Line：27条类型正确、27条内容正确，24条二者同时正确；
- All：24条类型正确、28条内容正确，23条二者同时正确；
- Base：23条类型正确、24条内容正确，19条二者同时正确。

#### 为什么 Base+Line 比 All 更好？

作者认为，commit message 不一定与某条行内评论直接相关。把不相关的提交级信息加入 Prompt，可能分散模型注意力。

这是一个很有价值的 context engineering 结果：

> 更多上下文并不自动意味着更好的解释；上下文与目标评论的因果、语义距离比上下文总量更重要。

但初始评价每个 Prompt 只有30条输出，差距也很小。论文没有报告配对显著性检验或跨随机种子重复，因此不能把它解释成稳定的 Prompt 排名。

### 第二阶段：扩大 Base+Line 的人工评价

作者选用 Base+Line，为六类解释各生成15条，共90条。个人偏好类被排除，因为作者认为 ChatGPT 不适合生成主观观点。

五位评价者平均具有6.4年编程经验。对于布尔判断，至少四人同意才记为正确。

结果是：

- **88/90** 符合指定解释类型；
- **89/90** 被判断为解释内容正确；
- 信息量平均 **6.13/7**；
- 清晰度平均 **6.07/7**。

这些数字看上去很高，但实验任务比真实自动审查容易：

- 输入中已经包含人类原始评论；
- 模型已被告诉目标解释类型；
- 目标代码行已明确提供；
- 任务是改写和补充解释，不是自主发现缺陷；
- 评价样本只有90条；
- 没有与人类审查者或其他模型做盲测比较。

因此，更准确的结论是：

> 当已知问题位置、原始评论和目标解释形式时，GPT-3.5 通常能把评论改写成符合该形式的解释。

这并不等于模型能自主生成正确的代码审查意见。

#### 一个重要失败案例

模型被要求提供“相似示例”时，有时会生成一个听起来合理、实际却不是相似实现的假想例子。

这说明七类解释对证据需求不同：

- “说明收益”可以依靠一般性语言推理；
- “指出当前问题”可以依靠局部代码；
- “引用项目规则”需要真实规范；
- “提供相似示例”需要可靠仓库检索；
- “讨论未来影响”需要架构和演化知识。

因此，不能给七类解释完全相同的生成权限和验证流程。

> **RQ4 真正告诉我们：LLM 具备解释形式控制能力，但涉及仓库事实的解释仍需要检索和独立验证。**

### 这篇论文最重要的证据问题

#### 解释是否有效，没有被实验

论文测量了：

- 解释是否存在；
- 解释属于哪一类；
- LLM 是否按类别生成；
- 生成文本是否清楚、正确和充分。

它没有测量：

- 作者是否更容易理解；
- 是否减少追问轮次；
- 是否加快合并；
- 是否提高正确采纳率；
- 是否改善最终代码；
- 是否提高知识保留。

论文自己在讨论中也承认，它停留在 reviewer perspective，并未判断解释何时真正有效。

#### Treatment 可能与信息量捆绑

“建议＋解释”必然比“只有建议”包含更多文本和信息。如果直接比较两组，观察到的效果可能来自：

- 更长的评论；
- 更多技术细节；
- 更礼貌的表达；
- 更明确的问题定位；
- 更严重的问题；
- 更有经验的审查者。

因此，后续因果实验需要保持技术内容、长度和语气尽可能一致，只改变解释机制。

#### 自动筛选会产生选择偏差

只研究“有用评论”，可能排除：

- 正确但作者未采纳的解释；
- 错误但表达充分的解释；
- 没有触发代码修改、却促进知识共享的解释；
- 因权限关系被采纳、但技术上不正确的解释。

特别是当“有用”模型使用后续代码修改和 resolved 状态时，样本进入条件本身已经和研究 Outcome 接近。

#### 人工分类没有报告一致性

三位作者通过讨论达成一致，适合探索性分类，但论文没有保存独立判断并报告 inter-rater agreement。

因此，七类分类可以作为有用的初始 taxonomy，却还不能视为已经稳定验证的测量量表。

#### 聚合比较可能掩盖项目差异

经验组与新手组的解释分布被跨项目合并。如果 experienced reviewer 更多集中在某些项目，而项目规范又影响解释风格，聚合差异可能部分来自项目构成。

更稳妥的方法是：

- 在项目内比较；
- 控制问题类别和模块；
- 使用 reviewer、project 和 thread 层级的混合效应模型；
- 或进行匹配设计。

### 对 Causality for Code Review 的直接启发

### Treatment 不应只是“有解释/没解释”

七类解释提供了一套更细的干预空间：

```text
T0：只有修改建议
T1：建议 + 项目规则
T2：建议 + 仓库中的相似实例
T3：建议 + 可执行失败场景
T4：建议 + 未来影响
T5：建议 + 当前问题根因
T6：建议 + 采纳后的收益
```

这样可以估计不同解释机制的异质效应，而不是把所有解释合并成一个二元变量。

### 可以设计一个配对随机实验

对每个真实代码问题，先由专家写出一个正确建议，然后生成不同解释版本。对同一问题的各个版本保持：

- 修改建议相同；
- 问题位置相同；
- 评论长度尽量匹配；
- 语气和礼貌程度相同；
- 只改变解释类型。

再将版本随机分配给参与者。

Outcome 可以包括：

1. 是否正确判断评论；
2. 是否采纳；
3. 最终补丁是否正确；
4. 处理时间；
5. 作者能否复述问题原因；
6. 对审查意见的信任；
7. 一周后的知识保持。

这种设计比从历史评论中比较“有解释”和“没解释”更接近因果识别。

### 还需要研究负面效应

解释未必总是有益。内容丰富、语气自信的错误解释可能增加自动化偏见，使开发者更容易接受错误建议。

因此可以引入第二个 Treatment：

```text
解释正确性：正确 / 部分正确 / 错误
        ×
解释形式：无解释 / 根因 / 规则 / 相似案例
```

这能回答一个比“解释是否有用”更重要的问题：

> 哪类解释既能提高正确建议的采纳，又不会提高错误建议的过度服从？

### Repository Context 应按解释类型供给

不同解释需要的上下文不同：

| 解释类型 | 最关键的上下文                      |
| -------- | ----------------------------------- |
| 当前问题 | diff、局部数据流、测试              |
| 项目规则 | CONTRIBUTING、style guide、历史规范 |
| 相似示例 | 仓库检索、调用图、语义相似实现      |
| 测试场景 | 输入约束、控制流、测试文件          |
| 未来影响 | 调用者、依赖图、架构与演化历史      |
| 建议收益 | 性能、可读性或维护性证据            |

这意味着 repository context 不应被当成一个笼统的二元 Treatment。更好的研究问题是：

> 与解释所需证据匹配的上下文，是否比固定的全仓库上下文更能提高解释正确性？

### 真正的 Takeaway

#### 作者证明了什么？

- 在793条经筛选的有用首轮行内评论中，42% 只有建议，没有显式解释。
- 当解释出现时，79% 同时附带具体建议。
- 代码审查解释至少可以归纳为七种具有不同信息需求的类型。
- 经验组和新手组提供解释的频率没有显著差异，但使用的解释类型分布不同。
- 给定原始评论、代码片段、目标行和目标类别时，GPT-3.5 在90个样本中通常能够生成符合指定类型的解释。

#### 作者没有证明什么？

- 没有证明解释会减少沟通轮次或缩短审查时间。
- 没有证明解释会提高建议采纳率或最终代码质量。
- 没有证明经验导致解释能力更加多样。
- 没有证明七种解释类型具有不同的实际效果。
- 没有证明 GPT-3.5 能自主发现问题并生成有事实依据的解释。
- 没有证明更多上下文普遍有益；只发现目标代码行在这组小样本中比加入 commit message 更合适。

#### 你真正应该记住什么？

- **“发现问题”和“解释问题”是两种不同能力。**
- 解释不是一种统一文本，而是规则、实例、失败场景、未来影响、根因和收益等不同机制。
- 不同解释类型需要不同的仓库证据，尤其是规则、相似实现和未来影响不能只靠语言模型补全。
- 这篇论文最适合作为 Treatment taxonomy，而不是“解释有效”的效果证据。
- 后续研究应随机操纵解释类型，同时固定建议、语气、长度和技术内容。
- 最有研究价值的 Outcome 不是文字是否清楚，而是开发者能否作出正确决定。

> **如果一周后只记得这篇论文的一件事：LLM 很容易把审查意见“解释得像真的”，但真正的研究问题是——这种解释是否有可靠仓库证据，以及它是否让开发者作出了更正确的决定。**
