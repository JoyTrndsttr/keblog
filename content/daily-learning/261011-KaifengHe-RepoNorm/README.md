## 1. 先建立整篇论文的地图

Coding Agent 交出的补丁即使通过所有功能测试，也可能不符合仓库的贡献要求：该补的测试没补、该写的 changelog 没写、公开接口的兼容约束被破坏，或者新路径忘记复用旧路径的容错行为。RepoNorm 研究的不是“怎样再给 Agent 塞更多仓库文本”，而是怎样把散落在文档、配置、工作流、源码和 Git 历史里的信息，整理成带有**作用域、触发条件、例外和证据**的仓库规范，再让现有 Coding Agent 按需查阅。

在 6 个 Python 仓库、14 个版本、121 个任务上，RepoNorm 相对不给额外指导的 Raw 条件，将总体规范遵从率相对提高 7.42%—10.77%，将贡献规范遵从率相对提高 31.64%—45.44%。不过，功能成功率虽然观察到 5.79—9.09 个百分点的提高，配对检验在多重校正后均未达到显著阈值。它证明得最扎实的是“结构化、经过适用性核查的规范包能帮助 Agent 遵守仓库要求”，不是“RepoNorm 已经可靠提升修复成功率”。

理解全文需要先区分五个概念：

1. **仓库规范（repository norm）**：指导代码如何实现、测试、记录和维护的要求、建议或已被源码支持的惯例。规范不只是句子，还要说明约束什么文件或实体、何时触发、有什么例外。
2. **显式规范**：直接写在贡献指南、配置或工作流中的规则，例如“新增测试使用 pytest”“代码变更必须更新 changelog”。
3. **隐式规范**：没有完整写成自然语言，但由多个源码实现共同体现的行为契约或惯例，例如多个“从序列中选一个元素”的过滤器在空输入时都返回环境配置的 undefined 值。
4. **适用性（applicability）**：某条规范是否真的约束当前改动。语义相关或位于邻近文件，并不等于适用；作用域、激活条件和例外共同决定是否适用。
5. **规范遵从率（Norm Compliance Rate，NCR）**：先在每个任务内计算通过的适用规范占全部已判定适用规范的比例，再对任务做宏平均。它测的是规范遵从，不等同于功能测试通过率。

### 顶层证据链

```text
现实问题：功能正确的补丁仍可能违反仓库贡献与行为规范
    ↓
研究对象：仓库中可复用、可检查适用性的规范
    ↓
操作化：显式提取 + 隐式推断 + 证据/反例/历史核查 + 规范包
    ↓
实验：Raw / CodeWiki / RepoNorm，3 个模型 × 121 个任务
    ↓
证据：四类 NCR、功能与联合成功、规范精度/覆盖率、成本
    ↓
结论：RepoNorm 稳定改善规范遵从，功能改进证据仍不足，精度/覆盖/成本存在权衡
```

这条链最重要的教学点是：论文同时测了**规范质量、Agent 是否遵守规范、补丁是否功能正确**。这三个构念不能互相替代。规范本身可能不准确；规范正确，Agent 也可能不查或不用；Agent 遵守规范，补丁也仍可能功能错误。

## 2. Research gap：普通仓库上下文为什么还不够？

### 2.1 文档说明“仓库是什么”，未必说明“贡献者必须做什么”

DeepWiki、CodeWiki 一类工具能解释模块结构、关键实现和开发建议，检索系统也能返回与任务相关的文件。但 Coding Agent 仍要自己判断：哪些内容只是描述，哪些是必须履行的义务；规则约束整个仓库还是某个目录；什么条件触发它；是否有例外。

例如，贡献指南写着“代码变更需要测试、相关文档和 changelog”。通用文档系统可能把这句话与大量背景知识并列展示；RepoNorm 则把它表示为一条有规范强度、作用域、触发条件和证据引用的记录。差别不只是信息量，而是把描述性文本转换为可行动的规范。

论文引用已有 AGENTS.md 研究指出：Agent 通常会遵守指令文件，但不同设置下任务解决率并没有一致提高。这个结果说明至少要拆开两个问题：指导内容是否准确且适用，Agent 是否遵守；遵守后是否真的改善任务结果。RepoNorm 正是沿着这条拆分路线设计评价。

### 2.2 位置相关不等于适用

规则写在哪，不决定它约束哪里。一段 helper 的异常处理可能约束所有新调用者；同一个文件里的另一种函数可能因为语义不同而构成反例。仅凭文件邻近、同名符号或调用关系把信息交给 Agent，仍然可能产生“看起来相关、实际不适用”的 guidance。

因此作者把 norm 表示成：

\[
n=(r,s,c,e),
\]

其中 \(r\) 是规则本身，\(s\) 是受约束的仓库相对路径或 glob，\(c\) 是激活条件，\(e\) 是例外。证据来源单独保存，因为证据所在位置和规则作用范围可能不同。这套表示本质上要求系统回答四个问题：做什么、约束谁、何时做、什么时候不用做。

### 2.3 两个动机案例说明了什么？

Figure 1 给出两个真实 Agent 输出。它不是方法架构图，而是在固定“功能测试通过”后展示剩余缺口。

**Jinja 案例**：任务要求给 `groupby` 增加大小写敏感控制。Agent 修改实现、同步/异步测试和 docstring，171 个功能检查全部通过，也写了 `versionchanged`，但没有更新 `CHANGES.rst`。遗漏的是 contribution requirement，不是功能行为。

**Tiktoken 案例**：旧编码路径捕获 `UnicodeEncodeError`，用 UTF-16 `surrogatepass` 修复包含 surrogate 的输入后重试。Agent 新增分块编码路径时保留了非分块 fallback，18 个功能检查全部通过，却让新分块路径直接调用 Rust encoder，没有复用 surrogate recovery。这里遗漏的是由旧实现体现的隐式行为契约。

两例共同说明“tests pass”只覆盖已有测试表达的行为。Jinja 缺的是交付物，Tiktoken 缺的是未被测试充分覆盖的边界行为。作者没有用这两个案例证明所有功能测试都不足，而是用它们定义 RepoNorm 需要覆盖的两类规范来源。

## 3. RepoNorm 怎么跑：从仓库到可查阅规范包

Figure 2 的阅读顺序是左上到右上、再到右下和左下：候选发现 → 统一验证 → 打包交付 → Coding Agent 执行任务。任务在规范包生成以后才出现，因此同一版本的包可被多个任务和模型复用。

```text
Repository
 ├─ Docs / Configs / Workflows → 显式规范候选
 └─ Source Code → 语义观察 → 隐式规范候选
                   ↓
      当前证据 + 反例 + 必要时的 Git 历史
                   ↓
      accepted / review / rejected（最多一次统一修订）
                   ↓
      按适用路径组织的 Markdown 规范包
                   ↓
      现有 Coding Agent 自主检索、选择和应用
```

### 3.1 显式通道：不要把出现过的句子都当成规则

显式通道分三步。

**第一步，确定性发现来源。** 系统扫描仓库指令、文档、配置和工作流；模型可以建议额外路径，但宿主程序会验证路径，防止把不存在的文件送入提取。

**第二步，候选提取。** 模型读、解析并切分来源，输出规则、作用域、条件、例外和证据引用。例如“新增测试使用 pytest”可能被表示为：规则是 `use pytest`，作用域是 `tests/**`，条件是“新增测试”，无例外，证据来自贡献指南原句。

**第三步，本通道核查。** 系统先把引用落回原文或配置值，再由独立模型检查规则内容和适用性是否真的被证据支持。贡献指南说“new tests use pytest”，不能外推成“所有现有测试必须迁移到 pytest”；一个工作流中出现某工具，也不能自动升级成全仓必须遵守的义务。

这一通道的价值不是让 LLM 总结文档，而是要求每个候选保留可检查的 grounding，并且把“要求、建议、描述事实”分开。

### 3.2 隐式通道：从共同实现推断惯例，但主动找反例

Figure 4 是全文最关键的方法图。它从源码观察开始，经由假设与代码总体检查，最后做反例分析。作者用 Jinja 的空输入行为说明这一过程。

1. **源码观察**：解析抽象语法树（Abstract Syntax Tree，AST），索引文件、实体、调用和 import，并把函数、类等有界单元交给模型解释。`first` 捕获 `StopIteration`，`random` 捕获 `IndexError`，二者都返回环境配置的 undefined。
2. **形成假设**：模型先提出“把序列归约为单值的 filter 在空输入时返回 configured undefined”，并给出 witness、用于枚举候选总体的 query，以及判断成员是否支持规则的 predicate。
3. **枚举总体并检查**：宿主执行 query，先枚举匹配代码，再采用完整普查或确定性分层抽样。每个被检查成员标为 support、counterexample、ineligible 或 unknown。
4. **处理反例**：`first`、`last`、`random`、`min`、`max` 支持假设，但 `sum` 在空输入时返回初始值，`join` 返回空字符串。说明原假设过宽。
5. **局部修订一次**：把作用域收窄为“从输入中选择一个元素的 filter”。`sum` 和 `join` 从反例变成不适用成员，再重新检查。

作者用 \(P_n\) 表示 query 匹配总体，\(I_n\) 表示实际检查集合，\(U_n=P_n\setminus I_n\) 表示未检查成员，并显式保留覆盖情况。这个形式化很重要：如果没有完整普查，就不能把“未发现反例”说成“没有反例”。

隐式通道也没有把多个相似实现机械计为独立支持。`min` 和 `max` 共用 helper，因此它们的相同行为不能算两个独立起源。这个设计减少复制代码或共享实现导致的虚假证据强度。

### 3.3 统一验证：当前证据优先，Git 历史只回答具体问题

显式和隐式候选最终进入统一验证。Algorithm 1 最多执行两轮：初始候选一轮，允许的统一修订一轮。每个候选先组装当前证据；能由确定性检查解决的，不再调用模型；否则再判断是否需要历史证据和语义判断。

Git 历史不是无条件扩大上下文，而是由候选触发一个具体问题。例如：异步 filter 移到同步实现旁边时，空输入 fallback 是否被保留？系统围绕相关符号、路径和当前证据，在有界祖先范围内检索，并将历史变化分类为支持、矛盾、限定、退役/替换、背景或不确定。

这里有两个重要约束：

- 历史证据不能单独让候选通过或失败；它只能补充当前证据、解决材料性歧义。
- 若必要的历史问题没有解决，候选留在 `review`；“预算内没搜到”与“历史不可用/被截断”分开记录。

最终状态有三类：

- `accepted`：当前证据支持、必要检查完成、重要冲突和不确定性已解决；
- `rejected`：核心规则被候选绑定的当前反例否定；
- `review`：作用域或限定不匹配、解释仍有分歧、必要证据不完整。

统一验证还允许一次有界修订，但只能澄清措辞、作用域、条件或例外，不能偷换核心行为方向。修订后必须重新收集和核查证据，不能把父候选的结论直接继承给子候选。

### 3.4 打包与交付：按适用路径索引，不按证据路径索引

默认交付的是 `Accepted-Only View`。规范按强度分成 required、recommended 和 observed；有条件的条目仅在条件满足时行动，reference-only 条目可以查阅但不默认当行动指令。

规范包是静态 Markdown：`START.md` 指向按仓库路径组织的页面和全量目录。每条详细记录保留完整规则、作用域、条件、例外和证据。多作用域规范可以在多个路径页出现，但都链接到同一条记录。

最细的一点是：**索引位置采用适用路径，而不是证据来源路径。** 某个 helper 的源码可能提供证据，但真正被约束的是另一组调用者。如果按证据位置组织，Agent 在改调用者时可能永远看不到这条规范。

RepoNorm 不改造 Coding Agent 的 generation loop。Agent 自己决定读哪些页面、应用哪些规则、怎样编辑和运行测试。因此下游结果同时受规范包质量、检索选择和模型遵从能力影响。

## 4. 实验坐标系：到底比较了什么？

### 4.1 RepoNormBench

作者从 CooperBench 的 9 个 Python 仓库中选择 6 个较小仓库，共 14 个版本、121 个功能开发任务：Outlines 22、DSPy 23、Tiktoken 10、Click 27、Jinja 30、Dirty Equals 9。

他们修改了所有任务描述以降低歧义和移除部分实现提示，并强化功能测试：新增 501 个测试函数身份、删除 503 个、修改 78 个保留测试。整个过程中不查看 RepoNorm 生成的包，避免用 treatment 内容反向设计 benchmark。

规范参考集包含 160 条不同规范、1,024 个 task–norm 关联，分成 11 类：作者编写测试、文档、changelog、内联改动、风格、类型、兼容性、依赖、公开导出、公开接口和运行时行为。每个关联还标注任务描述是否明确写出该规范。

规范检查器用符合规范的参考实现和人为违反版本校准。隐藏测试、参考解和参考规范都不提供给规范获取系统或 Coding Agent。

### 4.2 三个条件与三个模型

每个模型都运行全部 121 个任务、三个条件：

| 条件 | Agent 获得什么 | 它代表的对照 |
|---|---|---|
| Raw | 任务和仓库，无额外生成指导 | 无指导基线 |
| CodeWiki | task-independent 仓库文档 | 通用仓库知识 |
| RepoNorm | Accepted-Only 规范包 | 带适用性和证据的规范指导 |

CodeWiki 和 RepoNorm 都由 DeepSeek V4.1 Flash 生成，关闭 thinking，不接触任务描述、参考解或隐藏测试。两者都可跨任务复用，Agent 自主选择是否阅读。

执行 harness 为 mini-swe-agent v2.1.0，模型为 DeepSeek V4 Flash（0423）、Qwen 3.5 Flash 和 Gemini 3.1 Flash-Lite。温度为 0，每任务最多 300 次模型调用；DeepSeek 用 high reasoning effort，Gemini 用 medium，Qwen thinking budget 为每次 8,192 tokens。每个 model–condition–task 只有一次记录运行，因此无法估计随机运行方差。

### 4.3 四个 NCR 指标

对任务 \(i\) 和分析范围 \(s\)，若通过和失败的适用规范数为 \(P_{i,s}\) 与 \(F_{i,s}\)，则：

\[
NCR_s=\frac{1}{|T_s|}\sum_{i\in T_s}\frac{P_{i,s}}{P_{i,s}+F_{i,s}}.
\]

只有在该范围内至少有一个已判定规范的任务进入平均；不适用和无法判定的规范不进入分母。每个任务权重相同，避免规范多的任务支配结果。

四个范围分别是：

- Overall：全部类别；
- Contribution：测试、文档、changelog、内联改动、风格、类型；
- Behavioral：运行时行为、公开导出、公开接口、兼容性、依赖；
- Prompt-omitted：任务描述未明确写出的规范。

统计上，作者对 RepoNorm–Raw 和 RepoNorm–CodeWiki 的任务内 NCR 差异做 100,000 次配对 BCa bootstrap，报告双侧 95% 区间。区间是逐比较的，没有做同时覆盖校正。

## 5. RQ1：RepoNorm 是否提高规范遵从？

### 5.1 先看 Table 2 的决定性比较

Table 2 固定模型与 121 个任务，改变指导条件和 NCR 范围。

**总体 NCR**：

- DeepSeek：Raw 65.58%，CodeWiki 65.66%，RepoNorm 72.64%；
- Qwen：63.93%、62.18%、68.67%；
- Gemini：57.61%、58.36%、63.38%。

RepoNorm 在三个模型上都是最高，相对 Raw 提高 7.42%—10.77%。CodeWiki 则是 +0.12%、−2.72%、+1.31%，说明一般文档并没有稳定转化为规范遵从。

**贡献 NCR** 的差距最大：DeepSeek 33.82%→49.19%，Qwen 32.15%→43.39%，Gemini 25.28%→33.28%，相对改善 31.64%—45.44%。RepoNorm 最有帮助的是那些不会自然被功能实现覆盖的交付义务。

**行为 NCR** 几乎到顶：Raw 已达 87.60%—96.46%。RepoNorm 在 DeepSeek 和 Qwen 上略低于 Raw，在 Gemini 上提高 3.05%；Figure 5 的六个行为比较区间全部跨 0。作者没有把这些小变化包装成稳定提升。

**Prompt-omitted NCR**：RepoNorm 达 49.68%—61.28%，相对 Raw 提高 11.34%—17.69%。这说明效果不只来自重复题面已经写出的要求。

Figure 5 将配对平均百分点差和 BCa 95% 区间画出来。总体、贡献和 prompt-omitted 的 18 个 RepoNorm 对基线比较全部在 0 右侧；行为范围的区间跨 0。读图时应先看区间是否越过虚线，再看点估计大小，不能只读 Table 2 的最高值。

### 5.2 任务描述改写会不会人为放大效果？

作者检查 670 个 prompt-omitted 关联：651 个在原始描述中本来就没有提醒，16 个关联的部分提醒在改写时被删除，3 个对应关系不清而排除。去掉所有 14 个确认删除提醒的任务后剩 107 个任务，RepoNorm 的总体 NCR 相对 Raw 仍高 7.85%—10.63%，相对 CodeWiki 高 8.77%—11.18%，配对区间仍全为正。

这项敏感性分析排除了一个直接替代解释：主要效果不是作者先从题面拿走要求，再由 RepoNorm 把它放回来。但它仍不能排除任务重写的其他影响。

### 5.3 规范检查器可靠吗？

参考集抽查 42 条规范、84 个 task–norm 关联：42 条均被判断有效，其中 41 条证据充分、1 条部分支持；84 个关联均被判断适用。

作者还构造 455 个补丁，共触发 1,351 次规范检查。1,010 个预期遵从的检查全部通过；341 个定向违反中检测到 302 个，漏掉的 39 个全部是“文档被修改但内容仍误导”的变体。原因是文档检查器主要把“有改动”当交付代理，无法充分理解内容正确性。

去掉同一批 59 个文档 task–norm 对后，RepoNorm 的总体和贡献 NCR 优势仍保持，区间全为正。因此主结论不依赖这类已知薄弱代理，但绝对 NCR 仍不能被理解为所有文档内容都正确。

**RQ1 Takeaway**：RepoNorm 对“是否遵守仓库要求”有稳定配对证据，优势集中在功能测试不直接覆盖的贡献工作；行为规范的额外收益小且不确定。

## 6. RQ2：功能正确性真的提高了吗？

Table 3 采用二元任务结局：Functional 表示所有功能测试通过；Joint 表示功能通过且所有适用规范检查均通过，且至少有一个适用规范。

观察值上，RepoNorm 相对 Raw 的功能成功率分别提高：

- DeepSeek：59.50%→68.60%，+9.09pp；
- Qwen：44.63%→52.07%，+7.44pp；
- Gemini：30.58%→36.36%，+5.79pp。

但作者使用双侧精确 McNemar 检验，并对 12 个功能/联合比较做 Holm 校正。最接近显著的是 DeepSeek 功能成功的原始 \(p=.052\)，校正后为 .575；所有比较校正后均未达到 .05。

联合成功率更能揭示“能运行”和“可接受贡献”的差别。RepoNorm 下 DeepSeek/Qwen/Gemini 只有 10、6、2 个任务联合成功，即 8.26%、4.96%、1.65%。Raw 分别是 4、3、1 个。即使给出规范包，绝大多数任务仍会在功能或至少一条规范上失败。

这里不能写“RepoNorm 提升了功能正确性”。更准确的结论是：三个模型都观察到比 Raw 更高的点估计，但样本内不一致对数不足以建立经多重校正的统计改善。可能存在真实正效应，也可能是单次运行波动或任务集特性。

CodeWiki 也出现功能点估计改善，却没有一致 NCR 改善。这支持作者的解释：一般仓库上下文可能有助于完成任务，而显式规范指导更有助于满足贡献义务，两类价值并不相同。但论文没有对二者组件做等 token 或组合消融，因此这仍是解释，不是已分离的机制因果结论。

**RQ2 Takeaway**：功能成功的方向值得后续扩大样本和重复运行验证；当前最强结论仍是规范遵从，而不是功能性能。

## 7. RQ3：获取到的规范有多准，又漏掉多少？

作者比较两个视图：

- **Accepted-Only**：统一验证自动接受的保守集合，共 1,990 条可读记录；
- **Accepted-after-Review**：用 GPT-5.6-Sol-high 对 review 候选做独立自动审查并接受部分条目，共 6,277 条。

精度分别从两个视图固定抽样 300 和 600 条，由 GPT-6-Astra 判断；只要一条记录的任一字段不准确，就算整体错误。覆盖率则用全部 160 条任务相关参考规范，分 full、partial 和 uncovered。

Table 4 展示了清晰的 precision–coverage 权衡：

| 视图 | 抽样精度 | 完整覆盖 | 完整或部分覆盖 |
|---|---:|---:|---:|
| Accepted-Only | 86.00% | 21.88% | 39.38% |
| Accepted-after-Review | 75.17% | 52.50% | 78.13% |

默认视图精度较高，却完整覆盖不到四分之一参考规范；放宽后覆盖大幅提高，但约四分之一抽样条目至少有一个字段错误。RepoNorm 不是“自动挖出全部仓库规范”的系统，而是一个可调整保守程度的候选获取和验证框架。

模型评审的可靠性也被抽查：两个盲化人工评审在 140 条中一致 126 条（90%）；在这 126 条上，他们与 GPT-6-Astra 一致 114 条（90.48%）。这支持自动评审在该抽样上的一致性，却不能消除共同遗漏或把全量精度当成人工真值。

作者还说明，严格的“任一字段错即整体错”会把仍含有有效任务指导的记录判为错误。因此 75.17% 是记录级精度，不等同于“其余 24.83% 全部有害”。

**RQ3 Takeaway**：适用性核查能形成较高精度的保守包，但漏召回严重；加入审查可提高覆盖，代价是更高错误率。精度、覆盖和交付风险必须共同报告。

## 8. RQ4：一次性获取可复用，但使用规范并不便宜

14 个 Accepted-Only 包累计获取时间 2.14 小时，平均每包 9.18 分钟、中位数 8.86 分钟。相对 67.12 小时的 RepoNorm 编码执行累计时间，一次性获取只占 3.2%。这支持“task-independent 包可跨任务摊销”的工程价值。

但 token 账单呈现另一面：

- Raw 编码：346.45M 输入、10.10M 输出 token，53.56 小时；
- CodeWiki：391.73M、10.89M，63.72 小时；
- RepoNorm：463.83M、12.70M，67.12 小时；
- 规范获取本身：134.52M、7.67M，2.14 小时。

只看编码阶段，RepoNorm 比 Raw 多 33.65% 的记录 token、25.33% 的累计执行时间。把获取也算入，成本更高；且有些请求缺 token 记录，绝对总量并不完整。

这意味着 RepoNorm 的提升不是免费来自更好的表示。Agent 需要读包、执行额外动作，也获得更多上下文。论文没有做等 token filler 对照，因此不能把所有 NCR 改善归因于“适用性结构”本身；更多可用信息、更长交互和更高计算预算也是共同变化。

**RQ4 Takeaway**：包的生产可以摊销，但使用成本明显上升。实际部署要同时看每个新增合规项的边际成本，而不能只看总体 NCR。

## 9. Baseline、消融、负结果与失败边界

### 9.1 Raw 和 CodeWiki 是合理对照，但不回答全部因果问题

Raw 代表没有额外生成资源；CodeWiki 代表 task-independent 通用文档。两者能回答“规范包相对无指导或通用文档是否有效”。生成模型权限也基本对齐：CodeWiki 与 RepoNorm 都看仓库、不看具体任务和隐藏评测。

但对照仍有重要差异：资源长度、组织方式、获取计算、Agent 阅读行为和最终输入 token 均不同。论文没有 RepoNorm 规则打乱、去掉适用条件、只保留原始证据、等长随机文档等 treatment，因此无法精确定位是哪一组件造成改善。

### 9.2 论文没有组件消融

作者在 Threats 中明确承认没有隔离各组件贡献，也没有确定最佳参数。显式提取、隐式推断、反例搜索、历史检索、统一验证和路径打包是整体上线的。不能根据流程图推断“历史检索贡献最大”或“反例检查是提升来源”。

两个视图的比较也不是严格消融：Accepted-after-Review 不只是“放宽一个阈值”，还加入另一个模型审查，候选数量从 1,990 增至 6,277。它说明保守状态策略的精度/覆盖权衡，不提供下游 Coding Agent 性能比较。

### 9.3 值得保留的负结果

- Behavioral NCR 没有稳定提升，DeepSeek/Qwen 还略低于 Raw；
- 功能成功与联合成功的 12 个配对比较，经 Holm 校正后无一显著；
- Joint success 即使在 RepoNorm 下也只有 1.65%—8.26%；
- 默认高精度视图完整覆盖只有 21.88%；
- RepoNorm 编码 token 相对 Raw 增加 33.65%；
- 文档内容正确性检查存在明确盲区，39 个误导文档变体没有被检测出来。

这些结果限制了主张强度：RepoNorm 不是已解决的仓库级 instruction system，而是把规范获取、适用性与合规评价向前推进了一步。

## 10. Evidence audit：论文证据还能被怎样审查？

### 10.1 Benchmark 构建与 treatment 不是完全独立的人类真值

参考规范由作者在模型辅助下构建，虽然没有查看 RepoNorm 包，并经过抽样核查，仍可能不完整或体现作者判断。覆盖率只是相对这 160 条任务相关参考规范，不是整个仓库真实规范全集的召回率。

规范检查器与参考规范也由同一研究团队构建，开发时使用了符合/违反变体。抽样和对抗校准增强可信度，但没有外部独立 benchmark。尤其文档内容代理已知会漏错。

### 10.2 统计单位存在仓库内相关

121 个任务来自 6 个仓库、14 个版本，同一仓库和版本的任务共享规范包、代码和流程。作者以任务为 bootstrap/McNemar 单位，明确承认这可能低估对新仓库外推的不确定性。若要主张跨仓库普遍有效，仓库级重采样或更多仓库更合适。

### 10.3 单次运行无法估计随机性

温度虽为 0，但模型服务、工具轨迹和长程 Agent 行为仍可能存在非确定性。每个格子只有一次运行，功能成功的边缘差异无法与运行方差分开。Qwen 7.44pp 等点估计不能被理解为稳定重复收益。

### 10.4 模型参与了多个环节

DeepSeek V4.1 Flash 生成 RepoNorm 与 CodeWiki，GPT-5.6-Sol-high 做放宽视图审查，GPT-6-Astra 评价条目正确性，并参与 benchmark 规范构建辅助。人工一致性抽查是有价值的，但多个强模型共享训练语料和表达偏好，可能形成相关误差。论文没有完全独立的人工全量 gold。

### 10.5 外部效度有限

源码分析目前只支持 Python，且作者优先选择较小仓库。对 Java/Rust/C++、大型 monorepo、快速演化仓库、不同 Agent harness 的效果未知。规范包会随仓库变化变旧，增量更新尚未优化。

### 10.6 “Agent 遵守了规则”不等于“规则对任务有因果价值”

RepoNorm 使用任务相关 reference norms，因此 NCR 关注已标注为适用的要求。即便如此，某规范是否是功能成功的决定性证据、是否只增加交付完整性、或是否在特殊场景下造成不必要修改，仍需更细的配对干预。论文没有移除单条规范并重复同一任务，也没有分析哪条被读到、引用、执行后改变结果。

## 11. 作者与团队背景

第一作者 Kaifeng He 在论文中署名中山大学。其公开主页列出的研究集中在大语言模型与软件工程交叉，包括 AdaDec 的不确定性引导代码生成，以及代码生成数据/输出质量问题。RepoNorm 延续了这一方向：不只优化模型输出，而是把仓库级质量要求和证据组织成可复用的 Agent 输入。

明确通讯作者 Mingwei Liu 是中山大学软件工程学院副教授，长期关注 AI4SE、SE4AI、大语言模型、代码生成和知识图谱。其团队此前研究过 LLM 生成代码的稳健性、代码风格不一致和细粒度指令遵从。RepoNorm 与这些工作关系直接：评价目标从“代码能否运行”扩展到稳健性、风格、贡献流程和仓库治理要求。

Christoph Treude 来自新加坡管理大学，其长期研究涉及软件开发者实践、软件仓库知识与 AI 辅助软件工程。本论文把仓库文档、源码惯例和贡献实践共同作为规范来源，与这一研究积累相符。

这里仅依据论文署名和公开研究记录说明关系，不由作者排序推断具体分工，也不把团队既有研究自动视为本文方法有效性的证据。

## 12. 作者证明了什么，没有证明什么？

### 有数据支持的结论

1. 在 RepoNormBench 的 121 个任务、三个模型上，RepoNorm 的 Overall、Contribution 和 Prompt-omitted NCR 均高于 Raw 和 CodeWiki，配对 BCa 区间全部为正。
2. 改善主要来自贡献要求；行为规范基线已高，额外变化小且区间跨 0。
3. 默认 Accepted-Only 视图抽样精度为 86%，但对任务相关参考规范的完整覆盖只有 21.88%；放宽视图提高覆盖并降低精度。
4. 功能和联合成功率的点估计多数更高，但经 Holm 校正的 McNemar 检验未建立显著改善。
5. 规范包可跨任务复用，但 RepoNorm 编码阶段比 Raw 使用更多 token 和执行时间。

### 论文没有证明的内容

- 任意语言、任意规模仓库都能取得相同收益；
- 每条 accepted 规范都正确，或者默认包覆盖了大多数真实规范；
- 适用性验证、Git 历史、隐式通道中哪个组件独立有效；
- NCR 提升不是额外 token、阅读动作或更长运行共同造成；
- RepoNorm 会稳定提高功能修复率；
- 被 Agent 读取或遵守的某条规范真实因果地改变了最终结果；
- review 状态候选全是无效内容，或错误条目必然造成伤害。

真正应该记住的是：**仓库上下文的关键问题不只是“是否相关”，而是“它对什么改动、在什么条件下、以什么强度适用，并由什么证据支持”。** RepoNorm 把这四个问题显式化，并展示了它对规范遵从的价值；它也同时暴露了覆盖、成本和功能效应的不确定性。

## 13. 对当前研究的启发：把“plausible”推进到“适用性可审计”

本节结合 `causal-review` 最新第 108 节。当前阶段目标是建立全量成功轨迹池，先找同模型稳定可解的真实探索输入，再加外围上下文做干预；目前同十例五路中，严格且同输入稳定的核心仍只有 0b 一个任务一个 pack，不能把文件命中或单次非零行 F1 直接认证为成功 Oracle。

### 13.1 给 plausible context 增加 `(rule, scope, condition, exception)` 表示

当前 P 候选主要来自图邻近、词面关联和真实检索残余。RepoNorm 提醒我们：即使候选语义相关，也必须问它约束哪个实体、什么条件触发、有哪些例外。可以把候选 evidence 记录扩展为：

- `claim`：它可能支持的机制或约束；
- `scope`：适用文件、函数、类型或调用边；
- `activation`：在当前漏洞/任务上必须成立的条件；
- `exception`：已知使其不适用的情况；
- `evidence`：支持和反例位置。

只有 scope/condition 与冻结任务不匹配、且审计证据充分时，才更有底气称它“plausible but non-decisive”。图距离近或同名不能替代适用性判断。

### 13.2 为候选建立 support / counterexample / unknown，而不是二元 P

RepoNorm 的总体检查把成员分成 support、counterexample、ineligible、unknown。当前研究也可保留三/四值状态：

- support：增加新的机制边或决定性条件；
- counterexample：直接否定某个候选解释；
- ineligible：与任务表面相关但作用域/触发条件不满足；
- unknown：证据不足，暂不能叫噪声。

这样可以避免把未证明有用的代码全部塞进 P，也避免用实验下降反向挑选“真正干扰”。

### 13.3 成功轨迹池可同时记录“读了什么”和“什么被应用”

RepoNorm 下游 Agent 自主查阅规范，论文只评价最终合规，没有细分每条规范的实际阅读和使用。当前实验应更进一步，对冻结成功 pack 记录：retrieved、read、cited、mechanism-used 四层。加入 P 后若结果下降，可以区分：核心未进入输入、核心被读但未引用、外围被错误应用，或最终预测宽度改变。

### 13.4 受控实验应增加“适用性结构”对照

在已有 core-only / core+P / core+random 三臂之外，可在样本足够后增加：

1. `core + P-raw`：原始 plausible 代码；
2. `core + P-qualified`：同一代码附 scope、condition、exception；
3. `core + P-mis-scoped`：保持 token 与内容，打乱适用路径或条件；
4. `core + random`：等文件数、等 token 随机外围。

如果 qualified 能缓解伤害而 mis-scoped 恶化，才更接近支持“适用性表示”这一机制。RepoNorm 本文没有做这个消融，因此这只是由其设计引出的新假设。

### 13.5 不要只看定位 F1，也要看联合成功

RepoNorm 的 Joint success 提醒我们：单一质量指标可能掩盖其他失败。当前可以把成功定义为四层联合：

1. 核心代码实际可见；
2. 模型正确描述漏洞机制；
3. 最终归因位置落入冻结机制位置；
4. 文件/行预测满足预设定位门槛。

只有四层同时通过，才把该轨迹纳入稳定成功池。0b 的 Qwen 同输入重复满足哪些层，应按现有源码支持审计明确记录，不因文件满分或旧行 F1 自动升级。

### 13.6 成本也是 treatment 的一部分

RepoNorm 的 NCR 改善伴随 33.65% 编码 token 增长。当前 P/random 实验必须继续匹配实际输入 token、候选文件数和表示格式，并报告 completion token、工具调用和 wall time。否则所谓“语义干扰”仍可能只是预算挤压或更长输入造成的处理差异。

## 14. 结论

RepoNorm 最重要的贡献不是又造了一份更长的仓库文档，而是把仓库知识变成带有作用域、条件、例外和证据的规范，并在交付前主动检查支持、反例和适用性。它在规范遵从上的结果跨三个模型稳定，尤其改善功能测试之外的贡献要求。

同时，它的边界非常清楚：默认高精度集合覆盖有限，放宽会降低精度；功能成功的观察增益没有通过校正后的配对检验；没有组件消融和等 token 对照；成本显著上升。对当前研究而言，最可借鉴的不是直接使用 RepoNorm，而是其适用性表示和反例检查思想：**相关性只是候选生成，决定性必须通过作用域、条件、反例与受控干预来验证。**
