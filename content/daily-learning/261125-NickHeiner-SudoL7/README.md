# sudo L7：测试全绿，为什么这次工程任务还是没过？

> [原文](https://arxiv.org/abs/2611.30517) · [全文及图表](https://arxiv.org/html/2611.30517v1) · [项目说明](https://surgehq.ai/blog/sudo-l7) · [动态榜单](https://surgehq.ai/benchmarks/sudo-l7)

## 上来写代码，可能就做错了题

用户要在捐款应用里加一个功能：把认捐金额拆给几家机构。Agent 实现了新界面和数据结构，267 项测试和 4 项浏览器测试都过了。偏偏它在仓库里已经遇到支持同一功能的旧代码。结果是同一件事有了两套流程，测试验证了新实现能运转，却没有回答是否该新建。这个案例来自论文第 6 节，恰好展示了基准想抓的错误：手头证据已经出现，决策却没有用上它。

SWE-bench 等仓库级基准能检验一个补丁是否满足可执行的验收。对于规格明确的修复，这个问题本身很有价值。sudo L7 改问：当工单漏写风险、前提甚至不成立时，Agent 能否先弄清该做什么，最后如实说明做到了哪一步？最接近的 FrontierCode 也用维护者规则约束补丁是否可合并；sudo L7 还读运行过程和交付报告，也允许合理的结果是提出问题或解释不应动代码。差别在被测对象，不是把测试换成更难的测试。

[AI Engineer 的作者简介](https://ai.engineer/speakers/nick-heiner)显示，Nick Heiner 在 Surge AI 负责强化学习环境，曾在 Netflix 从事工程并参与创办 Fixie；团队此前也用专家评分规则研究 [ComplexConstraints](https://arxiv.org/abs/2606.09118)。这篇 workshop 论文续用专家规则来构造**评测**，并没有报告用这些任务训练参评 Agent。对正在写仓库上下文研究的人，它提供了一个有用的区分：见过证据、理解证据、依据证据作决定，要用不同观测量说明。

## 先设计一条合理但没把话说完的工单

一题给定一个仓库快照和一条单轮请求。专家通常从一个前沿模型确实失败过的地方起题，再写三份互相配套的材料：给 Agent 的请求、给裁判的仓库与领域事实、逐项评分规则。作者自己核查每条规则，由资深工程师复审，未解决的分歧再升级；还让不同 Agent 多次尝试，检查题是否可做、同样合理但不同的方案会不会被误杀，以及题目是否只卡住某个模型。先找到失败再出题是一种有意的挑战采样；它擅长找出上限，原文未以生产工单随机样本来估计日常失败概率。

**表 1** 定义了样本的形状：60 个任务跨 25 个仓库，38 个任务来自三家公司的 17 个私有生产仓库，其余 22 个来自 8 个开源仓库。28 题写功能、25 题调试或修复，代码审查仅 2 题；有 10 条请求包含需要反驳的前提。44 题配有确定性检查，17 题的运行环境可使用浏览器。因而这项工作适合作为工程判断的广义对照，不能直接当成一个代码审查专项基准。

## 评的不是一个分数，而是一组可以追问的判断

每题的评分表由 7–57 条独立规则组成，中位数 22；总共 1,287 条。规则有三个不同的维度：

- **为什么评它**：68% 检查任务主要意图，25% 检查看似合理却容易出错的路径，7% 是额外加分。它们区分「完成请求」「避免坑」「做得比预期好」。
- **它在测什么**：表 2 将规则标成正确性、工程质量、验证、协作判断、沟通、如实报告、持续推进、务实判断八类。241 条跨多个标签；一句声称跑过实际没跑的检查，可以同时伤害验证和如实报告，不能把各标签计数相加当成独立条数。
- **它能不能一票否决**：共有 69 项任务关键点（crux）、305 项严重项（critical），再往下的 632 项 major、191 项 minor 和 90 项加分不决定是否通过。至少一个关键点出现在 54 题中，每题至多两个关键点；不是每题都必须有这一档。

附录 A 用一个假想 webhook 工单解释何谓「独立规则」。用户想让失败的事件也返回成功，目的是停止对方重试。关键评估对象是事件会不会丢：可以选择保留待处理事件，也可以先告知用户照做的后果，规则不要求补丁恰好长成指定样子。这个例子专为论文编写，真实题目的规则没有公开。

图 1 把管线画成了一次接力。先由被测 Agent 读快照、执行任务、交付说明；它看不到规则。结束后，验证器收集会话、相对于起始快照的改动（含未提交改动）和确定性检查输出，并标注已知的原有失败。随后才轮到运行在 Codex 内、使用 high 推理设置的 GPT-6 Sol 裁判：它一并看专家事实说明、隐藏规则和上述证据，可以检查或运行代码；环境支持时也能打开界面。它给每条规则 pass、partial 或 fail，并留下文件、日志或会话中的依据。比如「我验证了迁移」是最终陈述，执行记录才是支持这句陈述的证据；小心区分宣称和实际观察。

最后由一个独立步骤套用严重度。裁判先不知道哪条会一票否决，因此可以复用同样的判分记录，事后计算其他规则下的通过率。榜单口径要求所有 crux 和 critical 均为 pass，partial 也算未达标；另外有给部分进展记分的连续奖励，但榜单不用它。374 条门槛规则里 203 条（54%）不带功能正确性标签；其中 179 条涉及验证、协作判断、沟通、如实报告或持续推进之一，分布在 55/60 题。「如实报告」共有 90 条，66 条可一票否决，覆盖 48 题，与正确性门槛的题数相同。因此这里确实可能功能正确但整题失败，这也是这个比例的设计含义。

附录 B 交代了评分信任边界：两个阶段的外部访问均只到各自推理端点；起始快照不提供后续仓库历史，规则在作答结束后才放入；工具输出作为证据隔离，验证器检查改动并不依赖工作区的 Git 配置；残留进程会清理，裁判不采纳 Agent 留下的指令文件，最终分从裁判输出读取，并记录异常标志。这些措施针对把裁判结论和待测产物混在一起的风险；论文没有提供独立攻击测试来量化防护覆盖率。

## 榜单回答了什么，三次重跑又意味着什么？

第 4 节固定任务集，让 12 家厂商的 19 个模型各做每题三次，尽量使用最高可用推理设置。平台支持时用开发者原生执行框架，例如 Claude Code、Codex；否则可用 OpenCode，另有 Qwen Code 等配置。每次最多五小时，不开放网络搜索，也没有人当场回答澄清问题。一份轨迹由裁判判一次。超时、Agent 或基础设施异常重跑；若仍拿不到有效结果则不纳入通过率。这个口径测的是有效作答下的任务完成，跟把超时也记成失败的服务可靠率不同。首发版本则是一次作答判三次，后来还改过约半数请求的措辞和部分评分文本，不应拿首发和当前榜分数当成一组对照。

**表 3：论文冻结于 11 月 13 日的榜单。** 先计算每题三次里的通过比例，再在 60 题上等权平均；用它比较的是这组模型与运行框架的组合。

| 组合 | 严格通过率 |
| --- | ---: |
| Claude Fable 5.2 | 52.2% |
| Claude Sonnet 5.5 | 50.6% |
| Claude Opus 5.5 | 46.1% |
| GPT-6.1 Sol（Max） | 33.9% |
| Claude Fable 5.1 / GPT-6 Astra | 32.2% / 31.1% |
| 其余 13 个组合 | 9.4%–18.9% |

重点并不在 52.2% 与 50.6% 谁更高。三次尝试可能被同一个难点绊住；同题三个结果不能天然当作三个彼此独立的新题。附录 C 用同题尝试相关程度从 0 到 1 来夹住不确定性：若通过率约 50%，有效独立样本量从乐观的 180 缩到保守的 60，单个通过率的近似 95% 半宽由 7.3 个百分点变成 12.7 个百分点。两模型差值另按两者方差之和估算，不应直接把单组合区间当成差值区间。榜单没公开逐题结果，无法直接估出任务层方差，也无法利用两模型做同题的配对关系；附件中的区间是条件化敏感性检查，不是精确的配对检验。

前 3 与后 13 的 39 组差至少 27.2 个百分点，都越过了论文采用的保守界限。Fable 5.2 相对 5.1 多 20 个百分点，也超过对应的 17.3 个百分点界限；前三内部最大差 6.1，甚至小于其乐观界限 10.3。所有 171 个两两组合中有 78 个越过各自保守界限，这不是做过多重比较校正的显著性名单。另有 Inkling 2 Small 的 14.1% 对不上 180 次整计数，论文指出其有效次数较少，榜单未提供精确分母。排序中最稳的是大致分层，不是每名次的微小差距。

## 表 4 的三次翻车，比排行榜更容易学到东西

1. **漏报风险。** 一条 Terraform 变量拼写错误本来只需一行修改，但变更部署后可能替换负载均衡器。评分希望在任何部署前标出影响。测试跑完只回答了技术验收的一部分。
2. **做了不必要的活。** 捐款应用就是开头的例子。Agent 找到相关代码仍做了平行系统，因此找到了文件和做出了正确决策可以分开失败。当前案例无法区分它究竟没理解旧逻辑，还是理解了却没有质疑工单前提。
3. **把局部修复说成全部解决。** 在欺诈标签任务中，Opus 修得比 Sonnet 多，但对仍有问题的数据宣称已经修好，关键项失败。Sonnet 则具体说明一个修复、哪些检查能够暴露剩余问题，以及没有真实数据时无法完成的工作。论文内部逐题对比发现两者各有擅长的题，并没有证明 Sonnet 整体更强。

作者提出两种可以区分的解释：有些 Agent 既漏报风险、又重复造轮子，可能是同一种未经核实便照做的习惯；也可能存在警惕性与服从之间的权衡。如果是后者，在控制总体能力后，擅长挑出危险的 Agent 可能在不需过度警惕的题上反而表现差。要判别须拿到按题分类的结果，文章只有案例和总榜，未识别这两种机理。

## 表 5：85% 一致，够不够说裁判已达到人工水平？

研究共覆盖较大任务池的 14 题，其中 5 题有第二位工程师复标。表 5 限于这 5 题、293 个单条规则判定：以第一位工程师为参照，第二位工程师同意 85%，候选 Gemini 4 Argon 为 85%、Claude Fable 5.1 和 GPT-6 Astra 都为 86%。换成「同题两个尝试选哪个」这个单位，人类为 14/15，三候选分别为 14/15、13/15、9/15。按条同意率近似，不保证尝试排序等同；在严格门槛下，小部分关键项分歧就足以翻转整题。

另外，在三候选一致的条目上，两位人类标注员都看过模型共识再确认或推翻；彼此没看到对方标签，**仍不构成独立于模型的双盲人工标签**。正式跑榜用的 GPT-6 Sol 也不是表中三候选之一。作者称内部比较显示它相当且更便宜，未公布可比的正式裁判逐条统计。正式裁判与两个被测模型同厂，最高三名均来自别家能缓解一个极端担忧，但排除不了对局部名次、任务或判据的偏移。若想让榜单更可审计，最值得公开的是正式裁判和盲审之间的关键项分歧、逐任务有效分母，以及改动门槛后的成对翻转。

## 应该带走的三件事

- 工单可执行、补丁可交付、工程上值得做，是不同问题；可执行测试可以帮裁判查证，无法单独评价未写明的风险、已有功能复用或最终说明。
- 该数据中强组合的严格通过率约一半，且大档差值得重视。题目经过失败导向挑选，框架、推理设置与模型绑定，私有仓库和真实规则没有开放；这不足以归因模型、估计日常生产失败率，或评价完整的 Staff Engineer 角色。特别是员工能开会追问，这里的作答不能。
- 规则拆分、证据保留、聚合后置值得借鉴。鲁棒的任务设计还应报告**谁被评、谁来评、按什么门槛、哪一步失效**，而不是仅汇报一个貌似客观的分数。

## 对仓库上下文研究的启发

这篇论文给「看到但没用上」提供了一个具体反例，但不测 plausible context 的增量伤害。它没有固定核心证据后再替换上下文，也没有把 token、候选集合和正确性规则作为配对控制，因此不能用来为某个上下文处理背书。用在论文里，我会将它放到评测构念或失败类型的讨论，而不是替代受控结果。

拿自己的 *Motivating Example* 时，可把已经冻结的配对结果拆成一张小证据表：核心节点是否在实际输入，正确位置是否进入最终预测，额外候选又挤进了哪些位置；保留文件级与节点级口径。若只能看到输出变化，就描述证据可用与选择错位，别把它写成模型内部已发生的注意力机制。表 5 还提示 CPI 的可信度应报告独立人工核查、正式裁决器身份和争议类别；一致率、标签可信度、最终结论稳定性是三个不同问题。在投稿前重算或整理已有成对结果，比为了追榜新跑一批任务更直接。
