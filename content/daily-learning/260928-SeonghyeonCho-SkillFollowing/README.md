# Skill Following: Evaluating Actual Skill Use in Retrieval-Enabled LLM Agents

> **论文**：[Skill Following: Evaluating Actual Skill Use in Retrieval-Enabled LLM Agents](https://arxiv.org/abs/2609.00549)  
> **作者**：Seonghyeon Cho, Chanjun Park  
> **单位**：Soongsil University（崇实大学）  
> **收录**：Findings of EMNLP 2026  
> **原文**：[arXiv:2609.00549](https://arxiv.org/pdf/2609.00549)  
> **关键词**：LLM Agent、Skill Retrieval、配对执行、选择偏差、Actual-Use Effect

## 先用三句话建立论文地图

很多 agent 论文会把“触发了 skill 检索的任务”和“没有触发检索的任务”拿来比较，然后把准确率差叫作检索收益；问题是，这两组任务本来就可能难度不同。本文让**同一个任务**分别在可用 skill 检索和禁用 skill 检索的条件下执行，观察正确性是否发生翻转，从而区分“系统选择了在哪些任务检索”与“检索真的改变了答案”。结果很尖锐：多个模型的常规聚合指标为正，但配对后的实际使用效应为负；高检索率也不保证模型会遵循或正确使用返回的 skill。

全文的证据链是：

```text
检索触发组与未触发组不是同一批任务
                ↓
聚合准确率差混入任务选择与难度差异
                ↓
同一任务运行 skill-enabled / skill-disabled 两个条件
                ↓
记录正确→错误、错误→正确等配对转移
                ↓
分别计算总体访问效应与“已触发检索”条件下的实际使用效应
                ↓
检验常规指标是否反转，并分析负效应发生在哪个阶段
```

理解全文需要四个概念：

1. **Skill**：不是模型参数里的能力，而是一段外部存储、可检索的过程性说明，例如“如何做边界条件检查”或“如何按指定接口返回代码”。
2. **检索触发（retrieval invoked）**：agent 决定调用 `search_skills` 并获得返回内容。它只说明内容被送进上下文，不说明模型采用了内容。
3. **配对执行（paired execution）**：同一任务分别在可检索和不可检索条件下运行，其他关键配置尽量保持一致。比较单位因此从“两组不同任务”变成“一对同任务结果”。
4. **选择偏差**：agent 自己决定何时检索。如果困难任务更容易触发检索，那么“检索组准确率低”未必说明检索有害；如果简单任务更容易触发，正向差值也未必说明检索有益。

## 1. 真正的研究缺口：暴露不等于利用

检索增强 agent 的评估常混合了三个问题：系统有没有调用检索、检索器有没有返回相关内容、生成模型有没有把内容正确用于答案。常见指标只看第一步附近的行为：把最终运行按“检索/未检索”切成两组，再比较组间准确率。

这个比较并不回答“skill 是否帮助了任务”。假设 agent 在简单题上常检索，在难题上反而直接作答，那么检索组准确率较高，即使 skill 对每一道题都毫无帮助，也能得到正的“retrieval lift”。反过来，若模型遇到难题才检索，检索组准确率较低也不能证明检索有害。这里缺少的是同一任务的反事实近似：**如果这道题不能访问 skill，它会不会得到不同结果？**

作者据此提出 Skill Following（SF）：评估完整的“发现 skill → 检索 → 注入上下文 → 在最终答案中利用”链条，而不是只测 skill 是否被找回。需要强调，这个 gap 一半是统计设计问题，一半是 agent 行为问题：论文用配对实验直接证明前者会造成指标反转；至于模型为什么忽略或误用 skill，后续诊断只能提供描述性证据。

## 2. 方法从输入到输出怎样运行

### 2.1 两个执行条件

每个任务都运行两次：

- **Skill-enabled（SE）**：prompt 中提供 `search_skills` 工具。模型可以查询 BM25 索引；每次返回排名前三的完整 skill 文本，最多调用三次。
- **Skill-disabled（SD）**：任务本身相同，但移除检索工具定义。它代表在当前 agent 配置下“不能访问 skill”的对照。

作者尽量固定任务、生成种子和解码配置。这样做的输出不是两个组的平均数，而是每道题的一对二元正确性结果。不过，SE prompt 多了一段工具说明，且温度为 0.7；跨供应商 API 即使种子相同也不保证采样完全等价。因此这里的 treatment 是“整条 skill access 链是否可用”，不是纯粹隔离的“插入某段文本”效应。

### 2.2 四种配对转移

令 SD 是禁用 skill 的结果，SE 是启用 skill 的结果。一对运行只有四种结局：

| 类型 | SD | SE | 直觉 |
|---|---:|---:|---|
| a | 对 | 对 | 无论有无 skill 都成功 |
| b | 错 | 对 | helpful flip，skill access 可能救回任务 |
| c | 对 | 错 | harmful flip，skill access 可能破坏原本正确答案 |
| d | 错 | 错 | 两个条件都失败 |

这张转移表比两个独立准确率更有解释力，因为 b 和 c 直接告诉我们净变化来自哪里。如果 b 多于 c，启用 skill 的净效应为正；如果 c 多于 b，则为负。

### 2.3 三个指标及其区别

**第一，常规 Aggregate Retrieval Lift。** 它比较 SE 运行中“实际检索的任务”与“没有检索的任务”的准确率。直觉上简单，但两组任务由 agent 自选，无法消除基线难度差异。

**第二，Overall Skill-Access Effect（OAE，总体 skill 访问效应）。** 对全部任务计算：

\[
\mathrm{OAE}=\frac{1}{n}\sum_i(Y_i^{SE}-Y_i^{SD})=\frac{b-c}{n}.
\]

这里 \(Y\) 是正确性，b、c 分别是全体任务中的 helpful 与 harmful flips。OAE 回答：把整个系统从“不能访问 skill”切换到“可以访问 skill”，总体准确率平均怎样变化。它包含检索触发行为本身。

**第三，Retrieval-Invoked Actual-Use Effect（RAE，检索触发后的实际使用效应）。** 只在 SE 条件下确实触发检索并获得 skill 的任务集合中，比较同任务 SE 与 SD：

\[
\mathrm{RAE}=\frac{1}{n_{cond}}\sum_{i\in S_{call}}(Y_i^{SE}-Y_i^{SD})
=\frac{b_{cond}-c_{cond}}{n_{cond}}.
\]

它问的是：**在这个 agent 确实决定检索的那些任务上，允许 skill 链运行后，最终答案净变好还是变坏？** 数值随 helpful flips 增多而上升，随 harmful flips 增多而下降。

两者还可分解为：

\[
\mathrm{OAE}=\frac{n_{cond}}{n}\mathrm{RAE}+\frac{n_{skip}}{n}\Delta_{skip}.
\]

也就是说，总体访问效应由“触发检索任务上的配对效应”和“未触发任务上的差异”按覆盖率加权组成。

一个关键边界必须说清：\(S_{call}\) 是 SE 运行之后才知道的集合，属于 treatment 后选择。RAE 比非配对聚合差更贴近实际使用，却仍不是预先定义总体上的无偏平均处理效应。它是**当前协议条件下、模型自行选择检索的任务子集上的配对描述量**。

## 3. 实验坐标系

- **模型**：17 个闭源与开源 LLM；表格中部分模型因输出或运行条件无法形成完整可报告单元，主要符号比较基于 13 个模型。
- **代码任务**：主实验使用 MBPP+，每个 seed 取 80 题，主 seed 为 42，并用 43、44 重复；另外使用 HumanEval+。正确性由 EvalPlus 的扩展测试判定，而不是 LLM judge。
- **数学任务**：Math500 的 80 题分区，用来检查现象是否局限于代码生成。
- **skill 库**：代码 9 个过程性 skill，数学 8 个；每个以 `SKILL.md` 保存标题、描述和正文，用 BM25 检索。
- **生成设置**：temperature 0.7，最大输出 8192 tokens，关闭显式 reasoning；检索 top-3 完整 skill，最多三次工具调用。
- **比较对象**：常规检索/未检索聚合差、OAE、RAE、检索覆盖率、阶段诊断、内容控制与检索深度敏感性。

这些设置的优点是任务对照和测试判定清楚；代价是外部有效性有限：短程函数题上的一次检索，不能自动代表长轨迹、可反复浏览仓库的 coding agent。

## 4. 主结果：漂亮的聚合增益可以在配对后反转

### 问题

常规 aggregate lift 与 RAE 是否给出相同方向的判断？如果不同，差异是否跨 seed、数据集和模型存在？

### 设计

作者对每个模型、任务和 seed 形成 SE/SD 配对；一方面在 SE 内部算“检索任务 vs. 未检索任务”的准确率差，另一方面在实际检索子集上算 RAE，并用置信区间判断不确定性。

### 结果与 Table 3 的读法

Table 3 的关键不是逐行找最大值，而是把同一行的 aggregate lift 与 RAE 并排看：前者改变任务集合，后者固定任务配对。

- Gemini-2.5-Flash-lite 在 MBPP+ seed 42 的聚合差是 **+6.2**，RAE 却是 **−15.6**；seed 43 为 **+16.2 / −15.9**，seed 44 为 **+4.4 / −22.2**。
- DeepSeek-V3.2 在 seed 42 是 **+31.6 / −9.1**，seed 44 更达到 **+46.2 / −23.1**。如果只报前一个数字，会把有害的同任务转移包装成显著增益。
- Llama-3.3-70B 也并非始终正向：seed 43 为 **+44.2 / −2.0**；另外两个 seed 的 RAE 分别为 +4.2 和 +7.5，说明结论具有模型与运行条件异质性。
- 在可报告的 13 个模型中，aggregate 与 RAE 的符号不一致数量为：MBPP+ 三个 seed 分别 **5/13、6/13、3/13**，HumanEval+ 为 **3/13**。

一些置信区间把“随机波动”解释压得更低：Mistral-S-24B 在 seed 44 的 RAE 为 **−45.5**，95% CI **[−57.6, −33.3]**；DeepSeek 同一 seed 为 **−23.1 [−33.3, −12.8]**；Gemini 在 HumanEval+ 为 **−21.1 [−36.8, −7.9]**。但也有正例：Qwen3-235B 在 HumanEval+ 的 RAE 为 **+15.5 [5.6, 25.4]**。因此论文支持的是“聚合指标不可靠且实际效应高度异质”，不是“所有模型都会被 skill 伤害”。

### Figure 1 与 Figure 2 真正在展示什么

Figure 1 把 aggregate lift 放在横轴、RAE 放在纵轴。右下象限的点最值得看：横轴为正、纵轴为负，表示表面上检索组更准，但同题配对后检索访问反而增加错误。点落入这一象限就是直观的符号反转。

Figure 2 的横轴是 SD 条件下“后来会检索”和“后来不检索”任务的基线准确率差，纵轴是常规 aggregate lift。它显示两类任务在没有 skill 时就已经不同，因此 aggregate lift 与选择出的任务难度纠缠。图证明了基线不平衡存在，但不能单凭相关趋势断言是哪一种内部策略导致模型选择检索。

### 跨领域复现

Math500 上，Llama-3.3-70B 的 aggregate lift 为 **+14.2**，RAE 为 **−39.4**；Gemini 为 **+13.2 / −11.0**。这说明反转不只来自代码测试器或编程 skill 的特殊设计。不过数学实验仍使用同类单轮工具协议，不能据此推广到所有 agent 系统。

**Takeaway：是否触发检索本身携带任务选择信息；只有同任务配对，才能看见检索访问究竟把多少答案从错变对、又把多少从对变错。**

## 5. 为什么高覆盖率仍然没有转化为收益

### 问题与设计

作者把“skill use”拆成 retrieval、adherence proxy、effective 三层。retrieval 表示拿到了 skill；adherence proxy 检查输出是否出现与 skill 一致的可观察结构；effective 则要求这种行为最终与正确性改善相联系。

### 结果

Figure 4 把检索覆盖率与 RAE 并列观察。DeepSeek 与 Gemini 在 MBPP+ 三个 seed 上的检索率约 **79%–100%**，但 adherence proxy 只有约 **13.6%–19.2%**，effective use 更低至约 **10.6%–12.8%**，同时 RAE 为负。图中也有高覆盖率而 RAE 负值的模型点。

所以“工具调用成功率”最多测到 exposure。它没有告诉我们模型是否理解、是否采纳、是否把程序接口和答案格式保持正确。论文把这一点说得很有价值：retrieval infrastructure 的健康指标不能替代 downstream utilization 指标。

但 adherence proxy 本身也只是代理变量。它依赖可观察的输出模式，不一定捕获隐式利用；反过来，表面遵循也不等于 skill 是答案改善的原因。

## 6. Harmful flips 到底是怎么产生的

作者请 GPT-5.5 对 harmful transitions 做盲标，类别包括：恰当遵循、忽略/独立作答、误用/过度应用、格式或接口失败、不清楚。标注时不告诉模型 SD 答案和正确性，减少结果导向的事后解释。

在 DeepSeek 的 harmful cases 中，**64.4%** 被判为忽略/独立，**15.6%** 是格式/接口失败，**13.3%** 是恰当遵循但仍失败，**6.7%** 是误用。Gemini 分别约为 **72.5%、2.5%、10.0%、12.5%**，另有 2.5% 不清楚。这意味着很多有害转移并不是模型明显照着坏建议做，而是 skill 被检索后仍没有可靠进入解题过程，或额外上下文改变了生成轨迹。

不过这部分证据不能过度解读。人工复核的 Krippendorff's alpha 只有 **0.377**，人工多数票与 GPT 细分类一致率 **52.4%**；把标签压成“参与/未参与”的二分类后，一致率才到 **84%**。因此细粒度比例适合描述现象，不足以证明具体认知机制。论文最可靠的结论是“许多 case 没有可确认的实质使用”，而不是“64.4% 的失败由某个确定机制导致”。

## 7. 内容控制：问题不只是 skill 写得不好

作者把正常 skill 换成 filler、随机 skill、损坏 skill，并保留 schema-empty 条件。这个实验想分开“任何额外工具/上下文带来的扰动”和“正确 skill 内容的专有效果”。

在 pooled MBPP+ 上：

| 模型 | Normal | Filler | Random | Corrupted |
|---|---:|---:|---:|---:|
| DeepSeek-V3.2 | −15.9 | −10.2 | −15.1 | −9.1 |
| Gemini-2.5-Flash-lite | −17.9 | −5.0 | −15.4 | −17.2 |

正常 skill 没有稳定优于随机或损坏内容，说明“返回内容质量”不能单独解释负 RAE；工具调用、上下文注入、注意力分配和输出接口都可能参与。schema-empty 没有返回 skill，RAE 因而未定义，这也是正确处理：没有满足条件的实际使用集合，就不该硬算指标。

这个 control 仍不能定位机制。随机、filler、corrupted 同时改变语义相关性、长度、格式和潜在干扰方式；它们为“内容质量不是唯一原因”提供边界，却不是干净的因果分解。

## 8. 检索深度敏感性与消融边界

作者改变 top-k 为 1、3、5。Gemini 在三个深度下均保持显著负 RAE；DeepSeek 也保持负向，在 k=1 时最强且显著；Claude 接近零。这说明主反转不依赖唯一的 k=3 设置，同时再次显示模型差异。

另一个 merged-1 条件把多个 skill 合成一个返回项。它不只改变“检索条数”，还改变覆盖率、文本粒度和检索机会，因此不能解释成纯粹的 k 消融。这里能说的是结果对若干检索配置有一定稳健性，不能说某个 skill 粒度是负效应的唯一原因。

## 9. 公平性、构念效度与证据边界

### 论文证明了什么

1. 在本文的代码与数学任务、模型和检索协议中，检索组/未检索组的聚合准确率差会频繁与同任务 RAE 异号。
2. agent 的检索选择与任务基线难度相关，因而 aggregate retrieval lift 混入选择偏差。
3. 高检索覆盖率不保证高 adherence 或有效利用；部分模型在几乎总检索时仍有显著负 RAE。
4. 负 RAE 对多个 seed、数据集和检索深度存在，但并非所有模型都负向。
5. 正常、随机、填充、损坏内容都可能出现负 RAE，说明内容相关性不是唯一需要诊断的环节。

### 论文没有证明什么

1. **RAE 不是预先定义总体上的因果 ATE。** 它条件化在 SE 运行后形成的检索集合上，存在 post-treatment selection。
2. 它没有隔离“skill 文本内容”的纯因果效应。SE/SD 同时改变工具定义、调用轨迹、上下文长度和生成过程。
3. 它没有证明模型忽略 skill 是负效应的唯一机制；细粒度 failure taxonomy 的标注可靠性偏低。
4. 它没有证明结论可直接推广到仓库级、多轮、长时程 coding agents。
5. 相同 seed 不等于完全相同随机轨迹；温度 0.7 和异构 API 仍可能贡献个别翻转。

### 还需要哪些更强实验

最直接的改进是预先定义 eligible task set，再随机分配是否注入同一 skill；这样估计对象不会由 treatment 后行为决定。还可加入 oracle retrieval、仅 metadata、先显示 skill 列表再显式 fetch 全文、等 token 的无关文本控制，以及多套独立 skill pool。对失败机制，应使用更清晰的操作化标签、双人以上人工标注与分歧仲裁。

## 11. 读完真正应该记住什么

- “检索过的题更准”比较的是两批不同题，不等于“检索让同一道题变准”。
- 最小可行的修正是同任务配对，并报告 helpful 与 harmful flips，而不是只报一个组间平均数。
- RAE 比 aggregate lift 更贴近实际利用，但因检索集合由 SE 行为决定，它仍是协议条件量，不应包装成一般因果效应。
- 检索率是 exposure 指标；真正需要追踪的是 adherence、正确利用和最终任务转移。
- 负结果不能简单归咎于“检索器差”或“skill 写得差”，工具提示、上下文干扰、接口失败和生成随机性都需要分开控制。

## 12. 对当前 causal-review 研究的启发

最新研究记录显示，当前主线正在比较 core-only、plausible extra context 与 random context，并特别关注“机制判断仍正确但归因被带偏”的状态。本文最直接的价值不是提供仓库上下文的现实性证据，而是提供一个**避免选择偏差的实验骨架**。

第一，不要比较“模型最终采用了 plausible context 的 case”和“没有采用的 case”。是否采用与任务难度、核心证据强度、模型信心都相关，正如本文的 retrieval decision。更稳妥的主分析是在处理前就固定 eligible cases，对每个 case 运行相同 core、相同 prompt 框架和相同 seed 配置下的 core-only / plausible / random 条件。

第二，把单一准确率拆成配对转移。对机制正确性 \(M\)、归因正确性 \(A\)、定位正确性 \(L\) 分别记录：

- helpful：control 错、treatment 对；
- harmful：control 对、treatment 错；
- concordant：两者都对或都错。

尤其应单列当前最关心的转移：\(M\) 保持正确，但 \(A\) 从正确翻为错误。这比只看 treatment 组中 \(P(M=1,A=0)\) 更接近“额外上下文改变了什么”。

第三，同时报告总体效应与条件效应。可以定义所有预先入组 case 上的 OAE-like 指标，以及 plausible/random 各自相对 core-only 的配对净翻转；如果还要看“模型确实引用了额外上下文”的子集，应明确它是 post-treatment 条件分析，只作为行为诊断，不充当主因果估计。

第四，random context 是必要但不充分的 control。应尽量让 plausible 与 random 在 token 长度、代码块数量、位置、格式和可执行性上匹配；否则所谓 plausibility 效应仍可能混入上下文负荷。本文的 filler/random/corrupted 控制正好说明：只换语义而不控制表示与长度，很难识别机制。

最后，这篇论文只能作为 **mechanism/evaluation precedent**：它支持“选择性调用会让聚合比较失真”和“exposure 不等于 utilization”。它没有证明仓库级 plausible context 会导致错误归因，也没有覆盖 call graph、代码审查或长轨迹 agent；这些现实性与外部有效性仍必须由当前实验自己建立。
