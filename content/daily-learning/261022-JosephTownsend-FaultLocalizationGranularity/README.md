# A Study on the Impact of Fault Localization Granularity for Repository-Scale Code Repair Tasks

## 定位已经“完全正确”，为什么修复仍可能失败？

想象一个修复系统已经拿到了标准答案告诉它的位置：错误就在 `parse_http_date` 的两位年份处理逻辑。接下来应该给模型看什么？只给真正需要改的两行，信息最精确；给整个函数，模型能看到变量从哪里来、结果往哪里去；给整个文件，背景最全，却也塞进许多无关代码。直觉上“越精确越好”，但修复模型并不只需要知道**改哪里**，还需要知道**怎样改才在周围语义中成立**。

这篇论文研究的正是这个交接问题。它不比较谁更会找 bug，而是先假设位置已经找对，固定 issue、模型、修复提示和评测，只把同一个 ground-truth 修改位置包装成行、函数、文件三种上下文，观察下游修复率是否变化。这个拆法很重要：如果把定位准确率和上下文粒度一起改，修得更多究竟来自“找得更准”还是“交接得更好”，无法分辨。

## 这篇论文值得怎样读

它值得读，不是因为已经给出“最佳粒度”的定论，而是因为它把常被当作实现细节的选择变成了可干预变量：**在已知修改位置相同的前提下，呈现范围本身会不会改变修复结果？** 论文给出的是一个 50 题、单模型、单提示模板上的 proof of concept；作者也明确说目标不是刷新 SWE-bench 排名。

四位作者均来自 Fujitsu Research of Europe。第一作者 Joseph Townsend 过去的公开工作集中在神经符号知识抽取、可解释 AI，也与 Kwun Ho Ngan 合作过视觉—语言表示和医学影像中的知识抽取；团队在 2026 年又参与了 Fujitsu 的开放权重软件修复 agent 工作。Chandresh Pravin 的公开研究背景偏模型解释与鲁棒性，Matthieu Parizy 则有把研究技术转向实际系统与优化问题的经历。换言之，这更像一个从“知识以什么表示交给模型”切入 APR 的产业研究团队，而不是长期只做传统 spectrum-based fault localization 的组。论文没有明确标注通讯作者，不能按作者顺序自行推断。

对当前研究，它恰好击中最新暴露的边界：`scanner.py::_unsafe_globals` 被裁定为一个模块级字典 GT 节点，说明“函数”并不是天然正确的语义单位；与此同时，新的实验又要求先确认完整 Core，再做 P/I 同期干预。本文能提供的是一个很干净的**先固定定位真值、再干预呈现方式**的设计先例；不能提供的是“函数节点永远优于模块对象”的结论。事实上，它的函数级条件把函数、方法和类合在一起，也没有系统处理模块级字典这类非函数语义对象。

## 用论文的例子看懂三种粒度

论文在附录展示了 SWE-bench Mini 实例 `django__django-11848`。issue 指出：HTTP RFC 7231 要求两位年份若落在未来超过 50 年，应解释为最近的过去年份；原实现却硬编码为 `00–69 → 2000–2069`、`70–99 → 1970–1999`。

同一个真实补丁可以产生三种交接材料：

| 条件 | 给修复模型看的内容 | 它得到什么 | 它可能失去什么 |
|---|---|---|---|
| 行级 | diff 中被修改的精确行，并向前后各扩 10 行 | 高指向性、较少噪声 | 函数入口、变量来源或相关分支可能被截掉 |
| 函数级 | 覆盖修改行的整个函数、方法或类，并带上下文窗口 | 一个相对完整的局部语义单元 | 跨函数依赖、模块常量或远处约束仍可能缺失 |
| 文件级 | 含有修改位置的整个文件 | 文件内依赖和辅助定义最完整 | 代码量和潜在干扰最大，模型还要再次定位 |

图 2 用一个 `mergeSort` 教学仓库画出相同差别：真正错误只是 `n` 应改成 `m`；行级只露出那几行，函数级给整个 `mergeSort`，文件级给完整 `merge_sort.py`。关键不是三者谁“更接近补丁”，而是**定位信号和可修复上下文之间存在 specificity–context trade-off**。

还要注意，作者所谓“行级”并不是孤零零的行号。他们担心 LLM 不擅长仅凭行号对齐代码，所以实际注入的是代码片段，并扩展前后 10 行。于是实验真正比较的是三种**上下文构造策略**，而非纯粹的空间粒度标签。

## 实验怎样把粒度单独拎出来

一句话概括：作者从标准补丁反推出三种 oracle 上下文，把它们分别塞进同一个 Agentless 修复阶段，用同一个 Qwen3-Coder 各跑 10 次，再以测试是否通过为结果。

### 1. 数据：50 个真实仓库级 issue

数据集是 SWE-bench Verified 的 50 题子集 SWE-bench Mini。它包含人工验证的 GitHub issue、故障版本和开发者修复补丁，但这 50 题只来自 `django/django` 与 `sphinx-doc/sphinx` 两个 Python 仓库。实验单位是“一个 issue 在一种粒度下的一次修复运行”；三种粒度、每题 10 次，共形成 1,500 个题次。

这里的标准补丁承担两个角色：一是最终测试评测所对应的参考修复，二是反推“正确位置”的 oracle。作者读取补丁 diff：

1. 修改行本身定义行级定位；
2. 包含这些行的函数、方法或类定义函数级定位；
3. 包含这些语义块的文件定义文件级定位。

这样三组输入都源于同一补丁，避免不同定位器的误差混入比较。但它也引入一个重要构念限制：**“开发者最后改过的位置”不等于“修复模型理解问题所需的全部相关位置”**。未修改的调用者、配置、测试约束可能很重要，却不会自动进入这个 oracle。

### 2. 管线：保留修复器，拿掉定位与重排

作者选择 Agentless，是因为它的顺序式阶段容易替换。实验跳过原始文件定位器，由 oracle 构造器直接生成上下文；修复模型统一使用通过 vLLM 0.15.1 部署的 `Qwen/Qwen3-Coder-30B-A3B-Instruct`；又跳过 patch validation / reranking，每次直接取第一份补丁。这样最终差异更接近“输入上下文粒度 → 首个补丁质量”，而不会被定位准确率或后验候选选择冲淡。

附录给出了共同提示模板。模型始终看到相同的 GitHub issue 文本和一种粒度生成的 `{content}`，然后必须只输出 SEARCH/REPLACE 块。模型服务配置还公开了 262,144 的最大上下文长度、bfloat16、prefix caching 等信息。不过论文没有在主文或模型配置表中完整报告采样温度、top-p、随机种子、每题实际 token 长度及硬件；十次运行为何产生波动因此不能完全复现和解释。

### 3. 指标：最后有没有真的修好

每次运行记录三件事：是否完成、是否解决、是否未解决。`Resolved Rate` 以全部 50 题为分母，而不是只在成功完成的题上计算；每种粒度汇报 10 次 trial 的均值与标准差。这个选择把格式错误、超时等执行失败也纳入系统效果，符合实际修复管线的视角。

## 结果一：函数级平均最好，但优势很小

Table 1 是整篇的主证据：

| Oracle 上下文 | 平均解决数 / 50 | 平均完成数 / 50 | 平均解决率 | 10 次 trial 的标准差 |
|---|---:|---:|---:|---:|
| 行级 | 21.8 | 48.6 | 43.6% | 2.6 |
| 函数级 | **22.8** | **50.0** | **45.6%** | **1.5** |
| 文件级 | 21.3 | 48.8 | 42.6% | 1.6 |

固定模型与修复提示后，函数级比行级高 2.0 个百分点，比文件级高 3.0 个百分点，约等于每 50 题平均多修 1.0 和 1.5 题。Friedman 检验报告为 `χ² = 12.8, p = 0.0017`，说明十次 trial 中三种条件的排序差异不像纯随机波动。

图 3 的箱线图补充了分布信息：函数级的中位数最高，箱体也最窄；行级箱体和须更分散；文件级集中但整体偏低。它支持“在这套设置下函数级平均更稳”，却不说明函数级对每个具体 issue 都最好。

论文文本有一处值得指出的自相矛盾：Table 1 清楚列出函数级标准差 1.5 最小、文件级 1.6 次之、行级 2.6 最大；结果段前一句也说函数级最小，紧接着却写“line-level yields the lowest standard deviation”。结论段又恢复为“line-level greatest variation”。结合表和图，应把中间那句视为笔误，而不能照抄。

更重要的是，最高的 45.6% 仍不到一半。即使模型已被告知真实修改位置，仍有约 27.2/50 题没有解决。这是论文最有分量的负面结果：**定位正确不是修复成功的充分条件**。剩余瓶颈可能在规格理解、跨位置推理、补丁生成、测试约束、提示格式或模型能力。

## 结果二：不存在对所有难度都占优的固定粒度

作者又按照 SWE-bench Verified 元数据中的人工解决时间，把任务分为 `<15 分钟`、`15 分钟–1 小时`、`1–4 小时` 和 `>4 小时` 四档。图 4 的纵轴是每档平均解决率，横轴是三种粒度。

读图时能看到，三组柱子的排序会随难度改变：函数级在总体均值上领先，却没有在每一档都稳定领先；某些档位文件级或行级更好。这一异质性才是比“45.6% 第一”更值得带走的结论：粒度效应可能由任务结构调节，固定一种粒度只是总体折中。

但这张图只能生成假设，不能证明“难度导致最优粒度变化”。原因有三：每档样本很少；难度由人工解决时间代理，可能同时混入仓库熟悉度、issue 文档质量和补丁规模；论文没有报告分层样本量、置信区间或粒度×难度的交互检验。因而更稳妥的表述是：**观察到任务级异质性迹象，值得预注册并在更大样本上验证自适应粒度策略。**

## 证据审查：作者证明了什么，又没有证明什么

### 能支持的结论

1. 在 SWE-bench Mini 这 50 个 Python issue、Qwen3-Coder-30B-A3B、该 Agentless SEARCH/REPLACE 提示和首补丁评测下，改变 oracle 上下文的呈现粒度会改变平均修复率。
2. 三个候选中，函数/方法/类级的总体均值最高、trial 间方差最小。
3. 完美知道开发者修改位置仍远不足以保证修复成功，说明定位与修复之间的 handoff contract 值得单独评测。

### 不能外推的结论

1. **不能说函数级是普遍最佳粒度。** 只有两仓库、50 题、一个模型和一个 prompt；分层结果还暗示任务依赖。
2. **不能说效果来自“函数语义”本身。** 三种条件同时改变代码量、边界完整性、排版与噪声；论文没有做 token 匹配或信息量匹配。
3. **不能说函数级提升来自模型训练粒度。** 作者提出 Qwen3-Coder 可能偏好训练时常见的函数/类单元，但没有训练数据消融或跨模型交互实验，这是解释性假设。
4. **不能说 ground-truth patch 给出了完整相关上下文。** 它只给出最终被改的位置；未改但必要的证据可能被遗漏。
5. **不能估计一个稳定的任务级因果效应。** 论文以 trial 聚合均值做 Friedman 检验，没有给出同一 issue 三条件的配对成败转移表、效应置信区间、多重比较或随机效应模型。

另外，函数级实现把函数、方法、类视为同一档。一个小函数和一个上千行类的 token 成本可能相差悬殊；行级还额外扩 10 行，文件级则完全受文件长度支配。因此“粒度”在这里实际上是一个捆绑处理：语义边界、上下文长度和噪声一起变化。论文诚实地把工作称为 preliminary proof of concept，这个定位是合适的。

## 对当前研究的深入启发

### 1. 先把“GT 是什么”与“怎样交给模型”分成两个变量

当前已经确认 GT 应按语义对象裁定，允许 `scanner.py::_unsafe_globals` 这类有界非函数节点。本文提醒我们，GT 身份和呈现粒度不能混为一谈：同一个 GT 对象可以以精确节点、带父级语境的节点、整文件三种方式交付。后续协议应记录两列：

- `gold_semantic_object`：真正要找的对象，允许函数、类、模块级字典等混合类型；
- `presentation_envelope`：实际给模型看的范围，例如对象本体、父级上下文、文件。

这样既不会为了适配“函数级评测”改写 GT，也能研究不同 envelope 的效应。

### 2. 把当前实验扩成二阶段 handoff 设计

论文的 clean intervention 可以直接迁移成两个阶段：

1. **Oracle-handoff 上限实验**：固定审定 GT 和同一 reviewer/repairer，只改变对象本体、对象+必要 Core、整文件等呈现方式，先验证哪种格式在无定位误差时可用。
2. **真实定位实验**：再接 Qwen/DeepSeek/EvidenceLoc 产生的预测节点，比较定位误差与呈现方式是否交互。

第一阶段回答“即使给对了，怎么交才有效”；第二阶段回答“现实中能否找对并保持效果”。这比直接比较五个端到端系统更容易解释。

### 3. 不应只报平均 F1 或平均修复率，要保留配对转移

对每个 case，至少记录 `对象本体成功/加 Core 成功/加 P 成功/加 I 成功` 的布尔向量，并报告：

- 从失败变成功的 rescue 数；
- 从成功变失败的 harm 数；
- 始终成功和始终失败；
- 置信区间及按 GT 类型、长度、语言、难度的异质性。

当前的 14 个 U、两个边界 P 和模块级非函数对象不应被平均数吞掉。它们很可能正是粒度效应发生变化的机制层子群。

### 4. 做预算匹配，才能把“信息”与“长度”分开

论文没有控制三组 token 数，这正是当前 P/I 干预可以超越它的地方。对 `Core + P` 与 `Core + I` 做同期、等 token、等节点数或等结构距离匹配；若非函数 GT 的本体很短，可分别比较：

- GT 本体；
- GT 本体 + 直接绑定/读取点；
- 同预算真实 P；
- 同预算审定 I。

只有这样，`P` 的增益或 `I` 的伤害才不容易被“只是多给了代码”解释掉。

### 5. 稳定确认必须先于干扰实验

本文每个条件跑 10 次，但它按粒度汇总；当前研究更需要先在 case 内确认固定 Core 的稳定基线。对候选成功例，至少用同一请求重复并要求多数次精确集合正确，再进入 P/I 配对。否则一次偶然成功后的下降会产生回归均值偏差，误报干扰效应。

## 最终判断

这篇论文最值得保留的不是“函数级 45.6%”这个孤立数字，而是一条实验原则：**先用 oracle 消除定位误差，再检验下游究竟需要什么形式的上下文。** 它用简单设计证明了呈现粒度并非无关紧要，也用低于 50% 的最高修复率提醒我们，找对位置和完成修复之间还有巨大鸿沟。

对当前课题，正确迁移不是把所有 GT 强行函数化，而是把“语义对象真值”“呈现 envelope”“P/I 内容类型”“下游成功”拆开，做配对、预算匹配且可复现的干预。模块级字典不是例外噪声，反而是检验这种更一般协议是否站得住的关键样本。
