## 报错说的是入口，真正要改的代码可能在远处

用户说“个人资料页面有 XSS 漏洞”，搜索结果很容易把个人资料页面找出来。但需要修改的可能是另一个目录里的共享校验函数。问题描述提供了一个入口，真正的修复位置却藏在调用、继承和导入关系后面。

把整个仓库放进模型窗口不现实；只做一次语义检索，又可能停在最像题面的函数。LocAgent 的办法很具体：先给仓库做一张有类型的导航图，再让模型用三种工具找名字、沿关系走、读取正文。模型不用自己从一堆路径猜依赖，也不必每次把整张图和全部源码读一遍。

图 1 用 Django 的四种维护请求说明定位的范围：媒体合并警告对应 `Media.merge`，支持新的重定向状态码涉及响应类，安全问题涉及 CSRF 中间件，性能优化涉及权限创建函数。共同目标都是找到“哪里需要修改”，而非仅检索一段主题相似的代码。

## 一次定位怎样跑：先确定“是什么”，再追“连着谁”

下面用一个教学示例串起来，非论文实际实验：题面说上传头像时某类输入绕过验证。仓库里有 `views.py:upload_avatar`、`validators.py:ImageValidator.validate` 和 `utils.py:decode_image`。

一次词面搜索可能先找到 `upload_avatar`。如果 Agent 能看到它调用了 `ImageValidator.validate`，就能继续检查验证入口；再读函数正文，才有机会判断具体哪条分支跳过校验。图负责缩小要去的地方，源码负责核实行为。

### 1. 先把仓库转成四类节点、四类边

LocAgent 解析 Python 源码的抽象语法树（Abstract Syntax Tree，AST），识别目录、文件、类、函数四类节点，函数是最细粒度。每个节点有稳定实体 ID，例如 `src/utils.py:MathUtils.calculate_sum`。

图中四类关系各有分工：

- `contain`：目录包含文件、文件包含类、类包含方法，保留仓库层次。
- `import`：指向被导入的代码实体，跨越文件边界。
- `invoke`：函数或类之间的调用；调用类可以表示实例化。
- `inherit`：类的继承关系，让模型能沿实现与父类追踪。

图 2 把这四层关系叠在同一仓库上。只有目录树时，两个远目录的模块看起来相隔很远；加入调用或继承边后，它们可能一步可达。图 1 的现实问题与图 2 的结构表示之间，正是通过这种“跨目录但在程序行为上相关”的联系搭桥。

表 1 比较了 CodexGraph、RepoUnderstander、RepoGraph、OrcaLoca 的节点、关系和检索方式。这里应抓住设计差异：LocAgent 统一了目录层次和三种依赖关系，并用有限种工具暴露给模型。拥有更多边只是能力范围，是否有用仍需消融验证。

### 2. 搜索也分层，精确名字优先

系统依次尝试四层索引：完整实体 ID、实体名字、实体 ID 上的 BM25、源码内容上的 BM25。BM25 是依据词项匹配及文档长度评分的稀疏检索方法。

如果题面准确写出 `MathUtils.calculate_sum`，不必再让语义模型猜；如果只写出一个变量或字符串，最后一层源码索引还能提供入口。这个设计把“精确符号定位”和“模糊线索搜索”放进同一接口，省掉模型反复选择底层搜索命令的负担。

### 3. 三种工具处理三个不同问题

**SearchEntity：这个线索在仓库哪里？** 输入关键词，输出匹配实体。输出量随候选数量和实体长度改变，而非永远返回全文。

图 6 展示三种真实返回：搜索 `ResolverMatch` 找到较小的类，直接给带行号正文；搜索较大的 `Piecewise` 类，展示类和方法骨架；搜索重复出现的 `__repr__`，只列各个完整实体 ID，提示进一步细化查询。匹配数量超过 3 时采用折叠表示，图中把超过 300 行的长内容作为预览情形。这样模型先知道“有哪些”，再决定“读哪个”。

**TraverseGraph：从这里沿什么关系继续找？** 输入起点 ID、方向、跳数、节点类型、关系类型，执行带类型限制的广度优先搜索。一次调用可以完成多跳，也可以只看继承和包含关系。

图 7 的原例从 `django/contrib/auth/validators.py` 出发，双向走两跳：可见该文件包含 `ASCIIUsernameValidator`，后者继承核心校验文件中的 `RegexValidator`；还能看见导入关系、父目录以及引用该文件的迁移文件。返回的树形文本保留完整路径、关系名和反向关系。它告诉模型可去哪里以及为何连在一起，尚未替模型证明哪个节点存在缺陷。

**RetrieveEntity：把这个实体的具体代码给我。** 输入实体 ID，输出完整源码及路径、行号等属性。前两个工具控制候选和视野，这个工具供模型核验条件、数据流和边界行为。教学示例中，沿调用边发现 `validate` 后，必须读它的分支实现，才能确定是否需要修改。

### 4. 模型组织探索，最后合并多次排名

图 8 的提示词先让模型分解题面的描述、错误栈、复现代码和补充信息；然后链接符号，重建从入口到错误的逻辑，最后输出按重要性排序的位置，建议约 5 个文件。它还明确要求区分同名实体，保持逻辑流聚焦问题。

工具均只读，因此定位本身不要求专门运行修复测试的 Docker 环境。支持原生 tool calling 的模型通过工具协议调用；不支持的模型由提示词描述接口，再解析其输出。本地执行工具，把观察写回交互历史，形成图 2 右侧的循环。

默认温度是 1.0，附录说明进行两次交互后按平均倒数排名聚合。直觉是：一个实体如果在多次结果里都靠前，排名应更稳定。比如两个候选都出现两次，排名分别为 1、2 和 4、5，前者的倒数排名均值更大。这是多次预测的一致性分数，不是经过校准的“有缺陷概率”。两次结果聚合也不等于整个 Agent 只有两轮工具动作，成本表里的平均交互轮数另行统计。

## Loc-Bench 怎样把维护工作变成可测对象

作者觉得 SWE-bench 以修 bug 为主，不能代表全部代码定位。表 3 中 SWE-bench Lite 的 300 题含 254 个 bug、43 个功能请求、3 个安全问题、没有性能问题。Loc-Bench 的 560 题则包括 242 个 bug、150 个功能请求、29 个安全问题和 139 个性能问题。

构建流程是：收集 Python 仓库和对应 PR，以 PR 的 base commit 确定修改前版本；保留显式解决关联 issue 的 PR；排除修改超过 5 个 Python 文件或超过 10 个函数的任务，也排除没有函数级修改的 PR。Bug 与功能请求主要来自超过 5000 stars 的项目，安全和性能类由 GitHub 关键词搜索补充。

类别标签使用 GPT-4o 对每题采样三次，不一致时人工复核。参考答案来自真实补丁涉及的原版本文件与函数；文档、注释、import 等修改不作为目标。这使答案可以从开发者已接受修复中提取，但评价对象也收缩到了这些可映射的代码修改。

作者为 bug 类收集 2024 年 10 月以后创建的 issue，以降低与当时模型训练材料重合的风险。这个时间选择是数据构建策略，并不构成对每个模型训练集的实际审计。

### Acc@k 要求找齐，和“命中一个”不同

主要指标是严格 Top-k 准确率：一道题需要修改多个位置时，前 k 个预测必须覆盖所有参考位置才算成功。假设 gold 为 A、B，预测前五个只有 A，这题仍为 0；两者都进前五才为 1。

文件级看文件；函数级看具体函数；较宽松的 module 级允许命中被修改类中的任意函数。附录另报告归一化折损累计增益（Normalized Discounted Cumulative Gain，NDCG），它奖励正确目标在排名中靠前，让部分命中也有区分度。

严格找齐的指标适合衡量交付一组完整候选的能力，但不能从一个 Acc@5 数字推出误报少，也不能直接与文件宏 F1 比大小。

## 实验坐标：先看同模型比较，再看训练与成本

SWE-bench Lite 定位实验保留修改已有函数的 274/300 题。对照包括 BM25、E5、Jina-Code、Codesage、CodeRankEmbed 等一次检索方法，固定分层流程 Agentless，以及 MoatlessTools、SWE-agent、OpenHands 等可探索 Agent。

Agent 对照使用 GPT-4o-2024-0513 或 Claude-3-5-sonnet-20241022；LocAgent 主表使用 Claude 及微调 Qwen2.5-Coder 7B/32B。向量检索基线按函数建立文档，之后映射到其他粒度，未使用付费 proprietary embedding。OpenHands 用当时的 0.12.0、默认 CodeActAgent。

这些比较回答不同问题：同 Claude 比框架，看导航与接口带来的整体差异；微调 Qwen 比 Claude，则同时改变模型和训练，衡量可部署方案；成本分析又包含不同单价。它们需要分开解释。

## 核心结果一：优势在细粒度定位上更清楚

表 4 中，同样用 Claude，关键比较如下。

| 方法 | 文件 Acc@5 | 函数 Acc@10 |
|---|---:|---:|
| Agentless | 79.56% | 58.76% |
| SWE-agent | 90.15% | 64.60% |
| OpenHands | 90.15% | 70.07% |
| LocAgent | **94.16%** | **77.37%** |

相比 OpenHands，文件找齐提高 4.01 个百分点，函数找齐提高 7.30 个百分点。图导航的价值不仅在找到大概文件，还在跨关系进一步落实到具体函数。

一次检索里最强的 CodeRankEmbed 文件 Acc@5 为 84.67%，函数 Acc@10 为 58.76%。它能把候选面铺开，但没有后续交互来追查隐含依赖。Agentless 在增加 k 后较早停滞，也与流程输出的候选有限有关。

表 11 的 NDCG 说明优势并非完全来自塞进更多候选：Claude LocAgent 的文件 NDCG@5 为 87.14，OpenHands 为 84.43；函数 NDCG@10 为 65.57，对方 63.80。差距比严格全覆盖指标小，提示“找齐最后一个目标”和“整体排序更好”是相邻但不同的收益。

### 离题面越远，所有方法都会变难

图 3 把任务按题面提及函数到补丁函数的图距离分组。先用 GPT-4o 抽取题面函数并匹配节点；对每个 gold 函数找最近的题面节点距离，再对 gold 取平均，向下取整分组。没有抽取到有效函数名的任务不进入此分析。

从 0 跳到 3 跳以上，LocAgent 文件找齐率约从接近 100% 降到 80% 左右，函数找齐约从 90% 多降到 50% 多。其它方法也下降，LocAgent 多数区间保持领先。这里的数值是读图近似值，不是表格精确值。

这个分析把直觉变成可观察现象：题面不直接说答案时，导航变得重要。它同时提醒我们，图也没有消除远距离推理困难；而且无明确符号的 CWE-only 题面，可能根本不属于这张图所分析的样本范围。

## 核心结果二：专门训练让小模型更会用工具

作者先收集 Claude 成功定位的轨迹训练 32B，再用微调 32B 生成成功轨迹进行自改进，最后合并轨迹训练 7B。训练采用监督微调（Supervised Fine-Tuning，SFT）与低秩适配（LoRA），学习下一 token，主要传递的是如何探索、调用工具和组织答案，而不是隐层对齐式蒸馏。

图 4 中，原始 7B 在三种粒度上的表现明显较低，训练后文件 Acc@5 达 88.32%、函数 Acc@10 达 71.53%；32B 训练后分别为 92.70%、77.01%，函数指标与 Claude 的 77.37% 接近。大模型轨迹可以把专门的任务操作习惯传给较小模型。

附录给出的训练配置是 SWE-bench train 来源、总计 768 个训练样本、5 epochs、最大长度 128k、学习率 2×10^-4。原文存在一个计数差异：正文为 Claude 433 条加 Qwen 335 条，附录却写 Claude 447 条及其余 Qwen 条，两者总量都指向 768。本次不替作者指定哪份来源配比正确。

### 省的是当时价格下的定位调用费用

表 5 中 Claude LocAgent 平均 7 轮、0.66 美元；微调 32B 为 9 轮、0.09 美元；微调 7B 为 6 轮、0.05 美元。0.66 到 0.09 对应约 86% 降低，这也是摘要的成本结论。

32B 多跑了轮次却更便宜，主要因为采用更低的模型计价。论文按 32B 输入输出各 0.20 美元/百万 token，7B 输入 0.14、输出 0.28 估算；这些是论文的历史价格，不是今天自托管 GPU 的实际支出。

同 Claude 下，OpenHands 平均 13 轮、0.79 美元，LocAgent 7 轮、0.66 美元；MoatlessTools 5 轮、0.46 美元更便宜，但函数找齐更低。真正的选择是准确率、轮次、模型价格和索引维护之间的权衡。

## 三种工具分别贡献什么：表 6 的消融

消融固定为微调 7B。下面看函数 Acc@10，因为它最能体现深层导航的难度。

| 条件 | 函数 Acc@10 |
|---|---:|
| 完整 LocAgent | **71.53%** |
| 不给 TraverseGraph | 66.06% |
| 图只保留 contain | 66.42% |
| 每次只能走 1 跳 | 66.79% |
| 不给 RetrieveEntity | 69.34% |
| 不给 SearchEntity | 53.28% |
| 搜索去掉 BM25 索引 | 60.22% |

最显著的是没有搜索入口：下降 18.25 个百分点。图邻居再丰富，首先也得找到可靠起点。去掉 BM25 下降 11.31 点，则表明大量题面线索并非完全匹配实体名。

去掉遍历下降 5.47 点；只保留包含边和限制一次一跳都没有恢复完整性能，支持依赖关系和多跳工具的实用价值。禁止多跳仍允许多次调用，因此结果更接近“接口一次能走多远”的效果，不能等同于证明单跳路径永远无法到达目标。

去掉完整实体读取只下降 2.19 点，原因之一是 SearchEntity 自身也可能返回源码，所以这个消融并没有把正文信息全部移除。它衡量专用精读工具的额外贡献。

## 图怎样写成文字，也会影响模型

附录 A.1.2 比较同一类子图的不同文本表示：邻接行、带属性的邻接行、整数节点编号、Graphviz DOT、JSON 树、带完整实体名的缩进树。实验使用 Claude 和一组困难任务。

表 9 的三个重要比较：

- 邻接行加入所有节点属性后，文件 Acc@5 从 70.59% 降到 64.71%，函数 Acc@10 从 38.24% 降到 32.35%。更多内容可能增加负担。
- 缩进树的文件 Acc@3 为 79.41%，优于邻接行 67.65%；函数 Acc@10 为 41.18%，也高于 38.24%。保留层次和实体身份有用。
- 它没有每项都赢：DOT 的文件 Acc@5 为 82.35%，高于缩进树 79.41%；JSON 的 module Acc@10 为 70.59%，高于缩进树 64.71%；函数 Acc@10 两种树都为 41.18%。

所以这组证据支持“表示方式值得设计”，没有产生一种跨指标统治的格式。还有一个需保留的报告问题：正文称 37 个困难样本，表中多项百分比却与 34 题的整数步长吻合，缺失或过滤分母没有进一步说明。

## 换到 Loc-Bench，跨任务优势还剩多少

表 7 在 560 题上改用更大的候选上限，文件看 Top-5/10，函数和 module 看 Top-10/15。

| 方法 | 文件 Acc@5 | 函数 Acc@15 |
|---|---:|---:|
| CodeRankEmbed | 74.29% | 46.61% |
| Agentless＋Claude | 67.50% | 42.68% |
| SWE-agent＋Claude | 77.68% | 51.96% |
| OpenHands＋Claude | 79.82% | 59.29% |
| LocAgent＋7B(ft) | 78.57% | 51.79% |
| LocAgent＋Claude | **83.39%** | **60.71%** |

LocAgent＋Claude 仍领先，但函数相对 OpenHands 只高 1.42 个百分点，远小于 SWE-bench Lite 的差距。7B 对 SWE-agent 保持接近，却明显落后于 OpenHands 的函数结果。概括为“小模型全面媲美大模型”会丢掉这些条件。

图 5 再按类别拆开：Claude LocAgent 的 bug 文件找齐约 91%、函数约 77%；性能类约降到 70% 和 38%。安全类函数结果约为 60%，但只有 29 题。以上为读图近似值。性能任务的目标可能需要理解资源与时序，bug 训练分布也可能偏置系统；后者是作者提出的合理解释，并未由训练分布干预单独验证。

这篇没有提供系统化的失败类型标注或逐例错误轨迹。它的负面证据主要来自高跳数衰减、任务类别差异和不同格式的反向结果，不能补写成作者已证明的失败机制。

## 定位更准以后，真的修得更好吗

表 8 保持 Agentless 的编辑方法和 Claude 编辑模型，只改变上游定位。结果如下。

| 定位来源 | Pass@1 | Pass@10 |
|---|---:|---:|
| Agentless＋Claude | 26.31% | 33.58% |
| LocAgent＋32B(ft) | 26.79% | 36.13% |
| LocAgent＋Claude | **27.92%** | **37.59%** |

Pass@1 看单次候选，Pass@10 看十次尝试中是否至少有一次成功。Claude 定位替换使 Pass@1 增加 1.61 个百分点，Pass@10 增加 4.01 个百分点。摘要的“12%”是 4.01/33.58 约 11.94% 的相对提升，不能写成提高 12 个百分点。

这个结果说明定位改善能传导到修复，但传导会被编辑能力等下游环节限制。相比函数定位的明显增长，单次修复增长更小；准备好更完整的位置后，多次编辑尝试更有机会利用它。

表 8 的 Agentless Acc@5 是 58.39%，与表 4 同类行的 58.76% 不完全一致，原文没有解释差别。报告下游实验时直接使用该表的修复分母与结果，不把两表定位差拼接成新的精确推导。

## 把贡献和边界放在一起看

最扎实的贡献有三点。第一，异构图、分层稀疏索引和三种接口构成了完整可执行的定位方案，同模型比较显示了更高的全目标覆盖。第二，成功轨迹监督能显著提升小模型操作能力，在论文价格假设下提供便宜的定位方案。第三，定位提升在固定编辑后端中转化为修复收益，且新基准扩展到功能、安全和性能任务。

证据解释仍有几处重要边界：

1. **图邻居不等于真正的因果证据。** 图表达静态关系。动态派发、运行时条件与实际漏洞机制仍靠后续读代码判断；文中没有把图边验证为漏洞因果链。
2. **框架效果和纯内容效果不同。** 工具消融同时改变可用操作、返回内容与交互过程，格式消融也未给严格等 token 对照。表 9 的属性增多伤害不能直接等同于 P 比 I 更有害。
3. **gold 是补丁位置。** 另一个合法修复可能改别处；无函数改动、超大修改、import 或文档修改被排除。参考目标的可度量性与维护任务的广泛性存在取舍。
4. **预算与统计尚不完整。** 论文未给统一等 token 的所有方法对照、重复整轮实验的置信区间，成功轨迹训练也混合了教师和自生成数据。小数点后两位并不代表这么精细的可靠差异。
5. **跨语言和安全外推有限。** 主实验是 Python，安全类 29 题；AST 支持别的语言不等于语义依赖抽取和工具表现已被验证。训练路径也只深入检查了 Qwen 与 LoRA。
6. **报告中的几处不一致保留原貌。** 训练来源计数、困难集分母、两表 Agentless 数值存在差异；不据这些局部问题抹去主结果，也不替作者猜答案。

## 读完应该真正记住什么

- 先找符号入口，再按结构扩展，再按需读正文，是三个不同的信息操作。
- 图的价值在把远目录中的依赖变成可操作的邻居；关系本身仍需源码验证。
- 该系统中稀疏搜索入口的消融损失，比单独去掉图遍历更大。
- 折叠、骨架和全文是不同可见性状态。发现实体不能直接记作已经阅读其全部代码。
- 专门训练可以让较小模型接近大模型定位表现；成本结论同时依赖模型价格。
- 更高的定位覆盖有助于修复，但定位指标的增量不会原封不动变成 Pass@1 的增量。

## 对当前研究最直接的启发

最新研究记录把瓶颈拆成“没有曝光到目标”和“已曝光却没选对”，并观察到一次性筛选可能误删关键证据。这篇给出的第一项直接帮助是把曝光再细分：`fold` 只给身份，`preview` 给骨架，`full` 才给正文。统计自然带入的 C/P/I 时，应以实际成功请求中可见的源码范围为依据，不能把图邻居或返回 ID 一并记成已读代码。

第二，LocAgent 已有**可恢复的结构压缩**：广搜时折叠，必要时调用 RetrieveEntity 回读。未来若提出“压缩待定证据、按需恢复”，创新不能只停在这一机制。更有价值的问题是如何根据竞争性漏洞解释决定回读谁，以及回读之后能否减少误删与误判。

第三，完整探索 Agent 与固定曝光后的筛选头应分别报告。若先保留同一份真实曝光，再比较 direct 和 filtered 裁决，回答的是下游筛选作用；若运行整个 LocAgent，图搜索、两次排名聚合、模型与停止策略都参与结果。两者的成本分母也不同。

第四，可以从原文学习一个小而清楚的诊断：分别记录目标进入候选、以全文被看见、被筛选保留、最终被选中四个事件。这样失败时能说清丢失发生在哪一层。这个记录方案是由本文和当前实验共同引出的建议，尚不是本文已完成的因果实验。

最后，表 9 是值得借鉴的机制先例：同一批关系，带全部属性有时反而更差。但若要解释当前 P 特异干扰，仍需维持自己的语义类别、实际剂量、位置与源码表示控制。LocAgent 为结构导航和可恢复阅读提供了现实框架，真正待回答的是这个框架中哪些似是而非的证据会改变最终判断。
