# SWE-Search：不是让 Agent 多想几遍，而是让它能回到错误发生之前

> Antonis Antoniades、Albert Örwall 等，**SWE-Search: Enhancing Software Agents with Monte Carlo Tree Search and Iterative Refinement**，ICLR 2025。精读日期：2026-11-16。
>
> 核心问题：一次探索走错以后，继续沿原路反思，未必能找回正确方向。能否保存分支，用阶段合适的反馈重新分配探索预算，再从多个候选中挑出真正有效的结果？

阅读版本为 [arXiv v6，2025-04-02，完整31页PDF](https://arxiv.org/pdf/2410.20285v6)，包含正文、图1–8、表1–4及附录A–L；[HTML全文](https://arxiv.org/html/2410.20285v6)、[作者代码](https://github.com/aorwall/moatless-tree-search)、[交互轨迹演示](https://streamlit.moatless.ai)。

本文是一份重新组织的中文教学笔记，不是原文逐段翻译。原论文由 Antoniades、Örwall 等以 **CC BY-SA 4.0** 发布；本笔记对原文的改写与分析亦以 [CC BY-SA 4.0](https://creativecommons.org/licenses/by-sa/4.0/) 提供，作者不为本笔记中的评论背书。

## 1. 从一个开发者熟悉的失败开始

设想你让 Agent 修复一个仓库问题。它搜到了一个看起来很像的函数，做了修改，然后测试失败。接下来，它连续微调同一个位置，甚至为了让测试通过而修改错误的测试。每一步都附有解释，整条路径却没有更接近真正的问题。

继续给它更多 token，只会让错误路线走得更远。真正需要的是三种能力：

1. **保留另一个选择**：回到尚未修改错误位置的状态，换一种搜索或解释。
2. **判断这一步的作用**：搜索阶段先找到必要定义就是进展，不能因为还没有补丁就判无效。
3. **分开生成与选择**：生成过正确补丁不等于最后提交的就是它。

SWE-Search 围绕这三个问题设计系统。它不是通过训练让模型永久学会新技能，而是在一次任务的推理过程中，利用树搜索和反馈改进后续动作。

## 3. 整个系统是什么样的？

图1可以用一条循环理解：

**选择一个已有状态 → 恢复它的代码和上下文 → Action Agent 做一步 → Value Agent 评价这一步 → 更新搜索树 → 必要时回到父节点换一个动作。**

任务结束后，再由 Discriminator 从候选补丁中选择最终输出。

这里实际有四个部件，而不是“几个模型自由聊天”：

| 部件 | 看什么 | 做什么 |
|---|---|---|
| Action Agent | 问题、当前文件上下文、历史及反馈 | 搜索、请求更多代码、规划、编辑、测试、结束 |
| Value Agent | 当前动作及其上下文、轨迹、代码变化、测试 | 给数值分数和自然语言原因 |
| 搜索算法 | 分数、访问次数、深度等 | 决定下一笔预算花在哪个节点 |
| Discriminator | 问题与多个候选补丁 | 比较候选并选最终答案 |

这些角色并不天然意味着不同底座模型，也不意味着意见统计独立。搜索算法本身是程序逻辑，不需要再让一个“管理者模型”决定每次调度。

### 3.1 状态不只是聊天记录

Moatless 把文件拆成 span，例如导入区、类、函数，并用 span ID 标识。模型每次看到有限的文件片段，可以继续请求其他片段。于是，一个状态至少关联：

- 当前可见的文件与 span；
- 已执行的动作和轨迹信息；
- 当前代码版本，以及相对初始版本的补丁；
- 已获得的测试结果。

每次代码修改保存到 Git，状态引用对应提交。切回旧节点时，恢复当时的代码和上下文，而不是只在提示词里说“假装回到过去”。这也是树搜索能有实际意义的基础：两个分支不能偷偷共用一份已经被另一分支改坏的工作目录。

附录B说明，测试在 SWE-bench Docker 环境运行；批量实验通过 Kubernetes pod 承载，每次重置后应用当前补丁。模型能够运行项目测试，但**不知道评测器指定的隐藏 FAIL_TO_PASS / PASS_TO_PASS 清单**。

### 3.2 为什么先改 Moatless 状态机？

原始 v0.0.2 大体按搜索、识别、规划、编辑推进，虽有部分回返路径，但转移结构受限。作者扩展后，规划阶段可以重新进入其他行动阶段，也能增加和执行测试。

然而，“工具更多、转换更自由”不自动带来好规划。GPT-4o 从原始 Moatless 的24.3%到 Moatless-Adapted 的25.7%，只增加1.4个百分点。作者随后加入搜索系统，才达到31.0%。这是支持搜索有用的一条观察，但并非把所有组件完全分开的因果消融。

## 4. Value Agent：分数负责调度，解释负责下一步

Value Agent 不只是回答“好/不好”。它同时返回：

- 一个约在 −100 至100之间的数值；
- 一段说明哪里有进展、哪里仍缺证据、下一步应该改什么的解释。

分数用来选节点；解释则可以送回父节点，让新的动作吸取已有子分支的教训。论文称其为 hindsight feedback。所谓“事后反馈”是已经执行过的子动作产生的反馈，不是读取未来金标准答案。

### 4.1 搜索动作不能按最终补丁的标准评分

图4a给了很具体的例子。Agent 请求查看 `QuerySet._batched_insert`，目的是理解带冲突更新的 `bulk_create` 如何实现 RETURNING。

通用评价器觉得“没有实质代码修改”，给0分；面向请求上下文的评价器认识到这是必要且明确的查证，给75分。

这个例子讲清了设计重点：**中间动作的价值，在于它消除了什么不确定性，而不只在于它有没有立即产出最终答案。**

附录G进一步按行为写提示词：

- 搜索：查询条件是否合适，结果和识别出的代码是否相关，有无明显遗漏。
- 请求上下文：是否必要、具体、范围恰当，是否可能补齐缺失信息。
- 规划与修改：改动是否正确、是否无意影响其他代码，测试结果和历史是否支持它。
- 宣称完成：补丁是否真正覆盖问题，是否补充必要测试，是否过早结束。
- 各阶段都注意重复动作：反复执行但没有新信息，应降低评价。

这些是启发式语言评价，不是经过校准的成功概率。75分不等于75%的成功率。

### 4.2 一条轨迹如何被救回来？

图2展示 `sympy__sympy-15678` 上的 Qwen2.5-72B 轨迹。初次修改后，Agent 因已有测试通过而倾向结束；评价反馈指出测试覆盖仍不足。重新展开相关节点后，Agent 增加测试，看到失败，再继续修复。

值得学的是“先通过了哪些测试”与“是否真正覆盖目标问题”的区别。评价器可以促使补充验证，但它也可能误判；图2是一例机制展示，不是所有实例都能自救的比例统计。

## 5. 搜索算法：好路线继续走，其他路线也留机会

普通贪心流程每一步只保留一个选择。树搜索让一个节点有多个后继，并比较继续深挖与另开路线哪个更划算。

论文使用修改后的 UCT 型打分，可概括为：

`价值估计 + C × √(ln 父节点访问数 / 当前选择访问数) + 浅层奖励 − 深度惩罚`

论文的深度项写作 `α exp(−β(d−1)) − γ√d`。第一项偏向当前看好的行动；第二项给较少尝试的选择机会；后面的启发式项避免过早钻入过深分支。实际还配有高价值叶节点等规则，不能把它当成不加修改的教科书 MCTS。

一次扩展的大致过程是：取分高且可继续扩展的节点，恢复状态，让行动模型生成新动作，执行并评价，再更新相关统计。连续低价值或反复无进展的分支可以终止。

正文实验设置是最多100次搜索迭代、每节点最多3次展开；附录表2列的实现默认值却是每节点5次展开、最大深度20。**复现时必须区分正文实验配置与代码类的默认配置**，不能随手拿默认值声称复现同一预算。

图6的 Django10914案例尤其直观：基线在错误测试和编辑之间不断循环，最后终止；搜索版本识别到某条低收益路径，终止该分支，再从其他分支到达完成节点。它说明“保存可回退状态”比仅延长原路径多了一种补救能力。

## 6. 最后一个问题：正确答案生成过，为什么还会交错？

搜索产生的候选里，可能有一个正确补丁，也可能一个都没有。最高平均轨迹分数不一定对应最好补丁，所以作者增加最终 Discriminator。

实现使用5个评价 Agent、3轮讨论，温度1.0；行动与价值模型温度均为0.2。讨论输入是问题与候选补丁，输出补丁ID及理由，最后再汇总选择。附录L给出了比较与总结提示词。

要分清两个指标：

- **候选覆盖**：多个候选里至少一个通过评测，论文用 Pass@5 表达。
- **最终选择**：系统最后选中的一个是否通过，论文用 Pass@1 表达。

Pass@5 接近“如果知道哪个正确，最多能拿到多少”；现实部署没有这个金标准选择器。不能用它替代最终提交效果。

## 7. 主实验：究竟赢了哪个基线？

任务是 SWE-bench Lite 的300个真实仓库 issue，输出代码补丁，用测试判断是否解决。五个模型使用一致提示词。关键基线是 **Moatless-Adapted**，即有适配行动能力、但没有完整树搜索系统的版本，不是 GraphLocator，更不是三模型上的 C 筛选基线。

表1的数据如下，单位为解决率百分比：

| 模型 | Moatless-Adapted | SWE-Search | 增加百分点 |
|---|---:|---:|---:|
| GPT-4o | 25.7 | 31.0 | 5.3 |
| GPT-4o-mini | 13.0 | 17.0 | 4.0 |
| Qwen2.5-72B-Instruct | 18.0 | 24.7 | 6.7 |
| DeepSeek-V2.5 | 16.3 | 21.0 | 4.7 |
| Llama3.1-70B-Instruct | 13.6 | 17.7 | 4.1 |

五组都提高，但这回答的是“完整搜索系统对比一次基线运行”，还不是同成本胜出。

还有一个容易漏掉的算术问题：摘要说平均相对提升23%，表中增幅约17%、24%、27%、22%、23%。这些值更接近用**新方法成绩作分母**，而不是通常的基线作分母。例如 `(31−25.7)/31≈17.1%`，但常规基线相对提升是 `(31−25.7)/25.7≈20.6%`。本笔记优先报告百分点，避免沿用含混的“提升23%”。

## 8. 加算力以后，收益还剩多少？

### 8.1 图4b：更多迭代能找到更多解

横轴是搜索迭代/转移数量，纵轴是已解决 issue 数。五个模型总体随搜索增加而找到更多解。这支持“初次失败不等于搜索空间没有解”。

但图中累计曲线并不是在每个相同 token 预算下独立重跑所有算法得到的公平前沿。迭代数、模型调用数、输入长度、美元成本不能互相替代。

### 8.2 表3：成本不是小幅增加

| 模型 | 基线API成本（美元） | SWE-Search（美元） | 约数倍 |
|---|---:|---:|---:|
| GPT-4o | 40.86 | 576.00 | 14.1 |
| GPT-4o-mini | 9.90 | 52.34 | 5.3 |
| Qwen2.5-72B | 8.50 | 42.50 | 5.0 |
| DeepSeek V2.5 | 3.66 | 18.37 | 5.0 |
| Llama3.1-70B | 9.00 | 45.00 | 5.0 |

这是附录表3的成本口径，不是每道题单价；Qwen与Llama还是按可比API价格估算。历史价格也不能当作现在价格。

因此，主实验5个左右百分点的增益，需要与5倍乃至14倍调用成本一起看。

### 8.3 表4：让基线也试五次

附录J给了更重要的补充：搜索一次产生5个答案，对比基线独立运行5次产生5个答案。

| 模型 | 搜索最终Pass@1 | 搜索候选Pass@5 | 基线五次Pass@5 |
|---|---:|---:|---:|
| GPT-4o | 31.0 | 34.0 | 未做 |
| GPT-4o-mini | 17.0 | 22.3 | 17.0 |
| Qwen2.5-72B | 24.7 | 25.7 | 22.3 |
| DeepSeek V2.5 | 21.0 | 23.3 | 22.0 |
| Llama3.1-70B | 17.7 | 22.3 | 21.7 |

给基线更多尝试后，候选覆盖差距明显缩小，DeepSeek只多1.3个百分点，Llama只多0.6。GPT-4o这一对照因API成本过高没有做。

这里仍不是逐例严格等 token 对照。作者按候选数和运行次数近似匹配计算量，但搜索包含额外评价与讨论，且各运行长度不同。我们可以说“比只跑一次更公平”，不宜说“已经完全排除算力因素”。

此外，图3把 Llama Pass@1 写成21.0%，与表1和表4的17.7%不一致。本笔记采用两张表一致的17.7%，保留这一版本内冲突，不自行替作者修数据。

## 9. 图5、图7、图8：总分之外的三件事

### 9.1 判断器确实重要，但不是每个模型都受益

图5a只看候选中确实有正确解的情况，比较能不能选出来。作者报告平均轨迹价值选对约73%，Discriminator约84%。这不是整个300例成功率从73%到84%。

图中特别有 GPT-4o-mini 的反例：讨论式选择不如平均价值选择。DeepSeek两者差距最小。说明额外讨论不应被视为必然增益，它可能引入新的判断错误。

### 9.2 各模型成功的题目并不重合

图5b的集合图显示，其他模型合起来有33个 GPT-4o 未解决的实例；各模型都存在自己独有的成功案例。附录图7按 Django、matplotlib、pytest、sympy、scikit-learn 展开，也能看到不同成功分布。

这提示多样性可能值得利用，但论文没有给出一个零成本的路由器：事先不知道应把哪道题分给哪个模型，汇总成功集合只能说明潜在上限。

### 9.3 价值分数有区分能力，不等于可靠的置信度

附录图8是正式系统之前的探索，比较最终成功/失败轨迹的平均状态分数及标准差，大体成功轨迹分数更高。这里用的是 Llama3-8B、Qwen2系列、GPT-4o、DeepSeek-Coder33B等，**不是主表全部五个模型的同一配置**。

原图说明还留有一个未完成的例外描述，因此不替作者补全哪个模型例外。它提供了采用价值函数的动机，但不是一个经过独立验证的校准实验；平均可分离，也不保证每个关键分叉都判断正确。

## 10. 这篇论文证明到哪一步？

最有价值的部分是把“允许回退”“给阶段匹配的反馈”“生成后再选择”做成可运行系统，并展示了普通顺序轨迹的具体失败方式。附录不只堆提示词，还交代了代码状态恢复与测试环境，方便理解工程代价。

证据最扎实的是：在这个版本的 SWE-bench Lite 上，完整系统相对一次 Moatless-Adapted运行，五个模型都有提高。

还没被充分拆开的部分是：

- 树搜索、反馈文字、数值打分、状态专用提示、最后讨论分别贡献多少；
- 对比等 token 的简单重试，是否仍有稳定收益；
- 不同随机运行是否稳定，接近0.6–1.3个百分点的差距是否可靠；
- 没有可执行测试、只有静态代码和漏洞类别的任务，反馈是否仍有效；
- 高分错误分支会不会持续占预算，低分但必要的查证会不会被提前终止。

论文讨论了安全等高价值应用，但没有直接完成我们漏洞裁决任务的实证。不能把修复成功率直接外推为漏洞判定准确率。

## 11. 对 SeerAgent，我会借什么，不借什么？

选题前已同步 GitHub master 的 `documents/研究记录.md`。该远端记录末尾仍是11月10日的文件级V2试验，涉及证据未曝光、读到却未选中、相似机制竞争和重复探索。它不是之后所有 WSL 实验的最新状态。下面是据此提出的研究建议，不替代当前实验报告。

### 11.1 先把两类实验分开

**固定上下文上的筛选实验**：五种来源收集的上下文保持不变，比较直接裁决与按既定 C/P/I 规则筛选后裁决。它问的是“已有证据如何被利用”。

**自主探索实验**：Agent 自己决定下一步读什么、何时停止、如何回退。它问的是“能否主动补齐裁决缺失的证据”。

SWE-Search 主要启发第二类。它不能替第一类证明 C 筛选有用。集成 GraphLocator 时，也应先固定其输出，再比较直接裁决与筛选后裁决；否则换检索又换判断，故事会混在一起。

### 11.2 比“再加一个 reviewer”更具体的改进

我更愿意先试一个小的**证据缺口驱动回访**：

1. 裁决前列出尚未核实、且可能改变判断的事实，例如输入是否经过特定校验。
2. 为每个缺口指定最小的查证动作，而不是笼统要求继续搜索。
3. 执行后记录新增了什么证据、排除了什么假设。
4. 若没有新增信息，停止重复该路径；若发现反证，回到相关选择点重新选证据。
5. 最后区分“没有漏洞证据”与“缺少裁决所需证据”，不要用格式完整掩盖查证失败。

这借鉴的是状态专用反馈与回访能力，而不是照搬100步树搜索、5人3轮讨论。C/P/I标签仍是模型判断，不能当作金标准驱动搜索。

### 11.3 怎样验证它比多花钱更好？

相同实例、相同底座、相同检索工具和总 token 上限，比较：

- 单次原方法；
- 简单独立重试并用相同最终选择器；
- 只加缺口反馈、不回退；
- 缺口反馈加有限回访。

分别报告正确证据是否曾曝光、是否进入最终上下文、最终裁决是否正确，以及格式失败、超时、调用数和token。对每个模型都统计“由错变对”和“由对变错”，不要只报三模型混合平均。

若回访只增加曝光却没有提高最终选择，问题在证据利用；若候选里有正确结论却选错，优先改判断器；若从未接触关键代码，再增加最终反思轮次很难补救。

## 12. 一句话带走

**Agent 的进展，不是它又说了多少解释，而是它新增了什么证据、纠正了哪个选择。**SWE-Search 给出了一种把这种进展组织成搜索的工程方案，也提醒我们：搜索收益必须与简单重试、最终选解能力和实际成本一起评价。
