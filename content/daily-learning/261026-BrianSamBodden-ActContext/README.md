## 先讲一个具体问题：已经知道改哪里，还要不要看周围所有代码？

假设一个 issue 已经被可靠定位到两个函数。编码代理现在要做的事情很明确：读懂这两个函数，改出补丁。此时有三种常见做法：

1. 把涉及的完整文件全部交给代理；
2. 让目标函数保留完整正文，其余类和函数只留签名、docstring 或 UML 式骨架；
3. 只保留真正要编辑的代码，其余部分全部删掉。

直觉上，第二种似乎最好：目标代码有细节，外围骨架又能告诉代理“项目里还有什么”，应该比第三种纯删除更容易理解架构。但这一直混着另一个问题：如果代理最后修好了，是因为它先找对位置，还是因为找到后获得的代码表示更好？

本文把这两件事明确拆开：

- **Find**：找到应该工作的文件、类和函数；
- **Act**：位置已经给定后，理解到足够信息并做出正确修改。

研究者用 oracle 固定 Find：每个实验臂都拿到 gold patch 涉及的相同文件和可编辑位置。随后只改变 Act 阶段的代码表示，并用真实 issue 是否解决来评分。这样实验问的不是“哪种检索器更好”，而是：**定位已经正确时，目标正文之外的结构信息还有没有可测的增量价值？**

这是一篇 2026 年 6 月的单作者 arXiv 预印本，没有正式同行评审 venue，作者也不是以高校课题组身份发表，因此不能把渠道当成质量背书。它值得读主要因为实验纪律，而不是发表标签。

作者 Brian Sam-Bodden 来自独立研发机构 Integrallis。公开资料显示，他长期从事企业软件、Java、Redis、向量检索和应用 AI 工程，曾任 Redis Applied AI Engineer，也是开源开发者和技术作者。Integrallis 当前把研究重点描述为本地可控 AI 基础设施、可执行测量和明确能力边界。本文与这条工程研究线一致：它不训练新模型，也不包装新的复杂 agent，而是构造一个可审计的测量装置，回答“哪些上下文真的转化为修复”。

对当前研究而言，价值尤其直接。最新四十五例 CPI 审计已经发现：P/I/R/E 不只改变参考信息，也改变候选数量、完整正文比例和模型可以选择的对象；同 token 并不意味着同候选空间。本文给出一种更干净的拆分办法：先固定可编辑目标和候选集合，再改变目标外信息的表示；同时逐例证明每个实验臂都能表达 gold edit。它也提醒我们，温度设为 0 仍可能有约 9% 的实例结果翻转，小的 P−I 差异必须先和运行噪声比较。

## 用一个教学例子理解三个实验臂

下面是一个教学示例，不是论文原项目。假设 gold patch 要修改：

- `parser.py::parse_header`
- `limits.py::validate_size`

三个臂都完整呈现这两个目标单元，区别在其余代码：

| 实验臂 | 目标单元 | 同文件其他内容 | 它想回答什么 |
|---|---|---|---|
| `oracle_full` | 完整正文 | 完整文件 | “多看全部代码”是否最有利 |
| `oracle_tier` | 完整正文 | 方法、签名、类骨架等分层表示 | 结构骨架是否保留了有用外围关系 |
| `oracle_keep_drop` | 完整正文 | 直接删除 | 只有编辑点正文是否已经足够 |

三个臂都知道改哪，也都能看到参考补丁需要删除或锚定的原代码。代理不能再自行打开仓库或运行测试，只做一次补丁生成。最终用 SWE-bench 官方 Docker harness 检查 FAIL_TO_PASS 和 PASS_TO_PASS。

如果 tier 明显胜过 keep/drop，说明外围结构在目标正文之外提供了可行动信号；如果二者相同，则这些签名和骨架至少在该单次、oracle 定位协议中没有可测增益。

## 研究地图：论文其实做了两个主实验

论文的证据链分为两层：

1. **行为探针实验**：完整源码、自然语言摘要、签名加 docstring，到底还能回答多少关于代码真实行为的问题？
2. **真实修复实验**：在 70 个多文件 SWE-bench Verified issue 上，完整文件、分层结构和纯 keep/drop 的解决率及成本怎样？

前者测“表示保留了多少可行动语义”；后者测“这些表示是否足以完成真实修复”。两者不能混成一个结论：探针回答得好不保证 issue 能修好，issue 修好也可能来自模型先验而非输入表示。

## 实验一：Find/Act 边界如何测

### 为什么不能从待评分源码里直接编问题

一种很容易做出漂亮结果的方案，是先读某个方法，再根据该方法正文生成问题，最后让模型用同一正文回答。论文附录承认，作者早期的自有代码探针就是这样构造的，完整源码达到 15/15。问题在于，问题本身已围绕源码中明确写出的事实生成，甚至由同一模型自问自判，形成循环。

正式实验改为从独立测试文件生成行为问题：

- 选择 seaborn、pylint、pytest 三个仓库固定提交中的 15 个类；
- 每个类有独立测试文件；
- 从测试中生成 3 个行为探针，共 45 个；
- 回答模型永远看不到测试；
- 允许回答 `UNKNOWN`；
- 由独立模型家族 GPT-4o-mini 判分，同时用 Claude 作第二判断器检查一致性。

两位判断器原始一致率为 94%，Cohen’s kappa 为 0.84。这里的 45 个答案仍聚类在 15 个类内，因此作者还给出按类聚类 bootstrap，避免把同一类的三个问题当成完全独立样本。

### 四种表示怎样比较

每个探针都由同一个 Claude Sonnet 4.6 回答，变化的只有上下文：

| 表示 | 正确数 | 准确率 | 平均 token |
|---|---:|---:|---:|
| 完整源码 | 27/45 | 60.0% | 1,124 |
| Sonnet 4.6 写的摘要 | 4/45 | 8.9% | 165 |
| Qwen2.5-Coder-3B 写的摘要 | 4/45 | 8.9% | 180 |
| 签名 + docstring | 6/45 | 13.3% | 212 |

Figure 1 展示的核心不是“摘要少了多少 token”，而是同一回答模型在完整源码与压缩表示之间的行为知识断层。完整源码的 27 个正确答案中，有 23 个在摘要臂失败；反向为 0，即摘要没有救回任何源码失败项。McNemar 检验为 23 对 0，`p<10^-4`。

更关键的控制是，两种摘要在相同约 180-token 预算下分别由前沿模型和 3B 模型生成，却同为 4/45。作者据此主张：在这一预算和探针上，主要瓶颈是“自然语言摘要这种表示”丢失可执行行为细节，不只是摘要模型太弱。

这仍不能推成“摘要对导航无用”。摘要可能帮助代理决定下一步打开哪个文件；本实验只证明它们难以替代源码完成 Act。论文自己的探索性层级检索也没有胜过 flat retrieval，但样本只有 16 个查询且来自自有代码，作者明确不把它作为主结论。

## 实验二：resolve@cost 测量装置怎样搭建

### 样本不是随意抽一批

作者预先登记规则：使用 SWE-bench Verified 中 gold patch 涉及至少两个文件的全部实例。500 个 Verified 实例中有 71 个满足条件。研究者先在 Docker 环境中运行参考补丁，发现 astropy-8707 的 gold patch 在自己的环境里也失败，于是排除，最终 N=70。

Figure 3 画的就是这条漏斗：500 → 71 个多文件任务 → 70 个通过 gold validation 的任务。因为使用全部符合条件的实例，不存在观察结果后再挑一批容易说明故事的抽样空间。

### 每个臂都必须通过 expressibility gate

“看到了正确文件”不等于“输入足以写出正确补丁”。如果某个压缩臂删掉参考补丁需要修改的行，它失败可能只是任务不可答。

论文为每个实例、每个臂检查：

- gold hunk 要删除的原行是否逐字存在；
- 若是插入，插入锚点是否存在；
- 模块级代码、类属性、装饰器和非 Python gold 文件是否按需保留。

70 个实例在所有臂都达到 70/70 可表达。这个检查只证明参考编辑在文本上可写，不证明模型已得到理解错误根因所需的全部语义，但它排除了最基本的输入缺失。

### 为什么不用模型直接写 unified diff

开发阶段 9 次模型生成 diff 中有 7 次无法应用。若不同表示使格式失败率不同，最终解决率会混入补丁序列化能力。

因此代理只输出 SEARCH/REPLACE 块。确定性 builder 用 `difflib` 生成 unified diff，并用 `git apply --check` 验证；若 SEARCH 找不到或不唯一，最多反馈两轮让模型修正块。这样模型仍负责“改什么”，机械程序负责“怎样编码成补丁”。

这并未完全消除格式差异。tier 臂有 24/70 个实例触发重试，keep/drop 为 15，full 为 11；结构化渲染中的非原文片段更容易诱使模型复制不可匹配文本。作者把它列为对 tier 不利的残余偏差。

### 模型、指标与统计

- 修复模型：Claude Sonnet 4.6；
- 单次调用，temperature 0，最多 8,000 输出 token；
- 不能运行测试、不能继续读取仓库；
- 官方 SWE-bench 4.1.0 harness；
- 解决条件：FAIL_TO_PASS 与 PASS_TO_PASS 均满足；
- 比例给 Wilson 95% 置信区间；
- 配对臂用双侧精确 McNemar 检验；
- 成本报告平均上下文 token 和 `总上下文 token / 成功实例数`。

作者没有用“解决率除以平均 token”，因为一个什么都解决不了、但输入极短的臂会被这种比值错误奖励。

## 主结果：结构化外围没有胜过直接删除

Table 3 给出三臂结果：

| 实验臂 | 解决数 | 解决率 | 平均上下文 token | 每个成功所需 token |
|---|---:|---:|---:|---:|
| `oracle_full` | 19/70 | 27.1% | 25,426 | 93,700 |
| `oracle_tier` | 23/70 | 32.9% | 8,629 | 26,300 |
| `oracle_keep_drop` | 25/70 | 35.7% | 6,876 | 19,300 |

预注册假设 H2 是 tier 优于 keep/drop。配对结果却是：

- tier 独赢 4 个实例；
- keep/drop 独赢 6 个实例；
- 精确 McNemar `p=0.754`。

因此 H2 失败。Figure 4 左侧显示三组 Wilson 区间大量重叠；右侧显示压缩臂的成本显著小于 full。论文可以支持的主结论是：

> 在 oracle 定位、单次无工具修复中，把非目标代码渲染成类骨架和签名，没有比直接删除这些非目标代码产生可测的解决率提升。

这里不能说“外围上下文永远无用”。tier 只包含静态签名和骨架，没有调用边、数据流或动态状态；代理也不能在需要时主动打开更多代码。

### 完整文件为什么不能直接作为公平对照

keep/drop 与 tier 都使用 gold-edited unit 构造，等于把“哪些函数值得完整保留”直接告诉模型。full 只拿到完整 gold 文件，没有同样的函数级高亮。因此压缩臂相对 full 的比较同时改变了 token 数、表示方式和位置提示。

keep/drop 名义上比 full 多解 6 个，配对检验为 7 对 1、`p=0.070`。作者没有把它写成显著优势，也明确指出这不是纯压缩效应。真正干净的主比较是共享相同 gold unit 的 tier 对 keep/drop。

## 调用序列切片：方向正确，但证据不足

静态骨架没有增益后，作者预注册了另一个跟进：在 keep/drop 的完全相同正文上，追加用 AST 确定性提取的局部调用顺序片段。65/70 个实例存在该片段，平均只有 215 token。

新鲜运行中：

- sequence slice：26/70，37.1%；
- keep/drop 重跑：23/70，32.9%；
- slice 独赢 4，keep/drop 独赢 1；
- `p=0.375`。

这是论文中唯一方向上支持“结构信息可能有帮助”的结果，但样本和不一致对数不足，不能宣称有效。它最多形成后续假设：与目标执行路径直接相关的局部交互结构，也许比全文件的静态目录更有价值。

## 最容易被忽视的结果：温度 0 仍有约 9% 实例翻转

为做 sequence-slice 对照，作者用完全相同的模型别名、prompt、temperature 0 和输入重跑 keep/drop。第一次为 25/70，第二次为 23/70；两次成功集合的对称差为 6 个实例。

也就是说，总体解决率只差 2 个，但有 6/70，约 8.6% 的实例改变了成败。这说明：

- temperature 0 不等于 API 结果逐字确定；
- 只看总体平均差会低估实例级不稳定；
- 两臂相差 2–3 个实例时，很可能仍处于运行噪声量级；
- 如果实验每条件只跑一次，应至少做 byte-identical 重复来估计噪声底。

本文自己的 H2 只有 4 对 6 的不一致，正处于这个噪声范围。作者没有用这一点抹掉主结果，而是把结论降为“未测到结构增益”，而非“证明结构完全无效”。

## 四幅主图应该怎样读

- **Figure 1**：完整源码与压缩表示在行为探针上的信息边界。重点是同一回答模型、独立测试生成问题和独立家族判分；frontier/3B 指的是摘要生成器，不是答题模型。

- **Figure 3**：500 → 71 → 70 的样本来源。它证明使用的是预注册条件下的完整总体，并披露唯一因 gold 环境失败而排除的实例。
- **Figure 4**：左图是三臂解决率与 Wilson 区间，右图是每个成功消耗的上下文 token。论文的价值不在某个最高柱，而在“预注册结构优势没有出现，压缩成本优势却很大”。

## 哪些设计很扎实

1. **把 Find 与 Act 拆开。**通过 oracle localization 固定位置，使表示效应不再和检索召回纠缠。
2. **逐实例验证 gold patch。**参考修复先在环境中运行，避免把坏基准当模型失败。
3. **逐臂验证可表达性。**每个参考 edit 的原行或插入锚点必须出现在输入中。
4. **预注册并公开阴性结果。**H2 与 H3 均未显著，作者没有事后改主假设或只报名义最高臂。
5. **确定性补丁构建。**把内容决定与 diff 格式错误尽量分开。
6. **独立探针来源与判断器。**正式行为问题从测试生成，答题模型看不到测试；判分用独立模型家族，并报告一致性。
7. **主动测量噪声底。**byte-identical 重复暴露 temperature 0 的实例级翻转。
8. **探索性结果隔离。**自有代码、自问自判和小样本层级检索被放入附录，明确不承担主结论。

## 哪些地方必须降调

1. **所有主修复臂都是 oracle ceiling。**真实系统还要先找到文件和函数；结果不能当成可部署检索策略成绩。
2. **只有单次、无工具修复。**多轮 agent 可以按需读取、运行测试和恢复，外围结构可能在交互中发挥作用。
3. **压缩臂与 full 不对称。**压缩臂编码了 gold-edited unit，只有 tier 对 keep/drop 是较干净的表示比较。
4. **结构表示很薄。**类骨架和签名不含真实调用边、数据流、控制依赖或运行时信息，null 不能覆盖所有图结构上下文。
5. **单语言、单模型家族。**70 个 Python 多文件任务、Claude Sonnet 4.6，不能外推到其他语言和模型。
6. **行为探针只有 15 个类。**虽然正式协议避免循环并做聚类区间，样本仍小，且问题有时需要类外上下文，所以完整源码也只有 60%。
7. **摘要预算固定约 180 token。**结果证明这一压缩尺度的自然语言摘要不足，不能证明任何长度、任何任务定制摘要都无用。
8. **判断器仍是 LLM。**kappa 0.84 是较好一致性证据，但不等于人工 gold；探针主结论依赖 judge 正确理解答案。
9. **token 统计有代理量。**主文用 cl100k_base，同时记录 Anthropic count；相对比例较稳，绝对成本要谨慎。
10. **论文尚未经正式同行评审。**工件透明度很高，但独立复现仍必要。

## 对当前四十五例 CPI 研究的直接启发

### 1. 下一轮先固定“可选对象”，再改变参考信息

当前 P/I/R/E 注入往往同时增加代码正文和新候选。模型从 GT 转向一个新增 P 函数，可能是该函数语义更有竞争力，也可能只是候选空间扩大。

可借鉴本文构造两个独立因子：

- **Candidate expansion**：是否新增可被输出的函数身份；
- **Reference representation**：候选固定时，附加完整正文、签名骨架、摘要或不附加。

这样能分别估计“多了一个可选对象”和“同一对象多了语义证据”的效应。不要继续把两者都叫 context dose。

### 2. 每个实验臂都做 answerability / expressibility audit

对每个 case、每个臂记录：

- GT 身份是否存在；
- GT 关键行是否可见；
- 每个 GT 是否允许被最终输出；
- 参考正文是否完整；
- 若要求机制解释，决定机制的语句是否可见。

论文只验证 gold edit 文本可表达；你的任务还需要“定位身份可输出”和“机制证据可见”两层。python-jose、json CLI、claircore 已经说明只写“函数已输入”不够。

### 3. 用 byte-identical 重复估计当前模型的噪声底

全量 P−I 均值只有 Qwen +0.0233、DeepSeek +0.0139，区间跨 0。先从 21 个至少一个模型基线成功的实例中选一批，对完全相同输入重复 2–3 次，记录：

- 节点集合完全一致率；
- GT recall 翻转率；
- full/partial/zero 状态翻转率；
- 配对 F1 差分布。

如果相同输入的翻转规模接近观察到的 P−I 差，就应把“未检测到特殊伤害”作为主结论，而非继续增大 P 剂量追方向。

### 4. 区分“源码表示”与“内容角色标签”

本文发现完整源码远胜摘要，但昨天的说明文件研究又显示输入权威会改变裁决。下一轮可固定同一函数身份，比较：

- 完整源码正文；
- 同 token 的行为摘要；
- 签名 + docstring；
- 只给函数名；
- 不给正文；
- 相同正文但标为“相关候选”或中性参考。

这能拆出语义保真度、结构身份和标签权威。HY 的弱规格线索、580 的定位线索、claircore 的截断片段可作为机制对照，但必须在实验前冻结。

### 5. 预注册一个可能失败的简单假设

例如：

> 在固定候选集合和 GT 完整可见时，为非 GT plausible 函数增加完整正文，相比仅给签名会降低精确定位率。

提前冻结主样本、主指标、无效输出处理和 paired test。若结果为 null，就像本文一样完整发布：它仍然能排除“只是片段太短”这一解释。不要在看到 Pinot 或 go-proxyproto 的结果后再决定哪些 case 属于主分析。

### 6. 成本指标不能奖励“短但无效”

若后续比较上下文压缩，建议并列报告：

- 成功/正确定位率；
- 平均实际输入 token；
- 每个正确实例的总 token；
- 合法输出率；
- 候选实体数量与完整正文数量。

不要用单一“F1/token”排序全部方法。一个极短、几乎不命中的臂会得到误导性的效率优势。

### 7. Find 与 Act 应成为论文叙事中的显式边界

当前五种方法的真实轨迹适合回答 Find：暴露了什么、GT 是否出现、P/I 候选如何进入。固定输入追加实验回答 Act/Decide：在候选已给定时模型如何选择和解释。两部分可以连接，但不应把“检索到了 P”直接写成“P 导致误导”，也不能用 Act 阶段的 oracle 条件替代真实 Find 评测。

## 一句话抓住全文

这篇论文最重要的结论不是“上下文越少越好”，而是：

> **只有先固定定位、验证每个臂都能表达正确编辑，再比较代码表示，才能知道外围结构是否真的帮助代理行动。**

在 70 个多文件 SWE-bench Verified 任务的单次 oracle 修复中，类骨架和签名没有胜过直接删除非目标代码；两种压缩臂用完整文件约三分之一的上下文达到相近解决率。独立行为探针还显示，约 180-token 自然语言摘要只答对 4/45，而完整源码答对 27/45。与此同时，完全相同、temperature 0 的重跑仍有 6/70 个实例翻转。

对当前研究最有用的不是照搬“删掉外围”，而是照搬测量纪律：固定候选集合，逐臂审查 GT 与机制证据的实际可见性，把候选扩张和参考正文拆成两个因子，并先测相同输入的运行噪声底。
