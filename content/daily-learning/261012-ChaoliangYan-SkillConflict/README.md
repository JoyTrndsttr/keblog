> Tags：`Coding Agent` `Agent Skills` `Skill Conflict` `Instruction Fidelity` `Controlled Experiment` `Repository Mining` `PreToolUse Hook`

## 一句话先说清

当两个“都能做这件事”的 Agent Skill 同时出现时，Agent 往往仍能把任务做完，却可能悄悄换用另一个技能，因而丢掉用户安装原技能时真正想保留的专属约束。论文从 20,947 个仓库重建技能安装环境，再对 312 对相似技能做 6,368 次受控运行；最关键的结果是：加入相似技能后，指定技能的使用率下降 19.9 个百分点，任务完成率没有显著下降，但其独占核心功能（exclusive core functions）忠实度下降 5.6 个百分点。冲突通常在第一次读取技能时已经决定；在这个点拦截错误技能，能把忠实度恢复到先读正确技能的水平。

这篇论文真正改变评价视角的地方是：**“任务成功”与“按指定方式成功”是两个构念。** 对技能、规则文件或检索上下文的实验，如果只看最终任务是否通过，就可能把最值得研究的行为偏移抹掉。

## 先建立全文地图

作者的证据链可以压缩成下面六步：

```text
Research Gap
任务通过率看不见技能专属要求是否被保留
    ↓
Research Object
一个已安装技能 A 与一个做同类工作的相似技能 B
    ↓
Operationalization
从 A 的文本预先提取“核心功能”，再标注哪些是 A 独占、哪些与 B 共享
    ↓
Controlled Experiment
比较 only-A、only-B、A+B、A+无关技能、交换顺序、改变 scope，并记录完整工具轨迹
    ↓
Evidence
任务完成、A/B 是否被读、核心功能忠实度、首次读取时点、用户是否获知替换
    ↓
Claim
相似技能会在任务仍成功时替换或稀释 A；首次读取是主要决策点，也是可干预点
```

### 理解全文需要的五个概念

1. **Agent Skill**：一个以 `SKILL.md` 为入口的目录。名称和描述先进入模型上下文，正文、脚本和参考资料通常只在模型选择该技能后才加载，因此“选哪个技能”发生在“读完整说明”之前。
2. **已安装技能 A 与相似技能 B**：A 是项目或用户为某个目的安装的目标技能；B 不是恶意技能，而是另一个做相同工作的真实技能。两者可以都完成任务，却对格式、流程、安全规则或工具使用有不同要求。
3. **核心功能（core function）**：从技能文本中抽取的、没有该技能时一个有能力的模型通常不会自然满足、可以在输出或工具轨迹中检查的具体要求。例如“不得改变 git 状态”比“写一份报告”更能代表安装这个技能的独特价值。
4. **独占与共享核心功能**：如果 B 也要求同一具体行为，它是 shared；只有 A 要求则是 exclusive。冲突应优先伤害 exclusive 项，因为 B 即使接管任务也可能保留 shared 项。
5. **替换与干扰**：A 没有被使用、B 代替它完成任务叫 substitution；A 被使用了但结果仍改变叫 interference。这个区分需要完整工具调用记录，不能从最终回答猜测。

## 为什么现有评价看不见这个问题

技能评测常问两个问题：任务通过了吗？该检索的技能检索到了吗？但技能的价值经常不体现在“能不能做”，而体现在“怎样做”。一个规范型技能可能规定提交格式、测试顺序、禁止操作或团队流程；即使这些规则全部丢失，代码仍可能通过测试。

论文中的直观例子是 `checkpoint`：项目技能 A 禁止改变 git 状态，只允许保存交接记录；加入同名的相似技能 B 后，Agent 改读 B 并直接提交。两次运行都完成了用户任务，但只有第一次遵守 A 的关键约束，第二次的最终回复也没有告诉用户换了技能。这不是普通功能失败，而是**在可观察成功之下发生的 specification drift**。

已有研究已经说明技能库变大后任务通过率可能下降，也说明模型会受到工具位置和描述的选择偏置。然而这些工作主要看“选了谁”或“任务过没过”，没有回答：目标技能独有的行为到底损失了多少、损失来自替换还是干扰、何时决定、能否在那个时点阻止。

## 从 55,698 个技能到 312 个可实验技能对

### 第一步：重建真实“安装列表”

作者从 2026-07-18 收集的公开 `SKILL.md` 语料出发，固定 20,947 个仓库的历史快照，得到 55,698 个不同技能、105,302 个非 fork 副本。随后按 Claude Code 的加载规则重建：某个项目会看见哪些项目级技能、dotfiles 中的个人技能和仓库启用的插件技能。最终得到 5,106 个安装列表，其中 4,342 个至少含两个不同技能。

这一步必要，因为“文本相似”不等于“实际会共存”。若不重建安装环境，只能证明网上存在相似文件，不能估计真实共装规模。其局限也很清楚：公开仓库通常看不到开发者本机个人技能与未提交的插件配置，所以作者的共装率更可能是下界。

### 第二步：过滤不可调用项并做近重复家族化

作者下载 219,817 个技能文件，只保留 frontmatter 合法、可被模型调用、名称与描述非空、正文至少十行的文件，保留 207,863 个（94.6%）。再用词 5-gram MinHash、Jaccard 阈值 0.8 把近重复版本合成 family，避免把同一技能的小版本当成冲突对。

这里 family 是去重单位，不是语义等价的证明。阈值太松会把不同技能合并，太严会把复制变体拆开；论文没有对这一阈值做大规模敏感性分析，因此 prevalence 数字仍依赖这一步的工程定义。

### 第三步：检索候选，再由 LLM 判断“是否做同一工作”

候选分两类：同一安装列表内的 within-project pair，以及已安装技能 A 与外部不同作者技能 B 的 cross-project pair。作者只用模型在选择时能看见的名称、描述和 `when_to_use` 文本做 Qwen3-Embedding-0.6B 向量检索，每个 A 保留相似度最高的十个候选，共得到 822,109 对。

但相似描述可能只是主题相关，并不代表能处理同一请求，所以 GPT-6 Astra 再判断：一个发给 A 的请求是否可能路由到 B，以及读完正文后两者是同工作、近重复、相关但不同还是无关。经校准，相似度下限要保持至少 95% 的已确认对；最终对 3,754 个分层抽样 pair 进行判断，确认 1,639 对。

这是一条合理的 retrieve-then-confirm 流程，但 pair judge 同时影响 prevalence 和实验样本。人工验证与 LLM 的 Krippendorff's alpha 为 0.72，达到论文采用的 tentative threshold，却不是无噪声金标准。

### 第四步：把技能价值变成可检查的“核心功能”

对每个技能，GPT-6 Astra 在看不到搭档技能和任何运行结果时，提取最多十条核心功能。每条必须：

- 对该技能足够独特；
- 能逐字回溯到技能正文；
- 能在文件、命令、提交信息或最终回复中检查；
- 不是示例、参考表或工具自动生成的默认行为。

作者共得到 26,198 条，平均每技能 8.4 条。实验时按措辞强度、与技能目的的接近程度、安全/交付物影响和出现顺序排序，取对任务适用的前三条作为 primary core functions；再把 A 的每一条与 B 的全文和核心功能比较，标成 exclusive 或 shared。312 个实验 pair 的 2,518 条适用功能中，73% 是 A 独占。

小例子：A 要求“生成报告、列出阻塞项、绝不提交 git”，B 也要求报告和阻塞项，却鼓励提交。前两条是 shared，“绝不提交”是 exclusive。若 B 接管，任务可能完成且 shared 项仍通过，只有 exclusive 指标能揭示真正损失。

### 第五步：构造任务与冻结检查

一个 pair 只有在 A 能离线运行、至少有三条核心功能、至少一条适用于任务、且两个目录都能从快照取回时才进入实验。GPT-6 Astra 为每对技能构造一个不点名技能、不复述描述的用户请求、最多 15 个文件的起始仓库，以及任务完成检查和每条核心功能检查。检查尽量使用脚本，否则交给盲化 output judge。

最终选择 312 对：规范型、能力型、带脚本型都覆盖，也同时覆盖 cross-project 和 within-project。这样的构造提高了内部可比性，但它不是从真实 issue 中随机抽取的自然任务；“能测出损失”本身就是纳入条件，不能把效应量直接外推到所有技能任务。

## 实验坐标系：究竟固定了什么、改变了什么

每个 pair 共用同一请求和起始仓库，主要配置是：

| 配置 | 目的 |
|---|---|
| only A | A 单独运行的参照 |
| only B | 检查 B 是否确实不能完整替代 A 的独占行为 |
| A+B | 相似技能冲突 treatment |
| A+C | 多装一个无关技能的控制组，排除“技能数量增加”本身 |
| swapped | 交换列表顺序，检验位置效应 |
| personal scope / plugin scope | 对 81 个同名 pair 改变 B 的安装 scope，检验平台覆盖规则 |
| A+B guard / no guard | 在第一次读 B 时阻止并引导回 A，检验决策点 |

主实验使用 Claude Code 2.1.283，模型为 Sonnet 4.6、Haiku 4.5、Opus 5；每个 pair × model × configuration 运行一次，最多 80 turns、25 分钟。作者把技能列表预算统一提高到 20,000 字符，否则 Opus 5 的默认 6,000 字符上限会让 95.8% 的 A+B 列表至少丢失一方描述。这个修改保障两项都可见，但也意味着结果对应“候选可见”的受控条件，不等同于默认产品设置。

主配置共分析 5,162 次运行，另有 guard 与重复实验，总计 6,368 次、169,294 次工具调用、542.4 agent-hours、约 6.3B 输入 token 和 110M 输出 token。主分析是 pass@1；512 个组合有 2—3 次重复，A 使用与否的 pairwise agreement 为 88.9%，ICC 为 0.78；脚本判定核心功能的 ICC 为 0.84。重复性较好，但一次运行仍无法刻画每个具体 pair 的完整随机分布。

四类结果分别是：任务完成率、A 的核心功能忠实度、A/B 是否实际被调用或读取、最终回复是否披露存在多个技能或说明用了哪个。327/921 个 primary 检查由脚本决定，其余及大多数任务完成由盲化 GPT-6 Astra 判定；judge 看完整仓库和去标识工具轨迹，但不知道配置与谁是 A。

## 先看规模：这种冲突常见吗

分层加权估计显示：23.5% 的已安装技能 family，在同一安装列表中已经存在一个做同类工作的技能；63.7% 在其他作者处存在可被加入的同类技能。复制完整技能集合的 489 个项目里，同列表同工作技能比例为 37%，其他项目为 19%。确认 pair 中规范型最多：cross-project 为 60%，within-project 为 56%；能力型分别为 31% 和 35%，其余约 9% 为带脚本型。

这支持“冲突机会并非罕见”，但不是生产环境实际冲突发生率。作者只观察公开可重建安装，且 prevalence 由“每个 A 的最相似候选”与 LLM 判定得到；它说明风险面大，不说明四分之一的日常会话已经受损。

## RQ1：相似技能会伤害什么

### 问题与设计

RQ1 比较 A+B 与 only-A，A+C 是“多一个技能”的负对照。核心问题不是 B 能不能做任务，而是加入 B 后 A 的使用、任务完成和 A 专属行为是否同时改变。

### Figure 4 应该怎样读

Figure 4a 把任务完成率、总体 fidelity、exclusive 与 shared fidelity 放在同一横轴。先看 task completion：only-A 为 57.2%，only-B 为 58.1%，几乎一样；再看 fidelity：only-A 的 primary 核心功能为 57.3%，only-B 只有 46.3%。这验证了测量思路——任务完成分不开两个技能，A 的要求可以。

Figure 4c 显示相对 only-A 的变化与 95% 置信区间。加入 B 后：

- A 的使用率下降 19.9pp，95% CI [-23.1, -16.7]；
- 任务完成率变化 +1.9pp，95% CI [-1.0, +4.9]，不能认为下降；
- primary fidelity 下降 2.6pp，95% CI [-4.4, -0.8]；
- exclusive fidelity 下降 5.6pp，95% CI [-7.3, -3.8]；
- shared fidelity +0.1pp，95% CI [-2.8, +2.9]，基本不变。

A+C 只让 A 使用率下降 5.9pp，fidelity 变化 -0.2pp；因此损失不是单纯因为列表里多了一个条目，而与“另一个做同类工作的技能”有关。

### 损失来自替换，还是 A 被 B 污染

Figure 4b 按 A+B 运行真正用了谁拆分损失。12.1% 只用 B，38.0% 两者都没用；substituted run 相对 only-A 的 fidelity 下降 8.0pp。总损失中，only-B 运行贡献 36%，neither 贡献 45%，使用到 A 的运行只贡献约 20%。所以主要机制是**路由替换或干脆不加载技能**，不是两个正文同时进入上下文后相互“语义污染”。

这个结论比“更多上下文导致 context rot”更具体：B 的存在先改变选择，A 的独占要求随后根本没有进入执行链。论文观察到工具轨迹上的中介，但没有随机强制“是否读取 A/B”来估计完整自然直接效应与间接效应；因此替换是强证据支持的机制解释，尚不是形式化 mediation analysis。

### 稳健性与负结果

使用全部适用功能时损失从 2.6pp 增至 4.1pp；去掉起始仓库已满足的脚本检查后仍为 2.3pp。纯脚本检查的损失为 4.2pp，大于 LLM judge 检查的 1.2pp，说明结论不完全由 judge 偏差驱动。不同模型、技能类型、pair 来源的点估计方向一致；within-project 的 A 使用率也下降 18.3pp。

但能力型技能没有显示出普遍任务完成下降，这是重要负结果。论文证明的是“独占行为会丢失”，不是“相似技能一定让代码功能失败”。

## RQ2：选择由什么决定，用户知道吗

### 列表顺序不是主因

作者通过给 B 加一个字符前缀反转列表顺序。Figure 5 显示，顺序只让 A 的使用率变化 +0.6pp，95% CI [-2.0, +3.3]；重命名 B 本身约 +4.4pp。至少在这里，常见的“把目标工具排前面”不是可靠解决方案。

### scope 规则远比顺序更强

对 81 个同名 pair，如果 B 放进 personal scope，Claude Code 按规则让 B 覆盖 project A：A 从列表消失，A 使用率下降 35.0pp。模型在 46.5% 的运行使用 B，却仍在 29.2% 的运行绕过列表直接读取 A 的项目文件，说明平台级 override 与模型实际文件访问并不完全一致。

如果 B 放在 plugin scope，它带前缀与 A 同时列出，A 的使用率为 58.0%，B 只有 2.9%；同一批 pair 的 A 使用率只下降 6.2pp，而 B 在 project scope 时下降 16.9pp。安装位置不仅改变呈现顺序，还改变命名、覆盖和可见性，是复合 treatment，不能把差异解释成纯粹的“模型偏好个人技能”。

### 模型异质性很大

Figure 5 的分模型列很有价值：A+B 下，Opus 5 同时读取 A+B 的比例为 36.8%，Haiku 4.5 不读任何技能的比例则为 56.4%。Opus 5 甚至在 A 未列出的 personal-scope 条件下，53.1% 的运行仍读取 A 文件。这说明“技能冲突率”不是技能对的固定属性，它由模型、平台加载规则和模型的文件探索策略共同决定。

### 最终回复几乎不披露替换

113 个 B 替换 A 的运行中，0% 告诉用户存在多个合适技能，0.9% 说出了实际使用的技能，0% 请求用户选择。仅看最终回复，用户几乎无法知道自己的项目技能被替换。因此论文提出的“显示技能来源与 scope”不是便利功能，而是可审计性的最低要求。

## RQ3：冲突在什么时候决定，能否阻止

### 首次读取是行为分岔点

作者寻找同一个 pair-model 在 A+B 与 swapped 两种配置下首次读取不同技能的情况，共 79 个 pair-model 组合、63 个 pair。两次运行在首次读取前工具调用中位数都是 6，之前轨迹相近；如果先读 B，A 的 exclusive fidelity 比先读 A 低 9.4pp，95% CI [-15.0, -4.0]，Holm 校正后 p=0.004。97% 的 B-first 运行在第一次读 B 前尚未修改文件。

Figure 6a 的横轴以首次技能读取为零点，纵轴是已经修改文件的运行比例；曲线在零点前贴近底部、零点后上升。Figure 6b 给出 B-first 相对 A-first 的 exclusive fidelity 差，整体显著，Haiku 4.5 的点估计 -22.1pp、Sonnet 4.6 -12.1pp，而 Opus 5 没有显著下降，符合它经常把两个技能都读到的行为。

“先读 B 导致损失”在这部分仍有选择偏差风险：愿意先读 B 的运行也可能有其他未观测差异。作者没有停在观察比较，而是继续做 guard 随机实验，这一点很关键。

### PreToolUse guard 的干预实验

guard 在 A 尚未读取时阻止首次读取 B，并提示模型使用 A；A 已开始使用后继续拒绝 B，但不泄露任何核心功能内容。作者从主实验中选出 187 个曾先读 B 的 pair-model 组合、119 个 pair，随机顺序运行 guard 与 no-guard；脚本可判定的组合再重复一次，共 670 次。

结果是：当模型先伸手去读 B，guard 拒绝后 96% 改读 A。总体 exclusive fidelity 提高 9.1pp，95% CI [+6.0, +12.1]；在两种条件都先尝试 B 的可比子集中，提高 17.8pp。Sonnet、Haiku、Opus 的提升分别为 17.4、20.7、12.8pp，均显著。重定向后的 fidelity 与无 guard 且先读 A 的运行差为 0.0pp，区间 [-10.2, +10.3]；任务完成率变化 +4.1pp，区间 [-1.3, +9.6]。

Figure 6c 因而不是普通相关图：它比较 no-hook/A-first、no-hook/B-first 与 hook/B-first，V 形差距在 guard 后回升。最谨慎的结论是：**对这批已经显示风险的 pair-model，首次读取时拒绝 B 并明确引导 A，可以因果地恢复 A 的独占功能忠实度，且未检测到任务完成代价。**

它仍不是“任意技能冲突都该自动拦截”的证据。guard 实验只在历史上先读 B 的风险组合进行，提示内容也明确告诉模型转向 A；在没有预先指定优先技能、A 本身质量较差或任务实际更适合 B 时，平台仍需要用户或项目声明优先级。

## 复现性、统计与证据审计

论文的优点是把高层 claim 落到可审查制品：复现包包含 312 个 case、5,162 个主运行、536 个重复运行、1,870 条首次读取摘要、670 条 guard/control 记录、3,754 个 prevalence 样本、712 个 Codex 观测、prompt、分析脚本和 guard。配置之间以 pair 和 model 配对，首次读取分析做 pair-cluster bootstrap，多个比较使用 Holm 校正。

仍有几条需要保留：

1. **构念效度**：core function 是“独特、可检查、文本可回溯”的要求，不等于用户主观上最看重的要求。only-A 也只满足 57.3% primary 功能，说明技能本身并不保证忠实执行。
2. **LLM 参与多环节**：仓库类型、pair 确认、技能类型、核心功能、任务构造和多数输出判断都依赖 GPT-6 Astra。两名人工评审覆盖每一步的抽样并给出 0.71—0.84 的 LLM-consensus alpha，但抽样验证不能消除全量系统偏差。
3. **样本选择**：312 对必须离线可运行、可取得快照、有足够可测核心功能。结果最适用于“能做受控检查的技能”，不代表所有自然工作流。
4. **单次运行**：主实验每组合一次。重复子样本说明宏观模式较稳定，却不能把每个 pair 的一次结果当成确定属性。
5. **平台与版本**：完整析因设计只在 Claude Code 2.1.283 上完成。Codex 对 193 对技能、三个模型的补充结果接近——A 使用下降 18.2pp、exclusive fidelity 下降 3.4pp——支持跨平台方向，但不足以覆盖 Gemini CLI、Copilot 或未来加载规则。
6. **scope 是复合干预**：移动目录会同时改变覆盖规则、显示名称、前缀和列表内容；因此可以说“scope 配置决定结果”，不能说某一个细节单独造成全部效应。
7. **现实损害尚未量化**：论文测的是受控任务中的要求丢失，没有进一步证明这些丢失在生产系统中造成多少安全事故、返工或 review 成本。

## 作者真正证明了什么

1. 在这 312 对真实相似技能构成的受控任务上，加入 B 显著降低 A 的使用与独占功能忠实度，而任务完成率没有显著下降。
2. 相似技能的影响显著大于无关技能，主要表现为 B 替换 A 或两者都未加载，而不是 A 已加载后的普遍干扰。
3. 列表顺序影响很小；同名技能的安装 scope、平台覆盖规则和模型差异更重要。
4. 技能替换极少在最终回复披露，用户不能依赖自然语言总结发现冲突。
5. 对预先识别的风险组合，在首次读取时实施 guard 能使模型转向 A，并因果地恢复 A 的独占功能忠实度。

## 作者没有证明什么

- 没有证明多一个相关上下文一定比随机噪声更伤害推理；这里的主要机制是技能选择与加载。
- 没有证明 B 是低质量或恶意技能。B 往往也能完成任务，只是没有 A 的全部专属要求。
- 没有证明先读 B 是所有观察损失的唯一中介；观察部分仍可能含未测混杂，guard 只验证了特定干预。
- 没有证明 23.5% 的安装技能已经在实际会话中发生有害冲突；这是同工作技能共装机会的估计。
- 没有证明所有平台都应无条件优先项目技能；优先级必须来自用户或项目声明。

## 读完应记住的六件事

1. 对指导、技能和规则文件，任务通过率是必要但远远不够的指标。
2. 最有诊断力的是“只有目标指导提供的要求”是否保留，而不是总要求平均分。
3. 要把“候选可见、文件被读、机制被理解、要求被执行、任务成功”拆成不同层级。
4. 相似指导最常见的损害可能发生在路由阶段，甚至在正文进入上下文之前。
5. 首次读取日志是高价值过程变量；最终回答几乎不能替代工具轨迹审计。
6. 安装 scope、命名和 override 是实验 treatment 的一部分，不是无关实现细节。

## 对当前研究的直接启发

当前研究正在全量筛查 Antares/GraphLocator/EvidenceLoc 的可解定位输入，并反复区分文件命中、实际读取、机制解释、行坐标与重复稳定性。本文最直接的价值不是替当前实验提供“相似上下文会伤害”的现实性证据，而是给出三个可以迁移的设计原则。

第一，把当前结果改写成分层 fidelity，而不是一个混合成功标签。对每个冻结输入可以预先定义：目标文件是否读取、根因机制是否被正确表述、关键 site 是否命中、范围是否过宽、重复是否稳定。只有目标方法/指导独有且预先冻结的要求，才对应本文的 exclusive core functions。文件 F1=1 但未读根因，与本文“任务完成但独占要求丢失”是同一种测量错位。

第二，把轨迹中的首次关键动作当作候选中介：首次读入核心文件、首次选择检索分支、首次提交定位结果，分别记录发生前后的工具轨迹。如果 plausible 指导改变的是首次选择，而非读入后的推理，那么干预应放在路由点；如果两组都先读到同一核心证据却后来分岔，才更像上下文内干扰。

第三，下一步干扰实验应采用任务内配对和显式对照：同一冻结成功输入做 only-core、core+plausible、core+matched-unrelated，并匹配可见文件数、字符/token 预算和安装/呈现位置。最终同时报告任务/文件、独占机制要求、精确 site、轨迹选择与稳定性，而不是把失败统一记 0。本文可以作为“为什么只看任务成功会漏检”的 measurement precedent；它不能替代当前研究对 repository-level 漏洞定位中 plausible context 因果效应的直接估计。

一个低成本的先导实验是：在已经较成熟的 0b 固定输入上，预先指定一条目标 evidence route 与一条同工作但缺少关键机制约束的替代 route，随机化它们的显示名称/scope/顺序，记录首次读取、实际曝光、机制陈述和 site。若首次读取不同且 exclusive 机制 fidelity 随之改变，再加一次 first-read guard；这样能把“选择效应”和“读入后干扰”真正分开，而不是从最终 F1 反推机制。

## 最终评价

这是近期 Agent Skill 研究中少见的、把大规模生态测量、任务内受控比较、过程轨迹与干预实验连起来的工作。它最强的贡献不是“技能多了会冲突”这个直觉，而是建立了一个可复用的评价单位：**目标组件独占的、预先冻结的、可检查行为**。它也诚实暴露了边界：only-A 本身忠实度不高，LLM judge 深度参与测量，完整实验集中于一个平台，真实生产损害仍待验证。对任何研究“额外指导是否有帮助/有害”的实验而言，这篇论文给出的首要提醒是：先定义你究竟要保住什么，再讨论任务有没有做完。
