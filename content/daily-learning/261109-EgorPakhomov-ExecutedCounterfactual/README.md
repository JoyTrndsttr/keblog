## 先别问“删掉这段历史会不会变好”，先问“我们真的回到了同一个时刻吗”

一个 Agent 读过错误信息，后来失败了。日志看起来很有说服力：错误先出现，推理随后走偏，最终答案也错了。但是，这至多告诉我们一种解释“很像是真的”。要证明这段历史确实影响了后续行为，需要让同一个 Agent 回到同一个中间时刻，只改变那段信息，再真实地往下执行。

困难藏在“同一个时刻”里。复制了文件、聊天记录和数据库，并不一定复制了进程已经消耗到哪里的一串随机数；两个复制品互相表现一致，也可能一起偏离原来正在运行的那条轨迹。**这篇论文不是提出一个更强的故障定位器，而是追问：什么样的实验，才有资格把 Agent 的失败归因于它看到的历史？**

可以先记住它的论证路线：日志分类只能产生待检验解释；历史干预需要可执行的中间状态；状态恢复本身必须用行为探针验证；最后才有资格比较不同历史下的后续结果。两组真实测量分别展示“统计分类看似有发现”和“快照哈希看似已恢复”怎样误导研究者。作者自己也强调：这两组测量没有完成其提出的历史因果归因标准，不能当作历史污染致败的新证据。

作者并不要求每次实际归因都重新运行整个实验。另一条合格路径，是使用在有代表性的干预验证测试集上经过验证的归因估计器，并报告校准情况与不确定性。不能省略的是：归因最终必须连接到真实执行过的干预证据。

## 一个复制游戏存档的例子：文件相同，下一次掷骰子却不同

下面是教学示例，不是论文原实验。假设 Agent 在一个小环境中依次调用工具，每次工具有 20% 概率暂时失败。环境通过一串伪随机数决定失败与否：原轨迹已经用了前七个数，下一次要读取第八个。

研究者保存了地图、任务计数器和消息记录，却没有保存随机数生成器的位置。把存档加载到一个刚设好相同 seed 的新进程，下一次读取的是第一个数，而不是第八个。于是：

- 文件和消息的 SHA-256 完全相同；
- 两个新进程都从第一个数开始，所以它们彼此一致；
- 但它们不一定与原进程的下一步一致。

此时若一边保留历史，另一边删掉一段错误历史，看到路径不同就归因于历史，实际可能夹带了恢复方式的影响。解决办法不是再多比一次文件哈希，而是让**不修改历史的恢复分支**与**原运行的真实延续**先做对照。

这也解释了为什么“设置 seed”和“恢复随机状态”不是一回事：seed 定义一条随机数序列，随机状态还要告诉我们走到了序列哪里。

## 作者真正要固定的，不只是文件系统

论文第 2 节把中间时刻拆成三部分：

- 环境状态 s：数据库、工作区、任务状态等已经发生的现实。
- 进程状态 p：随机数流、打开的句柄等影响后续执行的状态。
- Agent 可见历史 h：模型这次决策看见的消息和历史内容。

可执行状态 x=(s,p)。历史干预把 h 改成 h′，固定 x，再使用同一策略继续运行。如果某些缓存是从历史推导出来的，应由 h′ 重新计算，不能保留与旧历史相对应的隐藏缓存。

### 三个不能混称为“可复现”的要求

**第一，恢复忠实性。** 恢复出来的东西是否在指定探针下与参考运行相符？作者要求报告实测一致率，而且通过标准应在看结果前固定。这就是 replay certificate，即回放验证记录。

**第二，路径级精确回放。** 如果要断言“这条轨迹只因这一个改动而改变”，在确定的探针策略、耦合的外生随机性下，未改动分支应能逐步或逐字节复现。它比最终答对率相同更严格。

**第三，分布级相等。** 如果托管模型无法逐字节复现，也可以研究成功概率的差异，但需要重复续跑，检验恢复与原运行在预先指定指标上是否落入可接受的等价范围。不能把“没有显著差异”直接当成“已经证明等价”。

三者服务于不同的 estimand，也就是“到底想估计什么量”。一种探针通过，不等于所有 Agent 策略、提供商和后续交互都通过。共享一个恢复实例再分叉，可以增强分支间可比性；但若要把结果解释为原日志那一刻的反事实，还必须证明恢复实例与原运行的对应关系。若每条臂分别恢复，则还要检查臂间状态身份。验证记录还应包括检测能力对照，说明所选指标确实能发现相关的不一致，而不只是始终报告一致。

### 四类历史操作不是本文发明的

作者将已有工作中的操作整理为四类：修正错误历史；保持文字相同但改变来源角色；用 token 数和回合数匹配的合成历史作安慰剂；人为注入错误、过期值或压缩摘要。

它们回答的问题不同。修正文字主要问错误内容是否有害；只改“这是我自己说的”或“这是另一个 Agent 说的”主要问来源角色是否影响行为；长但无关紧要的历史可帮助区分长度负担；主动插错检验一种可控制的错误机制。不能把所有操作的效果统称为“记忆效应”。

论文承认 DoVer、REFLECT、Causal Agent Replay、Who&When Pro 等已有真实续跑或前缀回放方法，其增量主张较窄：**为因果目标补上数值化回放验证、未编辑历史的原运行对照，以及与执行方式匹配的验收标准。**文献普查不是完整系统综述，因此“所检查工作未报告这项测量”不能升级为“整个领域此前从未有人提出”。

### 固定世界、只修历史，不一定是错误事件的总效应

假设错误历史已经导致 Agent 删除了一个文件。现在只把聊天中的错误描述修好，却保留文件已被删除的现实，测得的是“在这个已实现世界里，更换所见历史的受控直接效应”。这甚至可能形成原系统正常执行时不会出现的历史与环境组合。

如果想问“当初没有那个错误，整段过程会怎样”，要在错误事件之前分叉，或联合改变历史与环境。**历史内容效应、状态效应与整个策略的累计效应，不能由一个末端实验包办。**

## 第一组测量：84.9% 的不安全行为来自某载体，为什么仍不能说它更危险？

### 研究问题和数据怎样构造

作者在 ActBench 上问一个观察性问题：攻击通过哪种载体进入 Agent，并最终伴随不安全动作？载体是信息进入系统的渠道，比如服务返回值、本地文件、持久记忆或工具元数据。

完整发布数据包括 300 对正常/对抗任务、24,000 条轨迹，覆盖 20 个模型与 harness 配置，涉及 15 个模型和 6 个 harness，并非完整交叉组合。作者读取任务元数据和正常/攻击输入的变更来源，用确定性规则给载体分类：251 对由元数据与变更源确定，另 15 对由路径规则补齐，合计 266/300，超过事先设定的 85% 覆盖门槛。34 对来源混合且缺少足够元数据的任务被排除，而不是强行猜标签。

原细类是服务返回 225 对、记忆 15 对、工具元数据 14 对、工作区文件 12 对。协议要求每类至少 30 对，所以后三类合成 local_file_state，共 41 对。每类样本量下限是预先规定的，但具体合并映射是在看到细类数量后选择的。合并后只有两个大类，不能再声称分清了记忆、工具元数据与普通文件的各自作用。

同一个执行分析的 LLM Agent 对 50 对样本复核，50/50 与规则一致。但它看得到规则标签，不是盲评，样本中只有 6 对属于本地类。这个检查适合发现明显规则矛盾，不能当成独立人类 gold 标注，也不能把“完全一致”解读成构念已被验证。

### Table 1：先看分母，再看醒目的占比

这张表固定的是被分类的 266 对任务及其 15,960 条攻击轨迹，列按服务返回与本地状态分开，行逐层切换分母。决定解释的数字如下：

| 比较量 | 服务返回 | 本地状态 |
|---|---:|---:|
| 任务对份额 | 225/266，84.6% | 41/266，15.4% |
| 已分类攻击轨迹 | 13,500 | 2,460 |
| 被 Benchmark 判为攻击成功 | 7,810 | 1,389 |
| 全部 9,199 次攻击成功中的份额 | 84.90% | 15.10% |
| 找到首次曝光位置的比例 | 96.65% | 69.31% |
| 已找到曝光轨迹中的转化率 | 58.47% | 65.81% |

“84.9% 的攻击成功来自服务返回”十分接近“84.6% 的已分类任务本来就是服务返回”。这首先是一个数据集组成事实，不是载体固有危险性的估计。

作者进一步用 logistic 模型控制 15 类风险行为与攻击方法，得到服务相对本地的优势比 OR=1.1484，95% 任务聚类 bootstrap 区间为 [0.6275, 2.0160]。OR 是相对 odds，不是概率提高了 14.84%；区间跨过 1，也不能说已证实服务更危险或两者等效。攻击方法与载体几乎共线，只有 context injection 同时包含两类，而且是 195 对服务、12 对本地，共同支持仍然很弱。统计调整没有创造出原数据中不存在的可比任务。

份额类统计使用 5,000 次重采样，调整模型使用 2,000 次，按任务聚类；同一 scenario 内不同任务的依赖没有被进一步表示。这个区间要按作者声明的单位理解，不能把所有轨迹当独立样本。

### 为什么“只比较真正看到攻击的轨迹”也没救回来

首次曝光不是直接观测到的真值，而是通过匹配注入内容来恢复。服务返回的候选含整个受攻击字段，片段匹配可能落在未变化的正常文字；本地文件则只拿改变的片段作匹配。两个类的测量口径并不完全相同。

服务类能找到 96.65% 的首次曝光，本地类只有 69.31%，相差约 27.3 个百分点。若只比较找得到曝光的子集，就可能比较两个偏差不同的选择样本。尤其未找到曝光的轨迹中仍有 181/452 个服务样本、267/755 个本地样本被判攻击成功，不能把“没匹配到”当成“没看过”。

作者在看完标注审计数量、但尚未计算结果统计时，增加了两个规则：少于三个有效类时不评集中度与排名；每类首次曝光恢复率至少 70%。两类穷尽全部数据时，top-two share 必为 1，排名相关也只能是 ±1；本地类则以 69.31% 未过恢复率门槛。这里的失败不只在于距离门槛差 17 条，更在于大幅不对称的恢复能力会改变估计对象。

### Table 2：复现很稳定，也可以稳定地复现混杂

表 2 保留了所有留一模型、留一 harness 检验。15 个模型留一折中 14 折排名方向相同、一折反转；6 个 harness 留一折都同方向。但只有两个类，Kendall τ-b 的 ±1 并不提供丰富稳定性证据。

更有信息量的是正常任务孪生对照：没有攻击载荷时，服务类任务失败率已是 607/4,500=13.49%，本地类为 72/820=8.78%。它说明分组从任务构造阶段就不完全可比。只用日志证据的代理分析也没有得出明确载体效应，调整 OR=0.8973，[0.4715,1.7043]。所有配置都达到可用样本下限，所以过滤配置没有改变结果，却也没有修复这些结构问题。

**本组结论不是“服务返回更危险”，也不是“载体没有作用”，而是这份数据与测量无法识别该比较。**作者将整组按修订后的协议判为不可评估。保留描述统计而撤回越界解释，是本组测量的价值。

## 第二组测量：五个克隆都一致，为什么仍然回放错了？

### 先造一个看起来很严格的快照检查

作者在 AgentCE-Bench revision 22ae16b7 外围实现自己的快照层，Benchmark 本身没有相应 fork/restore API。首先关闭随机工具失败，恢复五个克隆，比序列化状态哈希。

六个领域、三个网格大小、两种时程、两个分支预算、两个锚点组成 144 个检查记录，全部通过。但它们只覆盖 108 个独立状态，因为一部分单槽任务的两个锚点重合；不能写成“144 个独立状态”。另外 17 个由模型生成的状态也通过。

在 15 个状态中，分别改查询计数器、网格单元、最后一条消息，45/45 个改动都被检测到；20 个状态的并发独立进程检查也通过。这证明哈希能发现**已保存字段**被改动，却从逻辑上无法发现**根本没保存的字段**。

### 开启随机工具失败后，看三层结果

核心实验选 24 个析因单元：6 领域 × 隐藏槽数 5/21 × 时程约 1/3、2/3 的锚点，固定 5×7 网格和分支预算 8。首次未设种子实验中，前缀无工具失败，锚点后工具失败概率设为 0.05 或 0.20；续跑用确定性的真值策略，每个槽最多尝试 10 次。这里没有 LLM 参与后续决策。

作者记录：每次工具调用的成功/失败序列、末端序列化快照哈希、最终 grader 成败。末端哈希包含消息轨迹，因此它与失败序列并非独立证据。

Table 3 中，朴素恢复的五个克隆在 0.05 条件下有 17/24 个状态互相不一致，在 0.20 下有 22/24。不改历史的原运行与恢复运行也分别在 11/24、19/24 个状态分歧。把随机流位置一并捕获与恢复后，这两种概率下的克隆互比、原运行对恢复的分歧都变成 0/24。

未设种子的 live-vs-live 参照也会变动，它用于展示独立随机运行的背景，不是干预效果。论文还按实际调用长度给出独立随机序列的解析参考，但那是事后代入观察长度的检查，不能写成预先精确预测。

### Table 4 和 Figure 1：真正击中错误直觉的是设种子的复验

更有力的检查把每个任务从起点设好种子，始终使用相应工具失败率，再比较中间恢复。Table 4 的主要结果是：

| 恢复或参照方式 | 失败率 0.05 时偏离原续跑 | 失败率 0.20 时偏离原续跑 |
|---|---:|---:|
| 两次相同种子的全新执行 | 0/24 | 0/24 |
| 相同种子重放已记录前缀 | 0/24 | 0/24 |
| 仅快照恢复，每状态一个 seed | 9/24 | 20/24 |
| 仅快照恢复，runner 固定 seed | 18/24 | 24/24 |
| 快照加随机流位置恢复 | 0/24 | 0/24 |
| 五个设种子恢复克隆彼此比较 | 0/24 | 0/24 |

最后一行和第三行应连起来读：五个克隆彼此全部一致，但仍有 9/24 或 20/24 个状态一起偏离真实延续。它们从相同的错误随机位置出发，所以“一致地错”。runner 单一 seed 方案甚至在 24 个单元间只有四个不同的真实实现，作者因此另做每状态 seed 的版本。

Figure 1 将每状态 seed 的结果画成两个面板。左面板失败率 0.05，右面板 0.20；横轴依次是全新执行、前缀回放、设种子的快照、未设种子的快照、快照加随机状态；纵轴是 24 个状态中偏离原续跑的比例。橙色高柱集中在两类朴素快照上：设种子由 9/24 升至 20/24，独立的未设种子复验由 14/24 升至 21/24；全新执行、前缀回放和保存随机状态均为零。

图中的精确二项 95% 误差线只供观察量级。24 个状态是固定析因单元，不是从总体随机抽取；不能据此宣称某个总体的恢复错误率已得到可靠区间。表 3 的状态 bootstrap 同样是描述性的，零分歧时退化为 [0,0] 也不等于“未来绝无错误”。

设种子复验有预注册，但五克隆设种子臂和每状态 seed 臂是在看到固定 seed 结果后增补；每状态版本被指定为主要结果则发生在两组结果都已知之后。论文披露了这些时间顺序及时间戳更正，所以应称有透明修订的复验，不应美化为所有比较均完全事前固定。

### 最终评分全一致，并不说明恢复实验没问题

所有上述条件的最终 grader 分歧均为 0/24。确定性真值策略允许每个槽最多重试 10 次，因此工具调用序列可以不同，最终评分却仍相同。

这组证据说明两件事：最终成功率可能掩盖恢复不忠实；补上随机流位置能修好本次确定探针的路径回放。它**没有证明**随机流遗漏会怎样改变真实 LLM 的决策，也没有证明这一字段补齐后可执行状态已穷尽。不能把“修好一个具体遗漏”写成“完成通用 checkpoint 正确性证明”。

### AppWorld 与托管模型：两个不同层面的边界

附录 B.5 在 AppWorld 0.1.3.post1 检查 10 个任务各 5 次初始化，数据库摘要、时钟和 untouched-state 评分均一致；又在 5 个任务中执行包含一次写操作的短前缀，恢复 5 份副本、读取两步后，25/25 一致。值得注意的是，必须先重置具名内存数据库引擎缓存，否则直接复制数据库文件可能被静默忽略。这是作者自建文件级快照的缺陷，**不是对 AppWorld 官方 save_state/load_state 的失败判定**，后者未被此测量评估。

附录 B.7 则报告很小的托管模型观察：经第三方代理、温度 1.0、best-effort seed，三个相同请求形成四对可比较调用，没有一对逐字节复现；作者可控路径却复现了 34/34 次调用和 2/2 个 episode。56 次再生成中的 52 次已离开原关键路径，真正能逐调用比较的很少；响应也没有 system_fingerprint，无法排除 seed 被下游忽略。结论只限该托管路径，不能定位是模型、代理还是服务基础设施造成，更不能推广成所有托管服务必然不能做因果实验。

## TRACE 复现：作者也曾把不正确的解释套在复现差异上

附录 C 不只是旁注，它展示了报告规范应如何对作者自己的分析生效。TRACE 是一套 AppWorld 压缩前后配对续跑资料，含 590 个压缩边界、4,641 次续跑（4,640 次有评分）、20,133 步、147 个任务，其中 140 个有边界。作者只读重跑 revision 9be7d669。

初次使用 Python 3.10.8，六张输出表只有四张字节完全相同。两张有 bootstrap 区间的表不一致，作者当时错误地以为 bootstrap 没设种子，因而在看到失败后将验收改成点估计一致、区间重叠、显著性分类不变。

Table 5 表明，curves 的 285 行与 marginal 的 45 行均对应，330 个区间全部重叠，没有定性变化；最大点估计差约 1.33×10⁻¹⁵，最大端点差约 7.22×10⁻¹⁶。后来发现 bootstrap 实际设置了种子，而且项目要求 Python≥3.11。换成支持的 3.12.13 后，六张表全部逐字节一致、6/6 复现检查通过。差异与解释器引起的浮点差异相容，但作者没有隔离究竟是哪条求和路径，所以不能进一步写成已确定的底层机制。

**这里没有发现 TRACE 结果不稳健。**最初的失败首先是作者使用了不受支持的环境，并给出了错误解释；后来支持环境复现了原结果。诚实保留修订过程，比把极小浮点差讲成新的研究发现更有价值。

然而，统计产物复现与因果配对有效仍是两件事。TRACE 重新建环境、执行记录前缀，再放入压缩前或压缩后的历史；它用于确认身份的 recipe hash 来自任务、split、边界位置和前缀代码。输入配方相同，不直接证明到达的运行状态相同。作者的 AppWorld 小探针没有发现差异，但并未验证 TRACE 那 590 个真实边界。正确结论是**这些边界的状态配对缺少直接测量**，不是已发现它们实际上不同。

作者还撤下了一个原计划的“是否写过状态”前缀分类分析：所谓写操作主要是登录认证，标签实质可能只是轨迹已经走到哪一阶段。对 119 个 endpoint 函数的独立模型复核可以确认接口映射，却不能确认映射测到了研究构念。因此该分类不报告任何估计值。这与前面的载体测量一起提醒我们：标注规则正确执行，不代表问题定义正确。

## 八臂设计究竟要比较什么？这里全部是方案，不是结果

附录 D 提出未来怎样分离长度、错误内容和来源角色。作者重复说明尚未运行。正文若把 288 状态、成功率差或功效数字写成实测，就会颠倒论文证据。

### Table 6：八条臂和真正干净的对照

| 臂 | 看见的历史 | 用途 |
|---|---|---|
| 1 | 短的、已验证状态 | 短上下文参照 |
| 2 | 与长历史匹配长度和回合的无害内容 | 与 1 比长度负担 |
| 3 | 就地修正过错误的自有历史 | 内容修复参照 |
| 4 | 未修改的自有历史 | 与 3 比自然错误内容效应 |
| 5 | 匹配的真实外来错误，标为前一个 Agent | 内容与来源同时变化的探针 |
| 6 | 合成注入错误，仍标为自己 | 检验合成错误能否复现自然错误效应 |
| 7 | 固定错误包，归为自己 | 固定文字的来源对照 |
| 8 | 与 7 相同错误包，归为前一个 Agent | 与 7 比纯来源包装效应 |

长历史按具体 tokenizer 的 token 数与 assistant/tool 回合数匹配，只有短状态控制允许长度不同。操作只触及 assistant 侧文字，用户消息和工具输出相同。7、8 的错误包字节相同，区别只是来源包装，需哈希检查。**3–6 不是完整的 4×2 析因设计，只覆盖部分格子；5 也不是纯来源效应，因为它同时换了内容。**

构造历史的冻结 judge 不评最终结果，且计划先在人造损坏与盲化人工标注真实片段上达到 precision≥0.90、recall≥0.85。目标任务结果用确定程序评分。在预先指定的四分之一状态，还计划做两个模型间的双向交接。所有状态还须通过对本次策略、seed 和提供商适用的恢复验收，不能只靠五克隆内部一致。

### Table 7 的公式先按问题读

令 p 表示某条臂的精确续跑成功概率。长度负担 L=p短−p干净长：正值表示即使内容干净，历史变长也可能损害成功。

错误内容效应 Δerr=p修复−p自然：正值表示纠正自然错误后成功率增加。作者分别在早、晚两个时点估计。来源效应 Δprov=p同文字自有−p同文字外来：它的正负只描述包装的相对效应，不自动告诉我们自有历史一贯更可信或更有害。

Δforeign、Δsynth 用修复臂分别减外来、合成错误臂，再与 Δerr 比较。要声称它们复现自然错误效应，计划使用 ±5 个百分点的**等价检验**，区间两端都应在范围内；“差异不显著”不够。

次要指标 S 是“晚期相对早期新增的错误内容效应”，除以自然历史条件下从早到晚的成功率下降。它试图衡量：观察到的时程退化，有多大比例与错误历史效应增加相吻合。分母接近零时比值会很不稳定，因此只有分母至少 15 个百分点、分子符号稳定才报告，不截断到 [0,1]。若要说污染历史解释不到一半退化，还要求 95% 上界小于 0.5。

关键限制是：这些探针在不同内容分布上识别，**L、Δerr、Δprov 不是可相加的三个组成部分**，没有被识别的“剩余效应”。Table 8 给的是联合诊断模式：晚期内容修复效应大、外来和合成错误在 ±5 点内复现该效应、来源效应又小，才支持历史编辑方向；固定文字后的来源效应大且复现检验失败，则指向来源包装；长度负担大而匹配长度后的错误臂变化很小，才支持长度解释。这些仍是未执行设计的判读规则。如果都不清楚，只能说本设计没定位到原因，不能说没有别的机制。

### 功效分析为何也是论文必须读的负面结果

计划主通道用 144 个任务中的 288 个状态，每臂重复三次，按任务聚类。以成功率 0.4–0.6、任务内相关约 0.2 和用于规划的零状态内相关近似，臂差标准误约 3.0–3.5 个百分点，80% 功效、双侧 α=.05 可检测差约 8–10 个百分点。

这**不足以支撑 ±5 点等价范围**。作者估算需约 1,500 个有效配对或 pilot 中更准确的协方差，才能重新判断。36–48 状态的小环境与托管模型通道只适合很大效应的方向检查，约 20 点以上；S 的标准误约 0.3，区间宽约 ±0.55，也很难可靠判断是否小于 0.5。作者明确更正早稿中过于乐观的 4–5 点、8–12 点等功效数字。

这里可借鉴的不是照抄样本量，而是：**检测到方向、证明可忽略、证明两种干预等价，是不同难度的目标。**小样本不显著不能帮研究者免费完成等价结论。

## 文献普查测到了什么，又没测到什么

Table 10 中，“中途修改历史/状态并继续”的计数分别为 22 与 13；“恢复可执行状态并继续同一 Agent”分别为 1 与 3。Tables 11–12 进一步说明分歧：前一个问题一致率 32/41=78.0%、κ=.66，九个分歧全在中途干预和从起点改变系统设置的边界；后一个问题一致率 38/41=92.7%、κ=.70，但主要由 34 个一致的“否”构成，不能被高一致率掩盖。

因此，本节能支持的是：**在这组材料中，恢复与中途干预的术语边界不清，少数明确先例也缺乏作者要求的实测验证记录。**不能由 41 张二手卡片算出全领域可靠比例，更不能据零到两个计数宣布研究空白已被穷尽。附录 F 还披露了 LLM 用于载体复核、文献编码、工程和写作；这些是研究测量的一部分，需与独立标注或人工验证区分。

## 合在一起，论文到底建立了多强的结论

**它建立了四件值得保留的事。**

1. 完成轨迹上的失败标签不能单独识别历史因果作用；真实续跑和明确干预对象是更强证据的必要组成。
2. ActBench 的载体占比与任务分配、曝光恢复能力纠缠，作者自己的数据不足以支撑载体危险性比较。
3. 在模型无关的确定探针中，文件/消息哈希与克隆互相一致都可遗漏随机流位置；恢复位置后本次路径分歧消失。
4. 一份可解释的回放实验应把目标效应、状态恢复、原运行参照、过程指标、重复策略和验收边界一起报告。

**它没有建立四件更强的事。**它没有证明历史污染在真实 Agent 中造成多少失败；没有证明其八臂方案能提高定位或修复性能；没有证明所有被引用系统的回放实际错误；也没有给出跨平台、跨模型通用的完备状态证书。

两个警示测量不能合成一条强因果结论：第一个不可识别载体效果，第二个不用 LLM；它们的作用是说明为什么需要更好的实验，而不是代替那个实验。支持环境下的 TRACE 表格复现成功也应被完整保留，不能为强化批评而省略。

真正应带走的不是“多存一个 RNG 状态就好了”，而是三种区别：**材料相同与过程相同、过程相同与结果相同、验证某个探针与认证整个系统**。把这三组界限说清，才知道一个漂亮的对照到底排除了什么。

## 对当前 GraphLocator 研究：先让“自然臂”忠实，再解释“屏蔽臂”

以下是面向 GraphLocator 上下文反事实研究的迁移分析，不是本文实验结果，也不是已经实施的新实验。应把末端读出、某次工具观察分叉与整条动态策略干预分开；本文最直接补的是第二层在实施前的验证。

### 1. 把分叉对象写成一份可核验的状态契约

在首次合格 P 暴露前，不能仅恢复对话和仓库文件。还要按具体实现检查其他影响决策的状态，例如当时的 CIG、visited 集合、优先队列、候选注册表、缓存、工具子调用、模型配置与随机状态，并明确它们分别如何获得。若使用前缀重放，应比对**重放到达的状态及后续行为**，而不是只比较那段前缀代码的哈希。若最终图含未来边，不能拿它倒填中间图。

P 在此指似是而非、可能干扰定位的代码内容，I 指无关内容，C 指被审定为核心支持证据的内容。这些是研究者用于分配处理的 oracle 标签，不是可以直接喂给部署模型的答案。

### 2. 首先加入未编辑历史的回放参照

最小比较不是直接“自然、屏蔽 P、移除量匹配 I”三臂开跑，而是先问：自然恢复臂相对原轨迹续跑或独立前缀重建参考，下一次动作是否一致，读到的节点是否一致，图更新与最终定位是否一致？

如果服务端模型只能做分布级比较，就预先约定哪些动作/定位指标、什么等价容差、多少重复和怎样聚类。提供商的 seed 或温度 0 不能替代验证。不要把未显著观察到差异称为已经等价，也不要仅用最终 Recall 验收所有过程恢复。

### 3. 处理必须覆盖真正的暴露入口，但不能随意改变估计目标

如果 P 已经进入相关性子调用并改变种子，或者被 CIG 关联正文保留并再次发送，只改最后工具返回并不能测“未见 P”的反事实。需先列出本次干预要作用的具体消息面、子调用面和持久状态面。

但这不意味着无条件同时清空所有痕迹。冻结旧 CIG、只改下一次所见代码，研究的是给定旧状态的一步信息效应；从早期开始一致地屏蔽所有 P 暴露，让图与轨迹自然分叉，研究的是策略累计效果。两个设计都有价值，只是结论不同。

### 4. 完整 C 的保护约束决定哪些 P 可以被处理

若采用节点级标签，节点包围范围和真正 owned 源码不能混用，完整 C 内嵌的 P/I 也不能为了“删干净”而破坏 C。建议在设计中分别报告可操作的 P、受保护的残留 P、实际移除字节/token、候选身份变化和后续重复曝光。这样“屏蔽 P”才是一个有边界的处理，而不是标签上写了删除、实际又从另一路返回。

长度与候选数匹配依然重要，但它们不自动完成回放认证；回放认证也不自动完成语义内容控制。这是两组互补的检查。

### 5. 先把研究单位与失败条件固定下来

一次分叉可同时有下一动作、若干步的证据访问、末端定位三层结果。主指标、续跑预算、不可恢复状态的记录方式、无可处理 P 的排除规则，应在看到效果前确定。多次续跑不是多个独立任务，统计单位仍需保留任务聚类。

首个小样本可以用来验证输入恢复与处理可执行性，却不适合宣称 P 普遍比 I 更有害，更不应在已经反复用于调试的实例上挑最好结果。本文真正能帮助当前工作的，是让下一次实验即使效果不显著，也能清楚回答：**我们确实改变了什么，保持了什么，哪些轨迹能够被可信地放在一起比较。**
