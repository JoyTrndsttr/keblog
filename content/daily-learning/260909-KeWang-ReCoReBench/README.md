# ReCoRe-Bench：仓库上下文究竟能把代码精炼推进多远？

> 精读日期：2026-09-09  
> 论文：*Code Refinement with Repository Context: How Far are We?*  
> 作者：Ke Wang, Peng Lan, Jiakun Liu, Shengbing Ren, Lingfeng Bao, Junxiao Han, David Lo, Zhifang Liao  
> Venue：ACM Transactions on Software Engineering and Methodology, 2026  
> DOI：[10.1145/3820059](https://doi.org/10.1145/3820059)  
> 代码与数据：[JoyTrndsttr/RepoRefiner](https://github.com/JoyTrndsttr/RepoRefiner)

## 一张地图：这篇论文到底做了什么

过去的代码精炼通常把任务简化为“代码片段 + 审查评论 → 修改后代码”，但真实修改经常依赖当前片段之外的枚举值、API、调用关系和项目约定。论文先构建一个专门测量这种困难的 **ReCoRe-Bench**，再提出 **RepoRefiner** 检索并压缩仓库上下文，最后用 **ReDIs Match** 追踪关键标识符从检索、摘要、提示词到最终生成的流失。

最重要的结论不是“上下文越多越好”，而是：**文件内上下文能稳定提高关键标识符召回；跨文件上下文只有在检索准确且没有引入噪声时才有增益。即使模型已经看到关键信息，也常常无法在最终代码中正确使用。**

## 过去 → 问题 → 解法

### 过去怎样做

已有代码精炼方法多使用审查评论和局部代码片段。这个设定便于建模，却默认正确修改所需的信息已经出现在输入窗口中。论文对热门仓库的 150 个真实样本做人工检查：94 个需要仓库知识，31 个可由局部信息完成，25 个评论质量不足；两位标注者的 Cohen's κ 为 0.73。

### 真正的问题

如果修改必须使用仓库里已经定义的标识符，而模型根本没有看到其定义，那么失败不一定说明模型“不会改代码”，也可能只是任务输入缺失。反过来，把大量仓库文本塞进提示词又可能引入错误定义或无关概念。因此需要分别回答三个问题：

1. 现有模型在必须依赖仓库知识的任务上到底有多差？
2. 文件内与跨文件上下文分别贡献了什么？
3. 关键知识在检索、摘要、提示构造和生成的哪一步丢失？

### 论文的解法

论文把问题拆成“构造困难样本—提供仓库上下文—追踪信息流”三层：

`真实 PR / Review → 隐藏仓库标识符筛选 → ReCoRe-Bench → RepoRefiner 检索与摘要 → LLM 精炼 → ReDIs Match / EM / BLEU 评价`

## 四个核心概念

| 概念 | 直觉 | 它解决什么问题 |
|---|---|---|
| ReCoRe-Bench | 只保留修改时必须引入仓库既有标识符、且评论没有直接说出该标识符的实例 | 避免模型仅靠复制评论或局部代码完成任务 |
| ReDI | Repository-Defined Identifier，仓库中已有定义的标识符 | 把“是否利用仓库知识”变成可观测对象 |
| Added ReDI | 正确修订中新出现、原代码没有、评论也未明示的 ReDI | 测量最关键的隐藏仓库知识是否被恢复 |
| RepoRefiner | 检索完整文件与相关定义，再分别生成文件内和跨文件摘要 | 在提示预算内向模型提供结构化仓库上下文 |

## Benchmark 是怎样被筛出来的

原始数据有 254,678 个候选实例，最终只留下 1,000 个，来自 328 个仓库，语言分布为 Python 537、Java 225、JavaScript 238。

| 筛选阶段 | 剩余实例 | 占原始数据比例 |
|---|---:|---:|
| 原始候选 | 254,678 | 100% |
| 保留审查建议 | 209,707 | 82.34% |
| 新增代码不超过 6 行 | 180,810 | 71.00% |
| 可重建父提交 | 179,696 | 70.56% |
| 满足隐藏标识符约束 | 15,416 | 6.05% |
| 通过内部检查 | 7,234 | 2.84% |
| 去除冗余评论 | 3,784 | 1.49% |
| 人工确认 | 1,000 | 0.39% |

令原代码标识符集合为 `OI`，正确修订后的集合为 `NI`，则新增标识符为：

`AI = NI − OI`

其中，**ReHI** 是定义在仓库其他位置的新增标识符；**ReMI** 是评论中没有出现的新增标识符。Benchmark 要求 ReHI 和 ReMI 都非空，这意味着模型不能只复制评论，必须恢复仓库知识。

人工标注还区分“审查者要求的行为”与“开发者顺手做的修改”，只保留前者。两位标注者在该环节 κ=0.86，在方法类型标注上 κ=0.96。1,000 个实例中，920 个需要仓库上下文检索，63 个需要网站信息，17 个需要历史信息。

### 这里已经产生了怎样的选择偏差

这是一个有意构造的困难子集，不代表所有代码精炼任务。它还依赖提交可重建、语言可解析、静态分析工具可运行等条件。因此论文可以支持“模型在隐藏 ReDI 场景中仍很弱”，不能直接推出“模型在全部代码审查修改中都只有约 3% 的成功率”。

## RepoRefiner：输入到输出的完整链路

### Step 1：定位完整源文件

- 输入：OriginalCode、Review、ReviewLine。
- 动作：在父提交中定位局部代码所在文件并恢复完整内容。
- 为什么必要：局部片段可能看不到同文件中的常量、类型、辅助函数和异常分支。
- 输出：原始文件全文。
- 如果删掉：模型退回只看局部片段的 Simple Prompt，无法使用文件内定义。

### Step 2：生成文件内摘要

- 输入：完整源文件与当前审查任务。
- 动作：让模型提炼与修改有关的定义、控制流和项目约定。
- 为什么必要：完整文件可能很长，直接拼接会挤占上下文并增加噪声。
- 输出：In-File Summary。
- 下游用途：作为精炼提示中的第一层仓库知识。

### Step 3：解析相关标识符的跨文件定义

- 输入：OriginalCode 中的标识符。
- 动作：Python 使用 Jedi，Java / JavaScript 使用 Joern，结合 Tree-sitter 语法分析定位定义与数据流。
- 为什么必要：当前文件中的调用、类型或常量往往定义在其他文件。
- 输出：相关定义代码与位置。
- 关键限制：Java 泛型、链式调用以及 JavaScript 动态 import 会显著降低 Joern 的定位质量。

### Step 4：生成跨文件摘要

- 输入：相关定义代码与审查任务。
- 动作：压缩跨文件定义，形成 Repository-Level Summary。
- 为什么必要：将多个定义整理成模型可消费的上下文。
- 风险：检索错误或摘要选择错误会把“更多上下文”变成干扰项。

### Step 5：执行代码精炼

- 输入：ReviewLine、Review、OriginalCode、文件内摘要、跨文件摘要。
- 动作：LLM 生成 RefinedCode。
- 输出：预测修订。
- 设计控制：提示词沿用既有 simple prompt，并仅加入上下文摘要，使对比尽量聚焦于上下文贡献。

论文中的一个 pytest 案例很直观：评论说 `INTERNAL_ERROR` 不应表示用户空间错误。无上下文模型猜了一个未定义的 `TESTS_FAILED`；文件内摘要揭示已有的 `USAGE_ERROR`，模型才生成完全正确的修改。跨文件摘要在该例中没有增加关键知识，反而可能强化错误的 `INTERNAL_ERROR`。

## 评价指标：为什么 BLEU 不够

### ReDIs Match（RM）

把预测代码中出现的仓库定义标识符与正确修订中的 ReDI 集合比较：

- Recall@RM：正确 ReDI 中有多少被预测代码使用。
- Precision@RM：预测使用的 ReDI 中有多少属于正确集合。
- F1@RM：召回与精度的调和平均。

它测量整体仓库标识符一致性，但可能被原代码里已经存在的大量标识符“稀释”。

### Added ReDIs Match（ARM）

ARM 只评价正确修订中新增加的 ReDI，因此更接近论文的核心问题：模型是否恢复了评论未明说的关键仓库知识。

直觉上：Recall@ARM 高说明关键标识符找得多；Precision@ARM 高说明没有随意引入错误的仓库标识符；F1@ARM 同时惩罚遗漏与乱猜。

> 公式核查：论文公式排版中 `F1@ARM` 的分子写成了 `Precision@RM × Recall@ARM`，而分母使用 `Precision@ARM + Recall@ARM`。这看起来是一个排版不一致；按标准 F1 定义，分子应使用 `Precision@ARM × Recall@ARM`。这是读者核查，不是论文明确给出的勘误。

### EM、BLEU 与 CodeBLEU

Exact Match 要求预测与人工修订完全一致，过于严格；BLEU 偏好表面 n-gram 重合，可能惩罚等价实现、注释和中间变量；CodeBLEU 虽加入语法和数据流，仍不能证明代码能编译、通过测试或满足评论意图。RM / ARM 补足“仓库标识符是否正确”的维度，但同样不能证明标识符被正确使用。

## RQ1：现有模型在 ReCoRe-Bench 上表现怎样

### 研究设计

- 模型：CodeReviewer 223M、LLaMA-3-8B、DeepSeek-R1-Distill-Llama-8B、DeepSeek-R1、GPT-4o。
- Baseline：Simple Prompt、Self-Generated Context、RAG（BM25 检索 3 个示例）。
- Treatment：在相同任务提示上加入 RepoRefiner 生成的仓库上下文。
- 指标：RM、ARM、EM、EM-T、BLEU、BLEU-T、CodeBLEU。

### 结果

| 观察 | 数值证据 | 应怎样解释 |
|---|---|---|
| 既有设置的最佳 EM 很低 | DeepSeek-R1 + RAG 为 2.6% | 隐藏仓库知识场景对现有方法很困难 |
| 加入仓库上下文后的最高 EM | DeepSeek-R1 为 3.0% | 有改善，但绝对成功率仍很低 |
| DeepSeek-R1 的 ARM Recall | Simple 16.52% → Repo 20.01% | 关键新增标识符召回相对提高约 21%，但仍漏掉约 4/5 |
| 上下文的统计显著性 | 四个 LLM 的 p 值均小于 4.58×10⁻⁸ | 数据支持上下文与 ARM 改善相关；还需看效应量和实际价值 |
| BLEU 的方向 | Repo 上下文并不总有更高 BLEU | 表面重合与仓库知识利用不是同一构念 |

### 本题结论

论文证明了：仓库上下文能帮助模型恢复更多关键标识符。论文没有证明：模型已经可以可靠自动完成仓库级代码精炼。3.0% 的最高 EM 与 20.01% 的最佳 Added ReDI Recall 恰好说明距离可靠仍很远。

## RQ2：文件内与跨文件上下文分别贡献什么

### 消融设计

1. Simple：无额外上下文。
2. InFile：只加入文件内摘要。
3. Repo：文件内摘要 + 跨文件摘要。

总体上，InFile 和 Repo 相比 Simple 在 RM 上的 p 值为 2.4×10⁻⁴ 和 2.8×10⁻⁵，在 ARM 上为 1.4×10⁻⁶ 和 4.6×10⁻⁸。说明“加入上下文”有效，但不等于“跨文件部分额外有效”。

以 DeepSeek-R1 的 ARM Recall 为例：

| 语言 | Simple | InFile | Repo | 读法 |
|---|---:|---:|---:|---|
| Python | 17.62 | 21.28 | 22.02 | 文件内收益明显，跨文件仅小幅增加 |
| Java | 20.56 | 19.72 | 21.81 | 文件内甚至下降，完整上下文后回升 |
| JavaScript | 10.22 | 14.43 | 13.80 | 跨文件上下文引入后下降 |

文件内上下文在 Python、Java、JavaScript 上的召回改善 p 值分别为 5.1×10⁻⁴、0.063、2.0×10⁻⁴；Java 并未达到常用的 0.05 阈值。继续加入跨文件上下文的 p 值为 0.58、0.44、0.80，均不显著。

### 本题结论

文件内上下文是更稳定的收益来源；跨文件上下文的平均增益不显著，且会因错误定位和噪声产生负效应。语言差异不是模型能力的纯粹差异，它还混入了 Jedi 与 Joern 的工具能力差异。

## RQ3：关键信息在哪里丢失

论文逐步测量 Added ReDI 在“原始检索 → 摘要 → 提示词 → 最终输出”中的覆盖率。以下为 Python / Java / JavaScript 的 Recall（%）：

| 阶段 | Python | Java | JavaScript | 观察 |
|---|---:|---:|---:|---|
| 文件内原始检索 | 76.80 | 73.17 | 85.89 | 大部分关键信息其实能在完整文件中找到 |
| 跨文件原始检索 | 47.42 | 28.25 | 15.43 | 静态工具对 Java / JS 的跨文件召回明显不足 |
| 合并原始上下文 | 82.78 | 73.39 | 85.89 | JS 几乎没有从跨文件检索获得额外覆盖 |
| 文件内摘要 | 16.46 | 17.80 | 18.30 | 摘要阶段发生第一次巨大信息损失 |
| 仓库级摘要 | 23.25 | 20.82 | 20.26 | 跨文件摘要只恢复少量信息 |
| Repo Prompt | 30.53 | 27.14 | 30.45 | 提示里出现不代表模型会使用 |
| DeepSeek-R1 最终输出 | 20.17 | 20.09 | 14.85 | 生成阶段再次丢失，JS 甚至低于 InFile |

这张表是全文最有研究价值的结果：**information access ≠ information use**。把正确标识符放进上下文，只解决了可见性；摘要是否保留、提示是否突出、模型是否绑定到正确修改位置，仍是独立问题。

## 案例研究补充了什么

论文对 96 个分层样本检查“上下文是否有用”和“哪种方法更好”，排除 4、3、9 个无法可靠分析的实例；κ 分别为 0.84 和 0.76。低 ARM 组里 Self-Generated Context 在 71.43% 的案例更好，高 ARM 组里 Repo-Context 在 78.26% 的案例更好。低 BLEU 案例中只有 7.31% 真正质量更差，说明 BLEU 的测量偏差很严重。

对 InFile 提升样本的分析包含 50 个实例（排除 3 个，κ=0.78），超过一半的文件内上下文提供了关键标识符；JavaScript 中有用比例达 72.7%。跨文件分析取提升和下降各 36 个实例（κ=0.92）：Python 提升组 75% 的跨文件上下文有用，JavaScript 只有 18.2%；下降组几乎没有新增的有用信息。

## 证据审计：结论能走多远

| 风险 | 具体表现 | 对结论的影响 |
|---|---|---|
| 选择偏差 | 只保留可重建、可解析、需要隐藏 ReDI 的困难实例 | 不能外推到全部代码精炼任务 |
| 测量偏差 | EM、BLEU、RM/ARM 都不执行代码 | 不能证明语义正确、编译成功或测试通过 |
| 工具链混杂 | Python 用 Jedi，Java/JS 用 Joern | 语言差异同时反映检索工具差异 |
| Treatment 不纯 | “Repo Context”同时改变检索结果、摘要内容和提示长度 | 不能把效果只归因于跨文件知识本身 |
| 摘要器与生成器耦合 | 模型生成摘要后又使用摘要 | 上下文质量没有独立校准，错误可能自我强化 |
| 显著性不等于实用性 | 报告 p 值，但效应量与置信区间不突出 | 大样本下的小改善也可能显著 |
| Ground truth 单一 | 以历史人工 patch 为唯一参考 | 其他语义正确实现可能被 EM / ARM 惩罚 |
| 案例排除 | 无法提取或判断的样本被排除 | 解释性案例可能高估可分析场景中的效果 |

论文报告的成本约为每实例 2,338 个输入 token；GPT-4o 平均约 0.025 美元，DeepSeek-R1 约 0.026 美元，时延约 21.4 秒/实例。该预算说明方法可运行，但距离真实审查工作流仍需要端到端延迟、失败恢复和增量索引评测。

## 已证明、未证明、需要记住

### 论文较有力地证明了

- 局部代码 + 评论对一类真实代码精炼任务确实不充分。
- 文件内上下文能稳定提高关键新增仓库标识符的召回。
- BLEU 与仓库知识利用之间存在明显错位。
- 信息会在摘要与最终生成阶段大量流失，检索到不等于利用到。

### 论文没有证明

- RepoRefiner 生成的代码具有普遍的功能正确性。
- 跨文件上下文在平均意义上稳定优于文件内上下文。
- 语言间差异来自语言本身，而非静态分析工具。
- 观察到的指标提升一定转化为真实审查效率或代码质量提升。

### 一句话记忆

> 仓库级代码精炼的主要瓶颈已经从“模型看不到知识”推进到“检索、压缩和生成能否共同保住并正确使用知识”；最可靠的第一步往往是完整当前文件，而不是盲目扩大跨文件上下文。

## 下一步研究：与“代码审查中的因果推断”连接

1. **检索质量的随机干预实验**：固定同一任务，随机提供正确跨文件定义、相似但错误定义、无上下文，估计不同上下文质量对功能正确率的因果效应。
2. **分解总效应**：把 Pipeline 分成 Retrieval、Summarization、Prompt Salience、Generation 四个 Treatment，使用因子实验测量主效应与交互效应。
3. **异质性效应**：预先定义语言、调用深度、标识符类型、文件规模和评论明确度，研究哪些任务真正受益于跨文件上下文。
4. **替换 Outcome**：以测试通过、编译、静态契约、评论意图满足和专家盲评为主要结果；ARM 作为机制变量，而不是最终正确性的替代品。
5. **预算公平**：比较方法时固定 token、时延或成本预算，避免“更多上下文”与“更多计算”不可分。
6. **信息流可观测化**：让每次生成显式引用其使用的定义位置，测量“检索到 → 摘要保留 → 声称使用 → 实际正确使用”的转化率。

## 精读后的判断

这篇工作的最大贡献不是把 EM 从 2.6% 推到 3.0%，而是构造了一条可审计的证据链：先限定必须依赖仓库知识的任务，再用标识符指标观察知识，最后定位知识在哪个阶段流失。下一轮研究最值得做的不是继续堆上下文，而是把上下文质量当作可操纵变量，把功能正确性当作 Outcome，真正识别“什么上下文、在什么任务上、通过什么机制产生帮助”。
