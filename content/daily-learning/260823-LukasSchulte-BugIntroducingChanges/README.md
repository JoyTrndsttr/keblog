#### 必读一：为什么需要宽变量数据集

作者指出，假设观察到：

- 做过代码审查的提交缺陷更少；
- 测试更充分的提交缺陷也更少。

如果代码审查与测试经常一起发生，只单独研究其中一个，就无法判断：

- 是代码审查有效；
- 是测试有效；
- 两者都有独立作用；
- 只有二者组合才有效；
- 或二者都只是项目成熟度的代理变量。

因此，作者不急于估计某一个 treatment，而是先同时采集完整开发过程。

直观上，这是一项**因果问题的数据可行性调查**：先弄清楚哪些变量能够测到、哪些严重缺失、哪些变量经常共同变化，再决定未来的 DAG 和识别策略。

> **读完这一节，你只需要记住：因果代码审查的数据集不应从“有哪些容易挖的审查指标”出发，而应从完整 data-generating process 出发。**

#### 必读二：样本和对照如何构建

- **Bug group：** 71 个经过人工验证的缺陷引入提交；
- **Control group：** 71 个未被识别为缺陷引入的提交；
- **项目：** OpenStack Nova 与 Elasticsearch；
- 每个对照提交从相应缺陷提交前后 **±30 天**内随机抽取；
- 合并提交被排除；
- 因变量是提交是否属于 bug-introducing change。

这种时间邻近配对有助于控制项目演化阶段，但它不是严格的 matched causal design：

- “没有被识别为缺陷引入”不等于真的没有引入缺陷；
- 对照没有按修改规模、文件类型、作者经验或任务难度配对；
- 两个项目工具链不同，项目本身可能决定变量是否可观测。

> **读完这一节，你只需要记住：±30 天只控制了时间邻近性，并没有平衡代码变更难度和开发者背景。**

#### 必读三：81 个变量如何变成候选因果结构

作者从 Issue、邮件列表、其他讨论渠道、CI、构建、Commit、测试和 Code Review 中收集 **81 个变量**，其中约 40 个需要人工编码。

随后分析全部 **3,552 个变量对**：

- 数值—数值：Spearman 相关；
- 类别—类别：列联表及 Fisher 精确检验；
- 类别—数值：主要进行可视化比较；
- 再由研究人员把变量对归入 G1、G2、G3 或数据不足类别。

核心解释是：

- **G2：** 两组中都有相似关系，可能表示开发过程内部的中介链、共同原因或其他结构关系；
- **G3：** 关系在 bug 与 control group 间不同，被作者视为更值得检查的潜在混杂或结果相关关系。

需要谨慎：G2/G3 是探索性关系分类，不等同于 DAG 中已经确定方向的边，更不等同于 confounder identification。

> **读完这一节，你只需要记住：它生成的是“应由领域知识继续审查的候选边”，不是从数据中恢复出的可信因果图。**

#### Research Question 与证据链

**RQ 问什么**

哪些软件工程实践出现在缺陷引入过程，它们与非缺陷引入提交有何不同？

→ **作者怎么研究**

人工重建 142 个提交的完整开发过程，收集 81 个变量，分析 3,552 个变量对，再合并成 19 个逻辑组。

→ **数据、比较与指标**

- 71 个 bug-introducing commits；
- 71 个时间邻近 control commits；
- 变量对是否呈现相同关系或组间差异；
- Krippendorff’s α 衡量人工编码一致性；
- Fisher 检验与 Spearman 相关辅助判断。

→ **最关键结果**

- 3,552 个变量对中，**1,958 对（55.1%）**至少一组数据不足；
- **530 对（14.9%）**在两组中都不足，无法解释；
- 只有 **74 对（2.1%）**归为 G2；
- **157 对（4.4%）**归为 G3；
- 阈值从 6 调到 8 时，约 **14%**变量对改变分组；从 8 调到 10 时仍有 **不足 9%**改变；
- 19 个逻辑组中有 17 个存在有效关系；
- G3 的五组“强关系”中，四组都涉及讨论频率。

→ **实际上能支持多强的 claim**

可以支持：

> 软件开发实践高度相互依赖，未来研究代码审查与缺陷的关系时，应扩大候选混杂变量范围。

不能支持：

> 某种代码审查实践导致缺陷增加或减少。

论文作者在 Threats 中也明确承认，它测量的是相关关系，无法排除混杂，因而不提出因果结论。

#### 数据集、基线与指标

- **Dataset：** Nova 与 Elasticsearch；71 个缺陷引入提交及 71 个对照提交。
- **任务单元：** 一个提交及其关联 Issue、Review、CI、测试、邮件和代码历史。
- **Baseline：** 同项目、时间相邻且未被识别为缺陷引入的提交。
- **核心指标：**
  - G1/G2/G3：变量对关系模式；
  - Fisher/Spearman：是否存在统计关联；
  - Krippendorff’s α：人工编码可靠性；
  - threshold sensitivity：分组对稀有类别阈值的稳定程度。
- **无需关注：** 绝大多数单个变量的详细编码值，除非你准备复用数据集。

#### 可核验的核心结果

1. 数据包含 **71 + 71 = 142 个提交**，来自两个项目。（Sec. 1、4.1）
2. 共定义 **81 个变量**，产生 **3,552 个变量对**。（Table 2、Sec. 4.4）
3. **55.1%** 的变量对至少一组数据不足，另有 **14.9%** 两组都不足。（Fig. 6）
4. G2 和 G3 分别只有 **74 对（2.1%）**和 **157 对（4.4%）**。（Sec. 5.2）
5. 作者进行了 **5,680 次 Fisher 检验**，其中 559 次显著；113 次 Spearman 检验中 20 次显著。（Sec. 5.3）
6. 19 个逻辑组中，17 个存在有效关系；与代码审查相关的潜在外部因素包括 Issue 管理、讨论主题、CI 和重构。（Fig. 13、Sec. 6.1.1）

#### 局限与可质疑点

**作者承认的局限**

- 只有两个开源项目；
- 仅有 71 个缺陷引入提交；
- 很多历史 CI 和讨论数据不可获得；
- 多个人工变量的一致性低于 Krippendorff’s α = 0.667；
- 只能发现相关关系，不能排除混杂或进行因果推断。

**进一步值得质疑**

1. **多重检验问题非常严重。** 5,680 次 Fisher 检验没有多重比较校正。在原假设全部成立时，按 5% 阈值本就预期约 284 个“显著”结果。因此“显著比例超过 5%，所以不太可能偶然产生”的论证不足。
2. **控制组可能误标。** 未被 SZZ 识别为 bug-introducing 不代表真实无缺陷。
3. **任务难度未匹配。** 修改规模、变更类型、作者经验和模块复杂度都可能同时影响审查强度与缺陷。
4. **从关联到 confounder 跳得太快。** 变量与 treatment/outcome 相关并不能决定它是混杂、中介、碰撞点还是结果。
5. **数据缺失可能不是随机的。** 没有 Review、Issue 或 CI 记录本身可能由项目流程和任务类型决定。
6. **人工共识不等于测量正确。** 两名编码者事后协商一致可以形成最终标签，但不能完全消除 construct validity 问题。
