# CRJudgeBench：AI 能识别“看起来合理但技术上错误”的代码评审吗？

> 精读日期：2026-10-02  
> 论文：**CRJudgeBench: Can AI Detect Plausible but Invalid Code Reviews?**  
> 作者：Yue Pan, Jiawei Li, Ziyuan Zhang, Xiangxin Zhao, He Ye  
> 机构：University College London、Amazon、Zhejiang University  
> 通讯作者：He Ye（原文明确标注 correspondence）  
> Venue / 年份：arXiv / 2026  
> 原文：[arXiv:2609.37216](https://arxiv.org/abs/2609.37216) · [HTML 全文](https://arxiv.org/html/2609.37216v1) · [数据集](https://huggingface.co/datasets/dcloud347/CRJudgeBenchmark)  
> Tags：Code Review · Repository Context · Agentic Judge · Plausible Error · Benchmark · Action-level Distillation

CRJudgeBench 研究的不是“AI 能不能生成一条像样的评审意见”，而是更靠后的质量闸门：给定一条已经生成的评论、对应补丁和仓库，AI 能否判断评论中的技术断言是否真的成立、是否指向正确代码位置。作者构建了 1,199 个专家核验实例，并训练 repository-grounded agent **Sentinel** 主动搜索证据。Sentinel 在 359 个测试实例上达到 76.60% 准确率，但对不可信评论的召回仍只有 37.69%。

论文最值得记住的并不是“76.60%”本身，而是一个极不对称的错误结构：测试集中可信评论占 63.79%，所有模型却把至少 85.52% 的评论预测为可信；Claude-Opus-5 与 GPT-5.5 的该比例甚至达到 94.99%。模型很擅长为一条流畅、相关的评论找到支持，却很难主动证伪一个貌似合理的技术断言。

## 一、先建立全文地图

### 研究矛盾

自动代码评审通常把目标定义为“发现问题并生成评论”。但一条评论可以语言流畅、位置相关、建议具体，同时在程序行为上是错的。开发者若直接相信这种评论，轻则浪费核查时间，重则把正确代码改坏。因此，生成能力和评审意见的**技术可信性判断**是两个不同任务。

以往评价主要有三类：与参考评论做文本相似度；让 LLM 按相关性、完整性等维度打分；用测试或人工反馈评价端到端效用。这些方式都没有直接回答：**评论的核心技术断言在当前补丁及仓库版本中是否成立？**

作者把这个 gap 转成如下证据链：

```text
自动评审会生成大量流畅但可能错误的评论
    ↓
把单条评论的“技术可信性”定义为独立二分类任务
    ↓
从真实 PR 与人工扰动构造可信 / 不可信评论
    ↓
让 agent 在 base commit、PR patch 和仓库中主动找证据
    ↓
用带私有真值的教师纠正关键搜索动作，再蒸馏给学生
    ↓
比较整体准确率、正负类 precision / recall / F1
    ↓
发现：专门训练能减少盲目信任，但“证伪”仍远难于“确认”
```

### 理解全文需要的四个概念

1. **技术可信性（technical trustworthiness）**：评论的核心技术断言必须正确，并且 inline 评论要附着在正确文件/位置。一个说法即便在别处成立，只要挂错位置，在本文标签中仍是不可信。
2. **plausible but invalid review**：读起来合理、涉及真实符号或常见缺陷模式，却与当前补丁或仓库事实不一致的评论。它不是乱码或随机文本，困难正来自表面合理性。
3. **repository-grounded judge**：判断器不能只读评论文本，而要搜索定义和用法、检查 patch、区分修改前与修改后版本，必要时执行聚焦测试。
4. **action-level distillation**：学生不直接模仿教师的整段答案，而是在自己实际走到的轨迹状态上，学习教师建议的下一步工具动作与理由。

## 二、作者怎样把“可信”操作化

一个实例围绕 PR 中的一条目标评论构建。模型可见：

- PR 的 base commit、标题和正文；
- 评论正文、评论路径、diff hunk 与类型；
- 单独保存、尚未应用的完整 review patch；
- checkout 到 base commit 的隔离仓库；
-项目语言。

模型不可见后续回复、作者身份、review state、真值标签、扰动类型、是否为合成负例及原始样本键。每个任务运行在断网 Docker 环境，仓库保持 base 版本；如果需要查看修改后行为，agent 必须复制仓库并应用 patch。

这项版本分离非常重要。论文的 “Unused import” 案例中，学生在 base 文件里搜不到 PR 新增的 import，准备判断评论错误；教师提醒它：base 中不存在，并不能说明 patched version 中不存在，下一步应直接抽取目标文件的 patch 区段。这个例子把 repository-grounded judgment 的核心讲得很清楚：不是“搜到相似代码”就结束，而是要让证据与评论所指的**版本、符号和位置**对齐。

这一定义也有边界。Boolean 标签把多种情况压在一起：技术断言错误、符号错误、位置错误都记为 false；严重性、是否值得修、是否符合开发者偏好不是主要判据。它适合评价 factual validity，却不等于一条评论的总体 usefulness。

## 三、CRJudgeBench 怎样构建

### 3.1 从真实 PR 逐层过滤

作者从 GitHub star 最高的 1,000 个 Python 项目出发，保留累计 PR 超过 1,500、且在 2024-08-15 至 2025-08-15 仍有提交或 PR 活动的项目。随后收集 106,241 个 PR，通过 LLM 排除描述缺乏技术内容、依赖不可获得外部信息或少于 40 词的 PR。

两名拥有五年以上 Python 代码评审经验的专家随机核验 383 个 PR 的筛选结果；无法达成一致时由第三位专家裁决。筛选后得到 7,086 个 PR。对其中所有非 PR 作者写出的评审评论逐条建实例，共 76,190 条。

接着经过规则过滤：

- 去掉 bot 评论；
- 去掉 patch 超过 200,000 字符的实例；
- 去掉过短评论、简短致谢与短 “LGTM”；
- 再由 LLM 去掉社交、赞美、重复、纯格式以及依赖外部背景的评论。

规模依次降至 67,458 和 48,027。由于全部人工标注成本过高，作者只对 star 数最高的十个仓库中的 1,031 个实例进行联合人工审查，最终得到 764 个真实可信评论和 65 个真实不可信评论。

### 3.2 为什么还要生成 370 个扰动负例

自然数据高度不平衡：829 个可用真实评论中只有 65 个 false。作者从三位专家共同确认的正例出发，保持 PR、patch 与其他上下文不变，只修改评论文本或位置，构造 370 个负例：

| 扰动 | 数量 | 改了什么 | 想制造的错误 |
|---|---:|---|---|
| Negation | 130 | 翻转一个肯定/否定表达 | 断言方向错误 |
| Symbol | 88 | 替换被引用的代码符号 | 内容像真的，但实体对不上 |
| Location | 152 | 评论文本不变，换成同一 PR 中另一评论的文件和 hunk | 技术说法可能成立，但挂错位置 |

所有扰动都经三名 Python 专家联合检查，只有在新上下文中确实错误的才保留。最终数据为 1,199 条：764 true、435 false。

这套构造非常接近反事实思路：固定 PR 与仓库事实，只改变评论的一个局部属性。尤其是 symbol 和 location 扰动，确实能制造“高度相关、却不适用于此处”的难例。不过它主要证明判断器能否发现**局部语义不一致**，不等于覆盖真实 AI review 的全部失败模式。

### 3.3 数据划分

作者按 PR 而非单条评论划分，确保同一 PR 的实例不会跨 train/test。初始训练池 840 条、测试集 359 条；训练池再划出 126 条验证集，最终训练 714、验证 126、测试 359。测试集包含 229 个可信和 130 个不可信评论。

PR-disjoint 能阻止同一补丁泄漏，却不是 repository-disjoint：同一仓库仍可能同时出现在训练和测试中。模型可以学习项目结构、命名与常见模式。因此结果说明对“未见 PR”有泛化，不能直接写成对“未见仓库”泛化。

## 四、Sentinel 怎样从学生错误中学习

### 4.1 学生先真实运行，而不是先看教师答案

Sentinel 以 Qwen3-Coder-30B-A3B-Instruct 为基座，使用 mini-swe-agent。学生每轮只能调用一次 bash，最多 30 个模型调用，单任务 wall time 上限为 900 秒。它要自行读取 task、搜索仓库、检查 patch，最后提交 Boolean 判断。

作者收集学生在 714 个训练任务上的 ReAct 轨迹。教师不替学生从头完成整题，而只在三个代码评审关键状态后介入：

1. 搜索评论涉及的代码符号后；
2. 检查相关 diff hunk 后；
3. 准备进行最终判断时。

选择这些状态有两个目的：把监督集中在最可能改变判断的步骤，并控制教师调用成本。但“这三个状态最关键”本身来自作者结合既有评审研究作出的设计选择，论文没有与全轨迹监督做对照。

### 4.2 教师拥有标签，但不能把标签泄露给学生

教师使用 GPT-5.6 Sol，并获得学生当前历史、候选动作和私有人工标签。标签的作用不是让教师直接说答案，而是帮助它判断还缺什么证据。教师可以返回：

- 一个可执行的 bash 检查动作；
- 已有证据充分时的 finish；
- 证据与标签冲突、无法合理消解时的 needs_review。

教师必须基于学生已经看见的事实解释下一步，不得假装知道尚未执行命令的结果。每个 prefix 最多沿同一纠正分支再提出三步，因此每条分支最多四个教师动作。

### 4.3 独立 reviewer 再审查教师动作

教师建议执行后，另一个 reviewer 会看到真实执行结果，检查该动作是否：

- 推进了技术/位置验证；
- 使用了正确代码版本；
- 没有泄露答案；
- 没有把未来观察伪装成已有事实；
- 对最终判断提供了真实证据。

只有通过 reviewer 的动作才进入训练集。这里的 reviewer 使用与教师相同的模型和配置，只是独立会话。因此它减少了明显的执行错误和标签回声，却不是来自不同模型或人工专家的完全独立验证。

### 4.4 损失函数的直觉

每条训练记录由轨迹前缀 $h$ 与教师核验动作 $a^*$ 组成。优化目标是：

$$
\mathcal{L}_{action}(\theta)=
-\frac{1}{Z}\sum_{(h,a^*)}\sum_j
\log \pi_\theta(a_j^*\mid h,a_{<j}^*)
$$

直觉很简单：历史只作为条件，不计算损失；模型只学习“在这个已发生的状态下，下一步应怎样搜、怎样调用工具或何时结束”。这样无需取得教师 logits，也不要求教师与学生词表相同。

作者进行两轮迭代。第一轮得到 4,622 个动作样本、覆盖 701 个训练任务；第二轮 4,646 个样本、覆盖全部 714 个任务。每轮学生更新后重新 rollout，教师再纠正新策略实际遇到的状态。训练只更新 LoRA adapter，基座参数冻结；LoRA rank/alpha 为 16/32，可训练参数约 1,337 万，使用 4 张 H100 80GB。

## 五、实验坐标系

测试集固定为 359 条，包括 229 true 与 130 false。所有模型都放入同一个 mini-swe-agent 框架，以相同任务接口访问仓库。基线包括 GLM-5.3、kimi-k3、Claude-Opus-5、DeepSeek-V4.1-Flash、GPT-5.5 以及 Sentinel 的未训练基座 Qwen3-Coder-30B-A3B-Instruct。

指标不仅给 overall accuracy，还分别给 true/false 类的 precision、recall 和 F1。这一点必要，因为类别不平衡且模型存在强烈的 “true” 偏置；只看 accuracy 会掩盖几乎不会拒绝错误评论的问题。

论文采用一个较特殊的计分协议：若最终 Boolean 与标签一致，计为正确；或者模型在轨迹中明确发现并正确修复了评论的技术错误，即使后续是基于“修正后的评论”做判断，也计为正确。这个规则承认模型可能先校正命题再回答，但也使 accuracy 不再完全等价于最终分类接口的准确率。工程部署若只读取最终 JSON，实际收益可能低于论文计分。

## 六、主结果：整体准确率提升来自更愿意说“不”

| 模型 | Accuracy | True Recall | False Recall | False F1 |
|---|---:|---:|---:|---:|
| Sentinel | **76.60** | 98.69 | **37.69** | **53.85** |
| GLM-5.3 | 70.47 | 98.69 | 20.77 | 33.75 |
| kimi-k3 | 69.92 | 98.69 | 19.23 | 31.65 |
| Claude-Opus-5 | 67.13 | 98.69 | 11.54 | 20.27 |
| DeepSeek-V4.1-Flash | 65.74 | 96.07 | 12.31 | 20.65 |
| GPT-5.5 | 65.46 | 97.38 | 9.23 | 16.22 |
| Qwen3-Coder-30B-A3B | 56.82 | 87.77 | 2.31 | 3.73 |

Sentinel 正确判断 275/359，较最强 baseline GLM-5.3 高 6.13 个百分点，较自己的 base model 高 19.78 个百分点。两者 true recall 同为 98.69%，真正拉开差距的是 false recall：20.77% 对 37.69%。

换句话说，Sentinel 并不是主要靠更会确认正确评论获胜，而是通过训练学会了更多证伪路径：核对符号、区分 base 与 patched version、检查评论位置。但即便如此，它仍漏掉 62.31% 的不可信评论，远未达到可替代人工把关的水平。

论文没有给出置信区间、显著性检验或多次运行方差。359 个测试实例足以显示较大差异，但不能从单次点估计判断小差距是否稳定，也无法知道采样随机性对 agent trajectory 的影响。

## 七、最强现象：模型普遍倾向于相信评论

测试真值中 true 占 63.79%，但各模型预测 true 的比例是：

- Claude-Opus-5：94.99%；
- GPT-5.5：94.99%；
- DeepSeek-V4.1-Flash：93.04%；
- kimi-k3：92.20%；
- GLM-5.3：91.64%；
- Qwen3-Coder base：91.36%；
- Sentinel：85.52%。

这说明高 true recall 不能单独理解为“模型善于验证正确评论”，很大一部分来自默认接受。Sentinel 虽把接受率降到最低，仍比真实 true 比例高 21.73 个百分点。

一种合理解释是确认偏误式搜索：评论先给出一个技术叙事，agent 随后更容易寻找支持它的代码片段，而不是主动寻找反例。论文结果与这种机制一致，但没有通过轨迹标注或受控干预直接证明它。要把“默认信任”提升为机制结论，还需要比较支持性搜索、反证搜索、停止时机和证据覆盖。

## 八、跨仓库差异：有现象，但不能归因于规模

Figure 5 显示仓库间准确率差异很大。PostHog 有约 1,011 万行代码和 63,042 次提交，各模型准确率只有 59.46%–67.57%；较小的 AutoGPT 上，各模型约为 80.00%–82.50%，ComfyUI 上 Sentinel 与 Claude 分别达到 83.33% 和 100%。

作者据此提出，仓库规模和历史可能影响判断难度。这个解释有直觉，但图本身只显示相关性：仓库同时在评论类型、正负比例、语言构成、patch 大小和任务难度上不同，且仓库数很少。论文没有做多变量回归或分层匹配，所以不能说“大仓库导致准确率降低”。

更稳妥的结论是：benchmark 存在明显 repository heterogeneity，单一总体 accuracy 会掩盖部署风险。后续应同时报告宏平均、仓库内 class balance、评论类型和工具预算。

## 十、Baseline 与消融审查

将所有模型放入相同 agent scaffold 是合理比较；base Qwen 与 Sentinel 的差值也能说明“训练后的整体系统”优于原始基座。可是，论文没有报告以下关键消融：

- 只用最终 true/false 标签做普通监督微调；
- 直接模仿教师完整轨迹；
- 去掉 teacher private label；
- 去掉 reviewer verification；
- 一轮训练与两轮训练；
- 只监督 search、只监督 patch inspection 或只监督 final reasoning；
- 相同训练成本下更大 base model。

因此 19.78 个百分点提升不能单独归因于 iterative action-level learning 的某一个设计。它是教师模型、私有标签、关键状态选择、动作监督、reviewer 过滤、两轮 rollout 与 LoRA 的组合效应。

论文也没有报告每个模型的平均工具调用、token、时间、失败率或测试执行次数。Sentinel 可能更准确，但是否以显著更高探索成本换来，没有证据回答。

## 十一、负例构造是亮点，也是最大证据边界

370 个合成负例保持仓库与 patch 不变，只改评论，这为研究“评论局部错误”提供了干净对照。尤其 location perturbation 很有价值：评论文本本身没有任何异常，只有结合正确位置才能判断。

但数据集中 435 个 false 有 85.1% 是人工扰动，只有 65 个自然负例。这带来三个问题：

1. 模型可能学到 negation、符号替换或位置重挂产生的分布特征，而不是普遍的真实错误模式；
2. 论文没有分别报告 natural false 与三类 synthetic false 的性能，无法判断 37.69% false recall 来自哪一类；
3. 合成负例从确认正例派生，可能比真实 AI 评论错误更局部、更单一，也可能在语言上更容易或更难。

三位专家逐条核验保证了标签正确性，却不能自动保证分布真实性。若要支持“现实 AI review 可信度过滤”，必须在自然产生的 AI 评论、开发者拒绝反馈或线上 false alarm 上独立验证。

## 十二、证据审计

### 论文较充分证明了什么

1. “单条评审评论的技术可信性”可以被操作化为需要补丁与仓库证据的独立任务。
2. 在这 359 个测试实例上，通用模型存在强烈的 true prediction bias，不可信评论明显更难识别。
3. Sentinel 的整体系统显著改善了 base Qwen 的准确率和 false-class F1，并超过所选 frontier baselines。
4. 区分 base 与 patched version、核对符号和位置是此任务中真实存在的证据需求。
5. PR-disjoint benchmark、隔离仓库和元数据白名单降低了直接标签泄漏风险。

### 论文没有证明什么

1. 没有证明 Sentinel 能可靠过滤真实 AI 生成评论；大多数 false 是从人工可信评论扰动而来。
2. 没有证明 action-level distillation 中哪一组件必要或贡献最大。
3. 没有证明仓库规模导致准确率下降，Figure 5 只提供相关性线索。
4. 没有证明对新仓库、新语言或闭源项目泛化；数据主要来自十个高 star 项目，划分也不是 repository-disjoint。
5. 没有证明判断过程高效、稳定或可校准；缺少成本、重复运行与置信区间。
6. 没有证明“发现并修正评论错误”的轨迹计分等价于部署系统最终输出的可用正确率。

## 十三、作者与团队背景

论文署名横跨 University College London、Amazon 与 Zhejiang University。第一作者 Yue Pan 的可靠公开资料有限，因此这里只根据论文确认其参与 CRJudgeBench 构建、agentic judge 与实验工作，不额外推断职称或长期个人方向。

原文明确标注 **He Ye** 为通讯作者。UCL 官方资料显示其为 Computer Science 系 Software Systems Engineering 方向 Lecturer；个人主页将研究概括为构建下一代软件工程 code agents。CRJudgeBench 延续了这一方向：不把 LLM 当文本分类器，而是让它在真实仓库环境中搜索、执行和核验证据。

团队与 Amazon、浙江大学的合作使研究同时覆盖真实软件数据、模型训练和 agent infrastructure。不过，机构背景只能解释研究积累，不能替代 benchmark 构念与外部效度审查。

## 十四、真正应该记住什么

1. 流畅、相关、可执行的评审意见仍可能在技术事实或位置上错误；评审生成与评审可信性判断必须分开。
2. 强模型最突出的失败不是不会确认，而是不愿证伪：多数模型把九成以上评论判成可信。
3. repository context 的价值不只是“更多信息”，而是把断言与正确版本、符号、文件和执行证据对齐。
4. Sentinel 表明“学习下一步找什么证据”可以改善判断，但现有实验没有分离各训练组件的独立贡献。
5. benchmark 的主要负例来自受控扰动，这非常适合机制实验，却不足以单独代表真实 AI review 错误分布。
6. 任何总体 accuracy 都必须与 false recall、预测倾向和仓库异质性一起报告。

## 十五、对当前研究的启发

这篇论文与当前 plausible-but-non-decisive context 主线的真正连接，不是两者都用了 “plausible” 一词，而是它提供了三种可控反事实模板。

第一，**symbol perturbation** 可以直接迁移为“同类型、同模块、名称高度相似但非当前机制实体”的上下文。与随便选一个相似函数相比，先从正确证据出发只替换符号，能更清楚地控制语义结构。当前实验可新增 core-preserving symbol swap，但必须由人工或可执行检查确认替换后不覆盖新的必要证据。

第二，**location perturbation** 提醒我们单看代码块内容不够。相同片段放在错误文件、错误调用路径或错误 CIG 分支上，可能形成 attribution error。现有指标应把“机制判断正确”与“证据—结论配对正确”分开；这正对应关注的 (P(M=1,A=0))。

第三，CRJudgeBench 的 true prediction bias 可转化为当前研究的方向性假设：给模型一个看似合理的上下文叙事后，它可能更倾向于确认该叙事，而不是主动找反证。下一轮不应只比较最终 file F1，还可以统计支持性搜索与反证搜索的比例、首次引用处理材料的时间、是否核验 base/patched version，以及停止前是否访问过 decisive evidence。

但应避免直接照搬它的标签。CRJudgeBench 的 false 表示评论技术错误或位置错误；当前 plausible context 可能是真实、相关、甚至潜在有用，只是不决定当前任务。它们的构念不同。因此，合适的借鉴方式是使用其**局部反事实构造与 attribution scoring**，而不是把 plausible context 统称为 invalid。

最后，这篇论文暴露了一个对当前实验同样重要的问题：若绝大多数负例来自少数合成模板，模型可能学会模板而不是机制。后续扩展 VLocBench 时应分别报告 structural sibling、retrieval-plausible、symbol swap、location swap 与 natural distractor，不能把它们聚成一个“noise”平均值。
