## 历史精读正文

### MCR-Bench：代码审查不是一次判断，而是一段需要持续维护的缺陷状态

- **标题**：From Static to Dynamic: Benchmarking Real-World Code Review with MCR-Bench
- **作者**：Dewu Zheng、Yanlin Wang、Xiwen Wang、Kefeng Duan、Hongyu Zhang、Xilin Liu、Yuchi Ma、Zibin Zheng
- **来源**：ISSTA 2026，Proceedings of the ACM on Software Engineering，Vol. 3
- **DOI**：[10.1145/3832219](https://doi.org/10.1145/3832219)
- **arXiv**：[2608.27442](https://arxiv.org/abs/2608.27442)
- **代码与数据**：[MCR-Bench GitHub](https://github.com/DeepSoftwareAnalytics/MCR-bench)

> 一句话结论：现有 LLM 不仅容易漏掉多轮审查中的缺陷，还经常忘记缺陷是否已经修复；但论文尚未证明这种退化是“轮次增加”本身造成的，因为后期轮次样本更少，任务构成和难度也可能不同。

### 4.1 论文地图

过去的自动代码审查 benchmark 通常把任务处理成：

```text
输入一次代码变更
→ 模型生成一次评论
→ 与参考评论比较
```

真实代码审查却往往是：

```text
开发者提交代码
→ 审查者发现缺陷
→ 开发者修改
→ 审查者检查是否真正修复
→ 修改引入新问题
→ 旧缺陷可能再次出现
→ 最终接受或继续修改
```

作者认为，单轮 benchmark 只能测量模型是否在某个静态截面上发现问题，无法测量模型是否理解整个审查过程。

因此，MCR-Bench 把每个缺陷表示成一张会随轮次变化的 Defect Card，并要求模型同时完成两个任务：

1. 找出当前存在的缺陷；
2. 判断每个缺陷当前处于 New、Open、Resolved 还是 Reopened。

最终数据集包含：

- 2,269 个真实多轮 PR 审查任务；
- Python、Java、JavaScript、TypeScript、C# 五种语言；
- 每个任务最少 2 轮，平均 3.8 轮，最多 10 轮；
- 每个任务平均 2.37 个缺陷；
- 缺陷类型、严重性、位置、描述及跨轮状态标注。

### 4.2 为什么单轮审查会遗漏一个关键能力

假设第一轮审查发现：

> 资源在异常路径上没有释放。

开发者第二轮增加了释放逻辑，但只处理了一条异常路径。此时模型不应该：

- 把它当成一个全新的缺陷；
- 因为看到开发者声称“fixed”就判定已解决；
- 忘记第一轮已经发现过它；
- 重复生成完全相同的评论。

模型真正需要维护的是一个跨轮次状态：

```text
Round 1：New
Round 2：Open，部分修改但未完全解决
Round 3：Resolved
Round 5：Reopened，新修改重新引入问题
```

这就是论文所说的 defect lifecycle tracking。

它与普通缺陷检测的区别在于：缺陷检测问“现在有没有这个问题”，状态追踪还要回答“它从哪里来、以前是否存在、是否真的修复、是否再次出现”。

### 4.3 MCR-Bench 是怎样构造出来的

整体流程是：

```text
选择主流语言
↓
筛选活跃且成熟的 GitHub 仓库
↓
提取存在真实多轮修改—讨论过程的已合并 PR
↓
排除非代码变更、过大 PR 和机器人评论
↓
用 SZZ 排除后来被识别为引入缺陷的 PR
↓
LLM 分轮发现候选缺陷
↓
LLM 跨轮合并同一缺陷并标注状态
↓
三次独立运行，只保留结果完全一致的任务
↓
六名开发者进行人工交叉核验
↓
形成 Defect Card 和最终 benchmark
```

#### 第一步：选择仓库

仓库必须满足：

- 超过 100 个 Star；
- 最近五年持续有提交活动；
- Issue 解决率超过 40%；
- 超过 10 名贡献者；
- 至少包含 1,500 个 PR；
- 使用允许复现的宽松许可证；
- 不是 Fork。

这些条件提高了数据质量，但同时定义了 benchmark 的适用边界：它代表的是成熟、活跃、协作规模较大的开源项目，不代表小型仓库、课程项目、企业私有仓库或新项目。

#### 第二步：只保留存在真实修改反馈循环的 PR

作者要求 PR 中出现：

```text
commit → reviewer discussion → revision
```

也就是说，只有评论但没有后续代码修改的 PR 不算真正的多轮任务。

这个筛选很合理，因为它避免把“多条评论”误当成“多轮修改”。但它也产生选择偏差：更容易进入数据集的是审查者确实指出问题、开发者愿意回应、最终成功合并的 PR。

那些被直接拒绝、贡献者退出或讨论后没有继续修改的困难案例被系统性排除。

#### 第三步：为什么还要使用 SZZ

“已合并”并不保证代码没有问题。作者使用 SZZ 回溯后来修复缺陷的提交，排除被判定为引入后续缺陷的 PR。

SZZ 的直觉是：从 bug-fixing commit 出发，追踪被修改行最初由哪个提交引入，从而估计 bug-introducing commit。

这里需要警惕：SZZ 本身有误差，而且这种筛选使数据集进一步偏向“事后看来成功”的 PR。于是 MCR-Bench 更像是：

> 在最终成功且没有被 SZZ 标记为引入后续缺陷的审查轨迹中，模型能否复现人类审查者指出的问题？

它并不直接评价模型能否发现人类和后续测试都没有发现的未知缺陷。

### 4.4 Ground Truth 如何生成：local first，global later

这是论文方法上最核心的设计。

#### Phase I：逐轮找候选缺陷

作者不把完整 PR 历史一次性塞给标注模型，而是拆成独立轮次。

每一轮输入：

- 当轮代码差异；
- 当轮审查评论。

输出：

- 该轮出现的候选缺陷。

为什么拆开？因为完整历史过长时，模型可能混淆轮次、遗漏局部评论，或者把同一缺陷在多个轮次重复计数。

但这一阶段只知道“这一轮出现了什么”，尚不知道不同轮次中的两条评论是否指向同一个缺陷。

#### Phase II：合并同一缺陷并推断状态

作者把所有轮次候选缺陷放入全局池，由 LLM 判断：

- 哪些描述实际上是同一个缺陷；
- 后续代码是否修复了它；
- 它是否仍然存在；
- 它是否在修复后再次出现。

最终得到统一 Defect Card：

```text
缺陷描述
缺陷位置
缺陷类别
严重程度
Round 1 状态
Round 2 状态
...
```

如果删除 Phase II，数据集只能评价每轮独立缺陷发现，无法测量跨轮状态维护，也会把同一缺陷重复计数。

### 4.5 三次一致性过滤和人工核验解决了什么

标注流水线对每个任务独立运行三次。只有缺陷描述和状态转换三次完全一致，任务才进入下一步。

然后由六名具有五年以上经验的开发者组成标注池：

- 每个任务先由两人独立核验；
- 两人一致则接受；
- 不一致时交给第三人仲裁；
- 两名初始标注者的 Cohen’s κ 为 0.87。

这说明保留下来的标注具有较高人工一致性。

但一致性过滤也有明显代价：

> 三次 LLM 结果一致，更可能意味着样本对标注模型比较清晰，而不一定意味着它代表真实代码审查的全部困难。

模糊、跨文件、领域知识密集或存在多种合理解释的任务更容易被过滤掉。这是一种 selection-on-annotatability：benchmark 可能低估现实任务的歧义。

### 4.6 数据集具体是什么样

#### 语言分布

五种语言相对均衡：

- Java：556，24.50%
- C#：454，20.01%
- TypeScript：440，19.39%
- Python：410，18.07%
- JavaScript：409，18.03%

语言数量均衡是优点，但仓库、应用领域和任务难度是否均衡，论文没有提供同等细致的分析。

#### 轮次分布

- 3 轮任务：40.86%
- 4 轮任务：26.52%
- 5 轮任务：17.38%
- 最少 2 轮，最多 10 轮

这意味着 6—10 轮任务只占较小比例。因此后面 Table 10 中 R9、R10 的结果可能来自很少的任务，不能与 R2、R3 的结果同等看待。

#### 缺陷分布

每个任务：

- 平均 2.37 个缺陷；
- 中位数 2；
- 最大 13；
- 大多数包含 1—4 个缺陷。

缺陷类别中占比较高的包括：

- 文本、命名和注释：19.19%
- 逻辑：13.44%
- 解决方案/重构方式：11.79%
- 视觉表示和格式：10.25%
- 代码组织：9.61%
- 测试：8.98%

Security & Privacy 只有 **0.63%**。因此，这个数据集不适合据此得出模型安全审查能力的稳定结论。

### 4.7 评价指标是怎样选出来的

代码审查评论可以用完全不同的措辞表达同一个缺陷，BLEU、ROUGE 等词面相似度可能把正确评论判错。

作者比较了三类指标：

1. BLEU-4、ROUGE-L；
2. LLM Scoring：让裁判模型整体打分；
3. LLM-Hit-Judge：逐个判断生成评论是否命中真实缺陷。

他们随机抽取 10% 的生成评论，由四名资深开发者标注 Human Hit Rate，再用 Quadratic Weighted Kappa 衡量自动指标与人类判断的一致程度。

结果见 Table 4：

- ROUGE-L：0.21
- BLEU-4：0.27
- LLM Scoring：0.55—0.60
- LLM-Hit-Judge：0.67—0.73
- GPT-5.2 Pro 作为 Hit Judge 时最高，为 0.73

因此主实验使用 GPT-5.2 Pro 的 LLM-Hit-Judge。

#### 这个选择是否可靠

0.73 表明它比词面指标可靠得多，但仍不等于人类判断。

还有一个重要风险：GPT-5.2 同时是被评价模型之一，又是主要裁判模型。论文没有报告是否存在同模型偏好，也没有用所有三种 Judge 的一致结论完成主结果稳健性分析。

所以主实验中的 Precision、Recall 和 F1 仍然包含 Judge measurement error。

### 4.8 RQ1：现有模型究竟能做到什么程度

作者评价了七个模型：

- GPT-5.2
- Claude Haiku 4.5
- Gemini 3 Flash
- DeepSeek V3.2
- Qwen3-Max
- GLM-4.7
- Kimi K2

同时评价两个自动审查系统：

- PR-Agent
- Hybrid-Review

#### 缺陷发现：最好的 F1 也只有约 0.55

Table 5 的总体结果：

| 模型             | Precision | Recall |        F1 |
| ---------------- | --------: | -----: | --------: |
| Claude Haiku 4.5 |     0.579 |  0.630 | **0.551** |
| GPT-5.2          |     0.622 |  0.561 |     0.542 |
| Gemini 3 Flash   |     0.621 |  0.541 |     0.532 |
| DeepSeek V3.2    |     0.625 |  0.455 |     0.490 |
| Kimi K2          |     0.490 |  0.349 |     0.373 |
| Qwen3-Max        |     0.459 |  0.341 |     0.357 |

Claude 的 F1 最高，GPT-5.2 的 Precision 更高。后几个模型的主要瓶颈是 Recall：它们较少乱报，但漏掉了大量真实缺陷。

不同语言间也有差异，Python 和 JavaScript 通常更好，TypeScript 和 C# 的 Recall 更低。不过论文没有控制训练数据量、仓库类型和缺陷构成，因此不能把差异纯粹归因于语言本身。

> **RQ1 的第一层结论：现有模型在这批多轮任务上远未达到可靠自动审查水平，主要问题不是表达不好，而是没有持续覆盖真实缺陷。**

#### 为什么两个完整 ACR 系统反而不如直接提示模型

PR-Agent 最好的总体 F1 是 DeepSeek V3.2 的 0.416；Hybrid-Review 最好只有约 0.295。多数设置明显低于直接提示基础模型。

一种可能解释是：

- PR-Agent 和 Hybrid-Review 原本为单轮审查设计；
- 它们的上下文选择和中间处理丢掉了跨轮信息；
- Hybrid-Review 依赖静态分析警告，更适合局部、规则化问题；
- MCR-Bench 的目标缺陷大量来自语义、讨论和演化过程。

不过，这不能直接证明“Agent pipeline 没有用”。作者对两个系统进行了适配，但缺少详细的公平预算分析和组件消融。性能下降也可能来自 Prompt、检索范围、输出格式或适配方式不匹配。

### 4.9 缺陷找对之后，状态还能判断对吗

Table 7 只在模型已经正确发现的缺陷上计算状态准确率：

- Claude Haiku 4.5：79.69%
- DeepSeek V3.2：72.60%
- GPT-5.2：71.23%
- GLM-4.7：64.49%
- Kimi K2：45.95%
- Qwen3-Max：44.34%

最常见的状态错误见 Figure 5：

- Resolved → New：38.29%
- Open → New：22.06%
- Resolved → Open：18.20%
- Open → Resolved：16.01%

最明显的问题是模型没有把缺陷身份和历史状态稳定连接起来。它看见当前代码仍有相关信号时，容易将旧缺陷重新当成新缺陷；看到一次修改时，又可能过早认为已经修复。

但这里有一个指标陷阱：

> 79.69% 不是端到端状态追踪成功率，而是“在 Claude 已经找对缺陷的子集上，状态判断正确的比例”。

不同模型的条件子集不同。一个只发现简单缺陷的模型可能获得较高条件状态准确率，因此不能把这个数字单独用于比较完整审查能力。

更完整的评价应同时报告：

- 缺陷识别正确；
- 缺陷身份跨轮匹配正确；
- 生命周期状态正确；

三者联合成立的准确率。

### 4.10 RQ2：轮次越多，模型真的越差吗

Table 10 按任务总轮数报告 F1。

例如 Claude Haiku 4.5：

- R2：0.6495
- R3：0.6173
- R4：0.5359
- R7：0.4768
- R10：0.2857

这看起来像明显下降。但其他模型并不完全单调：

- GPT-5.2 在 R7 为 0.6238，R9 为 0.6048；
- GLM-4.7 在 R9 为 0.5333，高于不少早期轮次；
- Kimi 和 Qwen 的后期结果也出现反弹。

作者将总体趋势解释为上下文噪声增加、状态线索分散以及长程记忆不足。这个解释是合理假设，但实验还不能证明。

#### 最核心的混杂问题

这里比较的是“具有不同总轮数的不同 PR”，不是对同一批 PR 随着轮次增加进行严格的配对估计。

总轮数可能同时受到以下因素影响：

```text
任务难度 ──→ 审查轮数
    │
    └──────→ 模型表现

缺陷数量 ──→ 审查轮数
    │
    └──────→ 模型表现

仓库复杂度 ─→ 审查轮数与表现
```

因此，观察到更多轮任务表现更差，可能只是因为它们原本更困难。

此外，高轮次样本明显更少，R10 的 F1 可能非常不稳定。论文没有给出每个轮次的样本量、置信区间或显著性检验。

> **RQ2 真正证明的是不同总轮数任务的性能存在差异；它没有单独识别“增加一轮交互”对模型表现的因果效应。**

### 4.11 怎样真正验证长程记忆是不是原因

可以在同一个 PR—轮次实例上随机操纵历史信息：

| 组别 | 提供的信息                           |
| ---- | ------------------------------------ |
| A    | 只提供当前 Diff                      |
| B    | 当前 Diff + 上一轮                   |
| C    | 当前 Diff + 完整原始历史             |
| D    | 当前 Diff + 结构化 Defect Memory     |
| E    | 当前 Diff + 完整历史，但打乱时间顺序 |

保持模型、任务、Prompt、token 上限和工具权限相同。

这样才能区分：

- 历史信息是否有帮助；
- 原始长历史是否产生噪声；
- 结构化记忆是否优于简单扩大上下文；
- 时间顺序本身是否重要；
- 性能变化是否只是 token budget 改变造成的。

这比按自然发生的 PR 总轮数分组更接近因果识别。

### 4.12 RQ3：模型为什么产生误报和漏报

作者让四名有经验的程序员分析 FP 与 FN，通过两阶段开放编码建立错误分类。

#### 误报 FP

Table 11 中：

- 状态—时间错位：32.5%
- Over-reviewing：27.8%
- 缺少领域知识：22.4%
- 忽视版本兼容性：12.1%
- 其他：5.2%

最主要的问题不是模型完全不懂代码，而是它引用了错误时间点的证据。例如早期评论已经被后续提交解决，模型仍把它当成当前新缺陷。

Over-reviewing 则是把可选建议、风格偏好或推测性风险说成必须修复的缺陷。这对自动代码审查尤其危险，因为它会增加维护者的验证负担。

#### 漏报 FN

- 跨轮缺陷遗忘：25.1%
- 长程依赖遗漏：23.4%
- 语义缺陷盲区：22.3%
- 过度乐观地认为已修复：15.2%
- 迎合开发者陈述：6.5%
- 其他：7.5%

“Sycophancy”在这里不是一般意义上的讨好，而是模型看到开发者说“fixed”后，没有独立检查代码是否真的解决问题。

#### “根因”一词是否过强

这些分类来自研究者对错误表现的解释，并没有通过干预逐一验证。例如：

- 给模型增加领域知识后，相关误报是否真的下降？
- 加入结构化记忆后，遗忘错误是否减少？
- 隐藏开发者的“fixed”声明后，迎合错误是否变化？

论文没有做这些实验。因此 Table 11 更准确地说是**人工归纳的失败模式及候选机制**，而不是经过因果验证的 root causes。

### 4.13 RQ4：评论写得好，是否代表缺陷找得准

作者使用 ClearCRC 的三个维度：

- Relevance：是否和代码变更及问题相关；
- Informativeness：是否提供具体、有用的信息；
- Expression：是否清晰易懂。

Table 12 中：

- GPT-5.2 + PR-Agent 的平均评论质量最高，为 0.8810；
- DeepSeek V3.2 直接提示为 0.8128；
- Qwen3-Max + PR-Agent 为 0.7990；
- Hybrid-Review 在多数模型上更低。

最值得注意的不是最高分是谁，而是：

> 评论质量和缺陷覆盖是两个不同 Outcome。

一个模型可以生成非常流畅、相关、看似有帮助的评论，却没有命中 benchmark 中的真实缺陷。反过来，一个简短但准确指出关键问题的评论，表达分数未必最高。

这提示自动代码审查不能只用一个总分。至少应把：

- 正确性；
- 覆盖率；
- 可执行性；
- 表达质量；
- 验证成本；

分别评价。

### 4.14 作者证明了什么

1. 可以从真实 PR 历史中构造带有跨轮生命周期状态的代码审查任务。
2. 在 MCR-Bench 上，七个主流 LLM 的最佳缺陷发现 F1 仅为 0.551。
3. 即便已经发现缺陷，状态识别仍然不可靠，尤其容易混淆 New、Open 和 Resolved。
4. 现有单轮导向的 ACR pipeline 在该任务上不一定优于直接提示基础模型。
5. 人工分析发现，时间错位、跨轮遗忘、长程依赖遗漏和过度审查是主要失败模式。

### 4.15 作者没有证明什么

1. 没有证明模型表现下降是轮次增加本身造成的。
2. 没有证明长程记忆不足是 Table 10 趋势的唯一或主要原因。
3. 没有证明 LLM 标注三次一致的样本代表真实审查任务总体。
4. 没有证明 GPT-5.2 Judge 对 GPT-5.2 输出不存在同模型偏好。
5. 没有证明两个 ACR baseline 在完全公平的上下文、Prompt、工具和计算预算下劣于直接提示。
6. 没有评价被拒绝、未合并或开发者退出的审查轨迹。
7. 没有证明模型能发现人类审查者和后续流程都遗漏的未知缺陷。
8. 没有为安全代码审查提供充足证据，因为安全缺陷仅占 0.63%。

### 4.16 对 Causality for Code Review 最有价值的启发

#### 把 Outcome 从静态命中扩展成状态转换

你可以定义：

- `T`：是否提供仓库级 Call Graph；
- `Y1`：首次缺陷发现；
- `Y2`：未解决缺陷的持续追踪；
- `Y3`：正确判断缺陷已解决；
- `Y4`：识别缺陷重新出现；
- `Y5`：产生无效重复评论。

这样可以研究 Call Graph 到底帮助哪一个阶段，而不是只比较最终 F1。

#### 轮次既可能是时间变量，也可能是难度结果

审查轮次不是天然 Treatment。它可能是任务复杂度、缺陷数量和开发者响应共同造成的结果。

若直接控制轮次，还可能阻断 Treatment 的一部分作用路径。例如，更好的审查工具可能让缺陷更早解决，从而减少轮次；此时轮次可能是 Mediator，而不是 Confounder。

#### 缺陷状态适合建立多状态因果模型

可以把生命周期表示为：

```text
New → Open → Resolved
          ↘
       Reopened
```

然后估计不同上下文干预是否影响：

- 从 New 到 Resolved 的转移概率；
- 缺陷保持 Open 的时间；
- Resolved 后再次 Reopened 的风险；
- 不同严重性缺陷的异质效应。

这比把整个 PR 压缩成“成功/失败”更贴近真实代码审查。

### 4.17 你真正应该记住什么

- 多轮代码审查的关键不是保存完整聊天记录，而是维护可验证的缺陷身份和状态。
- MCR-Bench 的最大价值是提出了动态 Outcome，而不仅是增加数据量。
- 状态准确率只在已发现缺陷上计算，不能等同于端到端可靠性。
- 按 PR 总轮数比较性能不能直接证明长上下文导致退化。
- 真实因果实验应在同一任务上随机控制历史、结构化记忆、Call Graph 和 token 预算。
- “Root cause analysis”目前主要是质性归纳出的候选机制，下一步应通过组件干预验证。

> **如果一周后只记得一件事：可靠的自动代码审查不仅要发现缺陷，还必须知道这个缺陷以前是否出现、现在是否仍存在，以及开发者的修改是否真的解决了它。**
